# LLM Gateway Requirements

- Status: Approved
- Created: 2026-08-24
- Last updated: 2026-09-14

## 1. Confirmed intent

Model RPM amendment accepted 2026-09-13: each `model_aliases` definition may set the positive integer `requests_per_minute`, default 5. This extends the closed Alias DTO in FR-973; Provider QPS and Binding concurrency do not substitute for this model-request limit. Sync/SSE share a process-local rolling 60-second window per Alias; internal retry/fallback does not consume additional model-request quota, and excess requests return JSON 429 before stream commitment or Invocation creation. The setting cannot be overridden in a model request or configured on other resources. Default 5 is canonically omitted to preserve existing immutable v1 snapshot digests. Full counting/publication/restart semantics are in [model RPM](model-rate-limit.md).

Scope amendment accepted 2026-09-13: [ADR-0148](adr/0148-gateway-owned-basic-prompt-management.md) moves basic Prompt template assets, immutable versions, explicit publication and rendering into Gateway. It takes precedence over conflicting older Prompt exclusions in this document, including FR-032–038 and FR-211 and their configuration/evidence projections. Tool/Agent ownership and sensitive-content telemetry restrictions remain unchanged. Exact new protocol details and implementation acceptance remain pending; see [six-capability gates](basic-capabilities.md).

Build an independently deployable LLM Gateway for the Agent Engineering Platform that:

- is implemented in Python;
- uses FastAPI as its HTTP Host Adapter;
- is deployable with Docker;
- exposes an OpenAI-compatible API to approved consumers;
- connects to multiple OpenAI-compatible Providers;
- provides a unified model entry point for the Agent Engineering Platform;
- loads multiple Provider definitions, Model Aliases, routing weights, and routing priorities from YAML configuration;
- allows a caller to explicitly select a Provider;
- provides interfaces for configuring Providers, Model Aliases, routing, resilience, pricing, and resource policy;
- allows supported model invocation parameters to be adjusted per request;
- centrally handles model routing, streaming forwarding, structured output, usage and cost recording, retry, rate limiting, and failover.
- treats each caller request as one Model Invocation that may contain multiple internal Provider Attempts due to retry or failover.
- terminates the OpenAI-compatible protocol at the API Layer and uses a provider-independent internal Request Protocol, Model Result, and Model Adapter protocol.

## 2. Problem statement

The Agent Engineering Platform needs one stable model interface instead of coupling callers to individual Provider endpoints and operational policies. The LLM Gateway owns the cross-Provider concerns required to select and invoke models consistently, stream results, enforce requested output shape, account for usage and cost, and recover from Provider throttling or failure. Prompt management and Tool behavior remain Loop-owned.

## 3. Consumers and use cases

To be confirmed:

- approved callers;
- synchronous and streaming invocation scenarios;
- automatic model routing and explicit Provider-selection scenarios;
- Model Alias resolution and priority- or weight-based routing scenarios;
- Provider, Model Alias, routing, resilience, pricing, and resource configuration scenarios;
- cancellation, recovery, and duplicate-request scenarios;
- operational and administrative use cases.

## 4. Functional requirements

- **FR-001 — Chat Completions compatibility:** The Gateway must expose an API with request and response Schemas compatible with OpenAI Chat Completions so existing compatible SDKs can connect without caller-side protocol adaptation.
- **FR-002 — Compatibility boundary:** The API Layer must translate external OpenAI-compatible requests, responses, streaming events, and errors into or from internal protocols. External DTOs must not cross this boundary.
- **FR-003 — Service declaration:** The internal Request Protocol must express a provider-independent Service Requirement derived from the caller's configured Model Alias and validated request, without requiring or accepting a concrete Provider endpoint or Provider model ID.
- **FR-004 — Independent domain model:** Routing, retry, failover, structured-output handling, accounting, and other Gateway policies must operate on Gateway-owned domain types rather than OpenAI or Provider SDK types.
- **FR-005 — Unified result identity:** Every Model Result must retain both the Requested Model and the Resolved Model.
- **FR-006 — Model Adapter protocol:** Every Model Adapter must implement one Gateway-owned invocation protocol covering synchronous results, streaming events, usage, cancellation, and capability declaration.
- **FR-007 — Failure protocol:** Model Adapter failures must be represented by a defined, provider-independent failure protocol suitable for retry, failover, client-error mapping, and observability decisions.
- **FR-008 — HTTP declaration and validation:** The API Layer must use FastAPI to declare HTTP routes and Pydantic request models to validate incoming parameters before conversion to the internal Request Protocol.
- **FR-009 — Credential isolation:** Provider credentials must be resolved inside the Gateway and must never be required from or exposed to ordinary callers.
- **FR-010 — Response translation:** The API Layer must translate internal Model Results and failures into OpenAI-compatible responses and errors.
- **FR-011 — Requested and resolved identity:** The external response contract must preserve both `requested_model` and `resolved_model` without preventing existing OpenAI-compatible SDKs from consuming the response.
- **FR-012 — Multiple Model Adapters:** The Gateway must support multiple Model Adapters concurrently behind the same internal Model Adapter protocol.
- **FR-013 — Capability declaration:** Each Model Adapter must declare the Model Capabilities of its configured models, including at least streaming, structured output, and Tool Calling support.
- **FR-014 — Capability Registry:** The Gateway must maintain an authoritative Capability Registry that the Router can query without depending on Provider-specific types.
- **FR-015 — Capability-first routing:** The Router must reject candidates that do not satisfy the Model Invocation's required capabilities before applying preference policy. It must not infer suitability from model names or model size.
- **FR-016 — Routing policy inputs:** Among capability-compatible candidates, routing must consider configured priority, cost, and current health state. Weight-based routing remains an accepted configurable policy input.
- **FR-017 — Pre-stream failover:** Before the first response Token is emitted to the caller, a failed Provider Attempt may fall back to another eligible candidate according to policy.
- **FR-018 — Committed stream:** After the first response Token is emitted, a Provider failure must terminate the stream with an observable error. The Gateway must not switch models and concatenate output into the committed stream.
- **FR-019 — Explainable routing:** Every Routing Decision must record the evaluated candidates, the selected candidate, and a reason for every rejected candidate.
- **FR-020 — Eval replay:** Routing Decisions must contain or reference enough immutable input and policy evidence to be replayed and explained by an Eval.
- **FR-021 — Durable rejection evidence:** Candidate rejection reasons must be persisted according to an approved retention policy rather than existing only in transient logs.
- **FR-022 — Synchronous result path:** For each Provider Attempt in a non-streaming Model Invocation, the Gateway must send one internal request upstream and receive a complete Provider result before translating the final invocation outcome into one unified Model Result. Retry and failover semantics must be defined against this baseline path.
- **FR-023 — Internal stream protocol:** The Gateway must translate Provider streaming output into one ordered sequence of provider-independent Stream Events. The event protocol must represent at least content delta, opaque compatible payload fragment, usage, and termination without a Tool-specific event model.
- **FR-024 — External SSE:** The API Layer must translate internal Stream Events into one OpenAI-compatible SSE response without exposing raw Provider chunks.
- **FR-025 — Single terminal outcome:** Every stream must end with exactly one immutable Terminal Outcome: completed, failed, or cancelled. After a terminal outcome is selected or emitted, the stream must not change to another terminal outcome.
- **FR-026 — Structured-output request:** A caller may request JSON Object or JSON Schema output through compatible `response_format`; the API Layer must validate the outer request shape and preserve the declared Output Schema, dialect identity, and feature set for routing and final validation.
- **FR-027 — Two-layer guarantee:** Gateway must request the declared output constraint from the selected Provider and must independently validate the returned model output locally; a Provider conformance claim is not an application-safety guarantee.
- **FR-028 — Incremental stream extraction:** For Structured Output streaming, Gateway must incrementally extract and parse JSON as Provider deltas arrive, suppress wrapper bytes, and emit only normalized JSON bytes without waiting for all chunks.
- **FR-029 — Final structured validation:** Partial JSON may expose parser progress and normalized JSON deltas but cannot establish Schema conformance. Successful completion may be declared only after the stream or synchronous output is complete and final local Pydantic/JSON Schema validation succeeds.
- **FR-030 — Bounded output recovery:** Each Structured Provider output may run exactly one Local Structured Repair pipeline pass; no local extraction or repair loop may repeat. If that pass leaves an eligible pre-commit JSON Structure Failure, the ordinary retry policy may authorize at most one unchanged-request same-candidate retry. Other Structured Validation Failures are terminal, and none authorizes Provider/model fallback.
- **FR-031 — Explicit structured failure:** When extraction, parsing, validation, repair, and any permitted pre-commit Provider recovery are exhausted, Gateway must return stable `structured_output_invalid` rather than silently swallowing the failure, downgrading to text, or fabricating an object.
- **FR-032 — Gateway basic Prompt ownership (amended 2026-09-13):** Gateway owns basic Prompt template assets, variables, rendering, immutable versions and explicit publication. Automated Evals, optimization and content replay are not implied by this amendment.
- **FR-033 — Prompt management surface (amended):** Gateway must provide authorized asset creation/read, versioning, publication and bounded preview/rendering. Exact DTOs and permission mapping must be specified before enabling this surface.
- **FR-034 — Safe Prompt rendering (amended):** Gateway renders declared variables through a bounded non-executable template contract, without arbitrary code, file, environment or network access and without implicit recovery-prompt injection.
- **FR-035 — Prompt-backed invocation (amended):** Gateway supports a documented Prompt selection path in addition to existing rendered messages. One immutable Prompt version is selected before Provider execution and retained across retry/fallback; ambiguous simultaneous inputs must have a documented rejection or composition rule.
- **FR-036 — Rendered-message boundary (amended):** Caller-supplied and Gateway-rendered messages obey the same Compatibility Profile, resource/Token/Context, safety and transport checks. Prompt rendering cannot bypass ordinary admission or routing rules.
- **FR-037 — Safe Prompt provenance (amended):** Protected asset storage may retain versioned templates and publication facts. Invocation Evidence may reference authorized asset/version provenance; raw variables, template bodies and rendered messages must not enter ordinary Logs, Metrics or Trace.
- **FR-038 — Prompt correlation (amended):** Gateway links selected Prompt-version provenance to its Model Invocation; task/turn/step/call/Trace correlation remains distinct from asset identity. Tool semantics and Agent state remain Loop-owned.
- **FR-041 — Classified failure disposition:** Every Gateway, transport, or Structured Validation Failure exposed by the internal failure protocol must identify its processing stage and Failure Disposition so retry, failover, repair, and client mapping do not depend on Provider-specific messages.
- **FR-042 — Authentication and tenant rejection:** An invalid API key or disabled tenant must be rejected without an automatic retry or Provider Attempt.
- **FR-043 — Request validation rejection:** Invalid parameters, a missing required Schema, or another request-contract violation must be rejected without an automatic retry or Provider Attempt.
- **FR-044 — Input correction required:** A malformed message or exceeded request/Context budget must be rejected before a Provider Attempt. The caller may retry only after correcting the already-rendered request.
- **FR-045 — No compatible model:** If routing finds no capability-compatible model, the Gateway must return an explicit routing failure and must not retry unchanged routing state. A later invocation may succeed after a configuration or capability change.
- **FR-046 — Admission and queue boundary:** When the applicable concurrency pool is full or the remaining deadline is insufficient, admission control must reject the invocation or move it to another policy-approved pool without exceeding the caller's deadline.
- **FR-047 — Connection retry:** A transient connection failure or retryable upstream 5xx may trigger only bounded automatic retries subject to retry budget, deadline, idempotency safety, and policy.
- **FR-048 — Pre-commit retry and failover:** Before the External Commitment Point, a retryable 429, timeout, or Provider overload may trigger bounded retry or failover according to routing policy.
- **FR-049 — Post-commit interruption:** After the External Commitment Point, a connection interruption must terminate the existing stream explicitly. The Gateway must not blindly regenerate, switch models, or splice replacement output into that stream.
- **FR-050 — Structured-content disposition:** Only a caller-declared Structured Output contract may create Gateway content-validation, one-pass local-extraction, and the narrowly allowed pre-commit JSON Structure Failure retry. Structured Validation Failure never creates Provider/model fallback, while ordinary text and opaque Tool payloads remain unclassified content.
- **FR-051 — Safety refusal integrity:** A Safety Refusal must not trigger retry or failover whose purpose or effect is to bypass the applicable safety policy.
- **FR-052 — Retry amplification boundary:** Every Model Invocation must have finite limits for Provider Attempts, Local Structured Repair attempts, elapsed deadline, and queue time. Nested recovery layers must share invocation-level budgets.
- **FR-053 — Bounded exponential backoff:** Automatic retries must use exponential backoff with jitter and configured upper bounds for delay, attempt count, and total elapsed time. Backoff must not exceed the Model Invocation deadline.
- **FR-054 — Streaming retry boundary:** A streaming Model Invocation may retry or fail over only before the first externally emitted delta. After the first delta, any failure must terminate the existing stream according to FR-049.
- **FR-055 — Concurrency-first resource control:** In-flight concurrency limits are the primary admission-control mechanism because they bound occupied Gateway and Provider resources. QPS limits may supplement but must not replace concurrency limits.
- **FR-056 — Honest idempotency boundary:** Gateway idempotency must not claim to prevent duplicate Provider execution or duplicate Provider billing when a prior Provider Attempt has an Uncertain Provider Outcome.
- **FR-057 — Attempt-level accounting:** Usage and cost evidence must distinguish every Provider Attempt, including retries, failovers, and attempts with uncertain or potentially duplicated Provider charges, from the aggregate Model Invocation record.
- **FR-058 — Invocation Evidence:** The Gateway must create structured Invocation Evidence for every accepted Model Invocation and correlate it with the evidence for each Provider Attempt.
- **FR-059 — Execution correlation:** Invocation Evidence must retain `call_id` and `trace_id` for every Model Invocation and retain `task_id`, `turn_id`, and `step_id` when applicable under the caller-type rules.
- **FR-060 — Routing evidence:** Invocation Evidence must retain the requested logical model or Service Requirement, selected Provider, Resolved Model, all evaluated candidates, and every candidate rejection reason.
- **FR-061 — No Prompt evidence:** Invocation Evidence must not retain Gateway-derived Prompt identity, version, variables, render hash, or Eval metadata; it may retain only the requested output-Schema identity governed by Gateway.
- **FR-062 — Token usage:** Usage evidence must separately record input, output, cached, and reasoning Token counts when reported or derivable, while preserving an explicit unavailable or estimated state when they are not authoritative.
- **FR-063 — Latency phases:** Latency evidence must separately record queue, routing, Time to First Token, generation, and total latency using one documented clock and phase-boundary convention.
- **FR-064 — Resilience evidence:** Invocation and Attempt evidence must retain attempt ordinal, retry count, fallback transitions, and the applicable timeout budget and remaining deadline at each decision point.
- **FR-065 — Result evidence:** Invocation Evidence must retain Provider finish reason when exposed, Gateway Terminal Outcome, Structured Output validation result when applicable, and payload size/hash when policy permits.
- **FR-066 — Error evidence:** Failure evidence must retain a stable Gateway error code, external HTTP status where applicable, and Provider request ID where available, without exposing Provider credentials or prohibited content.
- **FR-067 — Estimated cost:** Cost evidence must separately record estimated input, output, cached, and total cost for every Provider Attempt and aggregate them for the Model Invocation.
- **FR-068 — TTFT semantics:** TTFT must end only at the first externally emitted business-meaningful delta. Connection establishment, headers, heartbeats, comments, and protocol-only SSE events must not count as the first Token.
- **FR-069 — Telemetry separation:** Metrics must aggregate operational trends such as QPS, latency percentiles including P99, and error rate; Logs must record permitted single-invocation operational details; Trace must connect the end-to-end call path. None of these alone replaces durable Invocation Evidence.
- **FR-070 — Single model boundary for Agent Loop:** The Agent Loop must invoke models only through the Gateway's unified model API and must not call Providers directly or depend on Provider credentials, endpoints, SDKs, or response types.
- **FR-071 — Agent Loop ownership:** The Agent Loop owns Tool execution, iteration control, and agent state management.
- **FR-072 — Gateway execution ownership:** The Gateway owns model execution, routing, retry, failover, rate limiting, circuit breaking, streaming translation, and the associated model usage and cost evidence.
- **FR-073 — Loop Step identity:** Every Loop Step must generate a `turn_id` and propagate it, together with its `task_id`, to every Model Invocation caused by that step.
- **FR-074 — Multiple calls per step:** One Loop Step may create multiple Model Invocations. Each invocation must have a distinct `call_id` that serves as its Model Invocation identifier.
- **FR-075 — Call trace evidence:** For each `call_id`, the Gateway must retain its `trace_id`, Routing Decision, Token usage, estimated cost, and the required Invocation Evidence.
- **FR-076 — Cross-boundary trace correlation:** Agent Loop and Gateway telemetry must propagate and correlate at least `task_id` and `turn_id` so the complete call chain can be reconstructed across the service boundary.
- **FR-077 — API surface separation:** The Gateway must expose a Data Plane with OpenAI-compatible model invocation endpoints and a separately versioned, Gateway-native Control Plane for Provider, Model Alias, routing, resilience, pricing, resource, safety, and health configuration. Prompt management is absent.
- **FR-078 — Plane authorization:** Data Plane invocation permissions and Control Plane configuration permissions must be independently authorizable; ordinary model callers must not gain configuration authority through OpenAI-compatible requests.
- **FR-079 — First-phase API scope:** The first compatibility target is `POST /v1/chat/completions` for synchronous and SSE streaming invocation, including opaque Tool and output-format field forwarding. `/v1/models`, Embeddings, Audio, Images, and other OpenAI API families are not exposed unless separately accepted; model capability discovery uses authorized Gateway configuration/read-only documentation instead.
- **FR-080 — External authorization integration:** The Gateway must integrate with an external Authorization Authority for caller authentication and authorization decisions.
- **FR-081 — No built-in authority:** The Gateway must not be the system of record for users, tenants, roles, permissions, or authorization policy lifecycle. It may validate credentials/tokens, consume claims or decisions, and enforce the resulting access boundary.
- **FR-082 — Plane-specific enforcement:** The Gateway must enforce independently scoped Data Plane and Control Plane permissions using the external authority's identity, tenant, and scope context.
- **FR-083 — Pluggable authority integration:** The Gateway's Authorization Authority integration must be replaceable through a defined adapter boundary and must not hard-code one identity or policy product.
- **FR-084 — JWT support:** JWT bearer tokens are one supported Authorization Adapter integration method. The Gateway must validate the configured signing algorithm and key identity, signature, issuer, audience, temporal constraints, and mandatory identity claims before enforcing plane-specific access. A caller-controlled failure of any such check is `unauthorized`/HTTP 401 rather than an Authorization Context contract failure.
- **FR-085 — External authority deployment:** A compatible Authorization Authority may be supplied as an independently deployed open-source Docker service, but using it through v0.1 `online_authority` must satisfy the same production-only HTTPS, certificate, hostname, non-private destination, and canonical-CIDR allowlist contract as any other Authority; deployment adjacency does not relax transport policy. Its lifecycle and policy data remain outside Gateway ownership, while local Gateway development continues to use `dev_bypass`.
- **FR-086 — Configuration database authority:** Provider, Model Alias, routing, resilience, pricing, resource, safety, and health configuration must be persisted in one Gateway configuration database that is the canonical synchronized state; Prompt state must not be stored there.
- **FR-087 — YAML synchronization:** YAML configuration must import into and export from the canonical configuration database through a validated, versioned synchronization path.
- **FR-088 — Control Plane synchronization:** Control Plane API changes must update the same canonical configuration database and must be reflected in the YAML synchronization view; YAML-originated changes must likewise become visible through the Control Plane API.
- **FR-089 — Atomic configuration revisions:** Every configuration change must use an explicit revision/version and atomic validation/publish behavior. Concurrent or stale YAML/API updates must not silently overwrite a newer revision.
- **FR-090 — Stale revision conflict:** A YAML or Control Plane API write based on a stale configuration revision must fail with an explicit conflict result and must require rebase, re-export, or deliberate merge before publication.
- **FR-091 — Configuration database technology:** The first-phase canonical configuration database must be PostgreSQL, deployed as an independently managed Docker dependency. SQLite may be used only for local development or tests and must not be treated as the production authority.
- **FR-092 — First Adapter path:** The first acceptance path must use a generic OpenAI Chat Completions HTTP Model Adapter without a vendor-specific SDK. Contract tests must use `MockTransport`; a separately configured OpenAI-compatible endpoint may provide Live Smoke Test evidence.
- **FR-093 — Secret references only:** Provider configuration must store only a Secret reference or indirection, never a plaintext Provider credential.
- **FR-094 — SecretSource boundary:** Runtime credential resolution must use a replaceable SecretSource adapter. Docker Secrets or environment variables may support development; production deployments must be able to integrate a dedicated Secret Manager.
- **FR-095 — Credential isolation:** Resolved Provider credentials must remain inside the Gateway's Adapter boundary and must not appear in Data Plane requests/responses, ordinary Control Plane responses, Logs, Metrics, Trace, or Invocation Evidence.
- **FR-096 — Content minimization:** The Gateway must not persist raw input messages or model output by default. Default Invocation Evidence must use the approved metadata, hashes, validation results, and usage/cost facts needed for operations and audit.
- **FR-097 — Opt-in content retention:** Raw input/output retention may be enabled only by an explicit tenant or deployment policy, with encryption, redaction, access audit, and a bounded TTL.
- **FR-098 — Replay under retention policy:** Invocation replay must distinguish metadata-only replay from content replay; exact content replay is permitted only when the approved retention policy retained the necessary protected content. Prompt replay remains outside Gateway.
- **FR-099 — Evidence persistence:** Invocation Evidence and Cost Ledger must be persisted in the first-phase PostgreSQL deployment using schemas/tables distinct from configuration state.
- **FR-100 — Append-only cost ledger:** Cost Ledger entries must be append-only per Provider Attempt and aggregate to the Model Invocation without overwriting prior attempt charges.
- **FR-101 — Evidence linkage:** Invocation Evidence must link stable Model Invocation, `call_id`, Provider Attempt, configuration revision, Routing Decision, and Cost Ledger identifiers.
- **FR-102 — Trace protocol:** Gateway Trace output must use OpenTelemetry-compatible spans and context propagation.
- **FR-103 — Metrics protocol:** Gateway Metrics must expose a Prometheus-compatible scrape or export surface for QPS, latency percentiles, error rate, resource saturation, retry/fallback, and cost/usage aggregates.
- **FR-104 — Structured Logs:** Gateway Logs must be structured JSON and include applicable `trace_id`, `task_id`, `turn_id`, and `call_id` correlation fields without prohibited secrets or raw content.
- **FR-105 — External observability boundary:** The Gateway must emit standard observability data but must not own or require a Gateway-specific Metrics, Trace, or Log storage platform.
- **FR-106 — Container topology:** The first-phase deployment must run one Gateway service and PostgreSQL as separate Docker containers. Authorization Authority, Secret Manager, Metrics, Trace, and Log storage may be independent optional dependencies.
- **FR-107 — Liveness and readiness:** Gateway liveness must indicate process health without requiring every external dependency. Data Plane admission readiness must verify PostgreSQL, the latest valid configuration revision, and local dependencies required to accept a Model Invocation; temporary Provider reachability, health, circuit, or capacity state must not make it non-ready. When local dependencies permit it, Control Plane configuration recovery remains available even if Data Plane admission is not ready.
- **FR-108 — Startup validation:** Invalid configuration, unavailable required persistence, or an unusable required dependency must prevent the Gateway from becoming ready and must produce an explicit startup diagnostic.
- **FR-109 — Graceful drain:** Shutdown must stop new admissions, propagate cancellation or deadline handling to in-flight work, and wait for a bounded drain period before terminating.
- **FR-110 — Client cancellation:** An explicit caller cancellation or disconnected streaming client must produce a single `cancelled` Terminal Outcome, propagate cancellation to the active Provider Attempt, and stop retry/failover.
- **FR-111 — Deadline exhaustion:** Exhausting the Model Invocation deadline must produce a single `failed` Terminal Outcome with stable `deadline_exceeded` classification, propagate cancellation to active upstream work, and stop retry/failover.
- **FR-112 — Shutdown cancellation:** Gateway shutdown during in-flight work must produce a single `cancelled` Terminal Outcome after bounded drain handling and must not start replacement retries or failover attempts.
- **FR-113 — Explicit configuration publication:** YAML or Control Plane mutations must create a validated, versioned candidate configuration that does not affect the Data Plane until explicitly published.
- **FR-114 — Atomic configuration activation:** The Gateway must activate only one complete published configuration snapshot at a time. Router and Model Adapters must never observe a partial or validation-failed snapshot.
- **FR-115 — In-flight snapshot stability:** A Model Invocation must retain the configuration revision selected at admission; later publication must not change its Routing Decision or retry policy mid-invocation.
- **FR-116 — Static health policy:** Health-check, circuit-breaker, recovery-window, and threshold policy must be stored in the canonical configuration database and activated through published snapshots.
- **FR-117 — Runtime health state:** Live health counters, circuit state, and rolling windows must be maintained at runtime without a database write for every request or event.
- **FR-118 — Health transition evidence:** Health and circuit transitions must emit structured evidence sufficient to explain candidate eligibility and rejection without replacing the runtime state machine.
- **FR-119 — Multi-instance boundary:** Shared health/circuit state across Gateway instances requires a separately accepted coordination mechanism; an instance-local state must not be represented as globally authoritative.
- **FR-120 — First-phase instance scope:** The first-phase deployment and acceptance target is one Gateway instance. Data Plane service decomposition, multi-instance deployment, shared circuit state, and distributed coordination are outside this acceptance scope.
- **FR-121 — Rate-limit hierarchy:** First-phase concurrency limits must be enforceable at Gateway instance, tenant, and Provider scopes; the policy must not require a Gateway-owned API-key identity model.
- **FR-122 — QPS as supplement:** QPS limits may supplement concurrency limits but must not replace them as the primary resource boundary.
- **FR-123 — Rate-limit outcome:** A rate-limited request must produce a stable `rate_limited` failure classification and may include `Retry-After` when a retry window is meaningful. Rate-limit policy must come from the published configuration snapshot.
- **FR-124 — Provider redirect rejection:** Provider transports must not follow HTTP redirects. Every Provider 3xx response must normalize to `provider_protocol_error`, be rejected before any redirected request is sent, and not authorize a same-candidate retry. Before the External Commitment Point, the Router may continue with the next eligible fallback Candidate under the locked routing policy. Redirect failure must not affect Provider Health State or circuit samples and must not authorize cache degradation.
- **FR-125 — Per-connection DNS enforcement:** Before every new Provider connection, including retries and fallback Attempts, Gateway must resolve the configured hostname and require every returned destination address to pass the active Provider Egress Allowlist. If any returned address is disallowed, the complete connection attempt must fail before network I/O; Gateway must not select an allowed address from a mixed result set. Cached or previously accepted DNS results must not authorize a later connection without revalidation.
- **FR-126 — Provider private CA:** A Provider may carry a configuration-owned, Provider-scoped Provider Trust Bundle for private PKI. Its content identity, optional human-readable `label`, and PEM content must be embedded directly in that Provider's canonical PostgreSQL configuration, unavailable to Data Plane callers, and included in the locked Active Snapshot; first phase has no separate shared Trust Bundle registry. Import must canonicalize PEM as UTF-8 without BOM, LF line endings, and exactly one final LF while otherwise preserving certificate order and content. The immutable identity is `sha256:<64 lowercase hex>` calculated over those canonical bytes; a supplied identity must match, the same identity must never name different content, and `label` must not affect identity, routing, validation, or transport behavior. Candidate validation must locally parse the PEM, require at least one CA certificate, reject private keys, and reject any certificate outside its validity period without Provider network I/O. The default deployment ceiling is 1 MiB of PEM and 100 certificates per Provider; lower-level policy may tighten but never raise it. When configured, that bundle replaces the system CA roots for that Provider; when absent, system roots apply. It must not disable certificate-chain or hostname verification. A new Active Snapshot changes the bundle for later admissions, while an admitted invocation retains its locked content identity and an already-established TLS connection is not rewritten.
- **FR-127 — No first-phase outbound proxy:** First-phase Provider transport must connect directly and must not support configured HTTP/HTTPS/SOCKS outbound proxies or environment-based proxy discovery. Docker startup may independently pass, replace, or omit standard proxy environment variables for other container concerns, but Provider Transport must ignore them and they must not change Gateway routing or egress behavior. Proxy support requires a later egress-security design and cannot be enabled by request fields.
- **FR-128 — DNS failure recovery separation:** A transient DNS failure such as timeout or `SERVFAIL` may consume bounded same-candidate retry, then pre-commit Provider fallback, then an explicitly eligible Cached Degraded Result, and otherwise terminates with the stable applicable failure. Transient DNS failures contribute to Provider health and circuit policy. A DNS result containing any address rejected by the Provider Egress Allowlist is instead an egress-policy violation: it must not retry the same Candidate, affect Provider health/circuit state, or use cache degradation, but may continue to a pre-commit fallback Candidate. Candidate Blacklist is only a derived routing view: transient faults use Provider Circuit state, an egress-policy rejection excludes that Candidate only from the current invocation, and administrative disablement uses published configuration. Gateway must not maintain a separate blacklist state machine or dynamic IP denylist. If all eligible Candidates are exhausted by egress-policy rejection, the outward failure is the existing `provider_unavailable`; authorized Evidence retains `egress_policy_violation` without exposing rejected IP addresses to the Data Plane.
- **FR-129 — Trust Bundle activation and expiry:** Provider Trust Bundle rotation must embed a new content-addressed identity in the Provider's PostgreSQL configuration and publish it through an Active Snapshot. Publication may prepare pool configuration but must not perform DNS, open a socket, complete TLS, or otherwise contact a Provider; a pool is initialized lazily by the first eligible Provider Attempt that acquires it. An unexpected local resource or program failure while initializing a configuration-valid pool must terminate as `internal`, without retry, Candidate fallback, cache degradation, Provider Health State mutation, or circuit sample. New admissions and their later new connections use the locked new identity; already admitted invocations retain their prior snapshot identity. Provider Transport pools must be keyed by `provider_id`, `trust_bundle_identity`, and `transport_config_digest`. The transport digest covers only connection-affecting configuration, including endpoint origin, TLS mode/settings, HTTP protocol selection, and connection/pool limits; it excludes model/routing/generation parameters, labels, and resolved credential values. Credential rotation remains per-Attempt header material and does not by itself recreate a pool. First-phase upstream transport supports HTTP/1.1 only; HTTP/2 is deferred. Pool defaults are a 30-second idle timeout and a five-minute maximum connection lifetime and may be configured per Provider. A connection reaching either bound accepts no later request acquisition, while an active request or stream retains the connection until completion, cancellation, or its original Invocation Deadline. Publication that changes either behavior digest creates a new lazy pool; the old pool accepts no new acquisition, closes idle connections, and lets active requests finish under their original cancellation and Invocation Deadline bounds before closing, without a separate pool-drain timeout or deadline reset. First phase must not depend on, watch, or hot-reload mutable CA files outside canonical PostgreSQL configuration and snapshot publication. Before opening every new Provider connection, Gateway must re-evaluate the locked Bundle's certificate validity; acquiring an existing established connection does not repeat certificate-date validation or interrupt its request. If any certificate in a previously valid locked bundle expires after publication, the complete bundle becomes invalid: only Candidates that require it become runtime-ineligible for new TLS connections and follow ordinary pre-commit fallback/exhaustion as `provider_unavailable`. Publishing an Active Snapshot with a valid replacement identity makes those Candidates immediately eligible for new connections and a new pool, without Circuit half-open, health-sample reset, or an additional cooldown. This time-based configuration condition must not change Gateway readiness, affect Provider Circuit samples, or terminate an already-established TLS connection. A local network-free task refreshes Metrics and expiry transitions. Metrics must expose `trust_bundle_days_until_expiry` at bounded Provider scope; at 30 days or fewer Gateway emits a warning at most once per `provider_id + trust_bundle_identity` per 24 hours, and emits one error when that identity transitions to expired, without certificate contents or destination details. Notification policy remains external to Gateway. A label-only change still creates and audits a Configuration Revision but must not change Candidate eligibility, Provider Transport pool identity, or Execution Fingerprint.
- **FR-130 — Configured Provider egress:** Provider endpoints must come only from an active published configuration revision; ordinary Data Plane callers must not supply arbitrary Provider URLs. A production Candidate without an explicit Provider host/network allowlist must fail validation and must never enable outbound Provider traffic.
- **FR-131 — Egress transport security:** Production Provider egress must require HTTPS with certificate and hostname validation. Any development exception must be explicit configuration, not an invocation-level override.
- **FR-132 — Egress SSRF boundary:** Provider egress must enforce configured host/network allowlists and block disallowed private, loopback, link-local, or metadata addresses. DNS resolution and redirect handling must not bypass this boundary. Local development may reach loopback or another local target only through an explicit environment-scoped allowlist entry; omission remains deny-by-default.
- **FR-133 — Retry budget:** Every automatic retry policy must have finite attempt, delay, and total-deadline bounds shared across nested Gateway retry layers.
- **FR-134 — Retry exhaustion disposition:** When bounded retry fails, the Gateway must enter an explicitly configured Degraded Outcome or terminal Failure Disposition, such as eligible pre-commit fallback or explicit client failure.
- **FR-135 — No silent degradation:** A Degraded Outcome must identify its degraded status and reason. The Gateway must not present a partial, cached, or substitute result as the requested full result unless that behavior was explicitly requested and represented in the contract.
- **FR-136 — Complete degradation design:** The Gateway design must cover every supported Degraded Outcome, including pre-commit Provider fallback, explicit terminal failure, cached or stale result, and reduced-capability model result. No degradation mode may remain an undefined implicit behavior.
- **FR-137 — Degradation contract:** The allowed Degraded Outcomes, ordering, freshness/capability limits, caller visibility, and opt-in/opt-out rules must be represented in the applicable Service Requirement, Model Alias, or invocation contract before execution.
- **FR-138 — Degraded-result evidence:** Every Degraded Outcome must retain its trigger, attempted recovery path, actual Provider/Model result, freshness or capability deviation, policy revision, and caller-visible status.
- **FR-139 — Degradation truthfulness:** A cached/stale or reduced-capability result must preserve `requested_model` and `resolved_model`, identify the actual source and deviation, and never be represented as an ordinary full-quality success.
- **FR-140 — Ordered Degradation Policy:** Each Service Requirement must carry an explicit ordered Degradation Policy. Unless overridden, the order is same-capability Provider fallback, explicitly allowed reduced-capability model, explicitly allowed fresh/stale cache, then terminal failure.
- **FR-141 — No implicit rich degradation:** Reduced-capability and cached/stale outcomes must be opt-in in the Degradation Policy; the Gateway must not infer permission from a Provider outage or deadline alone.
- **FR-142 — Cached degradation support:** The Gateway must support Cached Degraded Result as an explicitly policy-controlled degradation mode.
- **FR-143 — Semantic cache key:** A cache key must include the Execution Fingerprint plus required tenant, authorization, safety, degradation, freshness, and revocation isolation fields; Request Fingerprint alone is insufficient.
- **FR-144 — Cache provenance:** A Cached Degraded Result must disclose and record source invocation identity, resolved model, creation time, age, TTL/freshness decision, and cache-vs-live status. Its Data Plane response must expose `X-Gateway-Result-Mode: cached` and non-negative `X-Gateway-Cache-Age-Ms`; both are sent in the initial HTTP response headers for synchronous and streaming responses. Live results omit both headers.
- **FR-145 — Side-effect safety:** Tool Calling and other requests with side effects must not use cached results by default; enabling them requires an explicit contract and idempotency/safety policy.
- **FR-146 — Cache backend:** The first-phase Cached Degraded Result backend must be Redis, deployed as an independent Docker dependency with bounded memory and TTL/eviction controls.
- **FR-147 — Cache default:** Cached Degraded Result is disabled by default and may be enabled only by an active published Degradation Policy.
- **FR-148 — Cache miss neutrality:** A disabled, unavailable, expired, or policy-ineligible cache must not change ordinary live routing semantics except through the explicitly configured Degraded Outcome or terminal failure.
- **FR-149 — Cache tenant isolation:** Cache keys and lookup authorization must include the tenant/policy boundary and must prevent cross-tenant or cross-policy hits.
- **FR-150 — Cache transport and payload protection:** Redis access must use authentication and encrypted transport; sensitive cached payloads must use application-layer encryption with keys resolved through SecretSource.
- **FR-151 — Cache retention bound:** Cache TTL and eviction must not exceed the applicable content-retention policy, and cache evidence must identify expiry/eviction state without retaining prohibited plaintext.
- **FR-152 — Idempotency support:** The Data Plane must accept one optional `Idempotency-Key` header for a logical Model Invocation and bind its complete Idempotency Key Namespace to a canonical Request Fingerprint.
- **FR-153 — Same-key resolution:** A repeated Idempotency Key with the same fingerprint must resolve through the configured Idempotency Replay Mode and existing lifecycle state rather than create a second logical invocation or Provider execution.
- **FR-154 — Same-key conflict:** A repeated Idempotency Key in the same namespace with a different fingerprint must be rejected with an explicit, non-disclosing idempotency conflict.
- **FR-155 — Uncertain idempotency limit:** After an Uncertain Provider Outcome, idempotency may prevent a second Gateway logical invocation, but must not claim to prevent Provider duplicate execution or billing; the uncertainty must remain in evidence and caller-visible status.
- **FR-156 — Model response compatibility:** In an OpenAI-compatible response, the standard `model` field must identify the actual `resolved_model` used for the result.
- **FR-157 — Model identity extensions:** Responses must additionally expose both `requested_model` and `resolved_model` through the documented `gateway` object extension, which compatible SDKs may ignore.
- **FR-158 — Streaming model identity:** Streaming responses must expose the same requested/resolved model identities through the documented SSE-compatible extension without changing the standard event ordering or terminal semantics.
- **FR-159 — Pre-stream error mapping:** A failure before the first external SSE event must use the ordinary OpenAI-compatible JSON error response and must not start an SSE stream.
- **FR-160 — In-stream error mapping:** A failure or cancellation after the stream starts must emit exactly one documented Gateway SSE error/cancellation extension event with stable classification, then close the connection.
- **FR-161 — Normal completion marker:** The standard `[DONE]` SSE marker is reserved for normal completion and must not follow an error or cancellation terminal event.
- **FR-162 — Disconnect cancellation:** A streaming client disconnect must trigger cancellation of the logical Model Invocation and active Provider Attempt, subject to bounded cleanup.
- **FR-163 — Explicit cancellation API:** The Gateway must expose a versioned Gateway-native cancellation endpoint for synchronous or otherwise still-running calls, addressable by `call_id` or Idempotency Key.
- **FR-164 — Cancellation authorization and evidence:** Explicit cancellation must use the caller's Data Plane authorization context, produce the same single `cancelled` Terminal Outcome, and record who/what initiated it.
- **FR-165 — Invocation status recovery:** The Gateway must expose a versioned Gateway-native status query addressable by `call_id` or Idempotency Key for `accepted`, `running`, `cancelling`, `completed`, `failed`, `uncertain`, and `cancelled` states.
- **FR-166 — Status recovery evidence:** Status responses must include terminal reason when known, Attempt summary, Usage/cost summary, uncertainty/degradation indicators, and the closed Routing Evidence availability projection in FR-1000, including a safe opaque reference only while Evidence is available. They must never decrypt, return, or download raw input messages, model output, or Replay Artifact content; an enabled generic content-retention policy does not widen the status response contract.
- **FR-167 — Status authorization:** Status queries must enforce the caller's Data Plane tenant/scope boundary and must not reveal another tenant's invocation existence or evidence.
- **FR-168 — Status retention floor:** Invocation status must remain queryable for at least the complete configured Idempotency Binding Window, independently of any shorter Replay Artifact TTL.
- **FR-169 — Independent evidence retention:** Invocation Evidence, Cost Ledger, Trace, and Logs must have retention policies independent from lifecycle status and from one another.
- **FR-170 — Expired status behavior:** After status retention expires, a query must return the non-disclosing lifecycle state `unknown_or_expired` and must not create or re-run the logical invocation.
- **FR-171 — Data Plane version:** OpenAI-compatible model invocation must be exposed under a versioned `/v1` Data Plane.
- **FR-172 — Gateway extension version:** Control Plane, cancellation, status recovery, and other Gateway-native extensions must use a separately versioned `/gateway/v1` protocol family.
- **FR-173 — Protocol-wide versioning:** Request/response DTOs, SSE events, error codes, and extension fields must be versioned as one protocol contract.
- **FR-174 — Compatibility evolution:** Additive backward-compatible changes may remain in a major version; breaking changes require a new major version and an explicit migration/compatibility window.
- **FR-175 — Structured failure taxonomy:** Gateway must distinguish extraction failure, incomplete or malformed JSON, root-type failure, Schema violation, resource violation, truncation, and internal validator/configuration fault without treating arbitrary text quality as a Gateway failure.
- **FR-176 — Structured validation evidence:** Invocation Evidence must retain each Provider Attempt's normalized Structured Failure Reason, validation phase, at most 32 normalized validator errors, RFC 6901 instance/Schema pointers or UTF-8 parser byte offsets, extraction attempts and outcomes, commitment state, retry relationship, and selected disposition without storing prohibited raw content. If more than 32 errors exist, it must record `truncated=true` and the observed total when known. Cross-Attempt evidence must identify which first-Attempt failure was selected as the Presented Structured Failure.
- **FR-177 — Structured recovery ladder:** Gateway applies the configured one-pass Local Structured Repair to the existing output. If an eligible JSON Structure Failure remains before external commitment, Gateway may execute at most one unchanged-request same-candidate retry under the ordinary Attempt, deadline, and bounded exponential-backoff limits. If that Attempt fails, or the cause is ineligible, the Model Invocation terminates as `structured_output_invalid` without Provider/model fallback or higher-tier-model recovery. Ordinary model-quality dissatisfaction is neither retryable nor a fallback trigger.
- **FR-178 — Validation strategy restrictions:** Only model-generated JSON structural reasons explicitly included in the versioned retry allowlist may retry before external commitment. Schema mismatch, resource-limit failure, caller-invalid Schema, Provider Safety Refusal, Gateway validator/configuration fault, and post-commit stream failure must not trigger Provider retry, Provider switching, or hidden model escalation and must return their classified failure.
- **FR-179 — Streaming validation boundary:** Gateway must parse Structured Output incrementally, defer final Schema validation until completion, and after the first external delta terminate any final validation failure without Provider retry/fallback or output splicing.
- **FR-180 — Narrow content ownership:** Gateway owns only declared Structured Output syntax/Schema conformance and bounded recovery; Loop retains business-semantic validation and all Tool-content interpretation.
- **FR-181 — Provider-independent ordinary calls:** Ordinary Data Plane callers must select a configured Model Alias and must not bind a Model Invocation to a concrete Provider endpoint or Provider model ID. Gateway derives the internal Service Requirement from that Alias and the validated request rather than exposing a separately configurable caller-facing Service Requirement name.
- **FR-182 — Controlled Provider override:** The Gateway may support a permission-controlled Provider Selection Override for diagnostics or administration, limited to configured Providers and models.
- **FR-183 — Override policy integrity:** A Provider Selection Override must still pass capability matching, health/circuit eligibility, egress security, retry/fallback, evidence, and tenant authorization policy; it must not bypass those controls or accept an arbitrary endpoint.
- **FR-184 — Correlation hierarchy:** `task_id` must identify the overall task, `turn_id` the Loop Step, `step_id` an operation within that step, and `call_id` one Model Invocation.
- **FR-185 — Trace correlation:** `trace_id` must connect the end-to-end distributed call chain while preserving the task/turn/step/call hierarchy in Invocation Evidence and structured telemetry.
- **FR-186 — Trace root:** The Agent Loop must create or propagate the root Trace context for a task execution.
- **FR-187 — Invocation span:** Each `call_id` must create a Gateway Model Invocation span under the root Trace; Provider Attempt, Adapter request, routing decision, retry, and fallback work must be represented as child spans where applicable.
- **FR-188 — Trace identity:** All spans in one distributed call chain must share `trace_id`; `task_id`, `turn_id`, `step_id`, and `call_id` remain separate business correlation fields.
- **FR-189 — Normalized authorization context:** The Gateway must normalize the selected Authorization Adapter result into an immutable Authorization Context containing `subject`, `tenant_id`, `issuer`, one matched logical `audience`, `expires_at`, `authentication_method`, and a required normalized `scopes` set that may be empty. The Adapter contract guarantees that `subject` remains stable across credential refreshes for the same principal; Gateway does not infer or persist a cross-credential identity mapping. Exact field profiles and rejection rules are defined by FR-903–FR-905.
- **FR-190 — Claim mapping boundary:** Each selected Authorization Adapter must own external credential/claim/result mapping into the normalized context; Gateway policy must not depend on external role-object shapes.
- **FR-191 — Scope separation:** Data Plane and Control Plane authorization must use independently mapped scopes in the Authorization Context.
- **FR-192 — Context integrity:** Authorization Context fields used for a request must be immutable after authentication and must be propagated to rate limits, evidence, status authorization, and audit records.
- **FR-193 — Tenant identifier retention:** The Gateway must retain `tenant_id` in the Authorization Context, request correlation, Invocation Evidence, and applicable telemetry. Detailed tenant-isolation topology and cross-tenant data-access rules remain deferred design decisions.
- **FR-194 — Structured validation strategy:** Gateway must define one ordered, bounded strategy: extraction and parsing, final validation, exactly one Local Structured Repair pass over the existing output, at most one unchanged-request same-candidate retry only for an allowlisted pre-commit JSON Structure Failure, then success or explicit terminal `structured_output_invalid`. Structured Validation Failure creates no compatible fallback or hidden regeneration.
- **FR-195 — Validation recovery exclusions:** A Structured Validation Failure may create another Provider Attempt only for an allowlisted pre-commit JSON Structure Failure and at most once. Schema mismatch, resource-limit failure, caller-invalid Schema, Safety Refusal, Gateway validator/configuration fault, and every post-commit failure prohibit retry, Provider/model switching, and hidden regeneration.
- **FR-196 — Global resource ceilings:** Gateway-wide hard ceilings must bound Provider Attempts, Local Structured Repair attempts, request/input size, Schema size/complexity, parser depth/state, output/event size, queue time, and total invocation duration; policy cannot raise these ceilings.
- **FR-197 — Policy-specific tighter limits:** In v0.1, published `resource_policies.limits` may tighten only its six declared Gateway ceilings, a Model Alias may tighten only maximum output Tokens, and a caller request may further lower its applicable output/deadline constraints. No Service Requirement registry, tenant policy subtree, generic invocation-policy object, or undeclared lower-level limit may widen or silently add another configuration path; violations are explicitly classified.
- **FR-198 — Shared reliability accounting:** Repair, retry, fallback, queue, and Provider work must consume one Invocation-level deadline/Attempt allowance so nested policies cannot amplify resource use.
- **FR-199 — Caller deadline:** The Data Plane must accept an optional caller timeout/deadline and normalize it into the internal Request Protocol.
- **FR-200 — Deadline clamp/default:** Gateway policy must clamp caller deadlines to a configured global maximum and apply a configured default when none is supplied.
- **FR-201 — Remaining-budget propagation:** Queueing, outer request validation, Structured Output parsing/validation/repair, retry/backoff, Provider requests, and fallback must consume one monotonic-clock remaining budget. Recovery must not reset or extend the original deadline.
- **FR-202 — Supported-field validation:** OpenAI-compatible request fields within the first-phase scope must be type-validated and normalized before conversion to the internal Request Protocol.
- **FR-203 — Unsupported capability error:** A recognized but unsupported request capability must return a stable `unsupported_capability` failure and must not be silently ignored or implicitly degraded.
- **FR-204 — Unknown-field policy:** Gateway extension fields must use a documented Gateway namespace. Unknown non-namespaced fields that could carry request semantics must be rejected rather than silently dropped.
- **FR-205 — Stable Gateway error taxonomy:** The Gateway must define stable provider-independent error codes including `invalid_request`, `structured_output_invalid`, `configuration_invalid`, `unauthorized`, `forbidden`, `authorization_unavailable`, `not_found`, `not_acceptable`, `unsupported_media_type`, `conflict`, `already_terminal`, `invocation_in_progress`, `replay_unavailable`, `request_too_large`, `rate_limited`, `deadline_exceeded`, `cancelled`, `client_too_slow`, `safety_refused`, `unsupported_capability`, `no_route`, `gateway_not_ready`, `provider_unavailable`, `provider_credentials_unavailable`, `provider_protocol_error`, `persistence_unavailable`, `upstream_timeout`, `uncertain`, and `internal`. Prompt, Tool, and business-semantic content errors remain Loop-owned.
- **FR-206 — HTTP error mapping:** HTTP status codes must map to Gateway error codes for transport compatibility but must not become the domain error identity.
- **FR-207 — SSE error identity:** In-stream SSE error/cancellation extension events must carry the same Gateway error code and structured failure identity as the internal protocol.
- **FR-208 — Safe error mapping:** Data Plane callers must receive the stable Gateway error code, safe summary, and Provider request ID when available. For Structured Validation Failure they additionally receive only the stable Structured Failure Reason and either the first safe RFC 6901 instance pointer or a UTF-8 parser byte offset; raw Provider, parser, validator messages, payloads, and remaining validation errors must not cross the API boundary.
- **FR-209 — Normalized Provider error evidence:** Invocation Evidence may retain a normalized Provider error category and bounded metadata for routing/retry decisions, without credentials or prohibited content.
- **FR-210 — Controlled raw error retention:** Raw Provider error payloads may be retained only under an explicit encrypted, redacted, access-audited retention policy; default behavior is discard.
- **FR-211 — Bounded template subsystem (amended 2026-09-13):** Gateway basic Prompt storage/rendering is authorized by ADR-0148. Rendering must have explicit syntax and resource ceilings and cannot execute arbitrary programs; historic engines and schemas are not automatically reinstated.
- **FR-212 — Caller-rendered content:** The caller is responsible for all instruction composition before invocation; Gateway must not distinguish template output from ordinary message content.
- **FR-213 — Generic input limits:** Already-rendered messages and opaque Tool fields consume the Gateway's generic body, content, Token/Context, deadline, and transport limits.
- **FR-214 — Pre-Provider resource rejection:** Gateway global hard limits and model-specific tighter limits must be enforced before any Provider Attempt; over-limit request Context returns explicit failure. This is resource safety, not Business Budget enforcement.
- **FR-218 — Routing replay evidence set:** Routing replay evidence must pin Model Alias/Service Requirement, candidate list and rejection reasons, configuration revision, Capability Registry revision, health/circuit snapshot, the Pricing Table and Routing Policy revision-scoped resource references, weight random seed, output-Schema version, opaque Tool-payload hash when present, and the Degradation Policy revision-scoped resource reference. Prompt replay remains Loop-owned.
- **FR-219 — Deterministic routing replay:** Given the pinned replay evidence and identical request fingerprint, an Eval must be able to reproduce the Router's candidate eligibility and selection explanation without requiring the original Provider call.
- **FR-220 — Versioned cost table:** Provider/model/token-type pricing must be stored as versioned configuration with effective time, currency, and rounding rules.
- **FR-221 — Attempt pricing basis:** Each Provider Attempt must use and record the Pricing Table's Configuration Revision plus Resource ID effective for that Attempt, including input, output, cached, and reasoning Token rates where available.
- **FR-222 — Cost estimate state:** Cost Ledger entries must distinguish authoritative, estimated, unavailable, and potentially duplicated cost states and retain the source/assumption metadata needed to explain them.
- **FR-223 — Aggregate cost:** Model Invocation cost must aggregate immutable Attempt-level charges without overwriting prior estimates when later Provider evidence changes certainty.
- **FR-224 — Telemetry field allowlist:** Evidence, Logs, Metrics, and Trace must use an explicit field allowlist and must not record Provider credentials, Authorization headers, raw messages/model output, opaque Tool content, or unredacted Provider errors.
- **FR-225 — Safe metadata:** Telemetry may retain stable hashes, lengths, output-Schema version, opaque Tool-payload presence/size/hash, error categories, Provider request IDs, routing decisions, latency, Token counts, and other approved operational metadata, but no Prompt- or Tool-specific semantic state.
- **FR-226 — Controlled content path:** Raw content may be retained only through the approved encrypted, redacted, audited content-retention path and must never be emitted accidentally through ordinary telemetry.
- **FR-227 — Port-preserving migration:** Migration must preserve the Agent Loop's model-call Port while replacing its implementation with a Gateway HTTP Client.
- **FR-228 — Incremental cutover:** Migration may switch call paths incrementally with explicit configuration and evidence for each cohort/path.
- **FR-229 — No dual authority:** After Gateway cutover for a path, the Gateway is the sole real model-execution authority; the old in-process Provider path must not remain a second authoritative path.
- **FR-230 — Safe shadowing:** Shadow/compare traffic may be used only when it cannot create Provider side effects, duplicate billing, or alter caller-visible state.
- **FR-231 — Migration rollback:** Rollback must be an explicit path-level configuration change with evidence, and must not silently re-enable two real execution authorities.
- **FR-232 — Metadata replay evidence:** Default Gateway replay evidence must retain Request/Execution Fingerprints, output-Schema version, generation parameters, configuration revision, routing evidence, and the Degradation Policy Resource ID plus Configuration Revision; Prompt replay evidence remains in the Loop.
- **FR-233 — Exact-content replay gate:** Replaying original messages or output content requires explicit encrypted content retention, its policy identity, access audit, and unexpired TTL.
- **FR-234 — Replay limitation disclosure:** Metadata-only replay must identify that it can reproduce policy/routing explanation but not reconstruct prohibited raw content.
- **FR-235 — Pool switching deferral:** First-phase admission does not require moving an invocation between concurrency pools; when the applicable limit is full or deadline is insufficient, the Gateway may reject explicitly. Pool definitions and safe switching are deferred for a later extension.
- **FR-236 — Routing Evidence persistence:** Routing Decisions and candidate rejection reasons must be persisted as append-only Invocation Evidence with a retention policy independent from transient Logs.
- **FR-237 — Routing Evidence minimization:** Routing Evidence must retain candidate identity, capability/health/cost/policy decision facts, and rejection reason without raw messages or prohibited content by default.
- **FR-238 — Routing Evidence access:** Reading Routing Evidence must use an authorized Control Plane/audit path and must itself produce access evidence.
- **FR-239 — Routing Evidence TTL:** Routing Evidence retention must be configurable by deployment/compliance policy and bounded by a Gateway-wide maximum TTL.
- **FR-240 — Stricter retention:** A narrower tenant/deployment policy may shorten Routing Evidence retention but must not extend the Gateway-wide maximum.
- **FR-241 — Financial record independence:** Routing Evidence expiry must not delete or mutate completed Cost Ledger financial records.
- **FR-242 — Immutable audit history:** Configuration publication records and Cost Ledger history must not be rewritten or retroactively deleted; Prompt history is outside Gateway.
- **FR-243 — Controlled cleanup:** Expiring/deleting mutable or content-bearing records must use a controlled cleanup operation with policy enforcement and access authorization.
- **FR-244 — Cleanup tombstone:** Cleanup must retain a non-content tombstone containing object identity/hash, reason, actor, timestamp, policy/revision, and cleanup outcome.
- **FR-245 — Audit continuity:** Cleanup must not make a prior object appear never to have existed and must not alter historical financial or execution facts.
- **FR-246 — Configuration audit events:** YAML/API import, mutation, conflict, validation, publication, rollback, synchronization, and cleanup must each create an immutable configuration audit event.
- **FR-247 — Configuration audit fields:** Each configuration audit event must retain actor/Authorization Context, source surface, old/new revision, change hash or redacted diff summary, result, timestamp, and Trace correlation.
- **FR-248 — Sensitive diff minimization:** Configuration audit events must not expose Secret values, raw request/content, or other prohibited data; sensitive changes use hashes and redacted summaries.
- **FR-249 — Snapshot rollback:** Configuration rollback must copy one complete historical snapshot into a new immutable Candidate Revision, even when the initiating change targeted one resource. It must not activate that Candidate; activation requires the ordinary separately authorized publish operation.
- **FR-250 — Snapshot consistency:** A published snapshot must contain mutually consistent Provider, Capability Registry, Model Alias, routing, health, rate-limit, cost, resource, safety, and Degradation Policy references.
- **FR-251 — No mixed runtime revisions:** Router, Model Adapters, and resilience policies must not observe a mixture of revisions from different published snapshots during one invocation.
- **FR-252 — Snapshot syntax validation:** YAML/API input must pass syntax, shape, type, and field Schema validation before candidate snapshot construction.
- **FR-253 — Snapshot reference validation:** Provider, Model Alias, policy, cost, Secret reference, and dependency references must resolve and be internally consistent before publication; Loop-owned Prompt and Tool state are absent from the snapshot.
- **FR-254 — Snapshot policy validation:** Capability/routing/degradation, security/endpoint, rate-limit/resource, and cost-policy consistency must be validated before publication.
- **FR-255 — Provider-I/O-free publication:** Candidate validation and publication must not send a network request, health probe, or model-generation request to a Provider. They perform only static/local consistency checks; runtime availability is learned from real Provider Attempts or separately configured, non-billable active probes after publication.
- **FR-256 — Snapshot digest:** Every publishable snapshot must have the single deterministic Snapshot Digest defined by the versioned canonical profile in FR-916–FR-917; no route, import surface, or lifecycle state may define a competing digest identity for the same snapshot content.
- **FR-257 — Atomic activation:** A candidate snapshot becomes active only after all validation and digest steps succeed, and activation is atomic.
- **FR-258 — Failed publication isolation:** A failed candidate must not affect the active snapshot, Router, Provider Adapter, or in-flight invocation.
- **FR-259 — Startup snapshot load:** Gateway startup must load the latest active published snapshot from PostgreSQL and verify its digest/integrity before Data Plane admission readiness.
- **FR-260 — Fail-closed startup:** Missing/invalid snapshot, digest mismatch, or unavailable required PostgreSQL must keep Data Plane admission non-ready and must not accept Data Plane invocations. When PostgreSQL and authorization are available, the Gateway Control Plane may read/export, import, validate, and publish a replacement snapshot; it must not enable Provider work before Data Plane admission readiness is restored.
- **FR-261 — YAML initialization boundary:** YAML may initialize/import candidate configuration but must not bypass validation, publication, or active-snapshot loading rules.
- **FR-262 — Versioned DB migrations:** PostgreSQL Schema changes must use versioned, ordered, auditable migration artifacts.
- **FR-263 — Separate migration execution:** Production Schema migrations must run through an independent migration job, not an implicit Gateway startup action.
- **FR-264 — Startup Schema compatibility:** Gateway startup must verify the database Schema version and remain non-ready when it is missing, incompatible, or only partially migrated.
- **FR-265 — Non-destructive startup:** Gateway startup must not perform destructive or irreversible Schema changes automatically.
- **FR-266 — PostgreSQL backup scope:** PostgreSQL configuration, Invocation Evidence, Cost Ledger, and immutable audit records must be covered by an external encrypted backup/recovery process; Prompt data is not a Gateway backup responsibility.
- **FR-267 — Recovery objectives:** Deployment must define RPO/RTO and perform restore verification for PostgreSQL authority data.
- **FR-268 — Redis recovery scope:** Redis Cached Degraded Results are disposable and need not be included in authoritative backups; a restored Gateway may begin with an empty cache.
- **FR-269 — Post-restore validation:** After PostgreSQL restore, Gateway startup must revalidate Schema compatibility, active snapshot integrity/digest, and required references before Data Plane admission readiness.
- **FR-270 — Recovery evidence:** Backup, restore, validation, and recovery failures must produce operational/audit evidence without exposing protected data.
- **FR-271 — Restart state reconciliation:** On restart/restore, an `accepted` or `running` invocation without authoritative Provider terminal evidence must transition to `uncertain`.
- **FR-272 — No recovery replay:** Recovery must not automatically regenerate, retry, or fallback an invocation that became `uncertain`.
- **FR-273 — Terminal preservation:** Invocations with durable authoritative `completed`, `failed`, or `cancelled` state must preserve that terminal state across restart/restore.
- **FR-274 — Recovery status evidence:** State reconciliation must record the prior state, recovery event, uncertainty reason, and configuration/Schema revision used for recovery.
- **FR-275 — Controlled uncertainty resolution:** A privileged Control Plane operation may resolve `uncertain` only with submitted external evidence and an explicit target classification.
- **FR-276 — No fabricated completion:** Without trustworthy Provider evidence, an `uncertain` invocation must not be marked completed or have its original Attempt rewritten.
- **FR-277 — Unresolved expiry:** An unresolved `uncertain` invocation may become `expired/unknown` after its retention policy, without creating a replacement invocation.
- **FR-278 — Resolution audit:** Every uncertainty resolution or expiry must append actor, evidence reference/hash, prior state, target state, reason, policy revision, and timestamp audit data.
- **FR-279 — Trusted resolution evidence:** Uncertainty resolution may rely only on configured Provider query APIs, verifiable signed receipts, authoritative billing/usage records, or another explicitly trusted evidence source.
- **FR-280 — Insufficient evidence:** Caller assertion, Gateway-local timeout/connection logs, or an unverified Provider request ID alone must not resolve `uncertain` to completed.
- **FR-281 — Evidence verification failure:** Failed, ambiguous, expired, or unverifiable resolution evidence must leave the invocation `uncertain` and append the verification failure.
- **FR-282 — Uncertainty-resolution capability:** Model Adapter capability declarations must optionally include `resolve_uncertain` support and its evidence protocol.
- **FR-283 — Adapter resolution path:** When `resolve_uncertain` is supported, the Gateway may use the Adapter to query/verify Provider terminal state through the configured trusted path.
- **FR-284 — Unsupported resolution:** When an Adapter does not support `resolve_uncertain`, the Gateway must not infer a Provider terminal outcome or automatically retry; the invocation remains `uncertain` until another trusted source or expiry.
- **FR-285 — Generic Adapter capability:** The first generic OpenAI Chat Completions HTTP Adapter must not declare `resolve_uncertain` unless its configured endpoint explicitly provides a trusted compatible query/receipt protocol.
- **FR-286 — Generic uncertainty behavior:** Timeout or connection loss through the generic Adapter must transition according to the `uncertain` lifecycle and must not be automatically replayed.
- **FR-287 — Chat Completions and Replay Entry Point:** The first-phase Data Plane must expose `POST /v1/chat/completions`; repeating this route with the same Idempotency Key and Request Fingerprint is the only caller-visible exact-replay content entry point. Gateway must not expose a separate `/replay`, Artifact download, Control Plane content-fetch route, or caller-addressable `artifact_id`.
- **FR-288 — Status route:** The Gateway-native protocol must expose `GET /gateway/v1/invocations/{call_id}` and `GET /gateway/v1/invocations/by-idempotency-key` under the same authorization boundary. The keyed route accepts its target only through `Idempotency-Key`. Both routes return lifecycle, Attempt, Usage/cost, degradation/validation, and safe evidence summaries only; neither may decrypt or return Replay Artifact content.
- **FR-289 — Cancellation route:** The Gateway-native protocol must expose `POST /gateway/v1/invocations/{call_id}/cancel` and `POST /gateway/v1/invocations/by-idempotency-key/cancel` under the same authorization boundary. The keyed route accepts its target only through `Idempotency-Key`. Both routes affect only a still-running original Model Invocation and must not target a Replay Access or decrypt, return, revoke, or otherwise operate on Replay Artifact content. If the original invocation is already terminal while a Replay Access is transferring, cancellation returns `already_terminal` and leaves that transfer unchanged.
- **FR-290 — Route/version consistency:** These routes must use the versioned DTO, error, SSE, Authorization Context, and audit rules already defined for their protocol family.
- **FR-291 — HTTP error mapping table:** The stable Gateway error taxonomy must map as follows: `invalid_request` 400; `structured_output_invalid` 400 before stream commitment or one mapped SSE error after commitment carrying the same 400 classification and safe reason/first-path extension; `safety_refused` 400 when no valid compatible refusal response can be returned; `unauthorized` 401; `forbidden` 403; `conflict`/`already_terminal`/`invocation_in_progress`/`replay_unavailable` 409; `request_too_large` 413; `unsupported_capability` 422; `rate_limited` 429; `provider_protocol_error` 502; `authorization_unavailable`/`gateway_not_ready`/`no_route`/`provider_unavailable`/`provider_credentials_unavailable`/`persistence_unavailable` 503; `upstream_timeout`/`deadline_exceeded` 504; `cancelled`/`client_too_slow` 499 Gateway extensions when an HTTP response remains representable; `uncertain` 504 for an ended invocation and 200 with state `uncertain` for status query; `internal` 500.
- **FR-292 — Error-code stability:** HTTP status mapping may evolve only compatibly; Gateway error codes remain the stable domain identity across JSON, SSE, and status protocols.
- **FR-293 — Retry-After scope:** `Retry-After` may appear only for `rate_limited`, Provider 429, or a `provider_unavailable` outcome with a known recovery window.
- **FR-294 — Retry-After bounds:** `Retry-After` must use integer seconds or HTTP-date and must not exceed the applicable deadline, retry, or policy ceiling.
- **FR-295 — No misleading Retry-After:** Authentication, request/Schema, Safety Refusal, `gateway_not_ready`, `uncertain`, and other non-retryable failures must not include `Retry-After`.
- **FR-296 — Passive Provider health:** Provider Health State and circuit eligibility must be driven primarily by signals from real Provider Attempts, including configured transport, timeout, rate-limit, upstream, and protocol outcomes.
- **FR-297 — Optional active probes:** Active Provider health probes must be disabled by default and may be enabled only through published configuration when the Provider offers an explicitly configured, safe probe path.
- **FR-298 — Probe isolation:** Active probes must use separate timeout, concurrency, credential, and rate-limit budgets; probe activity must not create a user Model Invocation, Provider Attempt, Token usage, or Cost Ledger entry.
- **FR-299 — No synthetic generation by default:** The Gateway must not issue billable model-generation requests merely to measure health unless an explicit policy enables that probe and records its separate operational cost classification.
- **FR-300 — Health transition evidence:** Passive and active health changes must emit structured transition evidence identifying the signal/probe, Provider, policy revision, prior/new state, and outcome without exposing credentials or raw content.
- **FR-301 — Single local pipeline:** Local Structured Repair is enabled by the Gateway-wide default for `json_object` and `json_schema`. Published operator configuration may disable it globally or for a Model Alias, but configuration cannot enable a second pass or independently repeat any pipeline stage.
- **FR-302 — Fixed repair pipeline:** When enabled, the versioned first-phase pipeline runs once in the fixed order: remove one BOM when present, remove one enclosing Markdown code fence when present, then extract exactly one unambiguous complete JSON value from surrounding prose. Input/output size, parser-resource, and remaining-time limits still apply. Data Plane callers cannot alter its enablement, steps, order, version, or count.
- **FR-303 — No separate structured regeneration allowance:** After Local Structured Repair fails, only an allowlisted pre-commit JSON Structure Failure may consume the ordinary shared allowance for one unchanged-request same-candidate retry. It creates no separate Attempt, deadline, Token, cost, fallback, or regeneration allowance. First-phase Token and cost Business Budgets are absent.
- **FR-304 — Post-commit structured failure:** After the first externally emitted normalized JSON byte, Structured Output must continue incremental extraction/parsing and final validation. A later second JSON value, ambiguous or prohibited suffix, syntax/root/Schema failure, truncation, or resource violation must emit one `structured_output_invalid` SSE error and close without `[DONE]`, a new Provider Attempt, model switch, or replacement output.
- **FR-305 — Repair evidence:** Invocation Evidence must record the effective repair limit, each attempted strategy/version, safe original/output hashes or change summary, result, consumed reliability allowance, and final validation disposition. Raw original content is not retained by default.
- **FR-306 — Invocation execution order:** The Gateway must execute one Model Invocation in this order: authenticate and validate the already-rendered request and reliability/resource limits; admit and lock one published snapshot; capability-filter candidates; remove security/health/circuit-ineligible candidates; rank eligible candidates by policy; execute a Provider Attempt; classify its outcome; for a Structured Validation Failure apply the permitted bounded Local Structured Repair; if an allowlisted JSON Structure Failure remains before commitment, optionally execute the one unchanged-request same-candidate retry; then terminate if still invalid. Other causes follow their classified ordinary recovery path, explicitly allowed richer degradation stages, or terminal outcome.
- **FR-307 — Retry before candidate fallback:** For a retryable pre-commit failure, the configured retry allowance for the current candidate is consumed before that candidate is exhausted and fallback selects another eligible candidate, unless policy explicitly marks the failure or candidate as immediately failover-only.
- **FR-308 — Circuit update before reselection:** A Provider Attempt outcome must update the applicable runtime health/circuit state before the Router evaluates remaining candidates for the next retry/fallback decision.
- **FR-309 — Remaining-candidate evaluation:** Fallback must not restart routing from an unbounded fresh state; it must retain attempted/rejected candidates, shared budgets, the locked configuration revision, and updated runtime eligibility evidence.
- **FR-310 — Commitment terminates recovery order:** Crossing the External Commitment Point ends all retry, Provider fallback, reduced-capability substitution, and cache substitution for that Model Invocation; only the existing stream's completed, failed, or cancelled terminal path remains.
- **FR-311 — Dual cache windows:** Every enabled cache policy must define `fresh_ttl_seconds` and `stale_ttl_seconds`. The fresh window lasts for `fresh_ttl_seconds`; `stale_ttl_seconds` is an additional duration after that fresh window, so an entry is stale-eligible only after freshness ends and before the combined duration expires. A zero stale duration disables stale eligibility.
- **FR-312 — Stale disabled by default:** `stale_ttl` must default to zero. A stale Cached Degraded Result may be returned only when the active Degradation Policy explicitly enables it and the response/evidence discloses its age and stale status.
- **FR-313 — Retention-bounded TTL:** Cache TTL values are published configuration and must not exceed the applicable Gateway-wide content-retention ceiling; the first-phase design does not impose a fixed duration independent of deployment policy.
- **FR-314 — Versioned logical invalidation:** Cache eligibility and keying must include `tenant_id`, authorization/policy boundary, canonical message hash, logical model/service, effective generation parameters, response format, output Schema, opaque Tool-payload hash when applicable, safety-policy, and relevant configuration compatibility revisions so a material semantic or version change creates an immediate logical miss; Tool-bearing requests remain cache-ineligible by default.
- **FR-315 — Emergency cache revocation:** A published or privileged audited revocation marker must make matching entries immediately ineligible, including for already admitted invocations whose Invocation Cache Policy Snapshot would otherwise permit the cache stage; physical Redis deletion may complete asynchronously and must not reopen eligibility.
- **FR-316 — Cache eligibility order:** Cache lookup must enforce semantic-key equality, tenant/authorization/policy isolation, revocation, freshness window, and side-effect eligibility before returning a Cached Degraded Result.
- **FR-317 — Safety Policy Reference:** Every Model Invocation must lock a Safety Policy Reference containing the Gateway Safety Policy Resource ID, Configuration Revision, content digest, and enforcement identity applicable to that invocation; no independent operator-assigned policy version exists.
- **FR-318 — Refusal evidence:** A Safety Refusal must record the normalized refusal category and stable reason code, enforcement stage, Gateway or Provider enforcer, Provider Attempt and request ID when applicable, and the locked Safety Policy Reference.
- **FR-319 — Provider policy uncertainty:** Provider safety-policy ID/version may be recorded only when reported through a trusted Provider protocol; otherwise evidence must state `unavailable` and must not infer equivalence from Provider or model names.
- **FR-320 — Refusal terminates recovery:** A Safety Refusal must terminate all same-Provider retry, other-Provider fallback, reduced-capability substitution, and fresh/stale cache substitution for that Model Invocation.
- **FR-321 — Refusal audit chain:** Invocation Evidence must prove that no Provider Attempt or Degraded Outcome was created after the Safety Refusal and must retain the policy, Attempt, routing, and terminal-disposition links without prohibited raw content.
- **FR-322 — Valid refusal response:** When a Provider supplies a valid Chat Completions refusal result, the Gateway must return HTTP 200 and preserve `message.refusal` and/or `finish_reason="content_filter"`; the internal Terminal Outcome is `completed` while the Model Result disposition is `safety_refused`.
- **FR-323 — Pre-response safety block:** A Gateway or Provider safety block before a valid response or SSE stream begins must return an OpenAI-style JSON error with HTTP 400 and stable Gateway code `safety_refused`; the internal Terminal Outcome is `failed`.
- **FR-324 — Streamed valid refusal:** A valid streamed refusal must preserve refusal/content-filter fields, end normally with `finish_reason="content_filter"`, and emit `[DONE]`; its completed transport outcome must not authorize retry or substitution.
- **FR-325 — In-stream safety interruption:** A safety interruption after streaming starts that cannot be represented as a valid Chat Completions refusal result must emit one Gateway `safety_refused` error event and close without `[DONE]`; its Terminal Outcome is `failed`.
- **FR-326 — Refusal mapping invariance:** HTTP/SSE representation must not change the internal Safety Policy Reference, evidence, or prohibition on retry, fallback, reduced-capability, and cache substitution.
- **FR-327 — Universal correlation identity:** Every Model Invocation must have a Gateway-generated `call_id` and a W3C-compatible `trace_id`; a valid incoming Trace context may be continued, but callers cannot supply or select the Model Invocation `call_id`.
- **FR-328 — Agent correlation requirements:** Agent Loop callers must provide `task_id` and `turn_id`, and must provide `step_id` when the invocation is caused by a distinct operation within the Loop Step.
- **FR-329 — Non-Agent correlation boundary:** For non-Agent callers, `task_id`, `turn_id`, and `step_id` are optional nullable business fields; the Gateway must not fabricate task, turn, or step semantics.
- **FR-330 — Correlation transport:** Distributed Trace Context must use W3C `traceparent` and `tracestate`; business correlation enters through `X-Gateway-Task-Id`, `X-Gateway-Turn-Id`, and `X-Gateway-Step-Id` without adding non-namespaced fields to the OpenAI-compatible request body.
- **FR-331 — Business identifier format:** Caller-supplied business correlation IDs must be opaque ASCII values of 1–128 characters limited to letters, digits, `.`, `_`, `:`, and `-`; invalid values must be rejected before a Provider Attempt.
- **FR-332 — Response correlation:** Every Data Plane HTTP access, including errors and stream establishment, must expose its fresh access `request_id` through `X-Request-Id`. `X-Gateway-Call-Id` exposes a Model Invocation `call_id` only after the applicable response contract authorizes disclosure of that invocation; pre-admission validation/authorization failures and Idempotency fingerprint/quarantine conflicts omit it and must never place an original `call_id` in `X-Request-Id`.
- **FR-333 — Upstream propagation boundary:** `task_id`, `turn_id`, and `step_id` must not be sent to a Provider by default. Trace Context may be propagated through an Adapter only when the Provider endpoint and published egress/telemetry policy explicitly allow it.
- **FR-334 — Request-body ceiling:** The first-phase default maximum HTTP request body is 4 MiB.
- **FR-335 — Message ceilings:** A request may contain at most 512 messages, and each message or content item is limited to 1 MiB before Provider translation.
- **FR-336 — Opaque Tool resource accounting:** Tool-related fields have no Tool-specific count or definition-size limit; they consume the ordinary request-body, message/content, decoded-event, Token/Context, and transport ceilings.
- **FR-337 — Output-Schema ceiling:** A requested output JSON Schema is limited to 256 KiB before parsing, compilation, or Provider translation.
- **FR-338 — Header ceiling:** Request headers are limited to 32 KiB in aggregate in addition to the field-specific correlation and authorization validation rules.
- **FR-339 — Stream-event ceiling:** Each decoded internal or Provider-derived SSE event is limited to 1 MiB before external serialization.
- **FR-340 — Effective Token and Context limit:** Effective Token/Context safety limits must be the minimum of the caller request, the Model Alias maximum-output ceiling, the derived Service Requirement facts, the selected Binding capability limits, and the Gateway Resource Ceiling; the OpenAI-compatible protocol must not claim one universal Provider context size or treat the limit as a spend quota.
- **FR-341 — Resource-limit authority:** Deployment configuration owns Gateway Resource Ceilings. The closed v0.1 Resource Policy may tighten only its six named ceilings, Model Alias may tighten only maximum output Tokens, and a validated request may further lower applicable output/deadline values; no other v0.1 configuration layer may alter them.
- **FR-342 — Resource rejection:** Byte-size ceiling violations must fail before a Provider Attempt with HTTP 413 and stable code `request_too_large`; count or Token/Context safety-limit violations must fail with HTTP 400 `invalid_request`.
- **FR-343 — Relative timeout transport:** The Data Plane must accept caller timeout through `X-Gateway-Timeout-Ms` as a positive relative duration and normalize it into a monotonic Invocation Deadline Budget.
- **FR-344 — Invocation timeout defaults:** The first-phase default Model Invocation timeout is 120 seconds and the deployment-level maximum is 600 seconds; missing values use the default and larger caller values are clamped.
- **FR-345 — Queue-time bound:** Queueing may consume no more than the lesser of 2 seconds and 10% of the remaining Invocation Deadline Budget.
- **FR-346 — Provider phase timeouts:** The default Provider connection timeout is 5 seconds; time to first business delta for one Attempt is limited to 60 seconds; each is further bounded by the remaining Invocation Deadline Budget.
- **FR-347 — Stream idle timeout:** A stream with no business-meaningful content delta, Tool Call progress, or Usage progress for 30 seconds must time out. Heartbeats, comments, connection events, and other protocol-only traffic must not reset this timer.
- **FR-348 — Timeout classification:** Connection, first-delta, or stream-idle timeout is classified as `upstream_timeout` while invocation-budget exhaustion is `deadline_exceeded`; recovery remains subject to pre/post-commit and uncertainty rules.
- **FR-349 — No sub-budget reset:** Provider Attempts, retry/backoff, fallback, and repair must not create or reset an independent total timeout and must consume the original remaining Invocation Deadline Budget.
- **FR-350 — Timeout-policy authority:** Deployment configuration owns timeout ceilings and defaults. The v0.1 Resource Policy may tighten total invocation seconds, and a caller deadline may be earlier; Model Alias, tenant, and any undeclared generic policy cannot configure other timeout values.
- **FR-351 — Graceful shutdown bound:** Shutdown must stop admission and drain for at most 30 seconds; remaining invocations are then cancelled, upstream cancellation is attempted, and terminal/audit evidence records `cancelled` without replacement retry or fallback.
- **FR-352 — Provider Attempt ceiling:** The first-phase Provider Attempt Budget is at most three Attempts per Model Invocation, including the initial call, same-candidate retries, and Provider fallbacks.
- **FR-353 — Per-candidate retry ceiling:** One Provider/model candidate may be retried at most once after its initial Attempt; further execution must use an unattempted eligible candidate or advance the Degradation Policy.
- **FR-354 — Default retry backoff:** Every authorized automatic same-candidate retry uses the shared backoff profile: 200 ms base, multiplier 2, and full jitter, with actual delay sampled from `[0, min(calculated_delay, 2 seconds)]` using an injectable deterministic random source for replay/test evidence. Only retryable transport/availability failures enter this path; Structured Validation Failures never do. Retry/fallback never creates a separate delay allowance.
- **FR-355 — Retry-After wait bound:** A trusted Provider `Retry-After` may replace calculated backoff only when it is no more than 5 seconds and fits the remaining Invocation Deadline Budget. A longer required wait makes that candidate unavailable for the current invocation rather than permitting an early retry.
- **FR-356 — Retryable causes:** Provider 429, transient connection failure, and explicitly classified retryable upstream 5xx may consume retry/fallback budget before the External Commitment Point.
- **FR-357 — Non-retryable causes:** Configuration, authentication/authorization with the same credential version, caller request or caller-invalid Schema, non-allowlisted Structured Validation Failure, Safety Refusal, Gateway validator/configuration fault, `uncertain`, cancellation, and post-commit failures must not create a same-candidate retry Attempt. An allowlisted JSON Structure Failure is the sole Structured Validation exception and may retry only once before commitment after Local Structured Repair fails. Every Structured Validation Failure prohibits a different-candidate fallback Attempt. A confirmed different Provider secret version may use only the separately defined bounded rotation-recovery exception.
- **FR-358 — Shared retry budgets:** Retry delay, Provider Attempt, and fallback must consume the original Provider Attempt Budget and Invocation Deadline Budget; no Adapter or policy layer may create an additional allowance.
- **FR-359 — Retry exhaustion:** When the three-Attempt ceiling or remaining deadline prevents further eligible Provider execution, the Gateway must continue only through the active Degradation Policy's explicitly allowed reduced-capability, cache, and terminal-failure stages.
- **FR-360 — Circuit identity and states:** The first-phase Provider Circuit must be maintained per `provider_binding_id` with `closed`, `open`, and `half_open` states in the single Gateway instance.
- **FR-361 — Circuit sample window:** Failure-rate evaluation uses Provider Attempts from the preceding 60 seconds, capped to the 20 most recent samples; at least 10 samples are required for rate-based opening.
- **FR-362 — Circuit opening thresholds:** A closed Provider Circuit opens when Provider-attributable failure rate reaches 50% in the eligible window or when five qualifying failures occur consecutively, including when the rate window has fewer than 10 samples.
- **FR-363 — Circuit failure classification:** Transient connection failures, Provider timeouts, 429, and explicitly retryable Provider 5xx count as circuit failures. Caller, authorization, configuration, Safety Refusal, and every Structured Validation Failure or other Schema/validation outcome must not affect Provider Health State or count toward circuit samples.
- **FR-364 — Initial open duration:** A newly opened Provider Circuit remains open for 30 seconds before entering `half_open`; Router must reject it during that period with an explicit circuit-open candidate reason.
- **FR-365 — Half-open trials:** A half-open Provider Circuit permits at most one concurrent trial Attempt. Two consecutive successful trials close and reset the Circuit; any qualifying failure immediately reopens it.
- **FR-366 — Reopen backoff:** Each repeated reopen doubles the prior open duration up to 5 minutes; successful closure resets the next open duration to 30 seconds.
- **FR-367 — Probe recovery input:** An explicitly configured active health probe may supply a half-open recovery trial under its separate probe budget but must not bypass the one-concurrent-trial or consecutive-success rules.
- **FR-368 — Circuit transition evidence:** Every Provider Circuit transition must record `provider_binding_id`, cause, eligible sample counts, failure ratio or consecutive-failure count, thresholds, old/new state, open duration, timestamp, and configuration revision.
- **FR-369 — Circuit routing evidence:** Each Routing Decision must record a Circuit-rejected candidate and the applicable state/policy revision without treating the candidate as capability-incompatible.
- **FR-370 — Instance concurrency default:** The single-instance phase permits at most 200 concurrent Model Invocations by default.
- **FR-371 — Tenant concurrency default:** Each `tenant_id` permits at most 50 concurrent Model Invocations by default; the retained tenant field is used for this limit without expanding the deferred tenant-isolation design.
- **FR-372 — Provider-binding concurrency default:** Each `provider_binding_id` permits at most 20 concurrent active Provider Attempts by default, subject to the Provider's published limit configuration.
- **FR-373 — Permit lifecycle:** A Model Invocation holds its instance and tenant Admission Permits from admission through completed, failed, or cancelled terminal state. A streaming invocation holds them for the full stream lifetime.
- **FR-374 — Attempt permit transfer:** Retry or fallback must release the completed/failed Provider Attempt permit before acquiring a permit for the next `provider_binding_id`; it must not release or reacquire the invocation-level instance/tenant permits.
- **FR-375 — No default queue:** First-phase admission queueing is disabled by default. A full instance/tenant concurrency or QPS limit must return HTTP 429 `rate_limited`; a full Provider-binding limit may make that candidate runtime-ineligible under the locked route, and exhaustion of all candidates returns 429. Any later explicitly enabled queue remains subject to the accepted queue-time deadline bound.
- **FR-376 — Supplementary QPS defaults:** QPS uses a token-bucket supplement with defaults of 100 QPS at instance scope and 50 QPS per tenant. Provider QPS must be declared in published Provider configuration and must not be inferred from model identity.
- **FR-377 — Concurrency precedence:** A QPS token never overrides or reserves an Admission Permit; concurrency eligibility is checked as the primary resource boundary.
- **FR-378 — Rate-limit recovery hint:** `Retry-After` may be returned only when token-bucket refill or a known concurrency recovery window yields a meaningful estimate under the previously accepted 5-second wait bound.
- **FR-379 — Permit release safety:** Completion, failure, cancellation, client disconnect, timeout, Adapter exception, and shutdown must each release applicable Admission Permits exactly once; leakage and double-release are correctness failures.
- **FR-380 — Configuration authority restatement:** PostgreSQL is the sole canonical configuration and runtime-read authority. Development deployments may choose a Control Plane API or a pure configuration file as an explicit revisioned ingress path into PostgreSQL, but Router and execution components must never read the file as a second authority. YAML and Control Plane APIs remain ingress/egress surfaces over the same stored state.
- **FR-381 — Full YAML import:** A YAML submission must carry `base_revision` as a canonical quoted decimal string and one complete Configuration Bundle, reject YAML numeric Revision values and unknown fields, and create a Candidate Configuration Revision without changing the Active Snapshot. YAML cannot express a Configuration Change Set. Development file-based operation may provide one explicit one-shot apply command with a publish flag that performs the ordinary Candidate creation, validation, and publication workflow against PostgreSQL; Gateway startup and file changes must never auto-publish or bypass those gates.
- **FR-382 — Import publication boundary:** Imported YAML must pass the ordinary validation, Eval, digest, audit, and explicit-publication workflow; import success alone must not activate it.
- **FR-383 — Revision YAML export:** The Control Plane must export a requested stored Revision as the deterministic UTF-8 YAML Synchronization View in FR-939. Its content reflects canonical database state, carries the exported Revision itself as the quoted-string `base_revision`, and contains Secret References but never resolved Secret values. That base is directly apply-ready only when the exported Revision is the current Active; every non-Active export is archival until the operator explicitly selects a valid current base.
- **FR-384 — No implicit file synchronization:** The Gateway must not watch YAML files for live mutation and must not automatically rewrite operator-managed or mounted files. CLI, deployment job, or operator workflow invokes import/export explicitly.
- **FR-385 — API/YAML convergence:** Control Plane mutations and YAML imports must become visible through the same database-backed read APIs and subsequent YAML exports; no independent file-side configuration state may diverge from PostgreSQL.
- **FR-386 — Synchronization conflict:** Candidate creation must compare `base_revision` with the transaction-time current Active Revision and return HTTP 409 `conflict` on mismatch without last-write-wins or a new Revision. Re-export or an explicit rebase workflow is required before another Candidate can be accepted.
- **FR-387 — Import/export audit:** YAML import/export must record actor/Authorization Context, source, base/target revision, content digest, validation result, timestamp, and Trace correlation without raw Secret values.
- **FR-388 — Bootstrap scope:** Bootstrap Configuration may contain only `environment_id`, startup profile, HTTP bind address/port, PostgreSQL connection Secret file/reference, SecretSource type and minimum access settings, the dedicated Idempotency Index Key Ring SecretSource reference, an optional Cache Backend Connection Profile, the resolved authorization-mode selection and its closed deployment-owned branch under FR-934 or FR-935, Log/OpenTelemetry/Metrics export settings, expected database Schema version, and an optional first-initialization YAML path. Source-level omission is permitted only for the deterministic `dev`/`dev_bypass` defaults defined by FR-887.
- **FR-389 — No domain-policy override:** Environment variables and Bootstrap Configuration must not override Provider, Model Alias, Capability Registry, routing, cost, retry, circuit, rate-limit, cache, or Degradation Policy stored in the Active Configuration Snapshot.
- **FR-390 — Bootstrap Secret handling:** Production PostgreSQL and SecretSource credentials must use Docker Secrets, mounted files, or an approved bootstrap Secret mechanism; ordinary non-secret environment variables must not contain resolved Provider credentials.
- **FR-391 — Production dotenv boundary:** Production startup must not automatically load `.env`; local development may opt in explicitly without changing production precedence or secret rules.
- **FR-392 — Bootstrap validation:** Missing, malformed, mutually inconsistent, or unauthorized Bootstrap Configuration must keep the Gateway non-ready and prevent Data Plane admission.
- **FR-393 — First initialization import:** An optional initialization YAML path may be processed only when no active configuration exists, and it creates a Candidate Configuration Revision that still requires normal validation and explicit publication.
- **FR-394 — Bootstrap precedence:** Command-line/bootstrap settings may select infrastructure endpoints and startup behavior only; once PostgreSQL is reachable, all Gateway domain behavior comes from the locked Active Configuration Snapshot.
- **FR-395 — Bootstrap evidence:** Startup must record the non-secret Bootstrap Configuration digest, environment ID, Schema compatibility result, snapshot-load result, and readiness outcome without logging Secret contents.
- **FR-396 — Inward dependency direction:** Source dependencies must point from Infrastructure and Interface Adapters toward Application and Domain; inner layers must not import outer frameworks or implementations.
- **FR-397 — Domain purity:** Domain types and rules for Model Invocation, Provider Attempt, Routing Decision, Stream Event, Model Result, failure, reliability/resource limits, and policies must not depend on FastAPI, HTTP DTOs, Pydantic transport models, Provider payloads/SDKs, SQLAlchemy/database rows, or Redis values.
- **FR-398 — Application use cases:** Application must own invocation, streaming, cancellation, status, and configuration validation/publication as delivery- and infrastructure-independent use cases; Prompt orchestration is absent.
- **FR-399 — Client-owned Ports:** `ProviderPort`, `ConfigurationRepository`, `InvocationEvidenceStore`, `CostLedger`, `CacheStore`, `AuthorizationPort`, `SecretSource`, `Clock`, `RandomSource`, and equivalent interfaces must be declared by the Application client that consumes them, not by their Infrastructure implementation.
- **FR-400 — API adapter boundary:** OpenAI-compatible and Gateway-native controllers must validate/map external DTOs into Application Commands and map Application Results/Failures/Events through presenters; they must not implement routing, retry, cost, or state-transition rules.
- **FR-401 — Provider anti-corruption boundary:** Each Model Adapter must translate only between the Application-owned Provider Port protocol and Provider-specific HTTP/JSON; Provider request/response objects must not enter Application or Domain.
- **FR-402 — Persistence adapter boundary:** PostgreSQL and Redis Adapters must map stored records/values to Application/Domain types; ORM models, rows, sessions, and Redis serialization types must not cross inward.
- **FR-403 — Simple boundary data:** Architectural boundaries must exchange Gateway-owned immutable Commands, Results, Events, Failures, identifiers, and value objects rather than framework or storage objects.
- **FR-404 — Pydantic placement:** Pydantic is permitted at outer API DTO, Gateway metadata/error-envelope, and Structured Output validation Adapter boundaries; Domain types must not require Pydantic inheritance, and arbitrary JSON Schema evaluation remains behind an Application-owned Port.
- **FR-405 — Composition Root:** The outermost Composition Root alone selects concrete framework and infrastructure implementations, constructs them from Bootstrap Configuration, and injects them into Application use cases; it must contain no domain decisions.
- **FR-406 — Architecture enforcement:** Automated architecture tests must reject prohibited inward imports and direct use of Provider, FastAPI, persistence, Redis, or transport types in Domain/Application modules.
- **FR-407 — Explicit Provider completion operation:** Application-owned `ProviderPort.complete(request, context)` must return exactly one Gateway `ProviderResult` or `ProviderFailure` and must not return a stream-dependent union controlled by a boolean flag.
- **FR-408 — Explicit Provider streaming operation:** `ProviderPort.stream(request, context)` must return an asynchronous sequence of Gateway-owned Provider Events and must not expose Provider chunks or external SSE frames.
- **FR-409 — Optional uncertainty operation:** `ProviderPort.resolve_uncertain(evidence)` is available only when the Adapter declares and configures the trusted uncertainty-resolution capability; unsupported Adapters must not implement it as a guessed result.
- **FR-410 — Shared Provider protocol types:** Completion, streaming, and uncertainty operations must share Gateway-owned request, context, resolved-model, usage, receipt, and failure value objects without Provider SDK or HTTP types.
- **FR-411 — Provider Event vocabulary:** Streaming Provider Events must represent `content_delta`, bounded opaque compatible payload fragment, `usage`, and exactly one of `completed`, `failed`, or `cancelled` terminal events without Prompt- or Tool-specific domain events.
- **FR-412 — Provider stream terminal invariant:** `ProviderPort.stream` must produce exactly one terminal Provider Event and no event afterward; premature iterator completion is a protocol failure translated by the Adapter.
- **FR-413 — Adapter exception containment:** Model Adapters must catch and translate Provider SDK/HTTP, transport, decoding, protocol, and Adapter-internal exceptions into ProviderFailure or a failed Provider Event; raw exceptions must not cross the Provider Port.
- **FR-414 — Commitment decision ownership:** Application, not the Model Adapter, determines whether a failure may trigger retry/fallback using Provider Events, external commitment state, and shared budgets.
- **FR-415 — External stream separation:** Provider Events remain internal; the API presenter alone translates them to OpenAI-compatible SSE and Gateway extension events.
- **FR-416 — No Gateway Prompt selector:** `gateway.prompt` and any equivalent Gateway-owned Prompt name/version/variables extension must be rejected as unknown or unsupported; Prompt selection happens before the Gateway call.
- **FR-417 — Already-rendered messages:** API Layer accepts the Compatibility Profile's messages as caller-composed input and translates only their protocol representation, not their instruction meaning or provenance.
- **FR-418 — Message-order preservation:** Gateway must preserve caller message order through Provider translation and must not prepend, append, merge, replace, or synthesize System, developer, Few-shot, or other Prompt content.
- **FR-419 — Role validation boundary:** API Layer may validate supported message roles and structural shape, but Gateway must not enforce Prompt-authoring policies about which instruction roles the Loop may use.
- **FR-420 — Generic message limits:** Every message and content item consumes ordinary body, item-size, Token/Context, safety, and transport limits without Prompt-specific insertion or budget logic.
- **FR-421 — Structured-output ownership:** A caller-requested output Schema is a Gateway-enforced syntactic/structural contract: Gateway uses it for capability routing and final local validation, while Loop remains responsible for business meaning and application safety.
- **FR-422 — No Prompt composition failures:** Gateway exposes no missing-variable, template-syntax, Prompt-version, Prompt-publication, Prompt-Eval, or Prompt-override failure classes.
- **FR-423 — No Prompt evidence surfaces:** Responses, streams, status, Evidence, Logs, Trace, Metrics, configuration, and Control Plane must not contain Gateway-derived Prompt identity or rendering metadata.
- **FR-425 — Parameter default precedence:** Effective Generation Parameters begin with Model Alias defaults, then apply caller-supplied supported values subject to hard Gateway/model/tenant/safety constraints.
- **FR-426 — Caller parameter validation:** Caller generation parameters may replace Model Alias defaults when the Compatibility Profile and selected candidate support them; Gateway validates accepted type, range, enum, and hard constraints without a Prompt override allowlist.
- **FR-427 — Hard parameter constraints:** Gateway Resource Ceilings, Model Capability Registry limits, tenant policy, and safety policy are non-overridable and must constrain Model Alias defaults and caller parameter values.
- **FR-428 — No silent parameter clipping:** Except for the separately accepted invocation-timeout clamp, an out-of-range, conflicting, or disallowed generation parameter must fail with `invalid_request` before a Provider Attempt rather than be silently clipped or ignored.
- **FR-429 — Recognized unsupported parameter:** A syntactically valid parameter whose required behavior is recognized but unavailable on all eligible candidates must fail with `unsupported_capability` rather than be discarded.
- **FR-430 — Unknown parameter handling:** Unknown non-namespaced request fields remain rejected under strict compatibility validation.
- **FR-431 — Provider option boundary:** First-phase ordinary Data Plane calls must not accept arbitrary Provider-specific generation options. A future namespaced extension requires an explicit Provider/field allowlist, authorization, validation, translation, and audit design.
- **FR-432 — Effective parameter evidence:** Invocation Evidence must retain caller-supplied parameter values or permitted non-content representation, each applied default/override source, rejection or constraint decisions, final Effective Generation Parameters, and a canonical hash.
- **FR-441 — Model requirement:** Every OpenAI-compatible Chat Completions request must provide the standard `model` field as one configured Model Alias, which becomes the Requested Model. v0.1 exposes no separately named or caller-selectable Service Requirement resource.
- **FR-446 — Immutable Requested Model:** The Requested Model must be locked after outer request validation and remain unchanged across retry, fallback, and degradation; Provider fallback may change only the Resolved Model within that locked routing contract.
- **FR-447 — Model-selection visibility:** Responses, streaming metadata, status, and Invocation Evidence must preserve the effective `requested_model` and actual `resolved_model`; the standard OpenAI-compatible response `model` remains the concrete Resolved Model.
- **FR-448 — Model-selection evidence:** Invocation Evidence must retain the caller-supplied Requested Model, locked routing configuration, selected Resolved Model, and recovery path without any Prompt-derived default or override metadata.
- **FR-449 — Loop Tool ownership:** The Agent Loop exclusively owns Tool definitions, selection semantics, argument validation, execution, side effects, state, results, errors, and persistence; Gateway must not become a Tool domain service.
- **FR-450 — Opaque Tool request pass-through:** API Layer may accept the Compatibility Profile's `tools`, `tool_choice`, `parallel_tool_calls`, and Tool-history fields, but Gateway must carry them as bounded opaque compatible payloads without interpreting names, Schemas, arguments, or policy intent.
- **FR-451 — Opaque Tool response pass-through:** Adapter must preserve Provider Tool-related response fields semantically and return them through the compatible response path without constructing Gateway Tool Call domain objects.
- **FR-452 — Opaque Tool stream pass-through:** Provider Tool-related stream fragments must be forwarded in received order subject only to generic SSE framing, backpressure, cancellation, commitment, and terminal rules; Gateway must not assemble Tool Calls.
- **FR-453 — Generic limits only:** Tool payloads are subject to generic request-body, message/content, event-size, deadline, and transport limits, but not Gateway-owned Tool count, name, argument, nesting, or Tool-Schema limits.
- **FR-454 — No Tool semantic validation:** Gateway must not validate declared Tool membership, Tool Call identity, `tool_choice` satisfaction, parallel behavior, argument JSON completeness, or argument Schema conformance.
- **FR-455 — No Tool repair:** Gateway must not extract, repair, coerce, or infer Tool Calls or Tool arguments from native fields, ordinary text, Markdown, or incomplete content.
- **FR-456 — No Tool identity synthesis:** Gateway must not create, replace, stabilize, or reconcile Tool Call IDs or Provider indices; those values are passed through for the Loop to interpret.
- **FR-457 — No Tool-specific recovery:** Tool payload content must not independently trigger retry, fallback, repair, or circuit state; only ordinary transport/Provider failures and the existing pre-commit execution policy may do so.
- **FR-458 — Tool choice is opaque:** Supported external `tool_choice` values are forwarded as caller intent, but Gateway does not enforce whether Provider output satisfies `none`, `auto`, `required`, or a named choice.
- **FR-459 — Parallel field is opaque:** `parallel_tool_calls` is forwarded under the Compatibility Profile without Gateway enforcement, scheduling, merging, or call-count interpretation.
- **FR-460 — Coarse Tool capability:** Capability Registry retains only whether an Adapter/binding can transport the compatible Tool Calling fields; it does not model choice modes, parallel semantics, Tool limits, or argument guarantees.
- **FR-461 — Loop owns Prompt and Tool policy:** Gateway has no Prompt Bundle or Tool policy; the Loop supplies already-rendered messages and opaque Tool-related fields for each invocation.
- **FR-462 — Coarse Tool routing:** A request carrying Tool fields requires the coarse Tool Calling transport capability; Router records only capability availability/rejection and does not inspect Tool payload semantics.
- **FR-463 — Unsupported Tool transport:** If no eligible candidate can transport the compatible Tool fields, the invocation fails before a Provider Attempt with stable `unsupported_capability`.
- **FR-464 — No Tool behavior emulation:** Gateway must not emulate Tool behavior with additional model generations, Prompt injection, textual parsing, or response rewriting.
- **FR-465 — Minimal Tool evidence:** Invocation Evidence may retain presence/size/hash of the opaque Tool payload and selected candidate's coarse capability, but not Tool definitions, names, arguments, validation state, execution state, or Tool-specific result records.
- **FR-466 — Stream Commitment Barrier:** The API Layer must retain a streaming response behind a Stream Commitment Barrier until it has a valid externally serializable business event or a valid normal terminal result.
- **FR-467 — No pre-barrier downstream bytes:** Before crossing the barrier, the Gateway must not flush HTTP 200/SSE headers, heartbeats, comments, empty events, or any response-body bytes to the caller.
- **FR-468 — Protocol-only upstream traffic:** Provider connection events, heartbeats, comments, and empty or protocol-only chunks before the barrier must not be forwarded, count as TTFT, or establish the External Commitment Point.
- **FR-469 — Pre-barrier failure response:** If admission, routing, retry/fallback, timeout, cancellation, or Provider execution fails before the barrier, the Gateway must return the ordinary OpenAI-style JSON error with its mapped HTTP status and must not start SSE.
- **FR-470 — Barrier crossing event:** The barrier may be crossed only for the first valid content delta, Tool Call delta, refusal delta, or a valid normal completion with no preceding business delta; the first downstream flush must pair the HTTP 200/SSE response with that event without intentional delay.
- **FR-471 — Empty normal stream:** A valid normal result with no content or Tool Call delta must emit a valid Chat Completions chunk carrying its `finish_reason`, followed by `[DONE]`, rather than closing an empty SSE response.
- **FR-472 — Post-barrier terminal invariance:** Once HTTP 200/SSE headers or any SSE event has been flushed, subsequent failure or cancellation must use exactly one Gateway streaming terminal event and close; it must not switch back to a JSON HTTP error, retry/fallback to replacement output, or emit `[DONE]`.
- **FR-473 — Bounded streaming extraction:** The Stream Commitment Barrier must not buffer a complete Structured Output. Gateway may retain only bounded prefix detection, one-fence state, parser state, and suffix/lookbehind state; it suppresses wrappers and emits normalized JSON bytes as soon as their membership in the selected candidate is established. Opaque Tool fragments are never assembled or interpreted.
- **FR-474 — Streaming Usage option:** The Data Plane must support `stream_options.include_usage`; false or omitted suppresses caller-visible Invocation Usage only and must not disable per-Attempt Usage Measurement, invocation aggregation, or cost accounting.
- **FR-475 — Normal Usage ordering:** For a normally completed stream with `include_usage=true`, external order must be business deltas, the completion chunk carrying `finish_reason`, at most one usage-only Invocation Usage summary chunk aggregating every executed Attempt, then `[DONE]`.
- **FR-476 — Usage normalization:** Model Adapters must identify Provider Usage observations as cumulative or incremental and normalize them into Usage Measurements that Application can merge monotonically without double counting.
- **FR-477 — Usage provenance:** Usage Measurement provenance must be `authoritative` when explicitly reported by the Provider, `estimated` only when produced by a configured versioned tokenizer compatible with the actual Resolved Model, or `unavailable` when neither source is valid; missing counts must never be represented as zero.
- **FR-478 — Usage compatibility mapping:** Standard OpenAI Usage numeric fields may be emitted only for available authoritative or estimated counts. A versioned Gateway extension must disclose `estimated`, `unavailable`, and completeness state; unavailable Usage uses extension metadata without fabricated standard numeric counts.
- **FR-479 — Interrupted Usage:** On failed, cancelled, or uncertain streaming termination, the Gateway must retain all observed Usage as `partial` unless authoritative final totals are available, must expose safe partial-state metadata in the terminal/status protocol, and must not regenerate solely to obtain Usage.
- **FR-480 — Attempt-level Usage accounting:** Every retry and fallback Provider Attempt must retain its own Usage Measurement, including failed or uncertain Attempts. Caller-visible Invocation Usage must sum all known category counts across every executed Attempt, including a failed structured Attempt before successful retry, and must disclose aggregate authoritative/estimated/unavailable and complete/partial state without fabricating unknown counts as zero.
- **FR-481 — Cost consistency:** Cost Ledger calculations must use the same Usage Measurement provenance/completeness, Resolved Model, pricing-table version, currency, and estimation assumptions as Invocation Evidence; each Attempt is priced separately before invocation aggregation.
- **FR-482 — Usage timing semantics:** A business-meaningful Usage event may refresh stream idle progress but must not establish TTFT, the External Commitment Point, or content success by itself.
- **FR-483 — Tool envelope syntax only:** API Layer may reject malformed outer JSON or Compatibility Profile field types with `invalid_request`, but must not validate Tool definitions or Tool argument Schemas.
- **FR-484 — Unsupported Tool transport mapping:** No eligible coarse Tool Calling transport capability maps to HTTP 422 and stable `unsupported_capability`.
- **FR-485 — Provider Tool content pass-through:** Provider Tool payloads are not classified as `tool_call_invalid`; incomplete, duplicate, missing, or semantically invalid Tool content is passed to the Loop unless an ordinary transport/protocol failure prevents forwarding.
- **FR-486 — Synchronous Tool forwarding:** Synchronous Tool-related compatible fields must be returned without Tool-specific success or error reinterpretation.
- **FR-487 — Streaming Tool forwarding:** Tool-related SSE fragments must follow generic stream commitment, ordering, backpressure, cancellation, and terminal behavior without Tool-specific terminal errors.
- **FR-488 — No Gateway Tool validator:** Gateway must not contain a Tool parser, argument-Schema validator, Tool policy engine, Tool Call accumulator, or Tool-specific repair component.
- **FR-489 — Tool error ownership:** Every Tool semantic or execution error belongs to the Agent Loop; Gateway health, quality, retry, and circuit metrics must not infer Tool correctness from opaque payload content.
- **FR-490 — Attempt Cost Accrual:** When a Provider Attempt completes, fails after possible billing, or becomes uncertain, the Gateway must append one immutable Cost Accrual using that Attempt's locked pricing-table version, Usage Measurement, currency, rounding rule, and duplicate-charge state.
- **FR-491 — Append-only reconciliation:** Trusted Provider billing or usage evidence may correct an accrual only by appending a Reconciliation Adjustment that references the original Attempt and Cost Accrual; original entries must never be updated or deleted.
- **FR-492 — Reconciliation provenance:** Each Reconciliation Adjustment must retain Provider request/billing identifiers when available, billing period, external evidence hash/reference, source authority, import actor, timestamp, reason, and an idempotency key.
- **FR-493 — Credits and refunds:** Provider credits, refunds, and reversals must use explicit negative Reconciliation Adjustments rather than mutation or unsigned amount replacement.
- **FR-494 — Cost state and aggregation:** Cost views must compute the original accrual plus all effective adjustments while preserving `estimated`, `accrued`, `reconciled`, and `disputed/unallocated` states at Attempt and Model Invocation levels.
- **FR-495 — Unallocated billing discrepancy:** Trusted billing amounts that cannot be reliably mapped to one Provider Attempt must be retained as Provider/billing-period-level unallocated discrepancies and must not be guessed or proportionally assigned to invocations.
- **FR-496 — Currency preservation:** Every ledger entry must retain the Provider settlement currency. Optional reporting-currency conversion must be a separate derived amount with versioned exchange-rate source/time and must not replace the original currency or amount.
- **FR-497 — Prospective routing cost:** Routing must use the published prospective pricing configuration locked for the invocation; later reconciliation must not rewrite historical Routing Decisions or retroactively change candidate ranking evidence.
- **FR-498 — Reconciliation Control Plane:** Reconciliation import must use a separately authorized Control Plane operation with idempotent processing, validation, append-only audit evidence, and no Data Plane mutation path.
- **FR-499 — Admission Persistence Checkpoint:** Before a Provider Attempt can exist, one PostgreSQL transaction must durably create the Model Invocation, `call_id`, Idempotency Key/fingerprint binding when supplied, locked configuration/model/policy references, and `accepted` state.
- **FR-500 — Admission persistence failure:** Failure of the admission checkpoint must return HTTP 503 `persistence_unavailable`, create no Provider Attempt, and make the instance non-ready for new Data Plane admission while required PostgreSQL remains unavailable.
- **FR-501 — Attempt-start checkpoint:** Each Provider Attempt and its ordinal, selected Provider/Resolved Model, budgets, and pricing basis must be durably recorded as started before any upstream request bytes are sent.
- **FR-502 — Recovery-decision checkpoint:** An Attempt outcome, Failure Disposition, remaining budgets, and retry/fallback decision must be durable before the next Provider Attempt may begin; persistence failure must stop recovery rather than create unrecorded billing exposure.
- **FR-503 — Commitment checkpoint:** The External Commitment Point and selected Attempt identity must be durably recorded before crossing the Stream Commitment Barrier and emitting the first business event.
- **FR-504 — Metadata-only stream durability:** Ordinary operation must not persist every content or Tool Call delta or raw response content; durable checkpoints retain state, ordinals, safe hashes, Usage, validation, and required evidence under the content-retention policy.
- **FR-505 — Terminal transaction:** Before a synchronous success response or streaming `[DONE]`, one transaction must persist the terminal state, final Usage Measurement, Cost Accrual, validation outcome, and terminal Invocation/Attempt Evidence.
- **FR-506 — Post-Provider persistence failure:** If Provider execution may have occurred but a required outcome, commitment, or terminal checkpoint fails, the Gateway must return or stream `persistence_unavailable` according to commitment state, stop further retry/fallback, and treat the invocation as potentially billed and uncertain.
- **FR-507 — Persistence uncertainty recovery:** After PostgreSQL recovery, durable started/non-terminal records affected by lost checkpoints must follow the existing restart/reconciliation path to `uncertain`; the Gateway must not infer success or automatically regenerate.
- **FR-508 — Active-call outage behavior:** Required PostgreSQL loss must stop new admission immediately. Existing calls may proceed only until their next required Persistence Checkpoint, where failure closes them under FR-506; they must not bypass or indefinitely buffer required evidence in memory.
- **FR-509 — Published Idempotency Replay Mode:** Idempotency behavior must be selected by published policy as `execution_dedup_only` or `encrypted_exact_replay`; a caller cannot enable response retention outside the authorized policy.
- **FR-510 — Default deduplication-only mode:** `execution_dedup_only` is the default and must not persist raw response content. Same-key/same-fingerprint requests reuse the logical lifecycle; a completed success whose content is unavailable to replay must return HTTP 409 `replay_unavailable` from the Data Plane with `call_id` and an authorized status-query reference, rather than a fabricated OpenAI success or a non-compatible status-summary body. Status, terminal error, Usage/model, and evidence-summary data are retrieved through the Gateway-native status surface.
- **FR-511 — No live stream joining:** The first phase must not attach a duplicate client to an in-progress synchronous response or live SSE stream. A same-key/same-fingerprint duplicate while running returns HTTP 409 `invocation_in_progress` with the existing `call_id` and authorized status URL and creates no Provider Attempt.
- **FR-512 — Encrypted exact replay policy:** `encrypted_exact_replay` may be enabled only by an authorized policy that defines TTL, encryption/key management, size limits, eligible result types, and access scope within the Gateway-wide content-retention ceiling.
- **FR-513 — Replay Artifact binding:** Each Replay Artifact must be encrypted at rest and bound to tenant/authorization scope, the Idempotency Index Digest and its profile/key identity rather than the raw Idempotency Key, canonical Request Fingerprint, `call_id`, response protocol version, and original terminal outcome; it must be stored separately from ordinary Logs, Trace, and non-content Invocation Evidence.
- **FR-514 — Exact completed replay:** An eligible completed same-key/same-fingerprint request with an unexpired Replay Artifact must pass current authorization and the original tenant/scope binding, then return the stored synchronous response or normalized SSE event sequence without Provider execution and include `X-Gateway-Replayed: true`. Eligibility is limited to a complete successful result whose content-retention policy permits replay.
- **FR-515 — Streaming replay semantics:** SSE replay must preserve semantic event contents, ordering, terminal type, and `[DONE]` presence or absence but need not reproduce original inter-event timing.
- **FR-516 — Non-success idempotency behavior:** Failed, cancelled, uncertain, or persistence-unavailable lifecycles must return their existing terminal/status outcome and must never automatically regenerate through Idempotency handling.
- **FR-517 — Replay expiry without re-execution:** If a Replay Artifact expires while the Idempotency Key remains valid, a duplicate must return HTTP 409 `replay_unavailable` with `call_id` and status information and must not execute a Provider.
- **FR-518 — Idempotency conflict invariance:** A repeated Idempotency Key in the same namespace with a different canonical fingerprint must return HTTP 409 `conflict` in either replay mode. It reveals no prior content or historical invocation identifiers, state, model, timestamps, Fingerprint, or Artifact existence.
- **FR-519 — Replay metadata evidence:** Invocation Evidence may retain replay mode, artifact identifier/hash, creation/expiry, replay count, authorization decision, and deletion tombstone, but raw Replay Artifact content must remain outside ordinary evidence and telemetry.
- **FR-520 — Request Fingerprint timing:** Request Fingerprint must be computed after API validation and deterministic normalization but before Model Alias, Active Snapshot, routing, or other mutable execution resolution.
- **FR-521 — Request Fingerprint inputs:** Request Fingerprint must cover API route/version, normalized authorization scope identity, standard `model` value, already-rendered messages, opaque Tool-field set, output Schema, generation parameters, `stream`, `stream_options.include_usage`, semantic Gateway extensions, and any caller deadline field that changes the logical invocation limit without extracting Prompt or Tool semantics. Operator-owned extraction configuration is excluded because it is not caller intent.
- **FR-522 — Request Fingerprint exclusions:** Request Fingerprint must exclude the Authorization credential itself, Idempotency Key, Trace/request IDs, header ordering/casing, connection metadata, and client-side transport wait timeouts that do not change Gateway execution semantics.
- **FR-524 — Idempotency conflict basis:** Same-key conflict comparison must use Request Fingerprint, so later Gateway configuration publication does not detach a duplicate from the first invocation's locked outcome.
- **FR-525 — Execution Fingerprint timing and inputs:** After admission resolution, the Gateway must compute an Execution Fingerprint over the behavior-affecting projection of the locked Active Snapshot, Requested Model, Effective Generation Parameters, output-Schema identity, effective Structured Output extraction enablement and pipeline version, canonical message hash, opaque Tool-payload hash when present, safety/degradation policies, and other behavior-affecting resolved inputs without interpreting Prompt or Tool content. Snapshot revision/digest and non-semantic labels remain Evidence but are excluded from the fingerprint when their behavioral projection is unchanged.
- **FR-526 — Fingerprint usage separation:** Execution Fingerprint must support semantic cache identity, Replay Artifact execution binding, and replay/audit evidence; it must not replace Request Fingerprint for Idempotency conflict detection.
- **FR-527 — Isolation outside fingerprint:** Cache and replay lookup must apply tenant, normalized authorization, safety/policy, TTL, and revocation checks in addition to matching the applicable fingerprint; digest equality alone never authorizes access.
- **FR-528 — Keyed digest:** Request and Execution Fingerprints must use deterministic versioned canonicalization and keyed HMAC-SHA-256 or an approved equivalent; evidence stores algorithm/canonicalization/key version but never the secret key or canonical sensitive plaintext.
- **FR-529 — Fingerprint key rotation:** Fingerprint-key rotation must preserve verification of prior key versions until every dependent Idempotency record, Replay Artifact, and cache entry expires or is revoked, then retire the old key through the SecretSource lifecycle.
- **FR-530 — Cancellation initiators:** Explicit cancel API, client/context cancellation, streaming disconnect, and bounded graceful-shutdown expiry must enter one cancellation use case with an authenticated or system initiator and normalized reason.
- **FR-531 — Durable Cancelling transition:** Cancellation must first conditionally persist `accepted` or `running` as `cancelling`, including initiator/reason/time, before best-effort Provider cancellation; `cancelling` is observable and non-terminal.
- **FR-532 — Pre-Attempt cancellation:** Cancellation that wins while the invocation is `accepted` and has no Provider Attempt must finalize as `cancelled` without creating an Attempt.
- **FR-533 — Single terminal race:** Completion/failure and cancellation must compete through PostgreSQL conditional state transition. The first durable transition from an eligible non-terminal state owns the terminal path, and no later action may rewrite it.
- **FR-534 — Completion-first behavior:** If a normal terminal transaction commits before cancellation reserves `cancelling`, cancellation must not mutate it and the cancel API returns HTTP 409 `already_terminal` with the authorized current state.
- **FR-535 — Cancellation-first behavior:** Once `cancelling` is durable, later model content must not become caller-visible or change logical terminal ownership. The Gateway must attempt upstream cancellation and finalize `cancelled`; a writable committed stream receives one `cancelled` event and no `[DONE]`.
- **FR-536 — Late Provider outcome:** Provider completion, Usage, receipt, or billing evidence arriving after cancellation wins must be appended as a late Provider outcome linked to the Attempt and Cost Ledger without changing the logical Model Invocation terminal state.
- **FR-537 — Cancellation billing uncertainty:** Missing or ambiguous Provider cancellation acknowledgement must retain Provider Attempt `billing_outcome=uncertain`, possible Usage/cost, and no automatic retry even when logical Model Invocation state is `cancelled`.
- **FR-538 — Idempotent cancel responses:** A repeated authorized cancel request returns HTTP 202 while `cancelling`, HTTP 200 when already `cancelled`, and HTTP 409 `already_terminal` for `completed`, `failed`, or `uncertain`, without issuing a second Provider cancellation side effect.
- **FR-539 — Cancelling restart recovery:** A durable `cancelling` invocation found after restart must transition to `uncertain` unless trusted Provider evidence proves a terminal Provider outcome; recovery must not assume cancellation succeeded or regenerate.
- **FR-540 — Cancellation evidence:** Invocation Evidence must retain state-race versions, initiator/reason, cancellation dispatch/acknowledgement, downstream writability, winning terminal transition, late Provider evidence, and billing uncertainty without changing the original terminal record.
- **FR-541 — Cancellation Token propagation:** `ProviderPort.complete` and `ProviderPort.stream` must receive a Gateway-owned Cancellation Token through invocation context so Application can stop local waiting and request transport closure without exposing framework or Provider SDK cancellation types inward.
- **FR-542 — Explicit Provider cancel operation:** The Application-owned Provider Port must expose `cancel(attempt_handle, reason, deadline) -> ProviderCancelResult` independently of completion and streaming operations.
- **FR-543 — Opaque Attempt handle:** The cancel Attempt handle may contain Gateway Attempt identity, trusted Provider request identity, and an Adapter-owned opaque cancellation reference, but must not expose external SDK/HTTP types to Application or Domain.
- **FR-544 — Cancel result vocabulary:** ProviderCancelResult must be exactly one of `acknowledged`, `already_finished`, `not_supported`, `unknown`, or `failed`, with safe receipt/failure evidence and no raw exception.
- **FR-545 — Local versus remote cancellation:** Every Adapter must close or abort its local transport when requested. Only an Adapter with declared trusted remote-cancellation support may return `acknowledged`; local socket, task, or iterator closure alone must map to `unknown` or `not_supported` for remote execution.
- **FR-546 — Cancellation cleanup deadline:** Provider cancellation dispatch and cleanup must use the lesser of two seconds and the remaining Invocation Deadline Budget and must not extend the invocation or shutdown deadline.
- **FR-547 — Cancellation retry boundary:** Cancellation must not enter ordinary model retry, fallback, degradation, or circuit execution. It is dispatched once unless the Provider declares an idempotent cancellation protocol and a separately accepted cancellation retry policy exists.
- **FR-548 — Post-cancel Adapter events:** After cancellation ownership is established, Adapter content and Tool Call events must not re-enter the caller-visible stream; late Usage, Provider receipt, or completion evidence may enter only the Application late-outcome path.
- **FR-549 — Cancellation capability and metrics:** Capability/configuration evidence must disclose remote-cancellation support. Cancellation outcome/latency metrics are separate from Provider availability circuit inputs, and unsupported cancellation must not imply protection from subsequent Provider billing.
- **FR-550 — Bounded downstream queue:** Each stream must bound unsent downstream data to at most 64 events and 4 MiB of serialized bytes; reaching either limit is a Downstream Backpressure failure and must not allocate a larger queue.
- **FR-551 — Backpressure propagation:** The Gateway must pause Provider-event reading through asynchronous flow control when supported. An Adapter or transport that cannot pause must still obey the same Gateway queue bounds.
- **FR-552 — Downstream progress timeout:** A downstream write or queued stream with no successful byte progress for ten seconds must terminate with stable `client_too_slow`; this timeout must use the monotonic clock and remain separately configurable only downward by invocation policy.
- **FR-553 — Pre-commit downstream loss:** If the downstream becomes unwritable before the Stream Commitment Barrier, the invocation must enter caller-cancellation handling and must not use Provider retry or fallback merely to replace output for an absent caller.
- **FR-554 — Post-commit backpressure termination:** After commitment, the Gateway must emit one `client_too_slow` SSE terminal event only when the connection remains writable; otherwise it closes directly. It must then invoke the unified cancellation path, emit no `[DONE]`, and perform no replacement generation.
- **FR-555 — Upstream/downstream timer separation:** Provider no-progress timeout remains `upstream_timeout` after 30 seconds of no business/Usage progress; caller no-consumption remains `client_too_slow` after ten seconds. Neither timer may reset or classify the other.
- **FR-556 — TTFT downstream boundary:** TTFT ends only when the first business-meaningful event is successfully written/flushed to the downstream transport, not when it enters an internal queue.
- **FR-557 — Permit lifetime under backpressure:** Invocation and Provider Admission Permits must remain held until bounded cancellation/transport cleanup and the terminal Persistence Checkpoint complete, even if queued events are discarded.
- **FR-558 — Backpressure evidence:** Invocation Evidence must retain queue-limit type, peak event/byte counts, downstream progress timestamps, discarded unsent event counts without content, commitment state, cancellation result, and terminal disposition.
- **FR-559 — Backpressure metrics:** Metrics must expose queue events/bytes, downstream write latency, blocked duration, backpressure terminations, and Provider cancellation outcome without content labels or high-cardinality call identifiers.
- **FR-560 — Provider override extension:** Provider Selection Override must use the namespaced body extension `gateway.routing = {provider, mode}` so ordinary OpenAI-compatible clients may ignore it; `mode` is exactly `prefer` or `require`.
- **FR-561 — Configured Provider identity only:** Override `provider` must be a stable Provider ID in the locked Active Snapshot. Data Plane callers must never provide Provider URL, credential, Secret Reference, or arbitrary concrete Provider model ID.
- **FR-562 — Prefer mode:** `prefer` must rank compatible candidates from the selected Provider first, then permit the locked retry, cross-Provider fallback, and Degradation Policy; any deviation from the preferred Provider remains caller-visible and evidence-bearing.
- **FR-563 — Require mode:** `require` must filter all Provider Attempts to the selected Provider. Same-Provider retry or configured compatible-model fallback may proceed, but cross-Provider attempts are forbidden and ineligible/unhealthy/open-circuit outcomes fail explicitly.
- **FR-564 — Override authorization:** Provider override requires `gateway.model.provider_override` in addition to `gateway.model.invoke`. Authorization must occur before Provider existence disclosure, and v0.1 defines no weaker or stronger override wildcard.
- **FR-565 — Override error privacy:** An unauthorized override returns HTTP 403 without revealing whether the Provider exists. An authorized syntactically valid override referencing no Provider in the locked snapshot returns HTTP 400 `invalid_request`.
- **FR-566 — Override control invariance:** Neither mode may bypass capability/coarse Tool-transport/output-Schema matching, safety policy, health/circuit, SecretSource/egress/SSRF rules, admission/rate limits, deadlines, pricing evidence, or Invocation Evidence.
- **FR-567 — Provider override cache policy:** A `require` invocation may use a Cached Degraded Result only when its source Provider matches and policy explicitly permits it. A `prefer` invocation may use a different-Provider cache only as a disclosed Degraded Outcome.
- **FR-568 — Override fingerprinting:** Request Fingerprint and Execution Fingerprint must include Provider ID and Provider Override Mode; the Execution Fingerprint must additionally capture the locked Provider binding resolution and effective constraints.
- **FR-569 — Provider override evidence:** Invocation Evidence must retain requested Provider/mode, authorization scope and outcome, candidate reordering/filtering and rejection reasons, recovery/degradation path, and every actual selected Provider/Resolved Model.
- **FR-570 — Routing hard-filter order:** Router must first reject candidates for capability/Tool/Schema mismatch, Provider Override, authorization/safety/egress policy, health/circuit state, or Provider-binding admission/rate state before priority or weight selection. First-phase Business Budgets and projected-cost rejection are absent.
- **FR-571 — Specific candidate rejection:** Every filtered candidate must retain one or more stable stage-specific rejection reasons; a generic lower-score reason must not replace the actual capability, health, policy, capacity, or cost decision.
- **FR-572 — Priority tiers:** Eligible candidates must be grouped by integer `priority`, with lower values preferred. Selection and fallback exhaust the current lowest-numbered eligible tier before entering a later tier.
- **FR-573 — Weighted Candidate Order:** Within each priority tier, positive configured `weight` values must produce a seeded weighted-without-replacement permutation. The first item is the initial candidate and remaining items are that tier's fallback order; `weight=0` disables a candidate and negative/non-finite weights are invalid configuration.
- **FR-574 — Retry before candidate advance:** A retryable failure may use the already accepted single same-candidate retry before advancing through the remaining Weighted Candidate Order; all actions consume the shared Provider Attempt and deadline budgets.
- **FR-575 — Projected Cost Estimate:** Before selection, Gateway should calculate a Projected Cost Estimate from known/estimated input Tokens, effective maximum output Tokens, relevant cached/reasoning categories when applicable, and the locked prospective pricing table and rounding rules for explainability and operator policy authoring.
- **FR-576 — Unknown cost evidence:** Missing price or Token information must be recorded as cost estimate `unavailable` and must never be treated as zero. It does not by itself reject a candidate in the first phase.
- **FR-577 — Deferred cost enforcement:** First-phase routing may reflect operator-authored priority and weight informed by pricing, but Gateway must not enforce per-call cost ceilings, Token/cost spend quotas, tenant allowances, or automatic budget exhaustion. Dedicated dynamic cost-aware ranking and Business Budget enforcement are deferred.
- **FR-578 — Deterministic routing seed:** The routing seed must be deterministically derived from `call_id`, the Routing Policy's Configuration Revision and Resource ID, and a versioned keyed derivation/PRNG algorithm, persisted as replay evidence without exposing secret key material.
- **FR-579 — Runtime reevaluation without reorder:** Before each later Attempt, the Gateway must reevaluate dynamic health, circuit, Provider-binding concurrency, QPS, and deadline state and skip newly ineligible candidates with runtime rejection evidence, while preserving the original seed and relative Weighted Candidate Order.
- **FR-580 — Candidate-capacity exhaustion:** Provider-binding capacity may cause candidate fallback without moving the invocation's instance/tenant Admission Permit. If all locked candidates are capacity/rate-ineligible, the invocation returns `rate_limited` subject to pre/post-commit rules rather than creating a queue or exceeding limits.
- **FR-581 — Adapter Capability Contract:** Every Adapter type/version must publish a versioned Adapter Capability Contract declaring the protocol behaviors it implements and can translate, including only the accepted top-level capability families and their protocol properties.
- **FR-582 — Provider Model Binding capability:** Each Provider Model Binding must declare the capabilities and limits actually enabled for its concrete configured model, including Context/output ceilings, Structured Output modes, coarse Tool transport, Usage, and cancellation properties.
- **FR-583 — Capability narrowing only:** Provider/model configuration may disable or tighten Adapter capability values but must not enable a top-level capability, mode, or guarantee absent from the Adapter Capability Contract.
- **FR-584 — Effective Capability Set:** Router capability eligibility must use the immutable intersection of Adapter Capability Contract, Provider Model Binding declaration, and locked published policy constraints.
- **FR-585 — Capability publication validation:** Candidate publication must fail if a binding expands Adapter capability, violates a property Schema, lacks required limits, references an incompatible Adapter version, or has an unresolved required capability dependency.
- **FR-586 — Capability conformance gate:** A published policy may require version-pinned Capability Conformance Evals before activating selected capabilities; required Eval failure or absence blocks publication rather than weakening the gate.
- **FR-587 — Conformance execution boundary:** Capability Conformance Evals must use MockTransport by default. Any live non-production probe requires explicit operational enablement and isolated credentials, budget, evidence, and no representation as production health.
- **FR-588 — No runtime capability mutation:** Individual runtime output/translation failures may update health and model-quality evidence but must not automatically rewrite canonical capability declarations or the invocation's locked Effective Capability Set.
- **FR-589 — Emergency Capability Revocation:** An authorized audited Capability Revocation may immediately make a capability/property ineligible for new Attempts, including invocations with an older snapshot when safety or protocol correctness requires it, without rewriting historical snapshots.
- **FR-590 — Capability revision evidence:** Every effective capability item must retain Adapter type/version and contract hash, Provider Model Binding Resource ID plus Configuration Revision, capability Schema version, declaration source, Eval/validation state, policy/revocation references, final effective value, and canonical hash.
- **FR-591 — Capability-family scope:** First-phase top-level Model Capabilities remain only streaming, Structured Output, and coarse Tool Calling transport. Usage, remote cancellation, Tool choice/parallelism, and business-semantic correctness remain Adapter/protocol properties or Loop concerns and must not silently expand Gateway semantics.
- **FR-592 — YAML v1 envelope:** A Configuration Bundle must be one YAML document whose transport envelope contains, in canonical export order, `schema_version: gateway.config/v1`, canonical quoted-decimal-string `base_revision`, optional non-domain `metadata`, then `providers`, `provider_model_bindings`, `model_aliases`, `routing_policies`, `pricing_tables`, `safety_policies`, and the Gateway-wide singleton `resource_policies`, followed by the optional Gateway-wide singleton `replay_policies`; Prompt and `service_requirements` sections are forbidden. The six plural domain sections are mappings keyed by stable resource ID, their values must not repeat the ID, input member order has no semantics, and canonical order is the decoded ID's UTF-8 byte order. Every YAML Revision reference is a quoted canonical decimal string, the empty-state Sentinel is exactly `"0"`, and YAML integer `0` or any other numeric Revision scalar is invalid.
- **FR-593 — Provider definition boundary:** Each stable Provider ID keys one closed Provider value containing required `status=enabled|disabled`, Adapter type/version, policy-approved base URL, Secret Reference, egress, transport, health, and rate configuration, and it may contain one directly embedded Provider-scoped Trust Bundle object with content-derived `identity`, optional `label`, and PEM content subject to the active 1 MiB/100-certificate default ceilings. The value must not repeat its map-key ID and must contain no caller-controlled semantic version alias, plaintext credential, caller-supplied endpoint, private key, or reference to a separate first-phase Trust Bundle registry.
- **FR-594 — Separate Provider Model Binding:** Each stable Binding ID keys one closed `provider_model_bindings` value containing Provider reference, concrete upstream model identity, required `status=enabled|disabled`, capability/limit declaration, pricing-table reference, and optional tokenizer reference. The value must not repeat its map-key ID, and Bindings must not be duplicated as anonymous nested models inside aliases.
- **FR-595 — Model Alias references:** Each Model Alias ID keys one closed alias value containing binding candidates with explicit Binding reference, Candidate Service Level, priority, and weight, plus explicit routing-policy and safety-policy references, generation defaults, and Structured Output extraction mode `inherit` or `disabled`. Its selected Routing Policy owns the Degradation Policy projection under FR-969, so no separate Alias degradation reference or independent degradation registry exists. The value must not repeat its map-key ID, infer a unique/first/latest resource, or copy Provider or Binding definitions. First-phase aliases contain no Business Budget or projected-cost ceiling and cannot set extraction to `enabled`.
- **FR-596 — No Prompt configuration:** Configuration Bundle import/export must reject Prompt templates, variables, Prompt versions, Prompt Evals, and Prompt publication pointers because they are Loop-owned.
- **FR-597 — YAML safe subset:** Parsing must accept only the YAML 1.2 Core type subset and reject environment/string interpolation, custom tags, anchors, aliases, merge keys, duplicate mapping keys, multi-document streams, and arbitrary object construction.
- **FR-598 — YAML parser resource limits:** Configuration parsing must enforce deployment-owned byte, node-count, nesting-depth, collection-size, and string-length ceilings before creating a Candidate Configuration Revision.
- **FR-599 — Strict structural validation:** Unknown fields, missing required fields, invalid types/formats, duplicate stable IDs, non-finite/negative weights, and Schema-version incompatibility must be collected as structured validation failures and map to `invalid_request`/HTTP 400 outside a successful `/validate` result.
- **FR-600 — Referential and semantic validation:** Import must reject dangling/circular forbidden references, Adapter/binding incompatibility, capability expansion, invalid routing/degradation graphs, unusable pricing, Secret Reference policy violations, invalid/empty/oversized/out-of-validity Trust Bundles, Trust Bundle digest mismatch or private-key material, and any Prompt or Tool domain configuration. On a mutation these failures map to `configuration_invalid`/HTTP 422; `/validate` reports them through its HTTP 200 `valid=false` result.
- **FR-601 — Validate and dry-run:** Control Plane must provide Configuration Submission parse/validate/dry-run behavior over the closed input union in FR-938, returning all safely collectable structured errors and calculated digest/impact summary without writing a Candidate, Configuration Command Index entry, or Active-state change.
- **FR-602 — Import remains candidate-only:** A successful formal YAML v1 import with matching `base_revision` creates one immutable Candidate Configuration Revision and never publishes it automatically.
- **FR-603 — Deterministic export:** Export of the same Revision must use FR-592's fixed section order, UTF-8-byte-sorted stable-ID registry keys, stable field ordering, and canonical scalar representation, strict UTF-8 without BOM, LF-only line endings, and exactly one final LF so its semantic digest is reproducible independent of input or database row order. The response exposes the existing Snapshot Digest through `X-Gateway-Snapshot-Digest` as informational metadata, never as an ETag or conditional-request validator.
- **FR-604 — Bootstrap separation:** Bootstrap environment values remain limited to previously accepted infrastructure connectivity and must not interpolate, override, or synthesize Configuration Bundle domain fields.
- **FR-605 — Control Plane validation route:** `POST /gateway/v1/config/validate` must accept exactly one closed Configuration Submission branch under FR-938 and return safely collectable validation failures, impact summary, prospective digest, and prospective deterministic canonical Change Set without writing configuration state. This dry run is optional and does not create a validation token or waive validation by a later mutation.
- **FR-606 — Candidate creation route:** `POST /gateway/v1/config/revisions` must accept exactly one closed Configuration Submission branch under FR-938, require its `base_revision` to match the transaction-time Active Revision or the empty-Active Sentinel under FR-940, independently perform full validation, and create one immutable Candidate Configuration Revision with both the complete canonical snapshot and canonical Change Set. A preceding call to `/validate` is not required.
- **FR-761 — Empty-Active Candidate creation:** Whenever the transaction-time Active state is empty, the Control Plane candidate-creation route must accept the reserved JSON string `base_revision: "0"` as the Initial Configuration Base, even when other unpublished initial Revisions already exist. Every fully validated request creates another immutable Candidate with persisted `base_revision=null`; it still requires explicit publication, while a prior no-write validation call remains optional. `"0"` becomes invalid only after an Active Revision exists. The Gateway must not require editing an earlier Candidate, manual database mutation, or a container-private bootstrap script for this path.
- **FR-607 — Typed whole-resource operations:** Configuration Change Set operations must be the exact closed wire union in FR-957: whole-resource `add`, `replace`, and `remove` operations for each of the six registries, plus whole-singleton `replace` operations for `resource_policies` and `replay_policies`. Provider transport/Trust Bundle content and Model Alias candidate lists are atomic parts of their parent value. Field/subresource patches, singleton add/remove, Prompt/Tool or unknown operations, JSON Patch, raw field paths, and persistence-row operations fail validation.
- **FR-608 — No arbitrary patch or Active CRUD:** Control Plane must not expose arbitrary JSON Patch, raw database-row CRUD, field paths tied to persistence tables, or any direct mutation of the Active Snapshot.
- **FR-609 — Configuration read surfaces:** Authorized Control Plane reads must expose only the Configuration Read Projections and explicit deterministic YAML export defined in FR-939. Active and list surfaces return base metadata, detail adds the bounded base-relative deterministic redacted semantic diff but no full snapshot, and only export returns full secret-safe Configuration Bundle content.
- **FR-610 — Explicit publish preconditions:** `POST /gateway/v1/config/revisions/{revision}/publish` must require expected Active revision, exact Candidate digest, and publication description; the target must still be a Candidate whose base is the transaction-time current Active Revision. Mismatch, stale base, non-candidate state, or failed gates returns deterministic HTTP 409 without changing Active state.
- **FR-762 — Empty Active publication precondition:** When no Active Snapshot exists, the publication route must accept the reserved JSON string `expected_active_revision: "0"` Active Revision Precondition and atomically activate exactly one null-base Candidate only if the Active state is still empty. The winner becomes Active and every other null-base Candidate becomes Stale in the same transaction. A competing or repeated initial publication returns HTTP 409 without changing active state; after one Candidate wins, `"0"` is invalid and the expected value must be the actual Active revision represented under FR-930.
- **FR-763 — Health probe endpoints:** v0.1 must expose `GET /healthz` for process liveness and `GET /readyz` for Data Plane admission readiness. `/healthz` returns healthy only when the Gateway process can serve the probe and does not depend on PostgreSQL or Provider reachability. `/readyz` returns ready only when PostgreSQL, a valid Active Snapshot, and required local execution dependencies pass; an online Authorization Authority is included when that deployment mode requires it. Transient Provider reachability, health, circuit, and capacity state must not make `/readyz` fail. Idempotency Index Key Ring structure and protected-version retirement remain readiness gates, but Idempotency Index key-material unavailability or Idempotency Key Lockout under FR-866/FR-872 is explicitly excluded. Non-ready responses use HTTP 503 and disclose no configuration or destination details.
- **FR-764 — Health probe access boundary:** Health probes are not part of the OpenAI-compatible Data Plane or privileged Control Plane API and are not subject to caller JWT/permission checks. In production they must be reachable only through an internal/编排 listener or network and must not be routed through public Data Plane ingress; `dev` retains its loopback-by-default network boundary.
- **FR-765 — Development credential injection:** v0.1 real Docker Smoke must resolve Provider credentials through a Development SecretSource using Docker Secret/mounted-file input by default. An environment-variable SecretSource is permitted only when explicitly enabled in `dev`; it must use a named reference, never auto-load `.env`, and must not persist or expose the value through PostgreSQL, configuration API responses, caller requests, Logs, Metrics, Trace, or ordinary Evidence. `production` must use an approved mounted Secret, Docker Secret, or dedicated Secret Manager path and must reject plaintext environment-variable credentials.
- **FR-766 — Docker migration gate:** The documented v0.1 Docker Compose path must include an independent one-shot Migration Job that executes ordered, versioned, auditable PostgreSQL Schema migrations before Gateway admission. Gateway must not auto-apply migrations or destructive Schema changes. A migration failure, incompatible version, or partial migration must block Gateway Data Plane admission; the clean E2E path must not require manual SQL or a container-private setup script.
- **FR-767 — Repeatable migration execution:** `gateway-migrate` must be safe to run on every Compose start: it must perform a bounded wait for PostgreSQL readiness, no-op successfully when the recorded Schema is current, and apply only pending ordered migrations. A failed or partially applied migration must exit non-zero and block Gateway admission; automatic rollback of destructive or irreversible changes is forbidden.
- **FR-769 — Docker listener defaults:** Inside the Gateway container, the process must listen on `0.0.0.0:8000` for Data Plane traffic and `0.0.0.0:8001` for Control Plane and health traffic. The default v0.1 Docker Compose profile must publish only host `127.0.0.1:8000` to container port `8000` and host `127.0.0.1:8001` to container port `8001`; the container-internal bind must not widen host exposure. Bootstrap/deployment configuration may explicitly override host publication or port numbers without changing route paths or protocol semantics.
- **FR-770 — Management listener isolation:** In production, the Control Plane and health listener must be reachable only through the designated internal/编排 network or listener; public Data Plane ingress must route neither Control Plane resources nor `/healthz`/`/readyz`. The four caller-authorized invocation Status/Cancel routes remain on the Data Plane listener despite their `/gateway/v1` route family. Dev retains loopback-by-default exposure.
- **FR-771 — Optional Redis Compose profile:** The default `docker compose up -d` path must start only the Gateway, PostgreSQL, and `gateway-migrate` services needed for the live path. Redis must be assigned to an explicit `cache` Compose profile and must not start by default. The cache profile alone does not enable Cached Degraded Results; cache use additionally requires an explicitly enabled cache policy in the published Active Snapshot.
- **FR-772 — Cache dependency boundary:** When the `cache` profile is absent, or when cache policy is disabled, normal live routing, retry, fallback, readiness, and end-to-end invocation must remain unaffected. When the profile and policy are both enabled, Redis is required only for the cache stage and its authenticated/encrypted SecretSource configuration; Redis absence or outage must leave `/readyz` at 200 and the exhausted live path and its classification unchanged rather than creating a hidden dependency or Provider Attempt.
- **FR-773 — Cache connection authority:** Redis endpoint, TLS/transport settings, and the cache Secret Reference must come from deployment-owned Bootstrap Configuration as a Cache Backend Connection Profile. Cache behavior (`enabled`, freshness windows, degradation causes, retention, and key policy) must come from the PostgreSQL-backed published Active Snapshot. Callers and domain YAML bundles must not supply or override Redis connection details; Bootstrap Configuration must not synthesize or silently enable cache behavior.
- **FR-774 — Non-blocking cache backend configuration:** A published Active Snapshot may enable cache policy even when the Cache Backend Connection Profile is absent, the `cache` Compose profile is disabled, or Redis is unusable. In that state Gateway must classify the cache stage as `cache_backend_unavailable`, record safe Invocation Evidence/Metrics, perform no cache read or write, keep `/readyz` at 200, and preserve the exhausted live path's existing result/error and Provider recovery state; it must not reject publication or create a Provider Attempt on the cache's behalf.
- **FR-775 — Cache backend status privacy:** `cache_backend_unavailable` is an internal cache-stage disposition only. It must not appear in OpenAI-compatible response bodies, SSE events, cache-degradation headers, or caller-visible error codes; authorized Invocation Evidence, aggregate Metrics, and redacted operational Logs may retain the disposition without Redis endpoint, credential, or raw error details.
- **FR-776 — Cache backend recovery:** After a `cache_backend_unavailable` condition clears, a later eligible invocation must be able to use the cache automatically without Gateway restart or configuration publication. The failed cache operation itself must not be retried in place; recovery must not change `/readyz`, Provider routing/health, or the prior invocation's result and evidence.
- **FR-777 — Bootstrap reload boundary:** Changes to the Cache Backend Connection Profile (Redis endpoint, TLS/transport settings, or Secret Reference) take effect only at Gateway restart or an explicit Bootstrap reload. Gateway must not watch or hot-reload mutable connection files, and a reload must not alter already admitted invocation snapshots or in-flight Provider work.
- **FR-778 — Invocation cache-profile lock:** At Model Invocation admission, Gateway must lock the applicable Cache Backend Connection Profile for that invocation. A later Bootstrap reload affects only later admissions; an already admitted invocation continues with its locked profile for any cache stage, or records internal `cache_backend_unavailable` if that profile is no longer usable, without changing its live result, Provider work, or readiness.
- **FR-779 — Cache encryption-key rotation:** Rotation or revocation of the SecretSource key used for application-layer cache-value encryption must immediately make existing entries logically ineligible, including for already admitted invocations whose Invocation Cache Policy Snapshot references the old key. v0.1 must not dual-read with old keys or perform online re-encryption; new eligible writes use the current key, while Provider work, live routing, `/readyz`, and completed results remain unaffected.
- **FR-780 — Cache profile namespace boundary:** A changed Cache Backend Connection Profile creates a new logical cache namespace for later admissions. v0.1 must not migrate or read entries across profiles; old Redis data may remain disposable and expire under its prior policy. The namespace change must not alter live routing, readiness, or already admitted invocation outcomes.
- **FR-781 — Cache restart semantics:** Gateway and Redis restarts must not promise cache continuity. Redis data may survive operationally, but Gateway must function with an empty cache after restart/restore; cache loss or recovery must not block `/readyz`, change live routing, or create a replay/restoration workflow.
- **FR-782 — Disposable Redis storage:** The default Docker `cache` profile must use temporary Redis storage and must not require a named volume or authoritative backup. Operators may attach a volume for operational convenience, but retained Redis data remains best-effort and outside Gateway continuity, replay, and readiness guarantees.
- **FR-783 — Cache policy disablement and reactivation:** Disabling or re-enabling a published cache policy affects only Model Invocations admitted under the subsequently published Active Snapshot; it must not synchronously purge Redis. Re-enabling policy content with the same canonical material content identity may reuse entries that still satisfy the semantic key, tenant/authorization and policy isolation, freshness/retention, revocation, and current encryption-key checks; forced invalidation requires an explicit Cache Revocation or a material policy-content identity change. Neither transition may alter the locked cache-policy rules, live routing, Provider recovery, or cache outcome of an already admitted invocation.
- **FR-784 — Cache policy clock pause:** While a cache policy is disabled, its logical freshness/stale-age clock must not advance or count the disabled interval against `fresh_ttl`, `stale_ttl`, or policy retention for later admissions. Re-enabling policy content with the same canonical material content identity resumes eligibility from the pre-disable logical time, subject to the entry still existing and passing all other checks; physical Redis TTL/eviction remains best-effort and may turn the result into an ordinary miss. A Model Invocation retains the clock state and cache-policy rules locked at admission; disablement or reactivation must not create a Provider Attempt or a live-path/readiness change.
- **FR-785 — Invocation cache-policy snapshot:** At Model Invocation admission, Gateway must lock the effective cache-policy Resource ID, Configuration Revision, content identity, administrative status, logical freshness-clock state, and Cache Backend Connection Profile as an Invocation Cache Policy Snapshot. Every cache read or write for that invocation follows this immutable snapshot even if a later policy publication disables or re-enables caching; later publications affect only later admissions, subject to the security-invalidation precedence in FR-786. This is a Gateway-owned request-scoped value, not a caller-provided or cross-request Agent Session.
- **FR-786 — Cache security-invalidation precedence:** An explicit Cache Revocation or rotation/revocation of the SecretSource cache-encryption key overrides every Invocation Cache Policy Snapshot for cache eligibility, including already admitted invocations. After the security marker takes effect, matching entries or entries requiring the revoked key must not be read or written; the marker may complete physical deletion asynchronously. It must not cancel Provider work or alter an already emitted live result, Usage, Cost Ledger, or terminal outcome.
- **FR-787 — Cache security-invalidation race fence:** Cache security invalidation has one linearization point. A cache hit whose read began before that point but has not yet been emitted or otherwise committed to the caller must be discarded; cache writes after the point must be suppressed, and data written before it is logically ineligible. A cache result already emitted to the caller is not retroactively withdrawn. The fence affects cache use only and must not cancel Provider work or alter live output, Usage, Cost Ledger, or terminal outcome.
- **FR-788 — Security-invalidated degradation outcome:** If a security fence discards a Cached Degraded Result after the live Provider recovery path has already been exhausted, Gateway must return that path's previously classified terminal result (for example, `provider_unavailable`) without a new Provider Attempt, retry, fallback, or caller-visible revocation detail. A successful live result remains successful when only its optional cache population is suppressed.
- **FR-789 — Idempotency snapshot reuse:** After the normal authorization and fingerprint checks, a duplicate or replay with the same Idempotency Key and identical Request Fingerprint must resolve to the original Model Invocation and reuse its admission-locked snapshots, including the Invocation Cache Policy Snapshot and Invocation Replay Policy Snapshot. It must not perform fresh routing, create a Provider Attempt, or re-evaluate the current cache or replay policy. Cache Revocation, Replay Artifact Revocation, encryption-key revocation, and their security-invalidation fences remain authoritative and may block reuse of a cache or replay artifact; existing same-key conflict and lifecycle/replay rules remain unchanged.
- **FR-790 — Terminal idempotency immutability:** Once the original Model Invocation has a terminal outcome, including `no_route` or `provider_unavailable`, later configuration publication or Provider health recovery must not cause a same-key/same-fingerprint duplicate to execute again. The caller must use a new Idempotency Key for a new logical invocation; existing authorization, replay-artifact expiry, and security-invalidation rules still apply.
- **FR-791 — Expired-key tombstone:** Replay Artifact expiry while the Idempotency Binding Window remains active continues to use `replay_unavailable`, and status remains queryable through the full Binding Window. When that window ends, the same namespaced key must not silently become a new invocation: during the configured Key-Reuse Quarantine, its non-content Idempotency Tombstone returns `409 conflict`, reveals no raw prior content, and creates no Model Invocation or Provider Attempt. Only expiry of that explicitly published quarantine releases the key for a later new invocation.
- **FR-792 — Optional Idempotency Key:** The `Idempotency-Key` header is optional for OpenAI-compatible requests. When absent, each accepted request is a new logical Model Invocation and receives no same-key deduplication, replay, or status lookup; all ordinary authorization, routing, persistence, and evidence rules still apply.
- **FR-793 — Replay Protocol Binding:** `stream` and `stream_options.include_usage` remain Request Fingerprint inputs. A same-key request that changes either value must return `409 conflict`; a valid Exact Replay must use the original synchronous or SSE mode and original usage-event intent, without protocol conversion, Artifact transformation, or a new Provider Attempt.
- **FR-794 — Replay access observability:** A same-key duplicate or exact replay is a new HTTP access with a fresh `request_id`, `trace_id`, and Gateway entry span. Restricted Invocation Evidence/Trace must link that Replay Access to the original `call_id`; it must not create a new Model Invocation, Provider Attempt, Provider request ID, Usage Measurement, or Cost Ledger Accrual. The caller-visible replay response keeps the original result semantics and may expose only `X-Gateway-Replayed: true` as the replay marker.
- **FR-795 — Replay access rate boundary:** Replay Access must pass the normal authentication/authorization checks and consume the ordinary instance/tenant API QPS budget. It must not acquire or consume Model Invocation or Provider concurrency Permits, and it must be bounded by a separate lightweight replay-read concurrency ceiling; refusal at that ceiling uses the existing `rate_limited` classification and creates no Provider work.
- **FR-796 — Replay authorization revalidation:** Every Replay Access must revalidate the current Authorization Context and the original invocation's tenant/scope binding before key resolution or content/status disclosure. Expired, revoked, or insufficient current authorization returns the normal `401`/`403` classification without revealing the prior `call_id`, lifecycle, Replay Artifact, or content and without Provider work.
- **FR-797 — Replay policy revocation:** Publishing a policy that disables or restricts `encrypted_exact_replay` must immediately create a Replay Artifact Revocation for existing artifacts, including artifacts referenced by already admitted invocations. Revoked artifacts are logically ineligible and return `409 replay_unavailable`; physical deletion may be asynchronous, and revocation must not cancel Provider work or alter the original live result, Usage, Cost Ledger, or terminal outcome.
- **FR-798 — Replay security-invalidation race fence:** Replay Artifact Revocation must have one linearization point. A Replay Access read that began before the marker but has not yet been emitted or committed must be discarded and return `409 replay_unavailable`; a replay already emitted is not withdrawn. The fence affects replay content only and never starts Provider work, cancels the original invocation, or changes its Usage, Cost Ledger, or terminal outcome.
- **FR-799 — Replay encryption-key rotation:** Rotation or revocation of the SecretSource key used to encrypt Replay Artifacts must immediately make artifacts under the old key logically ineligible, including for already admitted invocations. v0.1 must not perform dual-key reads or online re-encryption; new artifacts use only the current key, and the invalidation must not alter the original live result, Provider work, Usage, Cost Ledger, or terminal outcome.
- **FR-800 — Replay Artifact eligibility:** `encrypted_exact_replay` may persist only a complete successful synchronous result or normally completed SSE event sequence when the applicable content-retention policy allows it. Successful Provider fallback, successful Local Structured Repair, and a complete eligible Cached Degraded Result may be included. Partial or interrupted streams, `failed`, `cancelled`, `uncertain`, Structured Validation Failure, and Safety Refusal outcomes must not persist raw replay content; they reuse only their existing terminal/status outcome.
- **FR-801 — Replay Artifact persistence failure:** Failure to persist an otherwise eligible Replay Artifact must not change an already completed live result, response, Usage, Cost Ledger, terminal outcome, or Provider recovery. Gateway must retain a safe artifact-write failure signal, keep the durable Idempotency binding that prevents regeneration, and return `409 replay_unavailable` on a later same-key content replay rather than creating a Provider Attempt.
- **FR-802 — PostgreSQL Replay Artifact Store:** When the optional `encrypted_exact_replay` policy is enabled, encrypted Replay Artifact content and its non-content lifecycle metadata must be durably persisted in a PostgreSQL-owned Replay Artifact Store, isolated in its own table or logical schema from ordinary Invocation Evidence, Logs, Trace, and Cost Ledger data. PostgreSQL remains the sole durable authority; Redis cache data and any optional external object store are neither an authority nor a fallback source for exact replay.
- **FR-803 — Replay storage availability boundary:** If a Replay Access cannot complete its PostgreSQL Replay Artifact Store read because persistence is unavailable, Gateway must return the existing `persistence_unavailable` classification (HTTP 503 where applicable), without revealing storage diagnostics, re-executing the Model Invocation, creating a Provider Attempt, routing/fallback, or changing the original lifecycle. A confirmed absent, expired, revoked, or over-ceiling artifact remains the distinct `replay_unavailable` path.
- **FR-804 — Replay Artifact Retention Ceiling:** The published policy-specific per-artifact ceiling and deployment-owned retained-content ceiling must be checked before writing an eligible Replay Artifact. When either would be exceeded, Gateway skips that artifact without truncating, semantically compressing, replacing, or deleting other artifacts as an implicit side effect; the completed live response, Usage, Cost Ledger, terminal outcome, and Provider recovery remain unchanged, safe evidence records the reason, and later same-key content access returns `409 replay_unavailable`. The retained-content ceiling is not a Configuration Snapshot field.
- **FR-805 — Replay Artifact Commit Boundary:** The terminal transaction must durably commit the successful Model Result, final Usage, Cost Ledger, terminal Evidence, and Idempotency binding before an optional Replay Artifact write. Artifact persistence uses a separate bounded operation; its failure, timeout, or Gateway restart cannot roll back the live response, alter metering or terminal state, or authorize a new Provider execution. A missing post-commit artifact follows `replay_unavailable` on later same-key content access.
- **FR-806 — Replay Artifact Retention Cleanup:** Expiry and revocation make an artifact logically ineligible at read time from their persisted markers. Physical deletion is an asynchronous PostgreSQL cleanup concern and may retain a non-content deletion tombstone for the configured key-reuse quarantine; cleanup delay, restart, or failure must not affect `/readyz`, live invocation behavior, authorization, or replay eligibility.
- **FR-807 — Atomic Replay Artifact visibility:** A Replay Artifact must become visible only as one complete committed record bound to its integrity and encryption metadata. Partial writes, integrity failures, or inability to decrypt a referenced record must be classified as `persistence_unavailable` without content disclosure, Provider work, re-execution, routing, or fallback; a confirmed absent or policy-ineligible artifact (including expired, revoked, or retention-ceiling-skipped) may use `replay_unavailable`.
- **FR-808 — Fixed Replay Artifact expiry:** An eligible Replay Artifact's absolute expiry must be calculated from the original successful terminal-commit time plus the applicable retention TTL. Replay Access, delayed Artifact persistence, cleanup retries, and Gateway restarts must not extend or reset that expiry; reads after the marker use `replay_unavailable`.
- **FR-809 — Retroactive policy tightening:** Publishing a material restriction to `encrypted_exact_replay`—including a shorter TTL, lower per-Artifact size ceiling, narrower eligible-result set, or narrower access scope—must immediately revoke or logically invalidate existing Artifacts that no longer satisfy the effective policy. Non-semantic metadata changes must not revoke them. A deployment retained-content ceiling change governs capacity prospectively and is not a policy-content rewrite or retroactive Artifact revocation. The change affects replay eligibility only and never alters completed results, live invocations, Usage, Cost Ledger, or Provider work.
- **FR-810 — Replay-store capacity pressure:** PostgreSQL disk, quota, or retained-content capacity pressure during an Artifact write is handled as a bounded Artifact persistence failure: Gateway records safe evidence, preserves existing valid Artifacts, does not implicitly evict or revoke them, and leaves readiness, live routing, Provider work, metering, and terminal results unchanged. A later same-key content replay for the skipped Artifact returns `replay_unavailable`; future calls may write after capacity recovers.
- **FR-811 — Replay policy expansion boundary:** Publishing a less restrictive exact-replay policy must not resurrect an expired, revoked, deleted, or previously skipped Artifact, and must not extend the fixed expiry of an existing Artifact. It applies only to later writes and existing Artifacts that remain unexpired, non-revoked, and compliant under the new policy.
- **FR-812 — Policy-change replay fence:** A material exact-replay policy tightening must use the same Replay Security Invalidation Fence as encryption-key revocation. A read that has begun but has not emitted is discarded, a pending write after the fence is suppressed, and an already emitted replay is not withdrawn; the fence never changes live invocation work or metering.
- **FR-813 — Complete exact-replay policy:** An `encrypted_exact_replay` policy is publishable only when TTL, encryption Secret Reference, per-Artifact ceiling, eligible result types, and access scope are explicitly present and valid under the Gateway-wide ceilings. Gateway must not synthesize defaults or silently widen a missing field; retained-content capacity remains a deployment-owned hard ceiling rather than a Replay Policy member.
- **FR-814 — SecretSource-independent publication:** Candidate validation and publication of an Exact Replay policy must validate the Secret Reference and policy constraints locally without connecting to, reading, or decrypting SecretSource material. SecretSource availability is evaluated only at Artifact write/read time; its outage must not block policy publication or readiness.
- **FR-815 — Deduplication snapshot stability:** Every admitted Model Invocation, including one under `execution_dedup_only`, must retain an Invocation Replay Policy Snapshot containing its effective mode and applicable policy identity. Same-key reuse follows that snapshot and cannot gain newly enabled exact replay or retroactively write an Artifact after the original admission.
- **FR-816 — Atomic replay-policy publication:** The Active Snapshot's canonical Exact Replay policy, its version/digest, and the Replay Artifact Revocation epoch must commit atomically in one PostgreSQL publication transaction. A failed transaction changes none of them; after commit, the in-process snapshot and shared Replay Security Invalidation Fence advance as one published version, with no mixed-policy observation.
- **FR-817 — Independent replay policy section:** The optional `replay_policies` section is a first-class Gateway configuration section exposed through the same YAML import/export, Control Plane validation, Candidate revision, publication, digest, and audit workflow as other domain policies. It must not be nested under a Provider, Model Alias, or caller request.
- **FR-818 — Deployment replay scope:** v0.1 supports at most one effective deployment-level Exact Replay policy for the Gateway. Provider-, Model Alias-, Service Requirement-, and tenant-specific overrides are not accepted, and callers cannot select, weaken, or widen the policy through Data Plane fields.
- **FR-819 — Replay policy omission default:** If `replay_policies` is absent, the published Active Snapshot explicitly resolves to `execution_dedup_only`, retains no raw response content, and exposes no exact-replay Artifact. `encrypted_exact_replay` requires an explicit, complete, validated section and cannot be inferred from cache, retention, or other policy sections.
- **FR-820 — Replay policy mode schema:** `replay_policies.mode` must be exactly `execution_dedup_only` or `encrypted_exact_replay`. When the mode is `execution_dedup_only`, exact-replay-only fields (TTL, encryption Secret Reference, per-Artifact ceiling, eligible result types, and access scope) must be absent; supplying them is a validation failure rather than silently ignored configuration.
- **FR-821 — Replay policy numeric profile:** Exact Replay TTL is an integer number of seconds and `max_artifact_bytes` is an integer byte count. Each must be positive and within its Gateway-wide hard ceiling; `infinite`, negative, fractional, and zero-as-disable values are invalid, and disabling uses `execution_dedup_only`. The separate deployment retained-content ceiling is also a positive integer byte count but is not part of `replay_policies`.
- **FR-822 — Replay policy mutation boundary:** Replay Policy changes, including mode and constraint changes or rollback, are accepted only by creating a fully validated Candidate and then using the ordinary publish workflow; an optional prior dry run does not replace Candidate or publish validation. Runtime environment variables, ad-hoc toggles, and Data Plane fields cannot alter it; each accepted or rejected operation records actor, revision, old/new safe summaries, effective scope, Revocation epoch, reason, and Trace correlation.
- **FR-823 — Asynchronous Replay Artifact persistence:** After the terminal transaction commits, Gateway must return the synchronous response or finish the SSE stream with `[DONE]` without waiting for Replay Artifact persistence. Eligible Artifact retention runs as a separate bounded asynchronous operation; write failure, timeout, process restart, or queue loss may affect only later exact replay availability and must not change the live response, Usage, Cost Ledger, terminal outcome, or Provider recovery.
- **FR-824 — Pending Artifact duplicate boundary:** A same-key/same-fingerprint Replay Access arriving while the original eligible Artifact write is pending must use the existing `409 replay_unavailable` classification with an authorized status reference when allowed. It must not expose a `replay_pending` state, join the write, start a new invocation, or create route/Provider/retry work; a later access may replay only after a complete Artifact commit is visible.
- **FR-825 — Streaming Replay Capture Cutoff:** For an eligible SSE invocation, once normalized event capture reaches or would exceed the applicable Replay Artifact or retained-content ceiling, Gateway must stop capturing replay content and mark that Artifact ineligible while continuing the live stream under its normal event, backpressure, and terminal rules through `[DONE]`. Gateway must not truncate, semantically rewrite, or interrupt the live stream; later same-key content access returns `409 replay_unavailable`.
- **FR-826 — Bounded Replay Artifact Write Queue:** Asynchronous eligible Artifact persistence must hand off through a bounded process-local queue. Queue saturation drops only the new Artifact write, records a safe reason and metric, leaves valid existing Artifacts intact, and does not block or alter the live response, Provider work, metering, readiness, or Idempotency binding; later same-key content access returns `409 replay_unavailable`.
- **FR-827 — Replay write restart boundary:** Gateway restart does not recover pending in-memory Replay Artifact write tasks and must not expose a durable outbox or `replay_pending` status in v0.1. A task not durably visible before restart is treated as unavailable for later exact replay; restart and queue loss do not affect readiness or the already committed live invocation.
- **FR-828 — Bounded Artifact persistence retry:** An asynchronous Artifact write may make at most one additional attempt after a transient PostgreSQL or network failure, using bounded delay and jitter and the same fixed expiry/fence checks. Policy, authorization, serialization/integrity, size/retention-ceiling, capacity/quota, and SecretSource contract failures are not retried; exhausted or non-retryable writes record safe evidence and leave later exact replay as `replay_unavailable`, without creating a Model Invocation or Provider Attempt.
- **FR-829 — Replay queue dual limits:** The process-local Replay Artifact Write Queue must enforce independent maximums for pending task count and estimated serialized bytes; reaching either limit rejects only the new retention task with safe evidence and metrics. These limits are Gateway resource boundaries, are not caller-overridable, and must not consume Model/Provider concurrency or block readiness.
- **FR-830 — Isolated Replay Artifact Persistence Worker:** Replay Artifact Persistence Worker concurrency must be separately bounded from Model Invocation and Provider concurrency. Worker saturation, queue drain, or worker failure must not create a Provider Attempt, hold a Model/Provider Permit, block a live terminal response, or make `/readyz` fail.
- **FR-831 — Replay Persistence Retry Gate:** Immediately before the single permitted persistence retry, Gateway must re-check the Artifact's fixed expiry, Replay Policy Publication/Fence epoch, revocation state, and all applicable policy/size constraints. If any check fails, Gateway drops the retry without extending TTL, bypassing revocation, or changing the committed live outcome.
- **FR-832 — Replay queue ceiling ownership:** Replay Artifact Write Queue task-count and byte limits are Gateway-wide deployment-owned Resource Ceilings. Effective lower values may be represented in canonical `resource_policies` Active Snapshot data and may only tighten the hard ceiling; `replay_policies`, Provider, Model Alias, tenant, and caller fields cannot widen or override them.
- **FR-833 — Replay worker shutdown boundary:** Graceful shutdown may drain live Model Invocations under their existing cancellation and deadline rules but provides no separate Replay Artifact drain window. Pending process-local Artifact tasks not durably committed when the process exits are discarded; committed Artifacts remain readable and shutdown does not alter readiness semantics for the next startup.
- **FR-834 — Replay Artifact byte reservation:** Enqueue must atomically reserve both one task slot and the estimated serialized-byte amount, using normalized retained content plus fixed encryption/metadata overhead. Unknown, non-finite, or over-ceiling estimates reject the new Artifact without allocation; actual write size must not expand the reservation or evict existing tasks, and every completion/drop path releases the reservation.
- **FR-835 — Replay queue order and retry placement:** Pending Replay Artifact tasks must be processed FIFO by terminal-commit handoff time. The single persistence retry remains part of its original task and must not create a second queue slot, reorder newer tasks, or evict an already reserved task.
- **FR-836 — Replay Worker shutdown behavior:** The Replay Artifact Persistence Worker has no separate graceful-drain window. On process exit, every queued task not durably committed is dropped and its reservations are released; already committed Artifacts remain authoritative, and no replay status or live invocation state is changed.
- **FR-837 — Replay task revalidation:** Before a queued Artifact's first write, the Worker must perform Replay Task Revalidation against the effective Resource Ceiling, policy eligibility, fixed expiry, revocation state, and Replay Security Invalidation Fence. A stricter limit, expired policy, or advanced Fence drops the task without writing, retrying, extending TTL, or changing the committed live outcome.
- **FR-838 — Replay persistence pool isolation:** Replay Artifact Persistence Worker operations must use a separately bounded PostgreSQL connection/transaction pool from live invocation checkpoints. Pool exhaustion, timeout, or failure drops or classifies only Artifact persistence and must not starve, block, or change live terminal persistence, Model/Provider work, readiness, or metering.
- **FR-839 — Replay Artifact task deadline:** Every queued Artifact persistence task must have a bounded task deadline covering queue wait, write, and its permitted retry. On deadline exhaustion the task releases all reservations and is dropped with safe evidence; the fixed Artifact expiry and live invocation outcome are unchanged, and later exact replay returns `replay_unavailable`.
- **FR-840 — Replay Artifact write idempotency:** Artifact persistence must use an immutable `artifact_id`/`call_id` key and an all-or-nothing idempotent write. A retry or unknown prior outcome may confirm the same committed content or complete that exact record only; duplicate rows, content overwrite, semantic mutation, and Provider re-execution are forbidden.
- **FR-841 — Replay Artifact wire form:** Exact replay must persist a deterministic Gateway-owned UTF-8 replay envelope containing the protocol version, response mode, normalized synchronous result or normalized SSE event sequence, and required lifecycle bindings. Provider raw bytes, headers, raw errors, and transport-specific payloads must not be stored as the replay source.
- **FR-842 — Replay Artifact encoding profile:** v0.1 Artifact serialization is uncompressed and deterministic. Per-Artifact and queue byte ceilings are evaluated on the canonical serialized envelope before encryption plus the fixed encryption/metadata overhead; compression ratio or encryption randomness cannot bypass the limits.
- **FR-843 — Replay Artifact key collision:** If an immutable `artifact_id`/`call_id` already exists with a different content hash or binding, the original complete record remains unchanged, the new write is classified as `persistence_unavailable`, safe evidence records the collision, and no overwrite, merge, or further retry is allowed.
- **FR-844 — Replay Artifact encryption envelope:** `encrypted_exact_replay` must store a versioned AES-256-GCM authenticated-encryption envelope containing ciphertext, nonce, key identity, required AAD bindings, and integrity metadata. The envelope must bind `artifact_id`, `call_id`, tenant/scope, Request Fingerprint, protocol version, and policy/key identity; plaintext response content must not be stored in the Replay Artifact Store.
- **FR-845 — Replay Artifact content hash:** Gateway must compute the Replay Artifact Content Hash as `sha256:<64 lowercase hex>` over the canonical uncompressed Gateway Wire Form before encryption and verify it after decryption, together with AAD and envelope integrity. Hash mismatch, corrupted ciphertext, or binding mismatch is `persistence_unavailable`; Gateway must not replay, repair, overwrite, or re-execute.
- **FR-846 — Replay response identity:** Exact Replay through the original `POST /v1/chat/completions` route must preserve the original stored synchronous/SSE protocol, usage-event intent, and response semantics, including OpenAI response `id`, `model`, `requested_model`, and `resolved_model`, and add only `X-Gateway-Replayed: true` as the replay marker. Replay Access still receives fresh request/Trace identity and creates no new `call_id`, Attempt, Usage, or Cost Ledger entry; original call correlation remains restricted to authorized status/evidence surfaces, and callers never address an Artifact directly.
- **FR-847 — Replay SSE pacing and backpressure:** Replayed SSE must preserve the stored normalized event order and terminal semantics but must not reproduce original inter-event timing. It must use the ordinary downstream event/byte/progress limits; a slow client ends only that Replay Access with the existing `client_too_slow` behavior and does not alter the Artifact.
- **FR-848 — Replay response cache suppression:** Exact Replay synchronous and SSE responses must emit `Cache-Control: no-store` and must not opt into intermediary/browser caching. This header policy does not delete, revoke, or mutate the encrypted Replay Artifact.
- **FR-849 — Replay Access cancellation:** Client disconnect or cancellation of the Replay Access HTTP request context stops only that response transfer. The Gateway-native invocation cancellation route cannot target Replay Access; when the original invocation is terminal it returns `already_terminal` and leaves any concurrent replay transfer unchanged. Replay Access cancellation must not cancel original Provider work, revoke or modify the Artifact, create a Model Invocation/Provider Attempt, or append Usage/Cost Ledger entries; the access outcome is recorded as safe evidence.
- **FR-850 — Replay key resolution lifetime:** For each Replay Artifact read or write, Gateway must resolve the exact-replay key just in time from the configured SecretSource and keep key bytes only in ephemeral memory for that bounded operation. Key material must not be persisted in PostgreSQL/Redis, placed in configuration or telemetry, or retained in a process-wide/TTL cache; SecretSource unavailability makes a new write unavailable without changing the live result and makes an existing Artifact read `persistence_unavailable`.
- **FR-851 — Replay key rotation fence:** Rotation or revocation of the exact-replay key advances the Replay Security Invalidation Fence. Artifacts and queued persistence tasks bound to an older key identity become immediately ineligible; a Worker must drop an old-key task before writing and must not re-encrypt it, perform a dual-key read/write, or retry around the fence. Live invocation results and their metering remain unchanged, and later eligible invocations use the new key identity.
- **FR-852 — Replay key format contract:** SecretSource must return an immutable key identity/version together with exactly 32 raw bytes for the configured AES-256-GCM envelope. Wrong length, algorithm, encoding, missing identity, or ambiguous material is a non-retryable persistence failure; Gateway must not auto-decode, derive, pad, truncate, or select another key implicitly.
- **FR-853 — Replay Artifact Tombstone lifecycle:** After an Artifact becomes expired, revoked, or otherwise permanently ineligible, cleanup may remove ciphertext asynchronously but must retain a minimal non-content Replay Artifact Tombstone keyed by immutable `artifact_id`/`call_id` at least until the original Idempotency Binding expires; a longer explicitly configured key-reuse quarantine may extend this period. The Tombstone may contain only lifecycle status, fixed expiry, revocation/policy epoch, and safe reason; it must not retain plaintext, Wire Form, Prompt, Provider payload, or usable key material. After the applicable binding/quarantine window expires, the Tombstone may be deleted without restoring replay or allowing regeneration under the old key.
- **FR-854 — Replay Access pre-emission fence check:** A Replay Access must re-check the Replay Security Invalidation Fence after decrypting and verifying an Artifact and before emitting its first downstream byte. If the Fence or expiry invalidates the Artifact before emission, the access is discarded and returns `replay_unavailable`; once a byte has been emitted, the access may finish its stored protocol and cannot withdraw bytes or mutate the Artifact.
- **FR-855 — Replay key failure isolation:** SecretSource lookup, key-format, decryption, or key-version failures are confined to Artifact persistence or Replay Access. They must not fail `/readyz`, change Provider Health or Circuit state, consume Model/Provider permits, create an Attempt, alter a live result or its Usage/Cost Ledger, or trigger Provider fallback; new writes are skipped and failed reads use `persistence_unavailable` with safe Evidence/Metrics.
- **FR-856 — Idempotency Key Namespace:** Idempotency identity must be the tuple `(Authorization Context.tenant_id, Authorization Context.subject, api_operation, idempotency_key)`, where `subject` is the Stable Authorization Subject. A matching key outside that complete tuple is unrelated and must neither collide with nor reveal another invocation. Authorization scopes are revalidated for access but are not namespace components, and bearer-token bytes are never used as subject identity.
- **FR-857 — Idempotency Key Profile:** `Idempotency-Key` must appear at most once and contain 1–255 visible ASCII bytes in the inclusive range `0x21`–`0x7E`. It is opaque and case-sensitive; Gateway must not trim, case-fold, Unicode-normalize, concatenate duplicate values, or interpret its syntax. Empty, whitespace/control-containing, non-ASCII, oversized, or repeated values return `400 invalid_request` before admission or Provider work.
- **FR-858 — Idempotency Binding Window:** `resource_policies.idempotency.binding_ttl_seconds` is a positive integer deployment policy with a default of 86,400 seconds and a Gateway hard maximum of 604,800 seconds. The immutable expiry is anchored when the admission checkpoint commits and is not extended by duplicate requests, Replay Access, status access, retries, terminal completion, or restart.
- **FR-859 — Idempotency retention ordering:** An Exact Replay Artifact TTL must be less than or equal to its Idempotency Binding Window, and Invocation Status retention must be greater than or equal to that window. Candidate validation must reject a snapshot that violates either relation; runtime cleanup must not shorten a locked invocation's effective relation.
- **FR-860 — Key-Reuse Quarantine:** `resource_policies.idempotency.key_reuse_quarantine_seconds` is a positive integer additional period beginning when the Binding Window expires, with a default of 604,800 seconds and a Gateway hard maximum of 2,592,000 seconds. During it, a non-content Idempotency Tombstone returns `409 conflict` for the same Idempotency Key Namespace; after it expires, that namespaced key may create a new Model Invocation, without restoring any prior status, Artifact, Evidence, Usage, or cost.
- **FR-861 — Idempotency Index Digest:** Gateway must encode the complete Idempotency Key Namespace using a versioned, unambiguous length-prefixed byte format and compute `HMAC-SHA-256` with the active member of the dedicated Idempotency Index Key Ring. PostgreSQL may persist only the digest, encoding/HMAC profile version, and HMAC key identity/version required for lookup; the raw Idempotency Key must not enter PostgreSQL, configuration, Logs, Metrics, Trace, ordinary Evidence, or error responses. Every ring member contains exactly 32 raw key bytes and is distinct from Request/Execution Fingerprint keys and Replay/Cache encryption keys; Gateway must not auto-decode, derive, pad, truncate, or implicitly substitute key material.
- **FR-862 — Stable subject requirement:** Production authentication succeeds for Gateway admission or Idempotency/Status/Cancel lookup only when the selected Authorization Adapter supplies a non-empty, format-valid Stable Authorization Subject in `Authorization Context.subject`. Gateway must not substitute `tenant_id`, username/display name, session ID, or credential hash. A missing, blank, malformed, or otherwise contract-invalid local-JWT `sub` is caller-controlled credential invalidity and returns HTTP 401 under FR-924; the equivalent field in an Authority `authenticated` decision is request-local `authorization_context_contract_invalid` and returns `authorization_unavailable` before persistence, cache lookup, routing, Provider work, or historical-state disclosure. Cross-refresh stability is an Adapter assurance tested through conformance fixtures rather than inferred from one request or a persistent Gateway identity map. The latter contract failure is non-retryable for the same request, emits no `Retry-After`, and neither closes the Authorization Probe Gate nor sets a new Live Authorization Fault; however, the underlying protocol-valid live decision may clear a pre-existing Live Authorization Fault under the generation rule in FR-932 and thereby restore aggregate readiness. Development mode uses the fixed subject in FR-927.
- **FR-863 — Idempotency conflict disclosure:** Fingerprint-mismatch and Key-Reuse-Quarantine conflicts return HTTP 409 with stable code `conflict`, a generic safe message, and only the current request identity required by the normal error contract. They must not disclose the original `call_id`, result/model, lifecycle, timestamps, Request/Execution Fingerprint, Artifact presence, retention state, or whether the conflict is mismatch versus quarantine. Authorized historical lookup remains a separate Status operation.
- **FR-864 — Idempotency Index Key Ring:** Bootstrap Configuration must reference one deployment-level, versioned Idempotency Index Key Ring through SecretSource and must not contain its secret bytes. Its descriptor must contain exactly one `active` member and at most eight `verification_only` members with immutable key identity/version metadata. A missing, malformed, or ambiguous Bootstrap reference/descriptor, an invalid member role, or zero/multiple-active members is invalid Bootstrap Configuration and keeps Data Plane admission non-ready. SecretSource material availability and content-profile validation follow the keyed-path failure boundary rather than this global readiness classification.
- **FR-865 — Idempotency Index rotation and lookup:** New Idempotency bindings must use only the current `active` ring member. A lookup must derive candidate Index Digests using the active member and every retained `verification_only` member, then match the persisted profile and key identity/version; an old member must never create a new binding. A former active member must remain verification-capable until every Idempotency Binding and Idempotency Tombstone that could reference it has expired, after which it may be retired. Rotation must not require raw-key persistence, online reindexing, or rewriting an existing digest.
- **FR-866 — Index-key material failure boundary:** At cold start after structurally valid Bootstrap configuration, and during runtime, missing, revoked, ambiguous, wrong-identity, wrong-version, wrong-profile, wrong-length, or otherwise unusable SecretSource material for the active member or any retained member required for exhaustive lookup must not make `/readyz` fail. Every invocation, Status, or Cancel operation that depends on `Idempotency-Key` must instead fail closed with `persistence_unavailable`/HTTP 503, without Provider work, replay, cache degradation, new binding creation, or treating an unsearchable key as new or unknown. Unkeyed invocations and Status/Cancel operations addressed solely by `call_id` must continue under their ordinary contracts.
- **FR-867 — Keyed lifecycle lookup namespace:** `GET /gateway/v1/invocations/by-idempotency-key` and `POST /gateway/v1/invocations/by-idempotency-key/cancel` must accept exactly one valid `Idempotency-Key` Header and must not accept the key through path, query, or body fields. They derive the Idempotency Index Digest from the current Authorization Context and the fixed original invocation operation identifier `chat.completions.v1`; the Status or Cancel HTTP operation must not become a different namespace component. Supplying `Idempotency-Key` to either `{call_id}` route is `400 invalid_request` before lookup, with no implicit target precedence.
- **FR-868 — Unknown lifecycle target:** For a valid, authorized Status or Cancel request selected either by `Idempotency-Key` or by `call_id`, an absent or expired target and a target belonging to another tenant or subject must produce the same non-disclosing HTTP 200 lifecycle response. Status has the closed JSON body `{"state":"unknown_or_expired"}`; Cancel has the closed JSON body `{"state":"unknown_or_expired","cancellation_accepted":false}`. Both use `Content-Type: application/json`, `Cache-Control: no-store`, and a fresh `X-Request-Id`, and strictly omit `X-Gateway-Call-Id`, `call_id`, and historical evidence. The result must not reveal which no-match cause occurred or create/re-run an invocation; missing/invalid credentials still return `unauthorized`/HTTP 401 and insufficient lifecycle permission still returns `forbidden`/HTTP 403 before lookup.
- **FR-869 — Authorization failure reason boundary:** An unavailable required online Authorization Authority must use internal reason `authority_dependency_unavailable` and outward `authorization_unavailable`/HTTP 503; Gateway performs no automatic authorization retry and emits no `Retry-After`, while a later request may succeed after the dependency recovers. Among request-time authorization failure reasons in an online-authorization deployment, only this dependency reason makes readiness false; an `authorization_context_contract_invalid` result after a conforming Authority `authenticated` decision remains request-local and non-retryable, while statically detectable Adapter or mapping defects retain the non-ready configuration behavior defined by FR-875. Missing, expired, locally invalid, or explicitly rejected caller credentials map to `unauthorized`/HTTP 401, while a valid identity lacking the required permission maps to `forbidden`/HTTP 403. Every classification occurs before Provider work and must not alter Provider Health or Circuit state.
- **FR-870 — Restart-only Idempotency Index rotation:** In v0.1, the Idempotency Index Key Ring descriptor, member set, roles, and active version form an immutable process-lifetime snapshot. A different ring may become active only through Gateway/Docker restart; Gateway must expose no hot reload, watch, rotation API, or concurrent in-process active-key transition. Emergency member revocation may invalidate and purge material under FR-873 but must not activate a replacement ring in the running process.
- **FR-871 — Key Ring size and retirement validation:** An Idempotency Index Key Ring may contain at most eight `verification_only` members in addition to its one `active` member. Exceeding this limit is invalid Bootstrap configuration and must not trigger automatic eviction. Before accepting a restarted ring that removes a previously referenced version, Gateway must query PostgreSQL using PostgreSQL database time and reject activation while any Idempotency Binding or Idempotency Tombstone for that version has `protected_until` later than that database time; it must not rely on the process wall clock, silently discard protection, or rewrite/reindex a digest.
- **FR-872 — Uniform Index material failure semantics:** SecretSource bytes that are missing, revoked, wrong-identity, wrong-version, wrong-profile, wrong-length, ambiguous, or otherwise unusable have the same keyed-path-only behavior whether detected during cold start or runtime: all Idempotency-Key invocation/Status/Cancel operations return `persistence_unavailable`/HTTP 503 and do no work, while readiness, unkeyed invocation, and `call_id`-only lifecycle behavior remain unchanged. Only Bootstrap reference/descriptor structure, role/count constraints, and premature version removal under FR-871 are global startup/readiness failures.
- **FR-873 — Emergency Index-member revocation:** Once Gateway observes revocation of any still-required Idempotency Index member, it must purge held key bytes and disable every Idempotency-Key invocation, Status, and Cancel path, even when the current active member remains usable. Gateway does not claim an unknowable guarantee from an external revocation timestamp it has not observed. It must not perform active-only lookup, classify a miss as new/unknown, create a binding, reindex, restore from another version, or degrade to Provider execution. The keyed paths may recover only after the current-Fence full-Ring validation rules in FR-909 succeed for the exact restored member, or after PostgreSQL database time passes the maximum `protected_until` of every record referencing it and a restart activates a valid ring with that member removed.
- **FR-874 — Closed unknown lifecycle representation:** `unknown_or_expired` is the single no-disclosure representation for missing, expired, or inaccessible-by-namespace lifecycle targets selected by either Idempotency Key or `call_id`. Its Status and Cancel bodies and headers are exactly those defined by FR-868, with no optional extension members, error envelope, replay marker, invocation identity, retention detail, or selector-specific distinction.
- **FR-875 — Complete Authorization Context contract:** The normalized Authorization Context contract requires valid `subject`, `tenant_id`, `issuer`, one matched logical `audience`, `expires_at`, and `authentication_method` fields plus a present normalized `scopes` set that may be empty, all under FR-903–FR-905. A statically detectable Authorization Adapter or field-mapping defect is invalid deployment configuration and keeps Gateway non-ready with `gateway_not_ready`. Only a conforming online-Authority `authenticated` decision that cannot produce the promised Context is request-local `authorization_context_contract_invalid`; it maps outward to `authorization_unavailable`/HTTP 503 without `Retry-After`, creates no persistence/cache/routing/Provider work, and neither closes the Authorization Probe Gate nor sets a new Live Authorization Fault. Its underlying protocol-valid live decision may nevertheless clear a pre-existing Live Authorization Fault under the generation rule in FR-932 and thereby restore aggregate readiness. Local-JWT Claim or resulting Context invalidity is HTTP 401 under FR-924. Gateway must not retry either authorization failure within that request, but a later independent caller request is permitted.
- **FR-876 — Online Authorization readiness state machine:** `online_authority` mode must expose one process-local, non-persistent aggregate state `unknown`, `available`, or `unavailable`, derived from the separate Authorization Probe Gate and Live Authorization Fault Latch in FR-932. It starts `unknown` and non-ready. A dedicated background `AuthorizationPort.check_readiness()` probe starts immediately, then is scheduled every 5 seconds with a 2-second timeout, no retry, and no overlapping execution. `/readyz` reads only the aggregate local state and must not synchronously call the Authority. The mechanism has no hysteresis, debounce, circuit breaker, half-open state, backoff, or durable history.
- **FR-877 — Safe Authorization probe and pre-admission telemetry:** An online-Authority readiness probe must never reuse a caller Token or caller-derived Authorization Context; when credentials are required, it may use only a dedicated least-privilege probe credential obtained through SecretSource. An online Adapter without a safe, configured probe cannot become ready. Any pre-admission authorization failure creates no `call_id`, Model Invocation, Invocation Evidence, Cost Ledger entry, or PostgreSQL authorization-health record; it may emit only redacted structured Logs, OTel HTTP/Auth Spans, and low-cardinality Metrics. Logs and Spans may contain safe request/Trace correlation, authorization mode, Adapter version, normalized reason, and latency; Metrics may contain only bounded authorization-mode, Adapter-version, reason, and latency dimensions. Token bytes, Claims, `subject`, `tenant_id`, other raw identity identifiers, Authorization endpoint, raw Authority responses/exceptions, and request-level identifiers as Metric labels are forbidden.
- **FR-878 — Exclusive authorization topology:** Each resolved deployment configuration must select exactly one authorization mode: `dev_bypass`, `local_jwt`, or `online_authority`. Authentication chains, multiple Authorities, fallback, and authorization degradation are not supported. The effective `dev` startup profile selects `dev_bypass`; `production` must explicitly select exactly one of `local_jwt` or `online_authority` and must never fall back to `dev_bypass`. `local_jwt` follows the one-file startup-only profile in FR-934; remote JWKS fetch and online JWKS rotation are deferred to v1. `online_authority` is production-only and follows FR-935 without a development HTTP/private-destination exception.
- **FR-879 — Caller-controlled credential classification:** A missing, duplicate, comma-combined, malformed, unsupported, unverifiable, expired, or not-yet-valid Bearer credential, or failure of its configured signing algorithm, key identity, signature, issuer, audience, temporal, or mandatory identity-claim checks, must return `unauthorized`/HTTP 401 under the exact raw-Header profile in FR-933. An online Authority's explicit unauthenticated decision also returns 401, dependency inability returns `authorization_unavailable`/HTTP 503, and a valid normalized Context whose scope set lacks the Gateway operation's exact permission is decided by Gateway as `forbidden`/HTTP 403. The Authority must not make a route-level Gateway permission decision, and caller-controlled invalidity must never be relabeled as `authorization_context_contract_invalid`.
- **FR-880 — Adapter-success contract boundary:** In v0.1, request-local `authorization_context_contract_invalid` applies only after a conforming `online_authority` `authenticated` decision cannot produce its promised normalized Authorization Context. A caller-controlled local-JWT Claim or resulting Context violation returns HTTP 401, while a defect detectable in Adapter registration, fixed mapping, configured local key material, or topology before serving is invalid Bootstrap/deployment configuration and keeps Gateway non-ready. None is retried within the request.
- **FR-881 — Stable-subject assurance ownership:** The selected Authorization Adapter must guarantee Stable Authorization Subject continuity across credential refreshes for one principal, and conformance tests must include paired credentials that assert the same subject. Gateway runtime validates only the supplied subject's required type, format, and non-blank value; it persists no credential-to-principal mapping and cannot infer drift. Two otherwise valid requests carrying different subjects are different principals and Idempotency Key Namespaces rather than a Gateway-detected contract failure.
- **FR-882 — Authorization Scope Set algebra:** `Authorization Context.scopes` must be present and normalize to one immutable de-duplicated set that may be empty. Production authorization uses case-sensitive exact string membership only; wildcard, prefix, hierarchy, implicit-admin, and unknown-scope grants are forbidden. An empty set represents an authenticated principal with no Gateway permissions and therefore yields HTTP 403 for every protected operation. Synthetic `dev:*` is descriptive context only because `dev_bypass` performs no scope matching.
- **FR-883 — Closed Gateway Permission Scope catalog:** v0.1 recognizes only `gateway.model.invoke`, `gateway.model.provider_override`, `gateway.invocation.read`, `gateway.invocation.cancel`, `gateway.config.providers.write`, `gateway.config.bindings.write`, `gateway.config.routing.write`, `gateway.config.pricing.write`, `gateway.config.safety.write`, `gateway.config.resources.write`, `gateway.config.replay.write`, `gateway.config.read`, `gateway.config.export`, `gateway.config.publish`, `gateway.config.rollback`, `gateway.audit.read`, and `gateway.cost.reconcile`. No alias, wildcard, role name, or generic admin scope implies one of these grants.
- **FR-884 — Data Plane permission mapping:** `POST /v1/chat/completions`, including same-key Replay Access, requires `gateway.model.invoke`; a Provider Selection Override additionally requires `gateway.model.provider_override`. Both Status routes require `gateway.invocation.read`, and both Cancel routes require `gateway.invocation.cancel`. Invocation-read permission covers the existing content-free safe lifecycle, Attempt, Usage, cost, and Evidence summary and grants no cross-subject or raw-content access. Missing any required member rejects the entire operation with HTTP 403 before validation or mutation, without deleting unauthorized operations or producing a partial result. Configuration metadata/list/read uses `gateway.config.read`, YAML export uses `gateway.config.export`, publication uses `gateway.config.publish`, rollback-Candidate creation uses `gateway.config.rollback`, configuration audit read uses `gateway.audit.read`, and reconciliation import uses `gateway.cost.reconcile`; rollback publication still separately requires publish permission.
- **FR-886 — Generic online introspection integration:** v0.1 `online_authority` must use a versioned generic HTTP JSON Authorization Introspection Adapter that exchanges a caller credential for a normalized Authorization Context. Gateway applies its closed permission-scope mapping after introspection and must not persist or import the Authority's user, role, group, or policy model. Vendor-specific shapes must terminate in an Adapter or sidecar, and must not leak into Application or Domain types.
- **FR-887 — Deterministic authorization defaults:** Omitting `startup_profile` resolves to `dev`; when the effective profile is `dev`, omitting `authorization.mode` resolves to `dev_bypass`. `production` must explicitly declare exactly one of `local_jwt` or `online_authority`, and `dev` with either production mode or `production` with bypass is invalid. Shipped Docker development configuration must nevertheless show both values explicitly, and the resolved profile and mode—not their source omission—must enter the Bootstrap digest and startup evidence.
- **FR-888 — Authorization probe contract success:** The first online-Authority readiness probe must start immediately after its local prerequisites are available; later probes follow the five-second schedule, and a second probe must not overlap a still-running probe. Success requires the configured side-effect-free Adapter probe result to pass protocol-version, Schema, expected-Authority-identity, and required probe-authentication checks; TCP connectivity or an arbitrary HTTP 2xx is insufficient. The readiness contract need not create a real-user Authorization Context, and its external HTTP wire details remain part of the separately defined Authority transport profile.
- **FR-889 — Authorization observation ordering:** Every real-request dependency observation and readiness-probe run must participate in one serialized, monotonic process-local observation generation. A completion may update only its own Probe Gate or Live Fault component and only when its captured generation is not stale for that component; Probe success can never clear a Live Authorization Fault, and live success can never clear a failed Probe Gate. Tests must deterministically cover stale success/failure, timeout, cross-component completion order, and concurrent scheduling without real sleep.
- **FR-890 — Authorization transition telemetry:** Authorization Dependency State emits one redacted structured transition Log when its value changes and bounded low-cardinality counters for repeated probe/request outcomes; repeated identical observations must not emit repeated transition Logs. These signals retain the pre-admission minimization rules and must not create durable authorization-health state.
- **FR-891 — Just-in-time Index key lease:** Each HTTP operation that depends on `Idempotency-Key` must resolve every member of the immutable process-lifetime Idempotency Index Key Ring as one bounded, all-or-nothing Idempotency Index Key Material Lease, with at most nine members. v0.1 must not reuse Index key bytes across HTTP operations or apply the generic cross-request SecretSource cache allowance to them. It must release operation-held bytes on every exit. A real required-member resolution or validation failure produces Idempotency Key Lockout; rejection solely because Gateway's process-local Lease concurrency capacity is exhausted does not advance the Fence, enter Lockout, or change the Lockout Gauge.
- **FR-892 — Index revocation linearization:** Gateway must maintain a monotonic process-local Idempotency Index Security Fence. Observation of a required member's revocation advances the Fence and purges operation-held material; “immediate” revocation semantics begin at that Gateway observation boundary rather than an unknowable external source timestamp. An operation and a Fence advance must have one ordered commit boundary so a pre-Fence commitment is not retroactively withdrawn and a post-Fence commitment cannot use revoked material.
- **FR-893 — Index Fence checks:** A keyed operation must capture the applicable Fence generation after successful material resolution and re-check it immediately before an Idempotency Binding/rebinding commit, historical lifecycle disclosure, Replay Artifact read/emission, or cancellation mutation. A changed or revoked generation fails `persistence_unavailable` without the guarded effect. A Model Invocation whose admission checkpoint committed before the Fence continues under its locked execution state; the Fence blocks later keyed access but does not cancel Provider work or rewrite a result already committed or emitted.
- **FR-894 — Gap-free Idempotency Protection Record:** The admission checkpoint must atomically persist one Idempotency Protection Record containing database-calculated `binding_expires_at` and `protected_until = binding_expires_at + key_reuse_quarantine`. PostgreSQL time derives whether the record is in its Idempotency Binding or Idempotency Tombstone phase, with no expiry-time insert/update required and no asynchronous protection gap. Physical cleanup may remove the record only after `protected_until`; phase-specific invocation and lifecycle outcomes retain their existing contracts.
- **FR-895 — Per-member Key Ring descriptor:** Bootstrap must express `idempotency_index_key_ring.members` as explicit entries containing `key_id`, immutable `key_version`, `role` (`active` or `verification_only`), and one exact `secret_ref`. The `(key_id, key_version)` pair and full Secret Reference must each be unique; one `key_id` may have multiple versions, but one reference must not hide a multi-key bundle or resolve implicit `latest`. Resolved identity/version/profile metadata and exactly 32 raw bytes must match the member declaration before the all-or-nothing lease is usable.
- **FR-896 — Key Lockout operational signals:** Gateway must expose a process-global 0/1 Idempotency Key Lockout Gauge, bounded transition and keyed-rejection counters by normalized reason and operation, and one safe structured Log on entry and recovery. Deployments may alert on the Gauge even though `/readyz` remains unchanged. Metric labels and Logs must exclude raw Idempotency Key, Index Digest, member key identity/version, Secret Reference, tenant, subject, credential, and other unbounded identity values.
- **FR-897 — Key Lockout request-record boundary:** A keyed request rejected before admission by material failure or the Index Security Fence may emit only a safe HTTP Span/access Log and the signals in FR-896. It creates no `call_id`, Model Invocation, Invocation Evidence, Cost Ledger entry, Replay Artifact access, or PostgreSQL key-health record and must omit `X-Gateway-Call-Id`; keyed lifecycle access must not disclose whether a target would otherwise exist.
- **FR-898 — Canonical Call ID profile:** Gateway must generate every public `call_id` as an opaque canonical lowercase UUIDv4 string of exactly 36 characters. Callers cannot select it, and uppercase, braces, URN forms, non-v4 UUIDs, or other path values are malformed and return `invalid_request`/HTTP 400 before lifecycle lookup. A canonical identifier with no visible retained target uses the existing HTTP 200 `unknown_or_expired` result; authentication-versus-selector-validation precedence is defined separately.
- **FR-899 — Lifecycle response cache suppression:** Every response from the four Gateway-native Status and Cancel routes must include `Cache-Control: no-store`, including found/terminal results and HTTP 400, 401, 403, 503, or `unknown_or_expired` outcomes. Intermediary caching must not retain lifecycle, Usage, cost, safe Evidence, authorization, or failure metadata.
- **FR-900 — v0.1 configuration lifecycle routes:** The management listener must expose exactly `GET /gateway/v1/config/active`, `GET /gateway/v1/config/revisions`, `GET /gateway/v1/config/revisions/{revision}`, `GET /gateway/v1/config/revisions/{revision}/export`, `POST /gateway/v1/config/validate`, `POST /gateway/v1/config/revisions`, `POST /gateway/v1/config/revisions/{revision}/publish`, `POST /gateway/v1/config/revisions/{revision}/rebase`, and `POST /gateway/v1/config/revisions/{revision}/rollback` for the v0.1 configuration lifecycle. Static route registration and identifier validation must prevent resource-name collisions, and these routes must never appear on public Data Plane ingress.
- **FR-901 — Rebase and rollback route effects:** Rebase replays only a Stale Candidate's stored canonical Change Set onto the explicit transaction-time current Active base and creates a new Candidate after ordinary validation; it never edits either Revision. Rollback accepts only a Superseded source, copies its historical snapshot into a new Candidate based on the current Active and marked `rollback_of`, and never publishes automatically. Both retain the state and conflict rules in FR-940, and later publication still requires the normal digest, Active Revision Precondition, audit, validation, and `gateway.config.publish` permission.
- **FR-902 — Deferred management HTTP surface:** v0.1 records the required audit, Invocation Evidence, Cost Ledger, uncertainty, capability-revocation, and retention-cleanup domain state but exposes no HTTP route for general Audit/Evidence/Cost queries, reconciliation beyond the already specified import contract, manual `uncertain` resolution, emergency Capability Revocation, or cleanup. Those public management contracts are v1 work and must not be approximated by a generic `/admin`, wildcard scope, or undocumented private route.
- **FR-903 — Authorization Context scalar profile:** `Authorization Context.subject` and `tenant_id` must each be an opaque string of 1–255 UTF-8 bytes, `issuer` an opaque string of 1–2048 UTF-8 bytes, and `audience` one Adapter-matched logical Audience of 1–255 UTF-8 bytes rather than an unresolved list. These strings must contain no control character and no leading or trailing whitespace. Gateway must reject rather than trim, case-fold, Unicode-normalize, or otherwise rewrite them. `tenant_id` remains reserved for namespace separation and correlation; v0.1 introduces no broader tenant topology or policy model.
- **FR-904 — Authorization Context time and method profile:** `Authorization Context.expires_at` must be a valid UTC Instant. `authentication_method` is the closed value `dev_bypass`, `local_jwt`, or `online_authority` and identifies the verification path, not the external Token format. All Context fields become immutable after Adapter normalization and successful contract validation.
- **FR-905 — Authorization Scope lexical and size profile:** Except for the synthetic `dev:*` bypass marker, every normalized scope must be ASCII and match `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`, contain at most 128 bytes, and contribute to a set of at most 64 distinct entries and at most 4096 total bytes. Valid unknown entries remain in the immutable Context but grant no Gateway permission. An invalid local-JWT scope Claim is caller-controlled credential invalidity and returns HTTP 401; an invalid scope returned after an online Authority has accepted authentication is `authorization_context_contract_invalid`/HTTP 503. `dev:*` is exempt from the production lexical profile because `dev_bypass` performs no scope matching and it grants no wildcard semantics.
- **FR-906 — Fixed online-Authority destinations:** The production-only `online_authority` Bootstrap branch must own one exact live-introspection endpoint and one different exact readiness-probe endpoint; both have fixed paths and share one fixed origin. HTTPS, TLS 1.2 or newer, certificate-chain and hostname verification, and a non-empty canonical-CIDR Authority egress allowlist are mandatory. Both endpoints and every request reject userinfo, query, fragment, redirect following, caller/request destination override, plain HTTP, and loopback/private destinations. Before each new connection, DNS is resolved again and every returned address must pass the allowlist and destination policy; a mixed allowed/disallowed answer rejects the connection. Environment-proxy discovery is disabled, and no development transport exception exists.
- **FR-907 — Introspection credential separation:** A live generic introspection request must carry the caller's Bearer credential only in the redaction-required JSON member `credential` under the exact wire contract in FR-919. Gateway's service credential for the Authority must come from a separate SecretSource reference and be sent through the outbound `Authorization` Header under FR-921; a dedicated least-privilege Probe credential must be separate from both. Request bodies, outbound authentication Headers, credentials, raw responses, and associated raw exceptions must never enter Logs, Trace, Metrics, Invocation Evidence, configuration export, or error responses.
- **FR-908 — Live introspection resource boundary:** A live online-Authority operation has total timeout `min(2 seconds, remaining caller deadline)`, no retry, no queue, and a process-wide maximum of 64 concurrent calls; the readiness Probe has one independent slot and does not consume live capacity. Secret resolution, pool acquisition, DNS, connect, write, and read all consume that one operation deadline under FR-935–FR-936. A live or Probe response may contain at most 64 Header fields, 16 KiB total Header bytes, and 64 KiB of decoded JSON and must use identity content encoding. Caller disconnect or cancellation cancels unfinished live introspection. Only the eligible Authority/service-credential dependency causes in FR-943 may set the Live Authorization Fault; caller cancellation, Gateway shutdown, exhaustion caused solely by a shorter caller deadline, and process-local live-capacity exhaustion retain their request-local outcomes but must not set or refresh that Latch. No failure creates admission or Provider work. A valid `authenticated` envelope whose source fields subsequently fail only the normalized Context contract follows the request-local exception in FR-920.
- **FR-909 — Index revocation observation and recovery:** The Idempotency Index Security Fence guarantee begins when Gateway observes revocation through a just-in-time resolve, metadata check, or SecretSource notification; v0.1 does not promise instantaneous detection of an unobserved external change, including a file-backed SecretSource mutation. Observed revocation and exact restoration each advance the monotonic Fence generation, which never decreases. A completion captured before a newer generation must neither pass a guarded final check nor clear a newer Lockout. The process-global Lockout Gauge may recover only after every currently declared Ring member has been successfully resolved and validated together under the current generation; retirement-after-horizon still requires the restart validation in FR-871 and FR-873.
- **FR-910 — Batched Index key resolution:** The Idempotency Index SecretSource Port must expose one logical `resolve_many` operation over all declared member references. One operation must return a complete Lease or one failure within `min(1 second, remaining caller deadline)`, without retry. Its Adapter may resolve at most four members concurrently; on any failure it must cancel unfinished member work, clear already obtained key bytes, and expose no partial result.
- **FR-911 — Index Lease process capacity:** Gateway may execute at most 32 Idempotency Index Key Material Leases concurrently in one process. Rejection caused solely by that local capacity ceiling uses the existing keyed-operation `persistence_unavailable` response but must not enter Key Lockout, advance the Fence, or alter readiness. A failure to resolve or validate an actual required Ring member follows the existing Key Lockout rules.
- **FR-912 — Atomic reuse after protection horizon:** Once PostgreSQL database time reaches an Idempotency Protection Record's `protected_until`, concurrent reuse of the same complete Idempotency Key Namespace must perform one atomic compare-and-create under the namespace uniqueness constraint and assign a monotonically increasing protection generation. Exactly one contender creates the new Binding; every other contender observes that Binding and applies the ordinary same-Fingerprint replay/deduplication or different-Fingerprint conflict rule. The Key no longer selects the old invocation, while an independently retained old invocation may still be addressed by its `call_id`; no transition may create an unprotected or multi-binding window.
- **FR-913 — Lifecycle evaluation precedence:** Each of the four Status/Cancel routes must apply one fixed evaluation order: authentication failure as HTTP 401, insufficient route permission as HTTP 403, malformed or forbidden selector/Header structure as HTTP 400, applicable Gateway-readiness/PostgreSQL/Idempotency-Index dependency failure as HTTP 503, and only then target lookup or cancellation yielding a found result or the non-disclosing HTTP 200 `unknown_or_expired` result. A stage failure prevents every later stage. Online-Authority inability retains its existing fail-closed authorization dependency classification because no Authorization Context exists from which a permission decision could be made. Every outcome retains `Cache-Control: no-store`.
- **FR-914 — Collision-bounded Call ID allocation:** Before creating Model Invocation, Provider Attempt, Invocation Evidence, or Cost state, Gateway must reserve its generated canonical UUIDv4 `call_id` through the PostgreSQL uniqueness constraint. A collision permits another random identifier, with at most three total reservation attempts for the logical admission. Three collisions return `internal`/HTTP 500 without Provider work or any partially created invocation record and increment only a low-cardinality collision-failure counter carrying no identifier.
- **FR-915 — Canonical Configuration Revision identity and state:** A Configuration Revision identifier is a positive base-10 integer within PostgreSQL `BIGINT` range. A revision path value must use unsigned canonical decimal form without leading zeroes; `0` is invalid in every revision path and the JSON string `"0"` is reserved only for the request-body sentinels `base_revision` and `expected_active_revision` under their empty-state rules. Revision state is the closed lowercase value `candidate`, `active`, `superseded`, or `stale`. Failed validation creates no Revision; publication transitions the selected Candidate to Active, the prior Active to Superseded, and competing unrebased Candidates to Stale. `rollback_of` is lineage metadata and never a state.
- **FR-916 — Versioned Snapshot Digest profile:** The sole Snapshot Digest representation is `sha256:<64 lowercase hexadecimal characters>` computed with canonicalization profile `gateway.snapshot-digest/v1`. Its input is the complete default-resolved, non-secret domain configuration including exact Secret References, while resolved Secret values are excluded.
- **FR-917 — Snapshot Digest exclusions and equivalence:** Bundle `base_revision` and non-domain metadata, Revision identity, lifecycle state, timestamps, actor, description, audit data, `rollback_of`, deployment hard ceilings, runtime observations, and secret values are excluded from Snapshot Digest input. Semantically identical default-materialized domain content submitted through API operations, YAML import, rebase, or rollback must therefore have the same digest. Candidate identity, publication digest precondition, validation prospective identity, deterministic export digest, and Active Snapshot integrity verification must all use this same definition rather than route-specific hashes; digest equality is content equivalence, not Revision uniqueness or command deduplication, under FR-942.
- **FR-918 — Configuration command idempotency:** `POST /gateway/v1/config/revisions`, publish, rebase, and rollback must each require an independent canonical UUIDv4 Configuration Command ID carried under FR-931; the read-only `/validate` route does not. A durable PostgreSQL Config Command Index must persist each eligible deterministic outcome under FR-941, atomically with the configuration mutation when one succeeds, and remain separate from Model Invocation `Idempotency-Key`, Idempotency Index Key Ring material, and Lockout. Repeating the same authenticated principal, operation, Configuration Command ID, and request digest returns the original result; reusing that command identity with a different request digest returns HTTP 409 without another mutation. Consequently Idempotency Key Lockout must not block authorized configuration recovery.
- **FR-919 — Live introspection request wire:** Gateway must call the fixed live-introspection endpoint with `POST`, `Content-Type: application/json`, `Accept: application/json`, UTF-8 JSON, identity content encoding, and no request compression. The body is a closed object containing exactly `protocol_version="gateway.authorization.introspection/v1"`, `credential_type="bearer"`, and `credential`. `credential` contains the exact Token octets represented as a JSON string after removing the syntactically validated caller `Bearer ` scheme; Gateway must not trim, normalize, or include the scheme. Unknown or duplicate body members are forbidden, and callers cannot add to or override this outbound object.
- **FR-920 — Online-Authority decision envelope:** Only HTTP 200 with `Content-Type: application/json` and an absent or UTF-8 charset is an Authorization Authority decision. Its strict UTF-8 JSON body must be a closed, duplicate-free object: `status="authenticated"` contains exactly `protocol_version="gateway.authorization.introspection/v1"`, `status`, `subject`, `tenant_id`, `issuer`, `audience`, RFC 3339 UTC `expires_at`, and `scopes`; `status="unauthenticated"` contains exactly that `protocol_version` and `status`, carries no identity or scope fields, and maps to `unauthorized`/HTTP 401. Gateway, not the Authority, sets `authentication_method=online_authority`. HTTP 204, every redirect or other non-200 status—including 401/403 service-credential rejection—an incompatible version, invalid content type/charset, malformed JSON, or a non-conforming envelope is `authority_dependency_unavailable` and maps outward to `authorization_unavailable`/HTTP 503. A conforming authenticated decision whose normalized Context alone violates FR-903–FR-905 remains request-local `authorization_context_contract_invalid`/HTTP 503 and neither closes the Authorization Probe Gate nor sets a new Live Authorization Fault; its underlying protocol-valid live decision may clear a pre-existing Live Authorization Fault under the generation rule in FR-932 and thereby restore aggregate readiness.
- **FR-921 — Authority service-token assembly:** The live and Probe SecretSource references must resolve separate raw service Tokens satisfying the exact 1–16,384-byte ASCII `token68` lexical profile in FR-945. SecretSource returns no HTTP authorization scheme; the Adapter constructs exactly `Authorization: Bearer <token>` without trimming, decoding, normalization, or case rewriting. Each live or Probe operation resolves its own reference exactly once into the operation-scoped Authorization Credential Lease in FR-935, and the live caller Token, live service Token, and dedicated Probe service Token remain three non-interchangeable credentials subject to FR-907 redaction and non-persistence rules.
- **FR-922 — Authorization Probe wire and identity:** Bootstrap must configure a distinct `probe_endpoint` on the exact live-introspection origin, a dedicated Probe service-token Secret Reference, and an expected `authority_id` that is an opaque 1–255-byte UTF-8 string with no control character or leading/trailing whitespace and is compared exactly without case or Unicode normalization. Gateway must send `GET` with no body and `Accept: application/json`; only HTTP 200 with `Content-Type: application/json` and an absent or UTF-8 charset plus a closed, duplicate-free strict UTF-8 JSON object exactly containing `protocol_version="gateway.authorization.probe/v1"`, `status="ready"`, and the matching `authority_id` is success. The Probe uses FR-908 response limits and identity encoding; every other status, content type/charset, version, identity, body, or transport result fails the Probe.
- **FR-923 — Local-JWT cryptographic and key profile:** v0.1 `local_jwt` supports only `RS256` with a 2048–4096-bit RSA public key loaded under the closed startup-only file profile in FR-934. Every usable key requires one unique 1–128-byte visible-ASCII `kid`; PEM input pairs its one key with an explicit Bootstrap `kid`, and every Token carries that exact selector and `alg=RS256`. A missing or unknown Token `kid`, Token algorithm mismatch, signature failure, or otherwise unverifiable caller Token returns `unauthorized`/HTTP 401. Duplicate configured Key IDs, private-key material, unsupported key type/size/algorithm, or algorithm/key mismatch are static configuration defects and keep Data Plane non-ready. Certificate metadata is never a trust source; remote key discovery and HS, EC, OKP, or `none` algorithms are unsupported.
- **FR-924 — Local-JWT Claim mapping:** The fixed Claim profile requires `sub`, `tenant_id`, `iss`, `aud`, and `exp`; `nbf`, `iat`, and `scope` are optional. `sub`, `tenant_id`, and `iss` map without rewriting to their same-named Context fields, and `iss` must exactly equal the configured issuer. `aud` is either one string or a duplicate-free string array and must contain the configured target Audience; Context retains only that exact matched value. `scope` is either an ASCII-SP-delimited string or a string array and maps to the normalized set under FR-905; an absent `scope` maps to an empty set. Unknown Claims are ignored. Token parsing, required-Claim, type, mapping, or resulting Context validation failure is caller-controlled credential invalidity and returns HTTP 401, not post-success `authorization_context_contract_invalid`.
- **FR-925 — Local-JWT temporal profile:** `exp` must be an integer NumericDate; optional `nbf` and `iat`, when present, must also be integer NumericDates. Verification uses a fixed 30-second clock allowance: a Token is not yet usable unless `now + 30 seconds >= nbf`, and `iat` must not exceed `now + 30 seconds`. The effective Context expiry is `exp + 30 seconds`; it is valid only while `now < expires_at`, so equality is expired. v0.1 imposes no additional maximum Token lifetime.
- **FR-926 — Local-JWT parser boundary:** The encoded JWS Compact value may contain at most 16 KiB; the decoded protected Header and Payload may contain at most 4 KiB and 12 KiB respectively. It must have exactly three canonical unpadded base64url segments, and both decoded JSON values must be strict UTF-8 objects without duplicate members or non-finite numbers. Gateway must reject `crit`, `zip`, embedded `jwk`, `jku`, and `x5u`; `typ` may be absent but, when present, must be exactly `JWT` or `at+jwt`. Any violation returns `unauthorized`/HTTP 401 before admission, persistence, routing, or Provider work.
- **FR-927 — Deterministic Development Authorization Context:** Every `dev_bypass` request must receive exactly `subject="dev"`, `tenant_id="dev"`, `issuer="urn:llm-gateway:dev"`, `audience="llm-gateway"`, `expires_at="9999-12-31T23:59:59Z"`, `scopes={"dev:*"}`, and `authentication_method="dev_bypass"`. These values are constant across requests and process restarts; no caller credential, wall-clock value, or production Claim may affect them.
- **FR-928 — Authorization expiry admission boundary:** Immediately before the atomic Model Invocation Admission Checkpoint commits, Gateway must compare the immutable Authorization Context `expires_at` with PostgreSQL database time and admit only when `expires_at > now`; equality or an earlier value returns the normal authentication-expired outcome without creating an Invocation, Attempt, Evidence, Cost entry, or Provider work. Once that checkpoint commits, the invocation must not re-check authorization expiry: queueing, synchronous generation, or SSE streaming may cross the expiry instant and continue under its locked Context. Every later Status, Cancel, or Replay access remains a separate request and must authenticate again under current rules.
- **FR-929 — Exact Idempotency Index HMAC encoding:** The profile is `gateway.idempotency-index/v1`. Its HMAC input is the exact ASCII profile bytes followed immediately, in order, by `tenant_id`, `subject`, `api_operation`, and `idempotency_key`; their one-byte tags are respectively `0x01`, `0x02`, `0x03`, and `0x04`, and each tagged field is encoded as `tag || uint32-big-endian byte-length || exact value bytes`. `tenant_id` and `subject` use their validated UTF-8 bytes; `api_operation` and `idempotency_key` use their validated original ASCII bytes. No issuer, audience, scope, terminator, normalization, or implicit value may enter the input. Gateway computes HMAC-SHA-256 with the active 32-byte Index Key and persists the 32-byte result as PostgreSQL `BYTEA` with the profile, `key_id`, and `key_version`; no API or telemetry surface may disclose it.
- **FR-930 — Configuration Revision base JSON DTO:** Every non-null Configuration Revision value in Gateway-native JSON must be an unsigned canonical base-10 string, never a JSON number, so positive PostgreSQL `BIGINT` identities use values such as `"1"` and the two empty-state request sentinels use `"0"`. Every Revision representation uses the `gateway.config/v1` base fields `revision`, `state`, `base_revision`, `snapshot_digest`, `created_at`, and `rollback_of`; `revision` is always a positive Revision string, while `base_revision` and `rollback_of` are either a positive Revision string or `null`. Every Candidate created from the Initial Configuration Base persists and returns `base_revision=null`; `"0"` is accepted only in the documented empty-Active request fields and is never returned as a persisted Revision reference. `created_at` is UTC RFC 3339 with exactly six fractional-second digits. Ordinary configuration responses must not expose actor identity; route envelopes and paging follow FR-939. v0.1 emits no ETag and rejects every `If-*` request Header under FR-946 rather than implementing conditional-request semantics.
- **FR-931 — Configuration command transport, digest, and retention:** Each mutation named by FR-918 must carry its canonical UUIDv4 Configuration Command ID only in `X-Gateway-Command-Id`; Gateway must echo the exact canonical value on every successful original or replayed command result. The ID must not occur in the JSON/YAML command body, Snapshot, Snapshot Digest, or authentication material. Command identity is `(Authorization Context.tenant_id, Authorization Context.subject, operation, command_id)`. Under `gateway.config-command-digest/v1`, Gateway parses and Schema-validates the command into its semantic JSON object, excludes authentication material and the Command ID, canonicalizes it with RFC 8785 JSON Canonicalization Scheme, and computes SHA-256; JSON member order or equivalent YAML presentation therefore cannot change identity. v0.1 must not automatically delete Config Command Index records: each record and its original result live at least as long as configuration history.
- **FR-932 — Dual-gate online-authorization recovery:** The externally visible Authorization Dependency State remains the closed `unknown | available | unavailable` aggregate, while Gateway internally maintains an Authorization Probe Gate and a Live Authorization Fault Latch. The Probe Gate starts unresolved; only a protocol-valid Probe success opens it and only a later Probe observation changes its state. Only a live observation eligible under FR-943 sets the Live Fault Latch; a later-generation live operation producing a protocol-valid HTTP 200 `authenticated` or `unauthenticated` decision clears that Latch, even when an authenticated decision later fails Context normalization. Probe success must not clear a Live Fault, and live success must not open a failed or unresolved Probe Gate. The aggregate is `available` only while the Probe Gate is open and no Live Fault is latched; it is `unknown` only while the initial Probe remains unresolved and no Live Fault has been observed, and is immediately `unavailable` when an eligible Live Fault is observed or a resolved Probe Gate is closed. Every observation is ordered by the monotonic generation in FR-889 so stale completion cannot clear newer state. Recovery admission follows FR-944 and is not conditioned on Live Fault being the Gateway's only non-readiness cause.
- **FR-933 — Raw caller Bearer Header profile:** Outside `dev_bypass`, Gateway must inspect the original uncombined HTTP fields and accept exactly one `Authorization` field whose value is a case-insensitive `Bearer` scheme, exactly one ASCII SP (`0x20`), and a 1–16,384-byte ASCII `token68` credential. Leading/trailing OWS, any additional whitespace, control or non-ASCII byte, duplicate Header field, comma-combined value, empty Token, or non-`token68` character is authentication failure; Gateway must not trim, split, decode, case-normalize the Token, or rely on a framework-combined Header. Every authentication HTTP 401 response, including a valid online `unauthenticated` decision and local-JWT failure, must carry exactly the generic `WWW-Authenticate: Bearer` challenge without a detailed reason or credential echo. `dev_bypass` ignores the Authorization Header entirely, including a malformed or duplicate field, and derives only FR-927's synthetic Context.
- **FR-934 — Closed local-JWT Bootstrap and key file:** `authorization.mode=local_jwt` selects one closed Bootstrap branch containing only its mode discriminator, one read-only mounted local key-file declaration and `pem | jwks` format, configured issuer and target Audience, and a PEM-only `kid` when applicable. Key material must not be inline, environment-sourced, URL/remote-fetched, or resolved through SecretSource. Gateway reads the file exactly once at startup; it does not watch or reload changes, and replacement requires process restart. The file is at most 256 KiB. PEM contains exactly one SPKI or PKCS#1 RSA public-key object and no certificate, extra object, or private key. JWKS contains at most 32 keys; each usable entry has `kty=RSA`, a unique FR-923 `kid`, and public `n`/`e`, which are the sole key truth. Optional `alg`, `use`, and `key_ops`, when present, must be exactly `RS256`, `sig`, and `["verify"]` respectively. Bounded certificate metadata may be ignored but never establishes trust; any private-key parameter or remote key locator is invalid. A branch, file, or key-set violation is a static Bootstrap defect and keeps Data Plane non-ready.
- **FR-935 — Closed online-Authority Bootstrap and credential Lease:** `authorization.mode=online_authority` is valid only with `startup_profile=production` and selects a closed branch containing exactly `live_endpoint`, `probe_endpoint`, `authority_id`, `live_service_token_secret_ref`, `probe_service_token_secret_ref`, and a non-empty list of canonical CIDR egress entries. It inherits FR-906's mandatory HTTPS, certificate, hostname, allowlist, and destination restrictions with no HTTP, loopback/private, or development exception. Each live or Probe operation resolves its corresponding Secret Reference exactly once after the operation deadline starts, validates the returned raw bytes under FR-945, holds them only in one operation-scoped Authorization Credential Lease, and destroys the Lease on every exit; plaintext material is never cached or shared across operations. Secret resolution and HTTP transport share the same two-second operation budget. An Authority HTTP 401/403 discards the current Lease, is not retried in that request, and a later independent operation resolves a new Lease rather than reusing bytes.
- **FR-936 — Isolated Authority HTTP/1.1 pools:** The Online Authorization Introspection Adapter must use two independent direct HTTP/1.1 connection pools—live capacity 64 and Probe capacity 1—and must never share a connection, credential, permit, or hidden acquisition queue between them. HTTP library retries are zero. Pool acquisition, fresh DNS resolution and allowlist evaluation for every new connection, connect, write, and read all consume the single two-second operation deadline, additionally clamped by remaining caller deadline for live calls. Each pool has a 30-second idle timeout and five-minute maximum connection lifetime; a connection reaching either time bound accepts no later acquisition. Capacity exhaustion refuses immediately without an Adapter/library queue and is request-local rather than a Live Fault observation; deadline exhaustion follows FR-943's full-Authority-versus-shorter-caller distinction.
- **FR-937 — Configuration API HTTP representation profile:** Every v0.1 `/gateway/v1/config` response, including success and failure, carries `Cache-Control: no-store`. JSON representations use strict UTF-8 `application/json`; Configuration Bundle import/export uses UTF-8 `application/yaml`. A request Content-Type outside the representation supported by that route returns HTTP 415, and an `Accept` value that excludes every supported response representation returns HTTP 406. v0.1 emits no `ETag`; every `If-*` request Header is unsupported input and returns `invalid_request`/HTTP 400 before persistence or semantic work, so explicit revision/digest fields are the only preconditions and no request produces 304 or 412. Candidate-producing create, rebase, and rollback successes return HTTP 201 with `Location` naming the new canonical Revision detail route. Validate, publish, Active/list/detail reads, and export successes return HTTP 200; no successful configuration route returns HTTP 204.
- **FR-938 — Closed Configuration Submission and canonical Change Set:** The validate and Candidate-create routes accept one closed Configuration Submission. JSON requires `kind="bundle"` with exactly one full Configuration Bundle payload or `kind="change_set"` with exactly one typed Configuration Change Set payload; both/neither, unknown kinds or members, JSON Patch, and persistence-shaped mutation are invalid. `application/yaml` accepts only one full Configuration Bundle and cannot express a Change Set. Every JSON or YAML Revision reference is a canonical decimal string; the empty-state request Sentinel is `"0"`, and a YAML numeric `0` is invalid. Every created Candidate durably stores both its complete canonical snapshot and one deterministic canonical typed Change Set relative to its declared base. A Bundle submission produces that Change Set by domain-semantic diff against the base; rebase replays the stored Change Set rather than deriving operations from database rows or a later export.
- **FR-939 — Configuration Read Projection and export:** `GET /gateway/v1/config/active` returns HTTP 200 with `{"active":null}` when no Active Revision exists; otherwise `active` is its FR-930 base DTO. Revision list results are ordered by Revision descending, default to 50 and permit at most 200 entries, use an exclusive keyset cursor, expose no total count, and support no state filter. A Revision detail is the base DTO plus a deterministic, bounded, redacted semantic diff relative to `base_revision`, never the full snapshot; after authorization, a missing Revision returns HTTP 404. Export alone returns the full secret-safe Configuration Bundle as `application/yaml`, encoded UTF-8 without BOM, using LF and exactly one final LF. Its `base_revision` is the exported Revision's own canonical string, and `X-Gateway-Snapshot-Digest` carries the Revision's digest as ordinary response metadata rather than an ETag. Only an Active Revision export is directly apply-ready against the current base; Candidate, Stale, and Superseded exports are archival views until an operator explicitly replaces `base_revision` with the transaction-time Active Revision or with `"0"` while no Active exists, after which the submission undergoes all ordinary validation and command rules.
- **FR-940 — Configuration mutation state contract:** Candidate create succeeds only when its `base_revision` equals the transaction-time current Active Revision; while no Active exists, any number of fully validated initial commands may use `"0"` and create independent null-base Candidates. Publish accepts only a Candidate based on the transaction-time Active state; one null-base Candidate may atomically win an empty Active state and every other null-base Candidate becomes Stale. Rebase accepts only a Stale Candidate and only the transaction-time current Active as target; replay conflict returns HTTP 409 with a bounded redacted conflict list, no new Revision, and no inline resolution. Rollback accepts only a Superseded source: selecting the current Active is a semantic no-op and selecting a Candidate or Stale Revision is a source-state violation. A valid rollback creates a new Candidate based on the current Active with `rollback_of` set to the source and requires a later ordinary publish. State/precondition violations return deterministic HTTP 409 and never mutate an existing Revision.
- **FR-941 — Config Command Index admission and concurrency:** The complete pre-Index order is fixed by FR-946. Once a mutation is structurally valid, dynamically authorized, and has its FR-931 Command Digest, Gateway must look up or atomically reserve the Command identity before evaluating mutable configuration state so a later retry can replay the original deterministic outcome despite intervening state changes. The Index stores successful outcomes and deterministic HTTP 409 or 422 outcomes atomically with their associated command transaction; it does not store HTTP 429, deadline timeout, transient 5xx, or a rolled-back transaction. Concurrent requests with the same identity and digest wait for the first transaction only within their own remaining deadline: a commit replays its stored outcome, while a rollback permits exactly one waiter to become the next executor and all others continue to coordinate on that execution. Wait expiry returns the existing `deadline_exceeded` result without storing it. A same-identity different-digest request retains the existing deterministic 409 conflict and cannot replace the first record.
- **FR-942 — Revision history is distinct from content identity:** Configuration Revision is immutable history and Configuration Snapshot Digest is semantic content identity. PostgreSQL must not impose digest uniqueness, deduplicate a valid command by digest, or return an older Revision merely because its content matches. Separate valid commands may create distinct Candidate or Active Revisions sharing one Snapshot Digest, including publication of an otherwise valid Candidate whose content equals the current Active; each retains its own base, state, timestamps, lineage, audit, and Command record. Digest equality alone neither makes an invalid command valid nor suppresses its error: rebase of a non-Stale/current-base Candidate remains a source-state violation, while rollback selecting the current Active remains a rejected semantic no-op under FR-940.
- **FR-943 — Live Authorization observation eligibility:** A live operation may set or refresh the Live Authorization Fault only for failure of the actual Authority/service-credential dependency chain: live SecretSource resolution or FR-945 credential validation; runtime DNS, egress-allowlist, TLS, connect, request-write, or response-read failure; exhaustion of the full two-second Authority budget when no shorter caller deadline is the cause; any HTTP status other than 200; or response header/body ceiling, content-encoding, media-type/charset, UTF-8, JSON, protocol-version, or decision-envelope failure. Caller credential syntax, caller cancellation/disconnect, Gateway shutdown, exhaustion caused solely by a shorter caller deadline, and process-local live-capacity exhaustion do not set or refresh the Latch. Valid `unauthenticated`, later Context Contract Failure, and later route authorization denial are protocol-valid or post-decision outcomes and never set it. Excluded observations retain their existing request-local HTTP/cancellation outcome and telemetry classification.
- **FR-944 — Online-authorization recovery admission:** While the Authorization Probe Gate is open, every normally protected Data Plane or Control Plane request may execute its ordinary online live authentication before the general Data Plane readiness gate, even when a Live Authorization Fault is latched and other readiness blockers such as an absent Active Snapshot also exist. A later-generation valid decision may clear the Latch; the same request then continues through its route-specific permission, persistence, configuration-recovery, or Data Plane readiness checks, and its `unauthenticated` or Context-invalid outcome remains 401 or 503 respectively. Direct listeners continue accepting requests while `/readyz` is 503; the existing live capacity of 64 is the only recovery-concurrency bound. v0.1 adds no shared authentication result, single-flight recovery, synthetic live canary, operator reset endpoint, or readiness-time caller credential.
- **FR-945 — Authority service Token lexical profile:** Each live and Probe Authorization Service Credential is exactly one raw 1–16,384-byte ASCII `token68`: one or more `ALPHA`, `DIGIT`, `-`, `.`, `_`, `~`, `+`, or `/` characters followed by zero or more trailing `=` characters. It contains no scheme, whitespace, control, non-ASCII byte, comma, internal `=`, or other character. Gateway must reject rather than trim, split, decode, pad, normalize, or log invalid material. Invalid live material is an eligible credential-chain failure under FR-943; invalid Probe material fails and closes the Probe Gate. Invalid Bootstrap reference structure remains a static configuration defect rather than a leased-material observation.
- **FR-946 — Configuration request evaluation order:** After management-listener and route-template selection, every configuration request uses one observable short-circuit order: HTTP framing and configured size ceilings; authentication; any scope fixed solely by the route; `Accept` and request `Content-Type`; conditional/Command/Header, path, and query syntax; strict UTF-8 decoding plus JSON/YAML parsing and closed structural Schema; touched-domain discovery and the exact dynamic union-scope authorization; required PostgreSQL/dependency access; for mutations, Config Command Index lookup or reservation; mutable Revision/Active state and semantic/reference validation; then read presentation or atomic effect. Validate/create derive touched domains from the structurally valid submission; rebase may read only immutable touched-domain metadata for its source before dynamic authorization and must not inspect mutable state or expose configuration content at that stage. Missing rebase source remains the authenticated 404 result. Early failure prevents every later lookup, reservation, validation, disclosure, or mutation. `If-*` is 400, and any read route or `/validate` carrying `X-Gateway-Command-Id` is 400; no configuration request produces 304 or 412. Configuration recovery bypasses Data Plane readiness but not authentication, authorization, or PostgreSQL requirements.
- **FR-947 — Empty-Active correction and archival export:** The Initial Configuration Base exists for the complete period in which Active is empty, not merely until the first Revision is allocated. Multiple null-base Candidates provide immutable correction without edit/delete semantics; the first valid empty-state publication wins and atomically stales the rest, which may later use ordinary rebase after an Active exists. Export preserves the selected Revision's own identity as `base_revision`; this is directly resubmittable only when that Revision is the current Active. A non-Active export is an archival synchronization view and acquires new apply intent only when an operator explicitly selects the then-current Active base, or `"0"` while Active is empty, and submits a new independently validated command.
- **FR-948 — Canonical Bundle and resolved Snapshot boundary:** Under `gateway.config/v1`, `providers`, `provider_model_bindings`, `model_aliases`, `routing_policies`, `pricing_tables`, and `safety_policies` are required stable-ID-keyed registries; `resource_policies` is one required Gateway-wide singleton and `replay_policies` is one optional Gateway-wide singleton. Every cross-resource choice is an explicit stable-ID reference; uniqueness, position, or latest-version inference is forbidden. Missing required domain sections are not synthesized. Omitted leaf values may use only versioned constant Schema defaults; those defaults are materialized before Change Set derivation, persistence, Snapshot Digest, and export so omission equals explicit default. Omitted `replay_policies` materializes as `execution_dedup_only`. Deployment hard ceilings do not enter the domain Snapshot; absence of stricter domain policy materializes as explicit inherit/no-additional-tightening semantics. The immutable resolved Snapshot contains `schema_version` and all fully resolved non-secret domain content, but excludes Bundle `base_revision` and metadata, Revision/state/lineage, description/actor/audit, deployment ceilings, runtime health/circuit observations, and secret values. The external `model` names only a Model Alias; Service Requirement is derived internally and no `service_requirements` registry exists.
- **FR-768 — Minimal full snapshot:** The v0.1 real Smoke path must provide and document a complete `gateway.config/v1` Minimal Configuration Bundle containing one Provider entry, one Provider Model Binding entry, one Model Alias entry, and explicit routing, pricing, safety, and Gateway-wide resource policy content in the registries/singleton shape of FR-948. Input may omit `replay_policies` for the default `execution_dedup_only` mode or provide it explicitly and completely when exact replay is enabled; the resolved Snapshot and export always materialize the effective singleton. Gateway must not synthesize an omitted required domain section or silently apply an implicit Active Snapshot; optional leaves may use only documented versioned constant defaults materialized into the hashed canonical Snapshot.
- **FR-611 — Concurrent Candidate behavior:** Multiple Candidates may share one base revision. After one publishes, every other unrebased Candidate from the prior base is Stale and must not publish through last-write-wins or automatic merge.
- **FR-612 — Explicit rebase:** Rebase is valid only for a Stale Candidate and must target the transaction-time current Active Revision. It creates a new Candidate by replaying the stale Candidate's stored canonical base-relative typed Change Set against that Active base and rerunning all validation/gates. A semantic conflict returns the bounded redacted HTTP 409 conflict list in FR-940, creates no Revision, and permits neither inline resolution nor automatic merge.
- **FR-613 — Monotonic configuration rollback:** Rollback is valid only when the selected source Revision is Superseded. It copies that historical content into a new Candidate whose base is the transaction-time current Active Revision and whose `rollback_of` is the selected source, then requires the ordinary publish path; selecting the current Active or any non-Superseded state is invalid, and Active Revision numbers never move backward.
- **FR-614 — Immutable Candidate correction:** Candidate content cannot be edited. Any correction creates another Candidate from an explicitly selected base or Candidate content lineage.
- **FR-615 — Configuration operation audit:** Validate, create, conflict, rebase, publish, rollback, read/export of sensitive diffs, and cleanup must retain actor/scope, operation/version, base/target/active revisions, digest, safe impact/redacted diff, description, outcome, time, and Trace correlation as applicable.
- **FR-616 — Control Plane scope separation:** Gateway Permission Scopes for Provider, binding, routing, pricing, safety, resource, replay, publication, rollback, export, audit-read, and cost-reconciliation operations must be independently assignable under the closed catalog in FR-883–FR-885; one write scope must not imply another Control Plane authority.
- **FR-617 — API/YAML semantic parity:** Equivalent typed Change Sets and full Configuration Bundle submissions based on the same Revision must pass the same Application validation and publication gates and produce semantically equivalent Candidate snapshots, Snapshot Digests, and deterministic canonical base-relative Change Sets. Ingress representation does not change the stored Candidate model.
- **FR-618 — Secret identity locking:** Active Snapshot and Provider configuration must lock only a Secret Reference and its policy, never secret plaintext; secret values remain operational SecretSource state outside the configuration digest.
- **FR-619 — Per-Attempt secret resolution:** Immediately before each Provider Attempt, the Adapter credential boundary must resolve the Secret Reference into one Provider Credential Lease carrying a non-secret `secret_version`, source, validity, and revocation state.
- **FR-620 — Attempt credential immutability:** One Provider Attempt must use one resolved secret value/version for its complete request lifecycle. Retry or fallback is a new Attempt and resolves again.
- **FR-621 — Bounded in-memory secret cache:** SecretSource integration may cache plaintext only in protected process memory under a deployment-owned maximum TTL; expiry requires refresh, and supported rotation/revocation notification must invalidate matching entries immediately.
- **FR-622 — Cached secret failure boundary:** A SecretSource outage may use only an unexpired, non-revoked cached credential. Missing, expired, or revoked values must fail closed and must never be used as best effort.

- **FR-660 — Deterministic extraction only:** Gateway may remove a BOM, remove one enclosing Markdown code fence, or extract exactly one unambiguous complete JSON value from surrounding prose. Synchronous success returns only extracted validated JSON text; streaming emits only extracted JSON bytes incrementally. Neither path may reorder keys, coerce numbers/types, apply Schema defaults, retain wrapper text, or repair trailing commas, single quotes, unquoted keys, escapes, missing delimiters, fields, types, or values. Pre-commit failure may enter bounded Provider recovery; post-commit ambiguity or invalidity terminates explicitly.
- **FR-661 — Unified failure envelope:** Internal failure classification covers Gateway, transport, Provider, and Structured Validation Failures; raw Adapter, parser, validator, and repair exceptions must not cross the Port.
- **FR-662 — Validation boundaries:** Pydantic validates API/envelope boundaries and may implement local validation for supported Structured Output models; arbitrary caller JSON Schema validation remains a replaceable bounded component behind an Application Port.
- **FR-663 — Adapter boundary:** Every Adapter normalizes Provider-specific transport, Usage, request IDs, failure behavior, and output-format request/response translation while preserving Tool fields opaquely.
- **FR-664 — Presenter translation:** API presenters translate validated Structured Output or classified failure into the active Compatibility Profile and attach documented requested/resolved model and trace metadata without exposing internal validator types.
- **FR-665 — Opaque Tool carrier:** Internal request/result/event protocols may carry bounded opaque JSON values for compatible Tool fields but must define no Tool Call domain object, accumulator, validator, or normalized Tool result.
- **FR-666 — Request preservation:** Opaque Tool request fields must preserve caller-provided compatible semantics and ordering through the selected Adapter, subject only to generic API validation, redaction, and transport limits.
- **FR-667 — Response preservation:** Opaque Tool response fields must preserve Provider-provided compatible semantics and ordering to the caller without Tool ID generation, argument parsing, validation, repair, or result reclassification.
- **FR-668 — Stream preservation:** Opaque Tool stream fragments must be forwarded incrementally rather than buffered into a final Tool Call, subject to generic backpressure, cancellation, timeout, and terminal behavior.
- **FR-669 — No Tool-specific persistence:** PostgreSQL, Logs, Traces, Metrics, and Cost Ledger must not persist Tool definitions, names, arguments, fragments, validation results, execution state, or results as Tool-specific records.
- **FR-670 — Content-retention boundary:** If a separately authorized generic encrypted raw request/response retention policy captures a payload containing Tool fields, it remains an opaque content artifact under that policy and must not become Gateway Tool state.
- **FR-671 — Loop validation:** The Loop is solely responsible for deciding whether passed-through Tool fields are complete, valid, allowed, executable, or successful and for associating Tool results with later model requests.
- **FR-672 — No required-call enforcement:** A Provider response containing text, missing Tool Calls, mismatched Tool names, duplicate IDs, or incomplete arguments is forwarded as received; Gateway does not create `required_tool_call_missing` or `tool_call_invalid`.
- **FR-673 — Coarse capability only:** Tool-related routing considers only the configured coarse ability to transport compatible Tool fields and records no detailed Tool capability profile.
- **FR-674 — No Prompt or Tool ownership:** Gateway configuration, invocation, replay, and rollback must not version, render, validate, inject, or override Loop-owned Prompt or Tool state.
- **FR-675 — No Tool-specific degradation:** Retry, fallback, repair, caching, and degraded-result policy must not be triggered by inferred Tool content correctness; requests containing Tool fields remain cache-ineligible by default because Gateway cannot prove side-effect safety.
- **FR-676 — Opaque fingerprinting:** Request and Execution Fingerprints may include a canonical hash of the entire opaque Tool field set so identity changes are detected without extracting Tool semantics.
- **FR-677 — Global extraction default:** The first-phase global field `resource_policies.structured_output.local_extraction_enabled` defaults to `true` and may be changed only through the immutable Candidate/publish configuration workflow.
- **FR-678 — Alias disable-only override:** A Model Alias may set `structured_output.local_extraction` only to `inherit` or `disabled`. Omission means `inherit`; `enabled`, Provider-binding, tenant, and Data Plane request overrides are invalid configuration or invalid request rather than silently ignored.
- **FR-679 — Effective extraction policy:** Effective local extraction is enabled only when the locked global setting is `true` and the locked Requested Model Alias is not `disabled`. The result and pipeline version must remain immutable across every retry/fallback Provider Attempt and be retained in Execution Fingerprint and Invocation Evidence.
- **FR-680 — Structured failure reason enum:** The first-phase stable Structured Failure Reasons are `json_missing`, `json_incomplete`, `json_malformed`, `json_ambiguous`, `json_wrong_root`, `json_duplicate_key`, `json_invalid_utf8`, `json_invalid_unicode`, `json_non_finite_number`, `json_extraneous_content`, `schema_mismatch`, `output_truncated`, and `structured_resource_limit`. `json_invalid_utf8` is reserved for invalid input bytes; `json_invalid_unicode` identifies an invalid decoded Unicode scalar sequence such as an unpaired surrogate. Caller-invalid Schema remains `invalid_request`; validator/configuration faults remain `internal`.
- **FR-681 — Caller-visible structured details:** Synchronous JSON errors and post-commit SSE error events must expose `error.code=structured_output_invalid` plus a documented Gateway extension containing `reason` and at most one of `path` or `byte_offset`. `path` is the first entry's failing instance location encoded as RFC 6901 JSON Pointer, including `""` for the root. `byte_offset` is a non-negative offset into the normalized UTF-8 JSON candidate—the same byte sequence returned synchronously or emitted through structured deltas, excluding suppressed wrappers. The fields are mutually exclusive and must not expose model fragments, raw validator text, expected/actual values, Schema contents, or additional errors.
- **FR-682 — Evidence-only error collection:** Invocation Evidence may retain at most 32 normalized validation errors per Provider Attempt under its authorization, retention, and redaction policy. Schema entries use separate RFC 6901 `instance_path` and `schema_path`; after normalization they sort by the UTF-8 byte sequence of `instance_path`, then `schema_path`, then Structured Failure Reason. Parser entries sort by numeric `byte_offset`, then the UTF-8 byte sequence of Structured Failure Reason. Sorting is locale-independent, occurs before selection/truncation, and its first entry supplies the caller-visible reason/path or reason/offset. Entry 33 and later are omitted, `truncated=true` is mandatory, and `total_observed` is recorded when known. Published resource policy may lower but never raise 32, and Data Plane callers cannot override it.
- **FR-683 — Output Schema dialect:** First-phase `json_schema` accepts only JSON Schema Draft 2020-12. Omitted `$schema` is interpreted as Draft 2020-12; any other declared dialect is `invalid_request` before a Provider Attempt.
- **FR-684 — Same-document references only:** Every `$ref` must be exactly `#` or a `#/...` RFC 6901 JSON Pointer and resolve within the same submitted Output Schema document. Named anchors, relative/absolute external URIs, file references, registry lookup, network retrieval, and `$id`-based resolution are forbidden; Gateway must never perform I/O to resolve a Schema.
- **FR-685 — Portable keyword profile:** The versioned first-phase profile `json-schema-2020-12-portable-v1` permits only `$schema`, `$defs`, `$ref`, `type`, `enum`, `const`, `properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `minLength`, `maxLength`, `pattern`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`, `allOf`, `anyOf`, `oneOf`, `title`, and `description`. Schema-aware traversal must not mistake property names or `$defs` member names for keywords.
- **FR-686 — Schema feature identity:** Gateway must derive a deterministic Output Schema feature descriptor and `schema_feature_hash` covering dialect, supported keywords, local-reference graph, profile versions, resource/evaluation requirements, root/type/object/array forms, and every other routing-relevant constraint. Router capability matching and Provider translation use this locked descriptor; Invocation Evidence retains it. It is not the canonical contract hash and must not be used alone as the Execution Fingerprint's Schema input.
- **FR-687 — Unsupported Schema features:** Every keyword not listed in `json-schema-2020-12-portable-v1`, including `format`, `$id`, `$anchor`, `$dynamicRef`, `$dynamicAnchor`, `unevaluatedProperties`, `unevaluatedItems`, `contains`, `minContains`, `maxContains`, `uniqueItems`, `prefixItems`, `dependentRequired`, `dependentSchemas`, `patternProperties`, `propertyNames`, `if`, `then`, `else`, `not`, `contentEncoding`, `contentMediaType`, `contentSchema`, custom vocabularies, and unknown keywords, must return `invalid_request` with a safe Schema path before routing.
- **FR-688 — Annotation semantics:** `title` and `description` are non-asserting annotations. Gateway may preserve and translate them to compatible Providers and must include them in Output Schema identity, but they must not change local validation, supply defaults, inject hidden messages, or bypass size/content policy.
- **FR-689 — Acyclic local references:** The first-phase Output Schema local-reference graph must be acyclic. Preflight must detect direct self-reference and indirect cycles deterministically; any cycle returns `invalid_request` with the first safe Schema path before routing and creates no Provider Attempt.
- **FR-690 — Output Schema structural ceilings:** The first-phase default Output Schema Resource Profile is 256 KiB encoded size, 64 JSON nesting levels, 32 edges in any local `$ref` chain, and 4096 total Schema nodes. Deployment configuration owns these ceilings; v0.1 `resource_policies.limits.max_output_schema_bytes` may tighten only encoded size, while the other structural counters have no Snapshot override and Data Plane callers cannot raise any value. Every limit is enforced during preflight before routing; violations return `invalid_request` with a safe Schema path and create no Provider Attempt, except the existing encoded byte-size violation remains `request_too_large` under the common resource protocol.
- **FR-691 — Portable pattern semantics:** The `pattern` keyword must use versioned Pattern Profile `re2-portable-v1`: linear-time RE2-compatible syntax, matching over Unicode code points with JSON Schema substring-search semantics. Lookaround, backreferences, conditional expressions, and every other construct outside the profile are forbidden. Each encoded pattern is limited to 2 KiB by default. Gateway must compile patterns during Schema preflight; invalid, unsupported, or over-limit patterns return `invalid_request` with a safe Schema path before routing and create no Provider Attempt. Gateway must not rewrite patterns into Provider-specific dialects, and Router must reject any candidate that cannot enforce an equivalent Pattern Profile.
- **FR-692 — Exact numeric semantics:** Schema numeric literals and Structured Output numbers must use versioned Numeric Profile `decimal-exact-v1`: strict JSON number syntax, bounded arbitrary-precision decimal evaluation, mathematical equality across equivalent lexemes such as `1`, `1.0`, and `1e0`, and exact `multipleOf` without epsilon tolerance. `type: integer` is determined by mathematical integrality. Gateway must not convert through binary floating point, round, truncate, or coerce values, and successful output preserves the original normalized-candidate number lexeme. Each number token is limited to 256 UTF-8 bytes and absolute exponent 1000 by default. Invalid or over-limit Schema literals return `invalid_request` before routing with no Provider Attempt; an over-limit model-output number returns terminal `structured_output_invalid` with reason `structured_resource_limit` after the permitted local pass and creates no further Provider Attempt.
- **FR-693 — Bounded combinator evaluation:** `allOf`, `anyOf`, and `oneOf` retain Draft 2020-12 semantics: respectively every branch, at least one branch, or exactly one branch must validate. First-phase defaults allow at most 32 branches in one combinator, 8 nested combinator levels, and 8192 instance-node-by-Schema-node evaluations in one final validation. Gateway must evaluate branches deterministically without discriminator inference or heuristic branch omission. Branch-count or nesting violations return `invalid_request` during Schema preflight with no Provider Attempt. Exhausting the runtime evaluation ceiling returns terminal `structured_output_invalid` with reason `structured_resource_limit`, creates no retry or fallback Attempt, and terminates an already-committed stream.
- **FR-694 — Unicode scalar string semantics:** Schema strings and Structured Output strings must use versioned String Profile `unicode-scalar-v1`. After JSON escape decoding, `minLength` and `maxLength` count Unicode code points rather than UTF-8 bytes or grapheme clusters; `pattern`, `enum`, and `const` consume that same decoded scalar sequence. Gateway must reject unpaired UTF-16 surrogates and must not normalize Unicode, fold case, trim, or otherwise transform strings. A successful result preserves the original valid normalized-candidate string lexeme and escape form. Invalid Unicode in a caller-supplied Schema returns `invalid_request` before routing with no Provider Attempt; invalid decoded Unicode in model output returns `structured_output_invalid` with reason `json_invalid_unicode`, distinct from byte-level `json_invalid_utf8`, and observes the existing commitment/recovery boundary.
- **FR-695 — JSON literal equality:** `enum` and `const` must use deterministic JSON Literal Equality: object member order is irrelevant, array order is significant, strings compare exact decoded `unicode-scalar-v1` sequences without normalization, numbers compare by `decimal-exact-v1` mathematical value, and booleans, numbers, strings, and `null` remain type-distinct. Every Schema object, including literal objects contained by `enum` or `const`, must reject duplicate member names. `enum` must contain from 1 through 256 values by default and must reject values that are duplicates under this equality. Contents of `enum` and `const` are literal data, so names such as `$ref` or `type` inside them must not be traversed as Schema keywords. Invalid Schema literals return `invalid_request` with a safe path before routing and create no Provider Attempt; model-output non-membership returns `schema_mismatch` without coercion.
- **FR-696 — Object Schema profile:** Every root or nested Schema node must use object form; standalone boolean Schemas `true` and `false` are unsupported in the first phase. One `properties` map and one `required` array each contain at most 256 entries by default. Required names must be unique and must name properties declared in the same Schema object. Omitted `additionalProperties` means `true`; an explicit value may be `true`, `false`, or an object-form Schema in the same portable profile. Gateway must not add missing fields, remove or reorder extra fields, promote optional fields to required, or otherwise rewrite caller semantics. Unknown output properties under `false` return `schema_mismatch`. Output member order is validation-insignificant and preserved. Capability matching must distinguish open objects, closed objects, and Schema-constrained additional properties; a Provider that requires every property to be required or lacks an equivalent form is rejected with a persisted candidate reason rather than receiving a rewritten Schema.
- **FR-697 — Array Schema profile:** First-phase arrays are homogeneous and may use at most one object-form portable `items` Schema; boolean item Schemas and tuple semantics are unsupported. Omitted `items` leaves element values unconstrained by Schema but not by Gateway resource limits. `minItems` and `maxItems` are non-negative integers, must satisfy `minItems <= maxItems` when both exist, and neither may exceed the deployment-default 1024-item per-array ceiling. Invalid declarations return `invalid_request` before routing with no Provider Attempt and are never silently clamped. A model-output array longer than the effective ceiling returns `structured_output_invalid` with reason `structured_resource_limit`, subject only to the existing pre-commit recovery boundary. Gateway must preserve array order and must not pad, truncate, deduplicate, reorder, or otherwise repair elements. `prefixItems` and `uniqueItems` remain unsupported. Capability matching records whether each candidate supports omitted/unconstrained items and homogeneous `items` without Schema rewriting.
- **FR-698 — Schema type sets and roots:** `type` accepts either one type name or an array containing from 1 through 7 unique names drawn from `null`, `boolean`, `object`, `array`, `number`, `integer`, and `string`. A type array is a semantic unordered set for validation, feature identity, and capability matching; omission permits any JSON type, with each other keyword applying only to its defined instance types. `integer` uses Numeric Profile mathematical integrality. Gateway performs no type coercion or default insertion. JSON Schema Structured Output may have any Schema-accepted root type, while JSON Object Mode continues to require an object root. Router must distinguish arbitrary-root, union-type, and nullable-type capability and persist a rejection reason for object-root-only or otherwise inexact candidates rather than rewrite the Schema or Provider nullable encoding.
- **FR-699 — Three-part Output Schema identity:** An accepted Output Schema must have `raw_schema_hash`, `canonical_schema_hash`, and `schema_feature_hash`, each using SHA-256 with an explicit canonicalization/profile version. `raw_schema_hash` covers the exact UTF-8 lexical span of the submitted Schema value for provenance. `canonical_schema_hash` covers the deterministic semantic contract and is the Schema component of Request/Execution Fingerprints, cache identity, and replay. `schema_feature_hash` covers the routing descriptor under FR-686. Canonicalization sorts object keys by decoded UTF-8 bytes; emits decoded strings with one deterministic JSON escaping; emits Numeric Profile values as normalized sign/coefficient/exponent with zero as `0`; sorts semantic-set arrays `type`, `required`, and `enum` by their canonical encodings; preserves declared order for `allOf`, `anyOf`, and `oneOf`; includes `title` and `description`; and preserves validated canonical local JSON Pointers without expanding `$ref`. Ordinary Logs must contain neither the raw nor canonical Schema body, only authorized hashes/versions and safe metadata; Invocation Evidence retention of Schema content remains separately opt-in and protected.
- **FR-700 — Schema capability failure ownership:** A request whose required Schema features are absent from a candidate's Effective Capability Set is rejected during routing with no Provider Attempt; no eligible candidate returns `unsupported_capability`. If an Adapter cannot exactly translate a request that the selected candidate declared representable before any Provider I/O, Gateway must classify `adapter_contract_violation`, return `internal`, create no Provider Attempt or fallback, and expose degraded readiness detail for the affected Adapter/binding; overall readiness remains true only while the active configuration retains another valid path for every required published service. If a sent Provider Attempt explicitly rejects a declared Schema capability, Gateway must classify `provider_capability_mismatch`, forbid same-candidate retry, and permit ordered fallback only before external commitment within existing Attempt/deadline limits. Exhausting candidates returns `unsupported_capability`; a post-commit mismatch terminates the stream without fallback. Capability mismatch updates drift/quality evidence rather than availability-circuit counters and must not mutate capability declarations automatically. An ambiguous rejection that cannot be safely distinguished from malformed Adapter translation is `adapter_contract_violation/internal`, not guessed into fallback.
- **FR-701 — Structured Output instance ceilings:** The default Structured Output Resource Profile limits one normalized model-generated JSON instance to 4 MiB UTF-8, nesting depth 64, 1024 members in one object, 1024 elements in one array, 65,536 total JSON value nodes, 262,144 Unicode code points and 1 MiB UTF-8 in one decoded string including member names, and 256 UTF-8 bytes in one number token. The root counts as one value node; property names do not add value nodes but consume string/byte limits. Deployment configuration owns these ceilings; v0.1 exposes no Snapshot override for these parser counters, while caller Schema assertions may tighten instance behavior and Data Plane callers cannot raise the hard profile. A Schema declaration such as `minLength`, `maxLength`, `minItems`, or `maxItems` outside the effective hard range is `invalid_request` before routing with no Provider Attempt rather than silently clipped. Incremental parsing must enforce every counter without full-document buffering. Runtime overflow returns terminal `structured_output_invalid` with reason `structured_resource_limit` and creates no retry or fallback Attempt; post-commit streaming emits one error and terminates. Upon detection Gateway stops consuming business output, best-effort cancels the upstream Attempt, suppresses late content, and retains permitted late Usage/receipt evidence.
- **FR-702 — Compiled Schema cache:** The single-instance Gateway should maintain an optional process-local Compiled Schema Cache, never PostgreSQL or Redis, keyed by `canonical_schema_hash`, Schema/String/Pattern/Numeric Profile versions, validator/compiler version, and effective resource/evaluation-policy digest. Entries may contain the parsed Schema, reference graph, compiled patterns, validation plan, and routing descriptor. Defaults are 1024 entries, 256 MiB aggregate retained memory, and 30-minute idle TTL; reaching any limit uses deterministic weighted-LRU eviction. A miss compiles locally, and cache infrastructure failure bypasses the cache without affecting routing. Every request still performs raw-size, syntax, duplicate-key, raw/canonical hash, authorization, and effective-policy checks before reuse; a hit must compare canonical Schema bytes/structure and may not trust digest equality alone. Version changes produce new keys. Cache content is sensitive, process-memory-only, unavailable to Logs/Metrics/debug APIs, and cleared on process exit; Metrics expose only counts, bytes, hit/miss/eviction, and compile latency. Failure to compile an already accepted Schema is `internal` and cannot trigger Provider retry or fallback.
- **FR-703 — Conclusive incremental validation:** Incremental Structured Output processing must immediately enforce UTF-8/Unicode validity, JSON syntax, duplicate keys, and every resource counter. It must also stop as soon as an irreversible Schema violation is proven, including wrong root/value type, a forbidden additional property, array length above `maxItems`, string length above `maxLength`, a completed number violating numeric assertions, or a completed subvalue outside `enum`/`const`. Assertions requiring closure or complete alternatives—including `required`, `minItems`, `minLength`, combinators, root uniqueness, suffix/trailing-content rules, and final whole-document Schema validation—remain deferred until their necessary boundary. Gateway must never declare success, emit a normal terminal event, or send `[DONE]` before the complete JSON, allowed suffix, and final validation succeed. A Conclusive Incremental Failure stops reads and requests best-effort cancellation immediately; sync may use only pre-commit bounded recovery, while committed streaming emits one error and terminates. When several failures become conclusive on one parser transition, existing normalization/sorting selects the first among observed failures. Evidence records `stopped_early=true`, `validation_complete=false`, and unknown `total_observed` rather than inventing unseen errors; a complete final validation records the corresponding completed state.
- **FR-704 — Retry decides, never rewrites:** Gateway's only model-retry transformation is a Retryability Decision. A retryable failure may authorize an equivalent new Provider Attempt after the shared bounded exponential backoff; a non-retryable failure cannot. The locked internal request, messages, Output Schema and all three identities, output mode, Effective Generation Parameters, Requested Model routing contract, safety/policy decisions, Active Snapshot, and Execution Fingerprint remain unchanged. Gateway must not inject a repair Prompt, change temperature/top-p/output limits, simplify or rewrite Schema, change optionality/root/type, switch JSON Schema to JSON Object/text, or otherwise alter caller semantics. Same-candidate retry creates a new `attempt_id` and Provider request ID; fallback only applies the next Adapter's exact translation of the same contract. Provider idempotency support may be used only when its documented generation semantics are trusted and never proves absence of duplicate execution or billing. Evidence records Retryability Decision, cause, delay calculation/jitter sample, Attempt linkage, immutable request-semantic hash, and any Provider idempotency reference without secret material.
- **FR-705 — Bounded JSON Structure Failure retry:** After bounded Local Structured Repair cannot make the existing result valid, an allowlisted model-generated JSON Structure Failure has `retryable=true` only before external commitment and only while the single structured request-retry allowance, shared Attempt limit, remaining deadline, and bounded exponential-backoff policy all permit it. The retry must send the identical semantic request to the same candidate. Every other Structured Validation Failure has `retryable=false`; all have `failover_eligible=false`.
- **FR-706 — Advanced Structured Recovery deferred:** The first phase must not invoke a higher-tier model, alternate model, repair Prompt, or regeneration workflow after Structured Validation Failure. A future Advanced Structured Recovery capability requires separate explicit design, opt-in configuration, invocation/attempt semantics, metering, tracing, and safety policy; no current behavior or compatibility field may enable it implicitly.
- **FR-707 — Structured failure transport and health classification:** `structured_output_invalid` is a caller-facing 4xx input/contract-class outcome and maps to HTTP 400 whenever headers are not committed. After SSE commitment, its single terminal error event must retain the same stable code and 400 classification even though the existing HTTP status cannot change. The outcome is excluded from Provider availability, Health State, circuit samples, and circuit transitions.
- **FR-708 — JSON repair-before-request-retry order:** For a model-produced JSON Structure Failure, Gateway must first exhaust the configured bounded local result-repair pass over the existing output. Only if that pass remains invalid may the retry policy authorize one new same-candidate Provider Attempt. The first-phase retry allowlist is exactly `json_missing`, `json_incomplete`, `json_malformed`, `json_ambiguous`, `json_wrong_root`, `json_duplicate_key`, `json_invalid_utf8`, `json_invalid_unicode`, `json_non_finite_number`, and `json_extraneous_content`. It excludes `schema_mismatch`, `output_truncated`, and `structured_resource_limit`; callers cannot expand it, and future reason codes are non-retryable until explicitly added by a versioned policy change.
- **FR-709 — First-Attempt structured error presentation:** If bounded JSON request retry is attempted and the retry also fails, the final outward `structured_output_invalid` must present the first failed Attempt's deterministically selected Structured Failure Reason and safe path/offset. A different retry-Attempt reason must not replace, merge with, or alter that caller-visible error. Invocation Evidence must retain both Attempts' full permitted validation evidence and their causal retry relationship.
- **FR-710 — No Data Plane attempt-count disclosure:** The first-phase Data Plane must not emit `X-Gateway-Attempt-Count`, `X-Gateway-Retry-Count`, retry causes, Provider request IDs, or per-Attempt details in response bodies, SSE events, or headers. Attempt/retry details remain available only through authorized Gateway-native status and Invocation Evidence surfaces. Aggregate successful Invocation Usage remains governed by FR-711.
- **FR-711 — Caller-visible Invocation Usage:** A successful response after bounded JSON request retry must report category-wise Invocation Usage aggregated across the failed first Attempt and successful retry Attempt. Synchronous `usage` and streaming `include_usage` must use the same aggregation algorithm. Per-Attempt Usage and Cost Ledger entries remain separate and linked; aggregation must not hide unknown, partial, potentially duplicated, or estimated input, output, cached, or reasoning Token counts.
- **FR-712 — Outward cost boundary:** Ordinary OpenAI-compatible Data Plane response bodies, SSE events, and response headers must not expose estimated, accrued, reconciled, disputed, converted, or total monetary cost. Authorized Gateway-native status, Invocation Evidence, and Cost Ledger surfaces may disclose cost only with the applicable pricing-table version, original currency, rounding basis, certainty/completeness state, reconciliation state, and access/audit policy. Caller-visible Token Usage remains governed by FR-711.
- **FR-713 — Budget estimation deferred:** The first phase introduces no Budget Estimate formula, DTO, persistence model, reservation, admission rule, or termination behavior. It only records the already-defined per-Attempt Usage Measurement and aggregate Invocation Usage. Any later budget design may consider Token consumption beyond Provider-reported model usage but requires a separate accepted design.
- **FR-714 — Failed-invocation Usage boundary:** A terminal OpenAI-compatible JSON error response, including final HTTP 400 `structured_output_invalid` after bounded retry, must not contain `usage`, a Usage body extension, or Attempt/Retry disclosure. Aggregate Invocation Usage, per-Attempt Usage Measurements, completeness/provenance, retry/repair history, and cost remain recorded and are available only through authorized Gateway-native status, Invocation Evidence, and Cost Ledger surfaces. After a terminal SSE error, no Usage event may be appended.
- **FR-715 — Internal repair-versus-retry accounting:** Local Structured Repair executes only over an existing Provider output and must not create or increment an internal Provider Attempt or request-retry ordinal. Only an actually dispatched repeated Provider request creates the second Attempt and first retry. Invocation Evidence must record local-repair stage/version/outcome separately from Provider Attempt and retry ordinals; none of these counts is emitted by the first-phase Data Plane.
- **FR-716 — Usage subset accounting:** For every per-Attempt Usage Measurement and aggregate Invocation Usage, `total_tokens` must equal `input_tokens + output_tokens` whenever both parent counts are known. `cached_tokens` is a subset/detail of `input_tokens`, and `reasoning_tokens` is a subset/detail of `output_tokens`; neither may be added again to `total_tokens`. Unknown parent or detail counts remain unavailable/partial rather than inferred as zero.
- **FR-717 — Provider Usage inconsistency:** When a Provider reports known `input_tokens` and `output_tokens` plus a different `total_tokens`, Gateway must normalize `total_tokens` to the exact parent sum. It must retain the raw Provider total only as restricted safe Attempt Evidence, emit a Usage inconsistency metric/log with Provider binding and model identifiers, and price from the normalized category counts. The anomaly must not change an otherwise successful Model Result, trigger retry/fallback, affect Provider Health State, or enter availability-circuit samples.
- **FR-718 — Total-only Usage:** If a Provider reports `total_tokens` without both `input_tokens` and `output_tokens`, Gateway must not infer a split or substitute missing parents with zero. The standard OpenAI `usage` object must be omitted because its required accounting invariant cannot be satisfied. A Gateway extension may disclose only `state=partial` without the numeric total; the Provider-reported total, provenance, missing categories, and Attempt linkage remain available through authorized status and Invocation Evidence. Cost categories that cannot be priced remain unavailable rather than guessed.
- **FR-719 — Tokenizer-based Usage estimation:** When a Provider returns no trustworthy Usage, Gateway may estimate input/output counts only if the active Provider Model Binding references a version-locked tokenizer implementation explicitly declared compatible with the Resolved Model and the exact translated request/output representation. The result must use provenance `estimated` and retain tokenizer identity/version. Missing, incompatible, failed, or over-limit tokenization produces `unavailable`, never zero, and must not change the Model Result, trigger retry/fallback, affect Provider Health State, or enter availability circuits.
- **FR-720 — Unobservable Usage details:** Local tokenizer estimation is limited to the observable translated model input and returned output content. It must not estimate, infer, apportion, or zero-fill `cached_tokens`, hidden `reasoning_tokens`, or any other Provider-internal Usage detail. Those categories remain `unavailable`; the parent input/output estimates and aggregate completeness metadata must disclose that limitation.
- **FR-721 — Cost from locally estimated Usage:** When observable `input_tokens` and `output_tokens` are produced by an approved local tokenizer, Gateway must create an immutable initial Cost Accrual using the locked published standard input/output rates and mark it `estimated/partial`. It must not assume cached-input discounts, hidden reasoning volume, or any other Provider-internal pricing detail. Later trusted billing may append a Reconciliation Adjustment; it must never rewrite the original estimate. If the observable parent estimates are unavailable, cost is `unavailable`, not zero.
- **FR-722 — No synthetic pre-dispatch Attempt:** Request/Schema validation, authorization, no compatible route, pre-Attempt admission/rate rejection, configuration/readiness rejection, and deadline exhaustion before Provider dispatch must create no synthetic Provider Attempt or retry record. The first-phase Data Plane returns no Attempt/Retry count header for these or any other outcomes.
- **FR-723 — Generic successful-result cache write:** A normally completed, non-exception Model Result may become a Cache Write Candidate when the active generic cache policy permits. Direct success, success after permitted Provider/model fallback, Local Structured Repair, and the bounded identical-request retry are treated identically. Failed, cancelled, `uncertain`, expired, partial, validation-incomplete, or Safety Refusal outcomes must not be written. Cached fallback results must retain their actual `resolved_model` and degradation provenance. Existing Tool/side-effect, tenant/policy, retention, keying, and version restrictions remain applicable; Structured Output creates no separate cache-write policy.
- **FR-724 — Cache-hit metering boundary:** A Cached Degraded Result creates no Provider Attempt, Provider Usage Measurement, or new Cost Ledger Accrual. Its OpenAI-compatible synchronous response and streaming completion must omit `usage`, including when `include_usage` is requested. Invocation Evidence must record `cache_hit` and the authorized source invocation identity; source Usage and cost remain attributable only to the original live invocation.
- **FR-725 — Cache lookup stage:** The Gateway may look up a Cached Degraded Result only after the live routing, retry, and permitted fallback path cannot deliver the requested service and the active Degradation Policy selects cache. It must not perform a cache lookup before normal live routing or let cache availability alter live candidate selection.
- **FR-726 — Streaming cached degradation:** A streaming invocation may return an eligible Cached Degraded Result during the degradation stage. Cache stores the complete terminal result, not upstream SSE chunks or timing. Gateway must emit a valid ordered SSE completion from that result without simulating Provider chunk boundaries, Provider TTFT, or generation pacing; the normal event-size and backpressure limits still apply.
- **FR-727 — Cache degradation headers:** `X-Gateway-Result-Mode` and `X-Gateway-Cache-Age-Ms` are the only first-phase Data Plane cache-degradation disclosures. They must not carry source invocation identity, Provider details, Usage, cost, retry, or per-Attempt information; detailed cache provenance remains restricted to authorized status and Invocation Evidence.
- **FR-728 — Effective semantic cache key:** Cache key construction must use the canonical Effective Generation Parameters rather than only caller-supplied parameter fields. A difference in effective `temperature`, `top_p`, output Token limit, response format, Output Schema, logical model/service, or any other result-affecting effective parameter must create a logical cache miss.
- **FR-729 — Non-blocking cache population:** Failure to write a Cache Write Candidate to Redis must not alter its completed live Model Result, response, Usage, Cost Ledger Accrual, retry/fallback disposition, or Provider Health State. Gateway must record a safe cache-write failure signal in Invocation Evidence and Metrics; subsequent requests treat the absent entry as a cache miss.
- **FR-730 — Cache-read failure boundary:** If Redis read fails during the cache degradation stage, Gateway must not retry Redis, create a Provider Attempt, or change Provider Health State. It must record a safe cache-read failure signal and return the live routing path's already classified terminal result.
- **FR-731 — Cache content-retention authorization:** Enabling Cached Degraded Results requires an applicable explicit content-retention policy. Redis connections must use authenticated encrypted transport, and cached response content must use application-layer encryption with SecretSource-managed keys. Missing, revoked, or unusable cache-encryption material makes an entry ineligible or prevents population without affecting the live Model Result.
- **FR-732 — Cache degradation cause allowlist:** Cached Degraded Result selection is permitted only after exhausted live Provider availability/capacity recovery, such as retryable upstream connection, timeout, 429, retryable 5xx, or circuit/health unavailability. Authentication/authorization, caller request or Schema validation, configuration/readiness, Safety Refusal, Structured Validation Failure, cancellation, `uncertain`, and all other non-availability causes must not select cache.
- **FR-733 — Authorization-authority outage:** When Gateway cannot validate or obtain the required Authorization Context because its external Authorization Authority dependency is unavailable, it must fail closed with internal reason `authority_dependency_unavailable` and outward `authorization_unavailable`/HTTP 503 before cache lookup, configuration/status disclosure, admission, or Provider work. It must not retry authorization automatically, emit `Retry-After`, use stale authorization, expose authority diagnostics, or alter Provider Health State.
- **FR-734 — Authorization dependency readiness:** In a deployment configured to require online Authorization Authority decisions, `authority_dependency_unavailable` must make Gateway readiness false while liveness remains true. An `authorization_context_contract_invalid` result neither closes the Authorization Probe Gate nor sets a new Live Authorization Fault, but its underlying protocol-valid live decision may clear a pre-existing Live Authorization Fault under the generation rule in FR-932 and thereby restore aggregate readiness. A deployment using only locally verifiable JWT credentials has no online-Authority readiness dependency.
- **FR-735 — Admission-locked authorization:** A successfully admitted Model Invocation retains its immutable Authorization Context through completion, cancellation, or terminal failure. A later Authorization Authority outage blocks new admission but must not interrupt an already admitted synchronous or streaming invocation.
- **FR-736 — First-phase authorization revocation boundary:** An explicit external authorization revocation affects subsequent admission and access checks but must not actively cancel an already admitted Model Invocation. Continuous revocation delivery, reconciliation, and in-flight cancellation are deferred from the first phase.
- **FR-737 — Provider stream protocol failure:** A malformed, out-of-order, premature-terminal, or otherwise nonconforming Provider stream event must normalize to `provider_protocol_error`. Before the External Commitment Point it may use the ordinary bounded retry/fallback policy; after commitment Gateway must emit one terminal error and close without replacement output or `[DONE]`. It is recorded as Provider protocol/quality evidence and does not change Provider Health State or circuit counters.
- **FR-738 — Process-local circuit state:** First-phase Provider Circuit state, counters, and samples are process-local runtime state and must not be persisted to PostgreSQL. Gateway restart initializes every configured Provider Circuit as `closed`; subsequent real Provider Attempts establish new health samples.
- **FR-739 — Removed binding snapshot boundary:** Removing a Provider binding from a newly published configuration affects only later admissions. An already admitted Model Invocation may complete under its locked snapshot, including its existing eligible binding set; emergency Provider credential revocation remains an immediate exception that blocks subsequent Attempts.
- **FR-740 — Response extension namespace:** First-phase non-standard Data Plane success fields must be members of the top-level `gateway` object, while error-specific fields must be members of `error.gateway`. `gateway.requested_model` and `gateway.resolved_model` are required for successful live and cached results; in streaming they appear only in the first business SSE chunk. No Gateway extension may appear as an unrelated top-level response field or modify OpenAI-standard field semantics.
- **FR-741 — Error extension namespace:** Gateway error details, including Structured Output `reason`, `path`, and `byte_offset`, must appear only inside `error.gateway` in synchronous error bodies and terminal SSE error events. They must not appear at the response root, change standard `error.code`/`error.message` semantics, or expose raw Provider/model content.
- **FR-742 — Non-ready configuration recovery:** A non-ready Data Plane with reachable PostgreSQL and valid authorization must leave only the authorized Control Plane configuration-recovery path available to read/export, import, validate, and publish a complete replacement snapshot. The Data Plane must reject invocation with `gateway_not_ready`; its status, cancellation, replay, and Provider-affecting work remain unavailable until the new snapshot passes Data Plane readiness validation. PostgreSQL unavailability remains `persistence_unavailable`.
- **FR-743 — Non-ready retry guidance:** `gateway_not_ready` must omit `Retry-After`; configuration recovery duration is not a reliably calculable client retry window.
- **FR-744 — Readiness restoration:** A Control Plane publication must atomically activate the replacement Active Snapshot for later Data Plane admissions. The Gateway must re-run admission readiness validation and permit invocation without a restart only after that validation succeeds.
- **FR-745 — Deferred Data Plane service decomposition:** The first phase deploys one Gateway service that contains Data Plane and Control Plane API surfaces. A standalone Data Plane service, separate releases, separate service probes, PostgreSQL notification-based snapshot propagation, and independent scaling are explicitly deferred.
- **FR-746 — In-process snapshot integration:** The Gateway Control Plane must publish Active Snapshots atomically to PostgreSQL and atomically replace the in-process snapshot used for later admissions. On restart, the Gateway reloads and validates the published snapshot from PostgreSQL before allowing Data Plane admission.
- **FR-747 — Control Plane management ingress:** In the first phase, Control Plane configuration, audit, and privileged operational routes must be exposed only through a designated internal/administrative ingress. The public Data Plane ingress must not route those resources. Gateway Control Plane authorization remains mandatory; network isolation is defense in depth, not a replacement for authorization. Gateway-native invocation status and cancellation remain Data Plane lifecycle extensions and retain their caller authorization boundary.
- **FR-748 — Reverse-proxy ingress enforcement:** A reverse proxy must expose a separate internal listener or hostname for the management ingress and enforce its route allowlist before requests reach Gateway. Gateway must not treat a caller-supplied header, including forwarded/internal-marker headers, as proof that a request arrived through the management ingress.
- **FR-749 — Management transport scope:** First-phase management ingress does not require mTLS. It relies on internal network isolation, reverse-proxy route enforcement, and external Control Plane authorization; mTLS may be added later as a deployment security enhancement without changing Gateway authorization semantics.
- **FR-750 — Provider-runtime readiness exclusion:** A statically valid Active Snapshot with no currently reachable Provider remains Data Plane-admission-ready. A request then follows normal routing, retry, fallback, and degradation policy and returns the applicable uniform Provider/route failure; only local configuration or required local dependency failure changes readiness.
- **FR-751 — Provider pool capacity boundary:** A Provider Transport pool's maximum simultaneous connections must equal the published Provider concurrency ceiling, and its idle connection count must never exceed that ceiling. Provider Transport must not introduce a second hidden request queue; waiting, admission, and rejection remain Gateway-controlled.
- **FR-752 — Provider TLS baseline:** HTTPS Provider connections must require TLS 1.2 or newer, may negotiate TLS 1.3, retain certificate-chain and hostname verification, and use the runtime's secure default cipher policy. First-phase configuration must not provide a weak-cipher or lower-version override.
- **FR-753 — Provider response compression:** First-phase Provider Transport accepts uncompressed responses and `gzip` responses only. Gzip data must be decompressed incrementally before normal response/event resource limits are applied. Unknown, malformed, or truncated content encoding normalizes to `provider_protocol_error` and follows the existing pre/post-commit protocol-failure boundary.
- **FR-754 — Provider response-header ceiling:** A Provider response must contain at most 64 KiB of header bytes and 100 header fields. A published Provider policy may tighten either ceiling but may not raise it. Exceeding a ceiling normalizes to `provider_protocol_error` and must not expose raw header content through ordinary telemetry.
- **FR-755 — v0.1 real end-to-end invocation:** With a valid published Active Snapshot, usable Secret Reference, and reachable OpenAI-compatible Provider, v0.1 must accept a caller Query, route it through the Gateway-owned Request Protocol and selected Model Adapter, send it to the real Provider model, and return the translated synchronous result to the caller. A Provider that supports streaming must also be usable through the same end-to-end SSE path. MockTransport contract and failure tests do not satisfy this gate; a controlled real-Provider Smoke test must verify it without exposing credentials or raw content in source, logs, or ordinary telemetry.
- **FR-756 — Docker-to-API delivery path:** A clean first-phase Docker startup must expose a documented, authorized API path to submit/validate/publish the required Provider configuration and then invoke `POST /v1/chat/completions` against a real configured model. The path must not require manual PostgreSQL edits, container-internal private scripts, or caller-supplied Provider credentials/URLs. Startup/liveness alone is not acceptance; the Docker acceptance gate must prove configuration publication, Data Plane admission readiness, real Provider execution, response translation, and caller-visible completion.
- **FR-757 — Explicit startup modes:** v0.1 must expose deployment/bootstrap startup profiles `dev` and `production`; an omitted source value deterministically resolves to `dev`, and no request may select it. Effective `dev` uses the sole authorization mode `dev_bypass`: all Gateway API authorization checks, including Data Plane, Control Plane, status, and cancellation, skip JWT bearer validation to enable local/controlled Smoke calls, while every request still receives the exact deterministic Development Authorization Context in FR-927. `production` must explicitly select exactly one of `local_jwt` or `online_authority`; an unknown, inconsistent, or invalid profile/mode must not silently select development bypass.
- **FR-758 — Development authorization bypass boundary:** The `dev` startup mode is a deliberate local/controlled execution bypass, not an alternative authorization system. Its Development Authorization Context is deterministic and synthetic; it must not create, persist, or expose production authorization claims. Switching to `production` must require a restart or an explicit deployment/bootstrap change before any request can use the production path.
- **FR-759 — Development network boundary:** The Gateway process listens on its configured container interfaces, while Docker `dev` mode must publish Gateway ports only to the host loopback interface by default. Exposing a `dev` port beyond the local host requires an explicit deployment configuration and must be visible in startup diagnostics; container-internal `0.0.0.0` listeners must not silently widen host exposure.
- **FR-760 — Minimal real Smoke topology:** The v0.1 real Docker-to-Provider Smoke gate must be satisfiable with exactly one configured Provider, one Provider Model Binding, and one Model Alias. The implementation must still support multiple configured Providers, capability routing, fallback, and their evidence; those paths may be proven by separate MockTransport/strategy tests and are not prerequisites for the first real Query.

- **FR-949 — Configuration Resource ID profile:** Every key in the six configuration registries and every reference to such an entry must be a 1–128-byte ASCII string matching `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`. Comparison is exact; uppercase, whitespace, non-ASCII, trimming, case folding, and Unicode normalization are forbidden. This profile identifies configured resources, not opaque upstream model names, Secret References, or Revision IDs. Registry values do not repeat their key identity. Rename is not an operation: changing an ID requires removal and addition with explicit reference updates. An invalid ID is a structural error; a well-formed reference with no target is a semantic configuration error.
- **FR-950 — Exact Configuration Submission DTOs:** The complete JSON Submission outer object is exactly `{"kind":"bundle","bundle":{...}}` or `{"kind":"change_set","change_set":{...}}`; no outer base, metadata, version, or other member is allowed. The Bundle payload is the complete FR-592 envelope. The Change Set payload is a closed object containing `schema_version="gateway.config-change-set/v1"`, canonical string `base_revision`, optional FR-952 `metadata`, and required `operations`. Each branch carries its base only inside its payload. YAML represents the full Bundle directly without `kind` or a `bundle` wrapper. Validate and create share these structures and reject missing, mixed, duplicate, or unknown members before Config Command Index admission.
- **FR-951 — Exact lifecycle command DTOs:** The publish request body contains exactly required `expected_active_revision`, `candidate_snapshot_digest`, and `description`; rebase and rollback bodies each contain exactly required `expected_active_revision` and `description`. The path identifies the Candidate or source Revision, so no body source/target Revision or source digest is accepted. `candidate_snapshot_digest` uses FR-916; every `description` uses FR-952. `expected_active_revision` is checked against transaction-time Active before any state change, and is also the explicit target base for rebase and rollback. Only empty-Active publication accepts `"0"`; rebase and rollback require a positive canonical Revision string. Missing or unknown members and invalid scalar forms fail structurally; valid but mismatching preconditions retain deterministic HTTP 409. Command IDs remain Header-only under FR-931.
- **FR-952 — Configuration Change Description and metadata:** A description is 1–1024 bytes of strict UTF-8 single-line text with no control characters or leading/trailing whitespace; Gateway rejects invalid input without trimming or Unicode normalization. Bundle and Change Set payloads may omit `metadata`; when present it is exactly `{"description":"..."}` with the description required. Publish, rebase, and rollback require their top-level description under FR-951. The supplied description participates in Configuration Command Digest and the applicable immutable creation/publication metadata and Audit, but never in executable Snapshot content or Snapshot Digest. Candidate creation retains submitted metadata; rebase and rollback retain their own command description as the new Revision's creation metadata. Publication records its description independently and does not overwrite creation metadata. Export preserves the selected Revision's creation metadata, omitting `metadata` if none was supplied.
- **FR-953 — Revision-scoped configuration resource versions:** A configuration resource version is identified by its Configuration Revision, resource kind, and Resource ID; operators must not submit or increment an independent resource version. A content digest may identify or validate canonical resource content but does not replace historical Revision identity. Adapter protocol versions, Schema versions, cryptographic/profile versions, and opaque Provider-supplied versions retain their separate contracts. Routing, pricing, capability, safety, degradation, cache, replay, and Eval evidence must use the revision-scoped reference and an applicable content digest rather than an operator-maintained resource counter. Where an earlier cache/replay requirement uses the shorthand “policy version,” it means this revision-scoped reference; “same policy version” for reuse means the same canonical material policy-content identity with administrative enablement excluded, while a material content change produces a different identity.
- **FR-954 — Administrative status boundary:** Provider and Provider Model Binding values must explicitly contain `status` with the closed values `enabled` or `disabled`; there is no default. Other v0.1 configuration registries have no shared administrative-status member. A reference to a disabled Provider or Binding is referentially valid, but Router must reject the affected Candidate with a stable administrative-disabled reason and persist that rejection evidence. Disabled state is published configuration and must not be inferred from Provider Health State, Provider Circuit State, or runtime failures. All other semantic publication gates continue to apply.
- **FR-955 — Configuration error classification:** Configuration request decoding, parsing, closed-Schema, type, unknown-member, Configuration Resource ID syntax, and other structural failures return `invalid_request`/HTTP 400. An authorized canonical Revision lookup miss returns `not_found`/404; unsatisfied response negotiation returns `not_acceptable`/406; unsupported request representation returns `unsupported_media_type`/415. Active precondition, lifecycle-state, idempotency reuse, and rebase semantic conflicts return `conflict`/409. A structurally valid mutation whose references, capabilities, policies, or domain relationships are invalid returns `configuration_invalid`/422. Dependency and authorization errors retain the existing global taxonomy and precedence.
- **FR-956 — Validation-route result boundary:** After authentication, authorization, representation, parsing, structural Schema, and required dependency checks succeed, `/gateway/v1/config/validate` returns HTTP 200 even when referential or semantic validation fails, with `valid=false` and safely collectable diagnostics; a valid submission returns `valid=true`. Structural, media, authentication/authorization, dependency, deadline, and internal failures remain ordinary non-200 errors. `/validate` creates no Revision, Config Command Index entry, or publication authority.
- **FR-957 — Exact Configuration Operation wire:** Each operation is a closed object using `op` and `section`. `section` is exactly one of `providers`, `provider_model_bindings`, `model_aliases`, `routing_policies`, `pricing_tables`, `safety_policies`, `resource_policies`, or `replay_policies`. For the six registry sections, `add` and `replace` contain exactly `op`, `section`, `resource_id`, and the complete typed `value`; `remove` contains exactly `op`, `section`, and `resource_id`. For either singleton section, the sole valid form is `replace` containing exactly `op`, `section`, and the complete typed `value`; `resource_id` is forbidden. `value` is forbidden on `remove`, and no operation ID, field path, precondition, or unknown member is accepted.
- **FR-958 — Configuration Operation set semantics:** `operations` is an order-independent set and may be empty. At most one submitted operation may target the same `(section, resource_id)` or singleton; duplicates are structural `invalid_request`. Canonical form orders targets by FR-592 section order and then registry Resource ID UTF-8 bytes. Touched-domain authorization is derived from every structurally submitted target before semantic no-op normalization. A `replace` whose resolved value equals Base canonical content normalizes away; an identical Bundle likewise derives an empty Change Set, and either form may create the already-permitted distinct same-digest Candidate. Against the declared Base, `add` of an existing target and `replace` or `remove` of a missing target are `conflict`/409. Operations apply atomically to a provisional Snapshot; removal never cascades, and only the complete provisional result undergoes reference and domain validation, so coordinated reference updates are allowed while remaining dangling references are `configuration_invalid`/422.
- **FR-959 — Whole-resource three-way rebase:** Rebase evaluates every stored Configuration Operation target using canonical resolved content from its original Base, the Candidate's intended result, and transaction-time current Active. When current equals Base, Gateway applies the intended result; when current already equals the intended result, including an already-identical add or already-absent remove, it records a convergent no-op; otherwise it emits `resource_changed` and rejects the complete rebase as `conflict`/409. Comparison and conflicts use the whole registry resource or singleton boundary, so disjoint field edits to one resource conflict and no field merge occurs. Gateway canonicalizes surviving operations, then validates the full provisional Snapshot; any later reference or domain failure uses `configuration_invalid`/422 and creates no Revision.
- **FR-960 — Configuration Diagnostic protocol:** Every exposed Configuration Diagnostic is the closed object `{"reason":<code>,"path":<RFC6901-string-or-null>}`. `path` addresses the logical parsed Configuration Submission for both JSON and YAML and is null only when no request-body location exists. The closed v0.1 reason catalog is `invalid_structure`, `reference_not_found`, `reference_cycle`, `target_exists`, `target_missing`, `resource_changed`, `active_revision_mismatch`, `invalid_revision_state`, `command_reused`, `adapter_incompatible`, `capability_invalid`, `routing_invalid`, `pricing_invalid`, `safety_invalid`, `resource_policy_invalid`, `secret_reference_invalid`, and `trust_bundle_invalid`. One response exposes at most 100 diagnostics, sets required `diagnostics_truncated=true` when additional safe diagnostics exist and false otherwise, and sorts by validation-phase order, then non-null path UTF-8 bytes with null last, then reason code UTF-8 bytes. It exposes no submitted/raw value, Secret Reference content, endpoint, PEM, Provider payload, parser/validator text, or exception. Top-level error code and HTTP status remain governed by FR-955.
- **FR-961 — Configuration success result envelopes:** `POST /gateway/v1/config/validate` returns one closed object with exactly `valid`, `base_revision`, `snapshot_digest`, `change_set`, `impact`, `diagnostics`, and `diagnostics_truncated`. On valid input, `valid=true`, `snapshot_digest` is the prospective FR-916 digest, `change_set` is the complete canonical `gateway.config-change-set/v1` result, `impact` and `diagnostics` are arrays, and truncation is false. On semantic invalidity, `valid=false`, `snapshot_digest`, `change_set`, and `impact` are null, at least one FR-960 diagnostic is present, and truncation follows FR-960. Returned `base_revision` and the nested result Change Set base are the persisted canonical positive Revision string or null for the Initial Configuration Base; a result never returns `"0"`. Every Configuration Impact entry is the closed object `{"section":<section>,"resource_id":<Resource-ID-or-null>,"change":"add|replace|remove"}`; registry entries require their ID, singleton entries require null, and ordering follows FR-958. Candidate create, successful rebase, and successful rollback return HTTP 201 with exactly `{"revision":<FR-930-base-DTO>}`; successful publication returns HTTP 200 with exactly `{"active":<FR-930-base-DTO>}`. These envelopes are closed.
- **FR-962 — Gateway error envelope for configuration routes:** Every non-success configuration response uses the existing closed Gateway error shape `{"error":{"code":<stable-code>,"message":<safe-stable-English>,...}}`. When and only when configuration diagnostics exist, `error` additionally contains `gateway` whose exact members are `diagnostics` and `diagnostics_truncated`; diagnostics never appear at the response root or in the message. With no diagnostics, `gateway` is omitted rather than emitted empty. The message must not interpolate raw input, protected configuration, dependency/library text, or exceptions. Correlation remains in the fresh `X-Request-Id` response Header and is not copied into the body. `/validate` semantic invalidity remains the FR-961 HTTP 200 result rather than an error envelope.
- **FR-963 — Provider configuration root DTO:** Each Provider registry value is a closed object with exactly required `status`, `adapter`, `endpoint`, `credential`, `egress`, `transport`, `health`, and `rate_limit` responsibility blocks. `status` follows FR-954. `adapter` owns Adapter type and protocol version; `endpoint` owns only the approved OpenAI-compatible base URL; `credential` owns only a Secret Reference; `egress` owns destination, DNS/IP, and proxy-use policy; `transport` owns TLS, the optional embedded Provider Trust Bundle, connection pools, and transport timeouts; `health` owns probe and health-sampling configuration; and `rate_limit` owns Provider concurrency and QPS ceilings. Every block is a closed typed DTO. Provider values contain no upstream model, pricing, Model Alias, candidate priority/weight, routing policy, or mutable runtime health/circuit state.
- **FR-964 — Provider Model Binding root DTO:** Each Provider Model Binding registry value is a closed object with exactly required `status`, `provider`, `upstream_model`, `capabilities`, `limits`, and `pricing_table`, plus optional nullable `tokenizer`. `provider` and `pricing_table` are exact Configuration Resource ID references; `upstream_model` is a case-sensitive opaque Provider-native model name and does not use the Resource ID grammar. `capabilities` is exactly `{streaming:<boolean>,tool_calling:<boolean>,structured_output:<none|json_object|json_schema>}`. `limits` is exactly `{context_tokens:<positive-integer>,max_output_tokens:<positive-integer>}` with context not less than maximum output. `tokenizer`, when non-null, is an opaque implementation reference; null or omission disables local estimation: when trustworthy Provider Usage is absent, Usage is `unavailable` under FR-719. Effective capability is the intersection with the locked Adapter Capability Contract, and publication rejects a Binding claim exceeding that contract. Binding values contain no routing priority/weight, retry, fallback, degradation, or generation parameters.
- **FR-965 — Provider Adapter, endpoint, and credential DTOs:** Provider `adapter` is exactly `{type,version}`: type follows the Configuration Resource ID lexical profile and must identify a process-registered Adapter, while version is a case-sensitive 1–64-byte ASCII protocol version supported by that type. `endpoint` is exactly `{base_url}` whose value is an absolute Provider API-root URL with an optional fixed path and no userinfo, query, fragment, or trailing slash; production requires HTTPS, and development HTTP still requires explicit Egress authorization. `credential` is exactly `{secret_ref}` and accepts only a Secret Reference, never plaintext, environment-variable selection, authorization Header naming, or Provider credential format. All three DTOs are closed.
- **FR-966 — Provider Egress DTO:** Provider `egress` is exactly `{allowed_hosts,allowed_networks,proxy}`. Both lists are non-empty, duplicate-free, and canonically sorted. Each host is a lowercase DNS A-label name without wildcard, port, or IP literal, and the endpoint hostname must be an exact member. Each network is either the exact token `public` or a canonical CIDR. Every resolved address for each new connection must match at least one entry; `public` matches only non-private, non-loopback, non-link-local, non-metadata public addresses, and one rejected address rejects the complete DNS result. Development private or loopback access requires its explicit CIDR. `proxy` is the sole v0.1 literal `disabled`; proxy URLs and Provider Transport discovery/use of proxy environment variables are invalid.
- **FR-967 — Provider Transport DTO:** Provider `transport` is exactly `{http_version,connect_timeout_seconds,idle_timeout_seconds,max_connection_lifetime_seconds,tls}`. `http_version` is the sole literal `1.1`; the three timeout/lifetime values are integer seconds in the inclusive ranges 1–30, 1–300, and 30–3600 respectively, with defaults 5, 30, and 300 materialized in canonical configuration. `tls` is the closed discriminated union `{trust:"system",trust_bundle:null}` or `{trust:"bundle",trust_bundle:{identity,pem[,label]}}`; bundle identity, PEM canonicalization/validation, and optional label follow FR-126. Certificate-chain and hostname validation cannot be disabled. Pool maximum connections is not another transport field and equals `rate_limit.max_concurrency`.
- **FR-968 — Provider health and rate-limit DTOs:** Provider `health` is exactly `{active_probe}`. Null disables active probing while passive Attempt sampling remains active. A non-null probe is exactly `{path,interval_seconds,timeout_seconds}`; it uses same-origin HTTP GET without a body and isolated concurrency one, path begins with `/` and contains no scheme, host, or fragment, interval is an integer 10–3600 seconds, and timeout is an integer 1–10 seconds strictly below interval. Provider `rate_limit` is exactly `{max_concurrency,qps,burst}` with positive integers; zero never means disabled. Transport pool maximum connections equals max concurrency. Circuit sampling windows and thresholds are the fixed FR-361–FR-366 profile and are not Provider DTO fields.
- **FR-969 — Routing-owned Degradation Policy:** Each Routing Policy value must contain one closed `degradation` projection; no `degradation_policies` registry, anonymous Alias copy, or separate Alias degradation reference exists. Selecting a Routing Policy selects that projection. Degradation evidence identifies it by the Routing Policy Resource ID and Configuration Revision plus a canonical digest of `degradation`; earlier references to a Degradation Policy Resource ID mean this revision-scoped Routing Policy identity. Routing and degradation are published atomically as one resource.
- **FR-970 — Pricing Table DTO:** Each Pricing Table value is exactly `{currency,unit,effective_from,rates,rounding}`. Currency is a three-uppercase-letter ISO 4217 code; unit is the sole literal `per_million_tokens`; effective time is UTC RFC 3339. Rates is exactly `{input,output,cached_input,reasoning_output}`: input/output are required non-negative decimal strings, cached/reasoning may be null, and non-null values use ordinary notation with at most 12 fractional digits, never a JSON number or exponent. Null means no separately known rate and must not cause a guessed discount or hidden-category price. Rounding is the sole literal `half_even_12dp`; calculations use decimal arithmetic and retain partial/unavailable certainty where rates or Usage are unavailable.
- **FR-971 — Minimal v0.1 Safety Policy DTO:** Each Safety Policy value is the closed object `{mode:"provider_refusal_terminal"}`. Gateway normalizes and records Provider refusal/content-filter outcomes and treats each refusal as terminal for retry, fallback, model switching, and cache substitution. The v0.1 policy contains no content-classification DSL, keyword list, Prompt checker, caller override, or external moderation-service configuration. Gateway-native pre-response safety blocking remains a protocol outcome but receives no custom Bundle rule language in this version.
- **FR-972 — Replay Policy DTO:** Omitted `replay_policies` materializes as the closed `{mode:"execution_dedup_only"}` branch, which accepts no other member. The exact-replay branch is exactly `{mode:"encrypted_exact_replay",ttl_seconds,max_artifact_bytes,encryption_key_secret_ref,eligible_results,access_scope}`: TTL and artifact bytes are positive integers within deployment ceilings; the key is a Secret Reference; eligible results is a non-empty, duplicate-free, canonically sorted subset of `sync|stream`; and access scope is the sole v0.1 literal `same_subject`. All exact-replay fields are required, tenant-wide/cross-subject access and caller/Alias/Provider overrides are absent, key bytes never enter the Snapshot, and every change uses the ordinary Candidate/publication workflow.
- **FR-973 — Model Alias DTO:** Each Model Alias value is exactly `{candidates,routing_policy,safety_policy,generation_defaults,structured_output}`. Candidates contains 1–64 closed `{binding,service_level,priority,weight}` objects with unique Binding references; service level is `full|reduced`, priority is an integer 0–65535 with lower preferred, and weight is an integer 0–10000 where zero remains configured but unselectable. At least one full candidate has positive weight. Routing and safety are Resource ID references. It is opaque, not a URL or authorization capability. v0.1 has no dereference API. Future complete queries require fresh authentication, `gateway.audit.read`, and tenant/subject authorization.
- **FR-1004 — Version invalidation scope:** The irreversible database mutation in FR-998 is deferred to v1 with dedicated authorization, idempotent commands, and atomic audit. v0.1 retains the schema fields and defensive checks, planned rotation, protection horizons, and observed SecretSource fail-closed behavior. No API, CLI, manual-SQL workflow, startup file, configuration side effect, or hidden command writes invalidation. SecretSource revocation observation does not itself create irreversible database invalidation.
- **FR-1005 — Indexed expiry selection:** Cleanup uses partial indexes `(expires_at,call_id) WHERE expires_at IS NOT NULL` and `(terminal_at,call_id) WHERE terminal_at IS NOT NULL`. Each batch takes bounded ordered expired candidates from both predicates, merges/deduplicates, sorts by effective expiry then call ID, limits to 1000, and applies skip-locked atomic deletion. Backlog metrics are `expired_backlog_present` and indexed `oldest_expired_age_seconds`, plus selected/deleted counts, failures, and duration; no periodic full-table exact count is required.

- **FR-1006 — Durable retention ceiling history:** PostgreSQL durably records retention ceiling history by effective time. Each Routing Decision remains subject to the strictest ceiling applicable during its lifetime, including any tightening that preceded physical cleanup. Increasing the deployment ceiling affects only newly admitted calls and cannot resurrect older evidence, extend its effective expiry, or discard an applicable historical tightening. The original terminal time, events, and stored expiry remain immutable. Reads, Status availability, cleanup, and backlog observations use the same historical-ceiling calculation; the current-ceiling-only formula is superseded.
- **FR-1007 — Independent Status Evidence lifecycle metadata:** Invocation Status retains minimal internal Evidence lifecycle facts: whether Evidence was successfully established, its terminal time, and original expiry. These facts survive deletion of the Routing Decision aggregate and allow Status to derive `expired` under the applicable ceiling history, while never-established Evidence remains `unavailable`. They follow the independent Status lifetime, contain no Candidate or routing-event copies, and are not returned as timestamps, TTLs, or internal fields to callers. Available still requires retained eligible Evidence; the existing authorization and lifecycle-target rules remain in force.

- **FR-1008 — Atomic ceiling history activation:** Before opening Evidence reads or Data Plane admission, startup commits the configured retention ceiling with a PostgreSQL-assigned effective time and ordered activation sequence. Failure keeps the Gateway non-ready and these paths closed. Restart with the same latest ceiling reuses its activation rather than appending a duplicate. Each new admission durably locks the current sequence; its applicable ceiling is the minimum of that activation and subsequent activations, including tightening while the Invocation is non-terminal. Increases benefit only calls admitted under the later activation and never extend old Evidence lifetime. Status retains the admission sequence with its minimal internal lifecycle facts so deletion of routing aggregates does not lose this association.

- **FR-1009 — First-phase ceiling history retention:** v0.1 retains all committed ceiling activation history in PostgreSQL without pruning or compaction. Evidence aggregate cleanup and independent Status expiry do not remove activation history. Only a changed ceiling creates a new activation; same-value restarts reuse the latest record. History pruning and compaction are deferred to v1 and must preserve every dependency and historical-expiry outcome before being introduced.

## 5. Non-functional requirements

- **NFR-001 — Reproducible performance profile:** First-phase performance acceptance must run one Gateway instance with 4 vCPU and 8 GiB memory against MockTransport or a local deterministic Provider.
- **NFR-002 — Reference load:** The Acceptance SLO Profile must sustain 50 QPS and up to 200 concurrent streams for 30 minutes.
- **NFR-003 — Gateway processing latency:** Under the Acceptance SLO Profile, P99 Gateway Added Latency for admission, routing, policy, translation, and protocol handling must not exceed 50 ms, excluding Provider wait/generation time.
- **NFR-004 — Stream forwarding latency:** After a Provider delta is received, P99 Gateway Added Latency to emit the corresponding external SSE event must not exceed 20 ms.
- **NFR-005 — Internal error rate:** Gateway-originated unexpected HTTP 5xx outcomes must remain below 0.1% under the Acceptance SLO Profile; expected Provider and policy failures are classified separately.
- **NFR-006 — Stream correctness under load:** No stream may lose, duplicate, or emit multiple terminal outcomes under the Acceptance SLO Profile.
- **NFR-007 — Bounded memory:** After warm-up under fixed reference load, process memory must reach a stable bounded operating range rather than grow monotonically without release.
- **NFR-008 — SLO ownership boundary:** End-to-end TTFT, generation latency, and availability must be measured by Provider and Resolved Model. The single-instance first phase does not claim a production high-availability SLA; formal availability targets require a separately accepted multi-instance design.

## 6. Scope and exclusions

The proposed first-phase boundary is summarized in [scope-v0.1.md](scope-v0.1.md); this document remains the complete target requirement set. v0.1 scope includes YAML/API-based Provider and Model Alias configuration, priority- and weight-based routing, permission-controlled Provider Selection Override, streaming forwarding, structured output, request parameter adjustment, usage and cost recording, retry, rate limiting, circuit breaking, failover, and optional degraded-result caching. Prompt management, Tool semantics/execution, Business Budget enforcement, Agent Loop iteration control, agent state, Session, Memory, unrelated platform administration, and multi-instance coordination are outside Gateway. Invocation Cache Policy Snapshot and Invocation Replay Policy Snapshot are internal, single-request admission values and do not introduce Agent Session handling. Reliability limits, resource ceilings, Usage measurement, pricing, and Cost Ledger recording remain in scope. Additional transport, recovery, distributed-operation, budget, and tenant-topology extensions are listed as v1 candidates in the scope document.

## 7. Constraints

- Provider credentials must not be transferred through ordinary Agent Loop/Data Plane requests.
- Existing OpenAI Chat Completions-compatible SDKs must not require a custom transport or caller-side Schema translation to invoke the Gateway.
- Provider-specific SDK objects and response payloads must not become the cross-service protocol.
- OpenAI-compatible DTOs and semantics must terminate at the API Layer and must not become the Gateway's internal domain model.
- The design must preserve explicit failure and uncertain-outcome semantics across the network boundary.

## 8. Success and acceptance criteria

Acceptance must verify protocol behavior, routing policy, failure semantics, streaming events, structured-output validation, and Invocation Evidence. A successful HTTP status alone is not sufficient evidence. The detailed Case IDs and negative evidence live in [test-acceptance.md](test-acceptance.md).

- How should configurable Token, cost, spend, tenant Business Budgets, and any broader Token-consumption estimate be designed after the first phase?
- Should a later routing policy use dynamic projected cost as a ranking dimension, an eligibility ceiling, or both?
- How should a future continuous authorization-revocation channel authenticate, order, reconcile, audit, and cancel in-flight work?
