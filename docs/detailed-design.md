## 1. Preconditions

2026-09-13 scope amendment: [ADR-0148](adr/0148-gateway-owned-basic-prompt-management.md) authorizes Gateway-owned basic Prompt assets/versioning/publication/rendering and supersedes contrary Prompt exclusions below. It does not automatically revive any historic Prompt DTO, engine, fingerprint or lifecycle contract. New public DTOs, tenant permissions, safe rendering, immutable version selection, publication transactions and provenance/fingerprint integration must be designed and tested before API activation. Existing messages input and sensitive-content restrictions remain effective.

Detailed design begins only after the requirements and architecture are approved.

The implementation target for the first pass is the proposed [Initial Scope v0.1](scope-v0.1.md); items marked v1 there are not prerequisites for this design.

## 2. Public protocol

The v0.1 live path is an actual Provider invocation, not a MockTransport-only demonstration: after a published Active Snapshot and runtime Secret resolution, the API request must cross the internal Request Protocol, Router, and HTTP/1.1 Adapter, reach a configured real model, and return a translated result. The minimum live Smoke topology is one Provider, one Model Binding, and one Model Alias. The same implementation supports multiple Providers, fallback, and complex routing, but those branches are independently proven with MockTransport and policy tests. CI uses MockTransport for deterministic protocol and failure cases; a controlled Smoke environment separately verifies the real synchronous path and, where supported, the real SSE path without persisting credentials or raw content.

All first-phase non-standard Data Plane response fields are nested in the top-level `gateway` object. Successful live and cached results include `gateway.requested_model` and `gateway.resolved_model`; standard `model` remains the actual resolved model. No unrelated Gateway response extension appears at the top level or changes an OpenAI-standard field's meaning.

Error-specific extensions instead live inside `error.gateway` in synchronous error bodies and terminal SSE error events. Structured Output `reason`, `path`, and `byte_offset` are contained there; standard `error.code` and `error.message` retain their documented meanings, and error extensions never expose raw Provider/model content.

For a streaming success, `gateway.requested_model` and `gateway.resolved_model` appear only in the first business SSE chunk. Later delta chunks omit the `gateway` object unless another separately documented first-phase extension applies.

A malformed, out-of-order, premature-terminal, or otherwise nonconforming Provider stream normalizes to `provider_protocol_error`. Before the Stream Commitment Barrier it follows the ordinary bounded retry/fallback path; after commitment Gateway emits one terminal error and closes without replacement output or `[DONE]`. This is Provider protocol/quality evidence, not a Provider Health State or circuit signal.

Cached Degraded Results preserve the OpenAI-compatible body and SSE event shapes. The initial HTTP response headers, including a streaming response's headers at the Stream Commitment Barrier, carry `X-Gateway-Result-Mode: cached` and non-negative `X-Gateway-Cache-Age-Ms`; non-cached results omit both. Independently, every reduced-service result carries `X-Gateway-Service-Level: reduced`, while full service omits it. These dimensions compose: cached reduced output carries all three headers. Standard `model` remains the Resolved Model and the existing Gateway model pair remains unchanged. None of these headers carries source identity, Provider detail, degradation cause, Usage, cost, retry, or per-Attempt data. Full provenance and freshness/service-level decisions remain restricted to authorized Gateway-native status and Invocation Evidence. A complete reduced success may be cached under the ordinary policy, but its service-level marker is retained and redisclosed on a later hit.

Cache storage treats `source_service_level` as part of entry identity beside the Execution Fingerprint and existing isolation/policy/profile dimensions. Full and reduced variants coexist and cannot overwrite one another. Once cache degradation is eligible, selection order is fresh full, fresh reduced, stale full, then stale reduced. Reduced entries require the locked policy's reduced-service enablement; every variant independently passes all ordinary key, authorization, encryption-key, revocation, profile, and freshness checks. The chosen variant supplies the composable service-level disclosure.

Population for one complete Variant key is immutable first-complete-write-wins. The non-blocking writer rechecks current encryption-key validity and the Cache Security Invalidation Fence, then atomically creates only when absent; the winner fixes content, provenance, creation/logical time, and expiry. A loser records `cache_write_skipped_existing` without overwrite or TTL refresh and without retry or caller/live-accounting effect. Redis failure similarly receives no retry. An observed corrupt, undecryptable, or revoked value is ineligible and can only be asynchronously compare-deleted by its observed identity; the current result cannot replace it in place, and a later independent invocation may populate after removal.

Cache population and physical cleanup use separate process-local, non-durable queues. The write queue is bounded at 256 tasks and 64 MiB of queued canonical content with worker concurrency four. The cleanup queue is bounded at 1024 tasks and 1 MiB with worker concurrency one; its records carry only a key plus observed identity and no result content. Cleanup receives scheduling priority but is never the logical eligibility or invalidation authority. Each task has one one-second total deadline, including key resolution, cryptographic preparation, and Redis work, and is never retried. A full queue drops the new task as `cache_write_dropped_capacity` or `cache_cleanup_dropped_capacity`; this changes no live result, readiness, Usage, Cost, Health, or Circuit. Write bytes are reserved while queued and released on every exit. Shutdown spends at most two seconds of the existing overall graceful-drain window on these queues, then drops the remainder; restart neither recovers queued work nor scans Redis. Metrics expose only bounded queue depth/bytes, drops, and latency, with no cache key, tenant, model, or other unbounded label.

The cache-population item is a closed immutable memory record containing only the derived cache key, source invocation/result identity, locked cache-policy and connection-profile identity, observed Cache Security Invalidation Fence generation, original logical creation time, absolute expiry, retention-authorized canonical Gateway result bytes, and reserved byte count. Raw requests/messages, Provider wire data, credentials, Secret values, and raw exceptions are forbidden. Encryption begins after worker pickup. Queue time does not consume the one-second worker-operation deadline but does consume the original fixed freshness/expiry window; an expired item is dropped before key resolution or Redis I/O. The worker rechecks current policy eligibility and Fence, resolves only the current cache-encryption key, encrypts, and performs create-if-absent. All exits release the byte reservation and content references. Queued plaintext is absent from telemetry and Evidence; v0.1 makes no physical-zeroization, `mlock`, swap-exclusion, crash-recovery, or process-dump guarantee for language-runtime objects.

The default Docker Compose startup does not start Redis: it starts only Gateway, PostgreSQL, and the one-shot `gateway-migrate` job needed for the live path. An explicit `cache` Compose profile starts the disposable Redis component, but the profile alone never enables cache behavior; the published Active Snapshot must also carry an explicit cache policy. Redis endpoint, transport protection, and its Secret Reference are deployment-owned Bootstrap Configuration in a Cache Backend Connection Profile, while the Active Snapshot carries only cache behavior. Neither callers nor domain YAML bundles can override that connection profile. Changes to the connection profile take effect only at Gateway restart or an explicit Bootstrap reload; mutable connection files are never watched automatically. At admission, Gateway locks the applicable connection profile for the invocation, so a reload affects only later admissions; an already admitted invocation retains its old profile for any cache stage or records `cache_backend_unavailable` if that profile is no longer usable. A cache policy remains publishable when the profile or connection profile is absent; each affected invocation marks the cache stage `cache_backend_unavailable`, records safe Evidence/Metrics, and performs no cache I/O. That disposition is internal-only: it never appears in OpenAI-compatible bodies, SSE events, cache headers, or caller-visible error codes, and operational records omit Redis endpoint, credential, and raw error details. If either the profile or policy is absent, live routing, retry, fallback, readiness, and the real end-to-end path remain unchanged. If both are enabled, Redis is a dependency of the cache stage only; a missing or failed Redis operation returns the exhausted live path's existing classification without a Provider Attempt, hidden queue, or readiness transition. When Redis becomes usable again, a later eligible invocation automatically re-enters the cache stage; the failed cache operation is never retried in place, and no restart or configuration publication is required.

Rotation or revocation of the SecretSource cache-encryption key immediately makes existing entries logically ineligible, including for already admitted invocations whose Invocation Cache Policy Snapshot would otherwise permit the cache stage. v0.1 performs no dual-key read or online re-encryption, and new writes use only the current key; this security exception affects cache eligibility only, leaving Provider work, live routing, readiness, and completed results unaffected. Cache Revocation and key invalidation use one Cache Security Invalidation Fence: a read that started earlier but has not emitted a hit is discarded, later writes are suppressed, and an already emitted cache result is not retroactively withdrawn.

A changed Cache Backend Connection Profile creates a new logical cache namespace for later admissions. Entries are never migrated or read across profiles; old Redis data remains disposable and expires under its prior policy. This namespace boundary does not alter live routing, readiness, or already admitted outcomes.

If the Cache Security Invalidation Fence discards a degradation-stage hit after the live Provider recovery path is exhausted, the presenter returns that path's existing classified terminal result without a new Provider Attempt, retry, fallback, or revocation detail. A live success remains successful when only its optional cache population is suppressed.

At Model Invocation admission, Gateway creates an Invocation Cache Policy Snapshot containing the effective revision-scoped cache-policy reference/status, logical freshness-clock state, and Cache Backend Connection Profile. A later policy disablement or reactivation applies only to later admissions: an already admitted invocation continues to use its locked cache rules for any cache read or write, just as it retains its locked live model rules. The disabled cache DTO remains the member-free branch except for `enabled=false`; PostgreSQL holds the separate Cache Policy Clock State keyed by `(routing_policy_id, cache_material_digest)`, with the digest covering every enabled-cache field except `enabled`. Only successful Active publication changes clock state, atomically with the publication transaction. Enabled D→disabled pauses D; disabled→enabled D resumes its prior logical elapsed time; disabled→enabled E starts E at zero and leaves D inactive until cleanup; an initial disabled projection creates no record. Candidate creation, validation, export, failed publication, rebase, and rollback have no clock effect until a resulting Candidate is actually published. Physical Redis TTL/eviction remains best-effort, so a missing entry is an ordinary miss. Explicit Cache Revocation or cache-encryption key rotation/revocation is the security-invalidation exception: it overrides the locked snapshot for cache eligibility, while not cancelling Provider work or altering a live result, Usage, Cost Ledger, or terminal outcome. A material policy-content identity change also forces invalidation for later admissions. This request-scoped snapshot is not an Agent Session or caller-provided session identifier.

The clock row contains the two-part identity plus `state`, non-negative `accumulated_enabled_ms`, nullable `running_since`, `last_transition_revision`, and `updated_at`. Running requires a UTC microsecond start timestamp; paused requires null. Effective elapsed time adds the non-negative interval from start to observation. Publication locks the Active singleton and affected clock rows, uses one timestamp for Revision publication and every transition, and enforces at most one running digest per Routing Policy. Pausing accumulates the current interval; resuming sets a new start. A backward database-clock step contributes zero and records internal Evidence. The transaction needs no second application row version.

Clock rows are intentionally retained without automatic cleanup in v0.1. Removing a Routing Policy pauses its running material, re-adding the same Resource ID/material resumes it, and rename starts a new identity; Redis loss/expiry and Cache Revocation do not erase timing history. Startup validation never synthesizes elapsed time. A missing, malformed, multiply-running, or Active-inconsistent row marks only that policy's cache stage `cache_clock_state_invalid`, leaves live readiness and routing intact, and is recoverable only from consistent PostgreSQL state or a newly published material identity. No management or runtime database-mutation path is exposed.

To define:

- versioned resource paths and HTTP methods;
- strict JSON request, response, error, and event DTOs;
- content items, opaque compatible Tool fields, output Schema, and model parameters;
- identifiers, idempotency, correlation, and causation;
- synchronous outcome and streaming event contracts.

Gateway-native lifecycle lookup supports four explicit routes: `GET /gateway/v1/invocations/{call_id}`, `POST /gateway/v1/invocations/{call_id}/cancel`, `GET /gateway/v1/invocations/by-idempotency-key`, and `POST /gateway/v1/invocations/by-idempotency-key/cancel`. The API Layer registers both static `by-idempotency-key` routes before the dynamic `{call_id}` routes. Gateway creates every `call_id`; its only accepted external representation is the canonical lowercase, hyphenated UUIDv4 text form of exactly 36 characters. Before creating a Model Invocation or doing Provider work, insertion under the PostgreSQL `call_id` uniqueness constraint may perform at most three UUID generation/insert attempts. Collisions create no Invocation, Attempt, Evidence, or Cost Ledger entry; exhaustion returns HTTP 500 `internal` and increments only a low-cardinality counter without any generated ID label. A dynamic-route selector that is malformed, noncanonical, not version 4, or not lowercase is structurally invalid. A key-based route requires exactly one valid `Idempotency-Key` header and derives the Idempotency Namespace from the current Authorization Context and the fixed original operation identifier `chat.completions.v1`; status and cancel route identities never become `api_operation`. Supplying `Idempotency-Key` to a `{call_id}` route is structurally invalid, so the API never chooses a locator implicitly. All four routes execute one fixed precedence: authenticate and return 401 when invalid; require the exact route scope and return 403 when absent; validate locator/header shape and return 400 `invalid_request`; check Gateway, PostgreSQL, and—only for a key selector—Index Key dependencies and return 503 when unavailable; only then look up, disclose, or mutate the target. For either a valid canonical `call_id` selector or a valid Idempotency-Key selector, no visible retained target—including a target outside retention or namespaced to another tenant/subject—uses one closed, non-disclosing response. Status returns HTTP 200 with the exact JSON body `{"state":"unknown_or_expired"}`; cancel returns HTTP 200 with the exact JSON body `{"state":"unknown_or_expired","cancellation_accepted":false}`. Both use a fresh access-level `X-Request-Id`, omit `X-Gateway-Call-Id`, and add no target, lifecycle, time, model, fingerprint, Artifact, or retention field. Every response from all four lifecycle routes sets `Cache-Control: no-store`, including a found or terminal result and every HTTP 400/401/403/503 response; explicit authentication or authorization failures retain HTTP 401/403 rather than being collapsed into an unknown result.

The Data Plane protocol is versioned under `/v1` with only `POST /v1/chat/completions`; `/v1/models` and every other OpenAI API family are absent in the first phase. Model capability discovery is supplied by authorized Gateway configuration/read-only documentation, not an OpenAI Models endpoint. Gateway-native Control Plane, cancellation, and status protocols are versioned under `/gateway/v1`, including `GET /gateway/v1/invocations/{call_id}` and `POST /gateway/v1/invocations/{call_id}/cancel`. A reverse proxy exposes a separate internal listener or hostname for Control Plane configuration, audit, and privileged operational resources and enforces its route allowlist before Gateway; public Data Plane ingress does not route those resources. Gateway never treats caller-supplied forwarded/internal-marker headers as proof of management ingress. First-phase management ingress does not require mTLS: internal network isolation, proxy enforcement, and mandatory Control Plane authorization are the accepted controls. Status and cancellation are caller-authorized Data Plane lifecycle extensions, not management resources, even though they share the Gateway-native route family. Supported fields are strictly typed; recognized unsupported capabilities return stable errors, and non-namespaced semantic unknown fields are rejected. Gateway-owned error codes remain stable across the documented HTTP mappings and SSE error/cancellation events; `uncertain` status queries return HTTP 200 with state `uncertain`. `Retry-After` is emitted only for bounded retryable rate/provider-unavailable cases with a known window. Correlation uses W3C `traceparent`/`tracestate` plus namespaced Gateway headers for optional business IDs. Every HTTP access returns its fresh `request_id` in `X-Request-Id`; `X-Gateway-Call-Id` appears only when that response contract may disclose an associated Model Invocation. Pre-admission failures and Idempotency conflicts omit it and never substitute the original call in `X-Request-Id`. Default transport ceilings are 4 MiB request body, 32 KiB aggregate headers, 512 messages, 1 MiB per message/content item, 256 KiB output Schema, and 1 MiB decoded SSE event. Opaque Tool fields consume those generic body/content/event and Token/Context budgets without Tool-specific count or definition limits. Byte violations map to HTTP 413 `request_too_large`; count or Token/Context violations map to HTTP 400 `invalid_request`, all before a Provider Attempt. For response compatibility, standard `model` identifies the concrete `resolved_model`; a documented Gateway extension carries both `requested_model` and `resolved_model` in synchronous and streaming responses. A valid Chat Completions refusal remains an HTTP 200 result with `message.refusal` and/or `finish_reason="content_filter"`: transport completes, while the Model Result disposition is `safety_refused`. A pre-response policy block instead uses HTTP 400 and Gateway code `safety_refused`. Before the first SSE event, other failures use ordinary JSON errors; after streaming begins, one Gateway error/cancellation event is emitted and the connection closes. A valid streamed refusal terminates normally with `content_filter` and `[DONE]`; an unrepresentable in-stream safety interruption emits `safety_refused` and closes without `[DONE]`. Streaming disconnects and the versioned Gateway-native cancellation endpoint share one cancellation state transition.

The external field contract is the published `chat-completions-v1` Compatibility Profile, not pass-through. It supports text message roles, stream/include-usage, the accepted generation parameter set, text/JSON-object/JSON-Schema response formats, function Tools, Tool choice/parallelism, and exactly one choice. Deprecated `max_tokens` is an exclusive alias for `max_completion_tokens`; `store=false` is a no-op. Media, custom/allowed Tools, log-probability controls, prediction, Provider prompt-cache/service-tier/moderation/web-search behavior, `store=true`, stream obfuscation, and deprecated functions/function-call/seed are recognized unsupported. Sensitive metadata identifiers require explicit minimization/propagation policy. Unknown upstream additions do not auto-activate. Candidate parameter support is still matched after Schema validation, and profile discovery exposes fields, limits, deprecations, and Gateway extensions. Adoption requires domain, Adapter, test, fingerprint, and compatibility review. The baseline tracks the official OpenAI create-chat-completion contract at https://developers.openai.com/api/reference/cli/resources/chat/subresources/completions/methods/create while intentionally preserving the narrower accepted scope.

Streaming uses a Stream Commitment Barrier. Until a valid ordinary content, opaque Tool fragment, refusal, normal-terminal event, or first normalized Structured Output JSON byte is ready, the API sends no HTTP 200/SSE headers, body bytes, heartbeat, or empty event; Provider protocol-only traffic and suppressed structured wrappers do not establish downstream commitment or TTFT. Structured streaming retains only bounded prefix detection, fence, incremental parser, and suffix/lookbehind state, emits selected JSON bytes immediately, and never buffers the complete document. A pre-barrier failure remains an ordinary JSON error. Crossing the barrier flushes HTTP 200/SSE with the first valid event immediately; for Structured Output that byte is the External Commitment Point and TTFT. A normal empty non-structured result emits a completion chunk with `finish_reason` and then `[DONE]`. After any flush, only the streaming terminal protocol remains available. Final structured uniqueness/JSON/root/Schema failure emits one `structured_output_invalid` error and closes without `[DONE]`; Tool content is never assembled or validated.

`stream_options.include_usage` controls only caller-visible Invocation Usage. Adapters label Provider observations as cumulative or incremental and normalize them so Application can merge each Attempt's monotonic, non-duplicated Usage Measurement. The Invocation Usage aggregator then sums known input, output, cached, and reasoning Token categories across every executed Attempt, including a failed structured Attempt before a successful retry. For both Attempt and Invocation levels, `total_tokens = input_tokens + output_tokens`; cached Tokens remain a subset of input and reasoning Tokens a subset of output, so details never increase the total again. If a Provider total disagrees while both parents are known, the normalized total is recomputed from the parents, the raw total is restricted to safe Attempt Evidence, and a non-terminal Usage inconsistency warning is emitted outside health/circuit accounting. If only Provider total is known, Gateway preserves Partial Total Usage in authorized Evidence, exposes only `state=partial` in the Gateway extension, and omits the standard OpenAI `usage` object rather than guessing parent counts or zeros. Synchronous `usage` and the streaming usage-only summary use the same aggregate eligibility rule. Normal external stream ordering with eligible Usage is deltas, `finish_reason`, one aggregate usage-only summary, then `[DONE]`. Provider-reported counts are authoritative subject to the Usage protocol invariants; a compatible versioned tokenizer may estimate only observable translated input and returned output content. Cached, hidden reasoning, and other Provider-internal details remain `unavailable`, never inferred or zero-filled, and aggregate completeness discloses the limitation. Otherwise the affected parent category is unavailable and zero is never fabricated. Usage may refresh idle progress but does not establish TTFT or content commitment. Each Attempt is measured and priced independently using normalized categories and the locked pricing-table version before invocation aggregation, including failed, fallback, and uncertain Attempts.

Every request contains already-rendered OpenAI-compatible messages and a required standard `model`, interpreted only as a configured Model Alias and locked as the Requested Model. The Application combines that Alias with the validated request's capability and hard-constraint facts to derive its internal provider-independent Service Requirement; v0.1 has no caller-facing or configured `service_requirements` registry. Gateway exposes no `gateway.prompt` selector, Prompt Bundle, template variables, renderer, publication pointer, preview, or Prompt Eval. It validates message protocol shape and generic request/Token/Context limits but does not inspect instruction provenance, inject or reorder instructions, or distinguish template output from conversation content. Prompt identity, versions, defaults, Evals, rendering, replay, and evidence remain in the Agent Loop or a separate Prompt service and correlate through task/turn/step/call/Trace identifiers only. Recovery may change only the concrete Resolved Model within the locked Alias routing contract.

Permission-controlled Provider Selection Override uses `gateway.routing = {provider, mode}` with a configured Provider ID and `prefer` or `require`. Prefer reorders compatible candidates and then retains normal cross-Provider recovery; require filters every Attempt to that Provider while allowing only configured same-Provider retry/model fallback. Neither mode accepts endpoints, credentials, or raw Provider model IDs or bypasses eligibility, safety, health/circuit, egress, admission, deadline, cost, or evidence controls. Authorization precedes Provider lookup, producing non-disclosing 403 for unauthorized use and 400 for an authorized unknown ID. Require-mode cache entries must originate from the same Provider; prefer-mode cross-Provider cache is explicit degradation. Both fingerprints and routing evidence retain the override and outcome.

Effective Generation Parameters resolve Model Alias defaults first and caller-supplied supported values second. Gateway/model/tenant/safety constraints remain hard. Other than the accepted timeout clamp, invalid, conflicting, or out-of-range values are rejected instead of silently changed; recognized unavailable behavior is `unsupported_capability`. Arbitrary Provider-specific options are outside the first-phase Data Plane. Evidence retains parameter sources, decisions, final values, and canonical hash. Gateway replay uses request/execution fingerprints and routing/configuration evidence; exact raw message/output replay requires the approved encrypted retention policy and unexpired TTL, while Prompt replay remains Loop-owned.

The first-phase Data Plane emits no Attempt/Retry count header, retry cause, Provider request ID, or per-Attempt detail in response bodies, SSE events, or headers. Internal Provider Attempt and retry ordinals remain durable Invocation Evidence; Local Structured Repair is recorded separately and creates no Attempt. Validation, authorization, no-route, pre-Attempt admission/rate, configuration/readiness, and pre-dispatch deadline outcomes create no synthetic Attempt. The OpenAI-compatible response body remains the ordinary success or error shape. No ordinary response body, SSE event, or header adds estimated/accrued/reconciled/converted cost. Authorized status, Invocation Evidence, and Cost Ledger surfaces own execution and cost disclosure and always pair cost with pricing version, original currency, rounding basis, certainty/completeness, reconciliation state, and audit policy.

A terminal OpenAI-compatible JSON error body never carries `usage` or Attempt/Retry disclosure, including HTTP 400 `structured_output_invalid` after two failed Attempts. Internal aggregate/per-Attempt Usage and retry/repair history are durably recorded and exposed only through authorized Gateway-native status/Evidence surfaces. A committed stream that emits its terminal error closes immediately; it cannot append a usage-only event after that terminal state.

`structured_output_invalid` is presented as a 4xx input/contract-class outcome: before the Stream Commitment Barrier it returns HTTP 400; after commitment, the one SSE terminal error retains stable code `structured_output_invalid` and a 400 classification although the already-sent HTTP status remains 200. This transport classification does not erase the internal evidence that the returned model content failed the declared contract. It is excluded from Provider availability, Health State, circuit windows, and circuit transitions.

## 3. Domain and application types

Define provider-neutral invocation, attempt, result, failure, uncertainty, usage, receipt, and Structured Validation Failure types. Domain is framework-free. Application owns immutable Commands/Results/Events/Failures and the Ports needed by invocation, streaming, cancellation, status, and configuration-publication use cases. Validation failures carry cause, phase, Schema path, extraction history, commitment state, Retryability Decision, request-retry count, and terminal disposition evidence. `resource_policies.structured_output.local_extraction_enabled` defaults to true. Each Model Alias may only inherit or disable it; effective enablement is global true AND alias not disabled, locked by Requested Model Alias before routing, and unchanged across ordinary transport fallback Providers. Provider binding, tenant, and Data Plane request overrides do not exist. When enabled the local pipeline runs exactly once per Provider output as one fixed pass: BOM removal, one enclosing-fence unwrap, then unique complete JSON extraction. Data Plane callers cannot override stages, order, version, or count; no stage or whole pipeline repeats, and local repair does not create a Provider Attempt. If an allowlisted `json_*` JSON Structure Failure remains before external commitment, the retry policy may create one new same-candidate Attempt with the identical semantic request, using the shared Attempt/deadline allowance and bounded exponential backoff. `schema_mismatch`, `output_truncated`, `structured_resource_limit`, and every post-commit validation failure are non-retryable. All Structured Validation Failures are ineligible for Provider/model fallback. A still-invalid final result returns `structured_output_invalid`; after the first business delta it emits the one terminal error and closes without switching or splicing output. Higher-tier-model repair or regeneration is deferred and absent from the first-phase execution graph.

The internal completion boundary exposes one successful `ModelResult` and one unsuccessful `ModelFailure`. `ModelResult` contains Requested Model, Resolved Model, one discriminated `ModelOutput`, Usage, finish reason, disposition, validation state, and evidence references. The closed first-phase semantic `ModelOutput` variants are `text`, `json_object`, `json_schema`, and `refusal`; Tool-related compatible fields travel separately as bounded opaque payload and have no Gateway Tool domain model. A requested JSON result is successful only after extraction, parsing, resource enforcement, and final local validation. For synchronous success after deterministic extraction, the presenter returns only Normalized Structured Output: pure validated JSON text with wrapper content removed, but without key reordering, type/number coercion, Schema-default insertion, Unicode normalization, or business mutation. Evidence retains the strategy/version and original/result hashes without raw original content by default. Missing or invalid JSON after bounded recovery is `ModelFailure(code=structured_output_invalid)` and is never downgraded to text, null, or a fabricated object. Its stable reason is one of `json_missing`, `json_incomplete`, `json_malformed`, `json_ambiguous`, `json_wrong_root`, `json_duplicate_key`, `json_invalid_utf8`, `json_invalid_unicode`, `json_non_finite_number`, `json_extraneous_content`, `schema_mismatch`, `output_truncated`, or `structured_resource_limit`. `json_invalid_utf8` is byte-decoding failure; `json_invalid_unicode` is an invalid decoded scalar sequence. Schema errors normalize and sort by UTF-8 bytewise `instance_path`, `schema_path`, then reason; parser errors sort by numeric `byte_offset`, then UTF-8 bytewise reason. Sorting is locale-independent and precedes caller selection and Evidence truncation. The outward JSON or SSE Gateway extension exposes the first sorted reason plus either RFC 6901 instance `path` or non-negative UTF-8 `byte_offset`, never both; root path is the empty string. It excludes raw messages, values, model fragments, Schema contents, and further errors. Evidence retains the first 32 sorted normalized entries per Attempt. Entry 33 onward is omitted with `truncated=true` and `total_observed` when known. Published resource policy may lower but not raise 32; callers cannot override it. Caller-invalid Schema maps to `invalid_request`; validator/configuration fault maps to `internal`. `ModelFailure` otherwise carries retryability, commitment and transport-mapping hints, normalized cause, Attempt references, and safe evidence, never a raw Adapter exception. Pydantic owns boundary/envelope validation; specialized incremental parsing, Draft 2020-12 Schema validation, and bounded extraction remain behind replaceable Application Ports. Adapters normalize ordinary Provider transport and result behavior while preserving opaque Tool fields, and API presenters translate outward to the active Compatibility Profile.

Output Schema preflight accepts only JSON Schema Draft 2020-12 profile `json-schema-2020-12-portable-v1`. Omitted `$schema` selects that dialect. The exact allowed keyword set is `$schema`, `$defs`, `$ref`, `type`, `enum`, `const`, `properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `minLength`, `maxLength`, `pattern`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`, `allOf`, `anyOf`, `oneOf`, `title`, and `description`; traversal distinguishes Schema keywords from arbitrary property and `$defs` names. Literal contents under `enum` and `const` are data leaves rather than Schemas, so keyword-looking member names inside them are not traversed. Every Schema or literal object rejects duplicate member names. `enum` contains 1 through 256 values by default and rejects semantic duplicates. `enum` and `const` compare by JSON Literal Equality: object order is irrelevant, array order is significant, strings use exact decoded String Profile values, numbers use Numeric Profile mathematical equality, and primitive types remain distinct. Model-output non-membership is `schema_mismatch`; Gateway never coerces it. `title` and `description` are annotations only: they are preserved for compatible Provider translation and hashing but never assert, default, or inject messages. All other and unknown keywords return `invalid_request` before routing. `$ref` is exactly `#` or a `#/...` RFC 6901 pointer resolving inside the submitted root; named anchors and `$id`/dynamic/external resolution are unsupported. The resolver performs no HTTP, DNS, file, package, registry, or Provider lookup. It builds a normalized local-reference graph, deterministically detects direct and indirect cycles before capability matching, and rejects the first sorted cycle path as `invalid_request`; recursive validation is absent in the first phase. Strings use locked String Profile `unicode-scalar-v1`. JSON escapes are decoded before validation; `minLength`/`maxLength` count Unicode code points, and `pattern`, `enum`, and `const` consume the same decoded scalar sequence. Unpaired UTF-16 surrogates are invalid. Gateway neither normalizes, case-folds, trims, nor counts grapheme clusters, and it preserves the successful output string lexeme and legal escape form. Invalid Schema strings fail preflight as `invalid_request`; model-output scalar failure is `structured_output_invalid/json_invalid_unicode`, distinct from invalid UTF-8 bytes, and follows the existing commitment boundary. The `pattern` keyword uses locked Pattern Profile `re2-portable-v1`: linear-time RE2-compatible syntax, Unicode code-point matching, and JSON Schema substring-search rather than implicit full-string matching. Lookaround, backreferences, conditional expressions, and constructs outside the profile are rejected; each encoded expression is limited to 2 KiB by default and is compiled during preflight. Gateway never rewrites it into a Provider dialect. Candidates incapable of equivalent upstream enforcement are rejected during capability matching, while Gateway local validation remains authoritative. Numeric Schema literals and model-output numbers use locked Numeric Profile `decimal-exact-v1`: strict JSON syntax and bounded arbitrary-precision decimal arithmetic, without a binary-float intermediate. Equivalent lexemes such as `1`, `1.0`, and `1e0` compare by mathematical value, integer type uses mathematical integrality, and `multipleOf` is exact with no epsilon. Gateway performs no rounding, truncation, or numeric coercion and preserves each successful output lexeme. Each token is limited by default to 256 UTF-8 bytes and absolute exponent 1000. Invalid Schema numbers fail preflight as `invalid_request`; model-output overflow is terminal `structured_output_invalid/structured_resource_limit` after the permitted local pass. Combinators use their exact Draft semantics and deterministic declared-array traversal with no discriminator inference or heuristic branch omission. The Schema Evaluation Ceiling defaults to 32 branches in one combinator, 8 nested combinator levels, and 8192 instance-node-by-Schema-node evaluations per final validation. Preflight rejects branch or nesting overflow; runtime evaluation exhaustion is terminal `structured_output_invalid/structured_resource_limit` and observes the same commitment boundary. Preflight also applies the Output Schema Resource Profile: by default 256 KiB encoded size, 64 JSON nesting levels, 32 local-reference edges along any path, and 4096 total Schema nodes. Deployment configuration may change those ceilings, subordinate policies may only tighten them, and callers cannot override them. Structural, literal, String, Pattern, Numeric, or static combinator-limit failures expose the first deterministic safe Schema path, occur before routing, and create no Provider Attempt; the common resource protocol preserves `request_too_large` for whole-Schema encoded byte overflow and uses `invalid_request` for other caller-Schema failures. Successful preflight derives an immutable feature set and hash covering dialect, keyword usage, annotations, literal equality, the acyclic local-reference graph, Schema, String, Pattern, and Numeric Profile versions, effective resource-profile identity, and Schema Evaluation Ceiling; Router capability matching, Provider translation, Execution Fingerprint, and Evidence use that locked identity.

Object Schema Profile permits object-form Schema nodes only; boolean Schema nodes are invalid in the first phase. `properties` and `required` each have a deployment-default limit of 256 entries, required names are unique and must be a subset of the same node's declared property names, and omission of `additionalProperties` has its Draft meaning of `true`. Explicit `additionalProperties` accepts `true`, `false`, or another object-form portable Schema. Local validation ignores object member order but the normalized output preserves it. Gateway never fills missing members, deletes extras, reorders output, promotes optional members, or rewrites a Schema to satisfy a Provider. The Schema feature identity distinguishes open, closed, and Schema-constrained additional properties. Adapter capability registration declares those forms and whether optional properties remain optional; Router records a precise incompatibility reason for a candidate that requires all properties or lacks equivalent enforcement.

Array Schema Profile permits homogeneous arrays only. `items`, when present, is one object-form portable Schema; omission means unconstrained element values within Gateway resource limits, while boolean item Schemas and tuple forms are invalid. `minItems` and `maxItems` are non-negative integer Schema values, maintain `minItems <= maxItems`, and cannot exceed the effective per-array resource ceiling of 1024 items by default. Preflight rejects an invalid or over-limit declaration instead of clamping it. Incremental parsing counts elements independently for each nested array; crossing the effective ceiling produces terminal `structured_output_invalid/structured_resource_limit` after the permitted local pass, without retry or fallback. Validation and presentation preserve element order and never pad, truncate, deduplicate, reorder, or repair a list. Feature identity and Adapter registration separately represent omitted/unconstrained items and one homogeneous item Schema; incompatible Providers are rejected with persisted reasons.

Schema Type Set accepts the seven JSON Schema primitive names as one string or a non-empty unique array. Array order has no semantic or feature-identity effect. An omitted `type` accepts any JSON instance type, and assertions retain Draft applicability—for example, `properties` does not reject a non-object merely because it is present. `integer` uses exact mathematical integrality, so `1.0` qualifies, without changing its output lexeme. No boundary performs type coercion, defaulting, or Provider-specific nullable conversion. JSON Schema Mode permits any accepted root; JSON Object Mode independently requires an object root. Candidate features separately declare arbitrary-root, type-union, and nullable-union support. Router rejects and records an object-root-only or union-inexact candidate and never changes the Type Set to make it eligible.

Output Schema Identity is a versioned three-hash record. The API boundary captures the exact UTF-8 lexical span of the submitted Schema value before DTO normalization and computes unkeyed SHA-256 `raw_schema_hash` for provenance. Preflight emits a deterministic canonical contract and its SHA-256 `canonical_schema_hash`; this is the Schema input to Request/Execution Fingerprints, semantic cache identity, and replay, which retain their independently keyed HMAC construction. A separately canonical routing descriptor produces SHA-256 `schema_feature_hash` for capability filtering and Provider translation. Canonical contract objects sort keys by decoded UTF-8 bytes. Strings use one deterministic JSON escaping without Unicode normalization. Exact decimals encode uniquely as normalized sign plus an unsigned coefficient without leading/trailing zeroes and a base-10 exponent without redundant sign/zeroes; mathematical zero encodes as `0`. The semantically unordered `type`, `required`, and `enum` arrays sort by canonical element bytes after duplicate rejection. `allOf`, `anyOf`, and `oneOf` retain declared order because deterministic evaluation and Evidence use it. Annotations remain included. Validated same-document `$ref` values use their canonical JSON Pointer spelling and are not expanded. Evidence retains all hash algorithms, canonicalization/profile versions, and hashes; ordinary telemetry receives only policy-approved hashes and safe metadata, never a Schema body. Any Provider-specific translated Schema has a separate Attempt-level payload hash and never replaces these identities.

Structured Output Resource Profile is enforced incrementally against the normalized candidate: defaults are 4 MiB UTF-8 total, depth 64, 1024 members per object, 1024 elements per array, 65,536 JSON value nodes, 262,144 Unicode code points and 1 MiB UTF-8 per decoded string or member name, and 256 bytes per number token. Root and every array element/object member value count as value nodes; property names do not. Parser state holds counters and bounded token state rather than the complete stream. Schema bounds outside the effective deployment range fail preflight instead of being clamped. Runtime overflow is terminal `structured_output_invalid/structured_resource_limit` after the permitted local pass. Synchronous processing returns the failure without another Provider Attempt; streamed Structured Output emits one error and closes. Detection stops business-output consumption, requests bounded best-effort Provider cancellation, suppresses later content, and permits only the established late Usage/receipt evidence path. These safety limits are independent of deferred Token/cost Business Budgets.

Incremental validation distinguishes conclusive failure from possible future success. Byte/Unicode decoding, lexical JSON state, duplicate names, and resource counters always advance with the stream. Type becomes conclusive when a value token/container begins; a closed-object unknown key under `additionalProperties: false` is conclusive when its decoded name is known; `maxItems`/`maxLength` fail on the first excess item/code point; numeric assertions wait for the number token; and `enum`/`const` wait for the relevant complete subvalue. `required`, minimum lengths/counts, every combinator result, root uniqueness, suffix legality, and final Schema outcome wait for container/document completion as applicable. A conclusive failure immediately follows the same stop-read/cancel and commitment behavior as a resource failure. If multiple failures arise on one parser transition, only observed normalized failures participate in the existing deterministic sort. Early-stop Evidence sets `stopped_early=true`, `validation_complete=false`, and leaves unknown `total_observed` absent; it never implies all errors were enumerated. Passing prefix state is never success. Only a complete unique JSON value, accepted suffix, completed resource state, and final local Schema validation can emit the normal terminal event and `[DONE]`.

Compiled Schema Cache is an optional in-process weighted LRU with default maximums of 1024 entries and 256 MiB retained memory plus a 30-minute idle TTL. Its composite key is canonical Schema hash, every Schema/String/Pattern/Numeric Profile version, validator/compiler version, and effective resource/evaluation-policy digest. A value can retain the strict parsed tree, canonical bytes, local-reference graph, compiled RE2 programs, validation plan, and feature descriptor. Lookup occurs only after per-request raw-size, lexical syntax, duplicate-key, hash, authorization, and policy checks; the cached canonical bytes/structure are compared after digest match. Digest equality alone never authorizes reuse. Misses and cache failures compile inline, while compilation failure after accepted preflight is `internal` with no Provider recovery. Version changes create misses without explicit mutation; weighted LRU or TTL eviction has no behavior effect. Entry bodies, literal values, and canonical bytes never enter Logs, Metrics, Trace, or debug endpoints. Metrics are aggregate hit/miss/eviction/count/bytes/compile-latency only. The cache is not durable, not Redis-backed, not shared between processes, and is empty after restart.

JSON Object Mode is a narrower syntax/top-level-type contract, not JSON Schema Structured Output. It requires exactly one object, rejects duplicate keys, non-JSON numbers, invalid UTF-8, ambiguous/multiple JSON, prohibited syntax/data mutation, and resource violations, and uses a bounded incremental extractor/parser with final validation at end. Only candidates declaring native JSON object mode are eligible; Gateway does not inject hidden instructions, and JSON wording in caller-rendered messages does not replace capability or local validation. The same fixed pipeline applies to sync and stream. Streaming suppresses BOM, one fence, and prose outside the selected candidate and emits candidate bytes incrementally using bounded prefix/tail state; it never buffers the full object or emits wrapper bytes. Neither path fixes trailing commas, quote/key/delimiter errors, escapes, fields, types, or values. After the local pass, an allowlisted `json_*` failure may create one identical-request same-candidate retry only before the first normalized JSON byte; it never creates different-candidate fallback. A still-invalid result is `structured_output_invalid`, and post-commit failure emits that error with no `[DONE]`. Evidence retains normalized cause, candidate-relative parser offset, extraction strategy/version, retry decision/count, safe hashes/change summary, commitment, and reliability limits.

Tool behavior is outside the Gateway domain. The API accepts compatible `tools`, `tool_choice`, `parallel_tool_calls`, Tool-history, response fields, and stream fragments as bounded opaque payload. Gateway does not parse definitions or arguments, construct or assemble Tool Calls, generate IDs, validate membership/Schema/choice/parallel semantics, repair content, decide whether a required call occurred, execute Tools, persist Tool-specific state, or emit `tool_call_invalid`. Synchronous fields and stream fragments are preserved semantically and in received order through the Adapter and API presenter under only generic framing, size, timeout, backpressure, cancellation, commitment, redaction, and terminal rules. Prompt and Tool management are both Loop-owned. Router checks only the coarse configured ability to transport compatible Tool fields; all Tool interpretation, validation, storage, execution, and error handling belongs to the Agent Loop. Evidence retains at most payload presence/size/hash and coarse capability. Requests carrying Tool fields remain cache-ineligible by default because Gateway cannot prove side-effect safety.

Cross-Attempt structured error presentation is stable. When the first failed Attempt triggers the one JSON request retry and the retry also fails, the API presenter uses the first Attempt's already normalized and deterministically selected reason plus safe path/offset as the Presented Structured Failure. It never replaces or merges that public error with the retry Attempt's reason. Invocation Evidence retains both per-Attempt validation sets, Local Structured Repair outcomes, retry causation, Usage, cost, and terminal relationship.

## 4. Provider Port and Adapters

Active Provider health probes are disabled by default. When explicitly enabled for a configured safe probe path, they remain isolated from user invocations and billing evidence and must not issue billable generation requests.

Application owns the Provider Port, capability contract, optional `resolve_uncertain` evidence-query capability, credential access requirements, and health-signal/probe protocol. The Port provides `complete(request, context) -> ProviderResult | ProviderFailure`, `stream(request, context) -> AsyncIterator[ProviderEvent]`, `cancel(attempt_handle, reason, deadline) -> ProviderCancelResult`, and capability-gated `resolve_uncertain(evidence)`. Complete/stream context carries a Gateway Cancellation Token. Cancel uses a Gateway/Provider identity plus Adapter-opaque handle and returns acknowledged/already-finished/not-supported/unknown/failed without external types. Every Adapter can abort local transport, but only declared trusted remote-cancel support can acknowledge Provider cancellation; connection closure alone is not acknowledgement. Cleanup is bounded by min(two seconds, remaining invocation budget), dispatched once without model retry/fallback/circuit behavior, and late content is suppressed while Usage/receipt/completion enters only the Application late-evidence path. Streaming vocabulary is content delta, opaque compatible payload fragment, Usage, and exactly one completed/failed/cancelled terminal event. Model Adapters are outer anti-corruption layers that implement this Port, contain Provider-specific HTTP/JSON transport mapping, carry Tool fields without semantic interpretation, and translate transport/protocol/internal exceptions before they cross inward. Application retains retry/commitment decisions; the API presenter alone serializes external SSE. Passive health signals from real Provider Attempts are authoritative by default. Configured active probes are optional, isolated from user invocation and billing evidence, and may not issue billable generation requests unless an explicit operational policy enables them. The first generic OpenAI Chat Completions Adapter does not declare uncertainty resolution unless its endpoint supplies a trusted compatible protocol; unsupported resolution preserves `uncertain` rather than guessing or replaying.

Schema capability failure classification occurs at three boundaries. Router rejection uses the locked feature descriptor and creates no Attempt; complete exhaustion is `unsupported_capability`. Adapter translation is a deterministic pre-I/O operation. Inability to exactly encode a selected candidate's declared feature is `adapter_contract_violation/internal`, creates no Attempt, performs no fallback, emits a correctness alert, and marks the affected Adapter/binding degraded in readiness detail. A static configuration with no other validated route for a published service is a configuration/readiness defect; transient Provider reachability, health, circuit, or capacity state never changes overall readiness. A Provider's explicit unsupported-Schema response after I/O is `provider_capability_mismatch`: the sent call is an Attempt, same-candidate retry is prohibited, pre-commit ordered fallback may consume remaining Attempt/deadline limits, and candidate exhaustion becomes `unsupported_capability`. After commitment it only terminates the stream. Mismatch signals feed capability-drift/model-quality evidence, not transient availability circuits, and cannot rewrite the active Effective Capability Set; configuration publication, conformance Eval, or authorized emergency revocation owns correction. If the Adapter cannot safely prove Provider capability rejection rather than its own malformed translation, it fails closed as `adapter_contract_violation/internal`.

Each Adapter type/version publishes an Adapter Capability Contract as its protocol-feature ceiling. A Provider Model Binding declares the concrete model's enabled subset and limits; configuration can only narrow the Adapter contract. Routing uses the immutable Effective Capability Set formed by intersecting those declarations with locked policy. Publication validates all property Schemas, limits, Adapter compatibility, and required version-pinned Capability Conformance Evals, using MockTransport by default. Tool Calling is only a coarse declaration that compatible Tool fields can be transported; no detailed choice, parallel, ID, argument, or Schema guarantee is registered. Runtime failures affect health/quality evidence but never mutate canonical capabilities. An authorized emergency Capability Revocation may make a capability immediately ineligible for new Attempts without rewriting historical snapshots. Evidence retains every source version/hash and effective result. Top-level families remain streaming, Structured Output, and coarse Tool Calling transport; other behaviors are properties.

## 5. State transitions and persistence

The Idempotency Index uses a deployment-owned, versioned Key Ring referenced from Bootstrap Configuration through SecretSource. A process locks one immutable descriptor snapshot at startup: exactly one member is active and at most eight are verification-only, for at most nine members total. Each member is a closed descriptor `{key_id, key_version, role, secret_ref}`. The `(key_id, key_version)` pair and the complete `secret_ref` are each unique within the ring; the same `key_id` may appear at multiple versions. Every reference selects one exact immutable SecretSource version rather than a bundled or moving “current” value. Resolution must return matching identity/version and HMAC profile metadata plus exactly 32 raw bytes; mismatch, implicit latest-version selection, decoding, derivation, padding, or truncation is forbidden.

New admission bindings use only the active member. Every keyed HTTP operation calls the SecretSource Port once through the logical `resolve_many` operation with the active reference and every retained verification reference. The operation has deadline `min(1 second, request remaining deadline)`, permits Adapter-internal parallelism of at most four, performs no retry, and returns either one complete Ring lease or no lease. The process permits at most 32 concurrent Ring leases and never queues above that ceiling. On any member failure or cancellation, the Adapter cancels remaining work, erases all material already obtained, and returns no partial result. Local lease-capacity exhaustion makes only that access `persistence_unavailable` and does not enter Key Lockout; an actual retained-member resolution or validation failure does enter Lockout. Index-key bytes and leases are scoped to that one access, are released on every success/error/cancellation path, and are never shared or cached across HTTP requests; the generic Provider-credential SecretSource cache is not used by this path. Lookup computes the namespace digest under every resolved member using the exact `gateway.idempotency-index/v1` wire form: `ASCII("gateway.idempotency-index/v1") || field(0x01, tenant_id UTF-8) || field(0x02, subject UTF-8) || field(0x03, api_operation ASCII) || field(0x04, idempotency_key ASCII)`, where `field(tag,value) = tag || uint32-big-endian(byte_length(value)) || exact_value_bytes`. No separator or terminator occurs beyond those bytes. It matches the persisted 32-byte PostgreSQL `BYTEA` digest, profile, `key_id`, and `key_version`; neither the digest nor its input values are normalized or exposed. Partial lookup, active-only creation, and unknown-as-miss behavior are forbidden.

One PostgreSQL Idempotency Index protection record is created atomically with admission and stores a namespace-monotonic `generation`, database-derived `binding_expires_at`, and `protected_until = binding_expires_at + key_reuse_quarantine_seconds`, together with the active key identity/version and digest profile. PostgreSQL time determines its phase without an expiry-time write: before `binding_expires_at` it is an Idempotency Binding, from that instant until `protected_until` it is the non-content Idempotency Tombstone, and at/after `protected_until` it no longer protects or identifies the prior invocation. At or after `protected_until`, contenders use one PostgreSQL compare-and-create operation under the namespace uniqueness constraint to replace the expired association with its next generation. Exactly one request establishes the new Binding; every loser re-reads that Binding and applies the new request's ordinary same-Fingerprint duplicate rule or different-Fingerprint conflict rule. The prior invocation remains addressable only by its `call_id`. Cleanup and replacement cannot expose an unprotected namespace interval.

A verification key must remain resolvable while any record bearing its version has `protected_until` later than PostgreSQL `CURRENT_TIMESTAMP`. Rotation neither persists a raw Idempotency Key nor scans/reindexes existing records. v0.1 activates a changed descriptor ring only by Gateway/Docker restart and has no descriptor hot reload, rotation API, or concurrent active-member switch. Startup rejects a supplied ring that omits a still-protected version, and it never automatically evicts the oldest verification key to satisfy the limit.

A missing or malformed Bootstrap Key Ring/member reference, zero/multiple active members, duplicate identity/version pairs or complete Secret References, more than eight verification-only members, or removal of a version whose database-clock `protected_until` has not passed is a static deployment defect and keeps Data Plane admission non-ready. Bootstrap validation reads no secret bytes. During either cold start or runtime, missing, revoked, ambiguous, identity/version/profile-mismatched, malformed, wrong-length, unavailable, or timed-out SecretSource material for any retained member is instead a key-material failure isolated to operations that use `Idempotency-Key`: Chat Completions admission/replay and key-based status/cancel return HTTP 503 `persistence_unavailable`, perform no Provider work, and never reinterpret an indeterminate lookup as a new key. Headerless invocations and lifecycle access by `call_id` continue, and a material outage changes neither `/readyz` nor Provider Health/Circuit state. Exhaustion of the separate process-local 32-lease ceiling has the same request result but is capacity pressure rather than a material failure and therefore does not advance the Fence or enter Lockout.

The process-local monotonic Idempotency Index Security Fence linearizes emergency revocation against keyed work. Gateway can observe revocation through a just-in-time `resolve_many`, a SecretSource metadata check, or a supported SecretSource notification; it does not promise instantaneous detection of an out-of-band change to a file-backed source. Observing either a retained-member revocation or its exact restoration advances the Fence generation, which never decreases. The revocation transition erases every in-memory copy Gateway controls and locks the entire Idempotency-Key path even if active material remains usable. A keyed operation captures the generation and must re-check it immediately before an Idempotency Binding/admission commit, lifecycle/history disclosure, Replay Artifact read or emission, and cancellation mutation. The same synchronization boundary orders a Fence advance against each critical action: if revocation wins, the operation stops as `persistence_unavailable` with no action or disclosure; if the critical action wins, its already completed effect stands. Results started under an older generation cannot clear a later Lockout or pass a later critical guard. Recovery requires an exact-version restoration followed by one successful all-member Ring validation begun after the current Fence; only that current-generation success may recover the Gauge. A Model Invocation whose admission checkpoint committed before the Fence continues under its locked execution state and is not cancelled. Alternatively, after PostgreSQL time passes the revoked version's maximum `protected_until`, a restart may activate a validated descriptor ring without it. Gateway performs no reindexing, key substitution, or unknown-as-miss recovery.

Define accepted, running, cancelling, completed, failed, uncertain, and cancelled transitions together with atomicity, Idempotency Key/fingerprint handling, duplicate replay, status recovery, restart reconciliation, controlled uncertainty resolution, cleanup, and independent retention. On restart/restore, non-terminal accepted/running calls without authoritative Provider terminal evidence become `uncertain` and are never automatically replayed. Privileged resolution requires external evidence, never rewrites the original Attempt, and appends audit data; unresolved uncertainty may expire to `expired/unknown`. Status remains through the Idempotency-Key validity window at minimum; Evidence, Cost Ledger, Trace, and Logs have separate policies. Same-key requests reuse one logical lifecycle; an Uncertain Provider Outcome preserves uncertainty rather than implying duplicate-charge prevention. Expired or invisible key-based lifecycle lookup returns the non-disclosing `unknown_or_expired` state and never re-runs the invocation. Status recovery returns authorized lifecycle/Attempt/Usage/cost and safe-evidence summaries and never decrypts or returns raw content, even when another retention policy permits encrypted content storage.

Cancellation adds durable non-terminal `cancelling`. Explicit API, context cancellation, disconnect, and shutdown expiry use one conditional PostgreSQL transition from `accepted/running`, which reserves terminal ownership before best-effort Provider cancellation. If completion commits first, cancel returns 409 `already_terminal`; if cancellation reserves first, later content is suppressed and the invocation finalizes `cancelled`, with one SSE cancellation event only when the downstream is still writable. Repeat cancellation is idempotent: 202 while cancelling, 200 after cancelled, and 409 for another terminal. Late Provider completion/Usage/billing is appended to Attempt and cost evidence without rewriting the logical terminal, and ambiguous acknowledgement leaves billing uncertain. Restarted `cancelling` becomes uncertain unless trusted evidence resolves it.

Idempotency has two published modes. The default `execution_dedup_only` retains no raw response; when a completed success cannot be reproduced, a same-key Data Plane request returns HTTP 409 `replay_unavailable` with `call_id` and an authorized status-query reference, while the Gateway-native status surface supplies the lifecycle summary. Optional `encrypted_exact_replay` creates a short-lived encrypted Replay Artifact bound to authorization scope, key, fingerprint, call, and protocol version; completed duplicates replay it with `X-Gateway-Replayed: true` and no Provider call. After authorization and fingerprint checks, every same-key/same-fingerprint duplicate or replay resolves the original Model Invocation and reuses its admission-locked snapshots, including the Invocation Cache Policy Snapshot and Invocation Replay Policy Snapshot; it performs no fresh routing, Provider Attempt, or current cache/replay-policy lookup. This remains true after the original reaches any terminal outcome, including `no_route` or `provider_unavailable`; a new execution requires a new Idempotency Key. Normalized SSE replay preserves semantic event order and terminal behavior, not timing. First-phase duplicates never join a live execution or stream: running calls return 409 `invocation_in_progress`. Failed/cancelled/uncertain calls retain their outcome. Artifact expiry during the key window returns 409 `replay_unavailable`, while a different fingerprint remains 409 `conflict`; neither path regenerates. Cache Revocation, Replay Artifact Revocation, and encryption-key invalidation remain authoritative exceptions that can block cache- or replay-artifact reuse, subject to their security invalidation fences. Artifact content is isolated from ordinary evidence and telemetry, which keep metadata and deletion tombstones only.

The `Idempotency-Key` header is optional. Without it, each accepted request is a new logical Model Invocation with no same-key deduplication, replay, or key-based status lookup. Exact-replay content is reachable only by repeating the original `POST /v1/chat/completions` request with the same key and Request Fingerprint; no separate replay/download route or caller-addressable `artifact_id` exists. `stream` and `stream_options.include_usage` are Request Fingerprint inputs, so changing either under the same key is a 409 `conflict` and never converts the response protocol or creates an Attempt. A valid replay preserves the original synchronous/SSE mode and usage-event intent. Idempotency identity is `(Authorization Context.tenant_id, Authorization Context.subject, api_operation, idempotency_key)`; `subject` is the required Stable Authorization Subject, scopes are revalidated separately, and bearer credentials are excluded. Production fails closed as `authorization_unavailable` when the authority cannot supply that subject, while `dev` uses `subject=dev`. Exactly one opaque, case-sensitive header value of 1–255 visible ASCII bytes is accepted; no trimming, folding, Unicode normalization, or duplicate joining occurs. Gateway applies the exact `gateway.idempotency-index/v1` tagged, uint32-big-endian-length-prefixed wire form defined above and computes `HMAC-SHA-256` with a dedicated SecretSource key. PostgreSQL stores the 32 digest bytes as `BYTEA` plus profile, `key_id`, and `key_version`; the digest is absent from APIs and telemetry, raw keys are absent from durable state, and this key is distinct from Fingerprint and content-encryption keys. The admission checkpoint anchors a non-sliding Binding Window: default 86,400 seconds, hard maximum 604,800 seconds. Replay Artifact TTL cannot exceed it and status retention cannot be shorter. When it expires, a non-content Tombstone enforces an additional Key-Reuse Quarantine: default 604,800 seconds, hard maximum 2,592,000 seconds. During quarantine the same namespaced key returns a generic 409 `conflict` exposing only current request identity and no historical call/model/state/time/Fingerprint/Artifact facts; after quarantine it may create a new invocation without restoring any prior state.

Replay Access is a new HTTP access through the original Chat Completions route, not a new invocation: it receives fresh `request_id`, `trace_id`, and an entry span linked by restricted evidence to the original `call_id`, while creating no Attempt, Provider request, Usage Measurement, or Cost Ledger Accrual. It passes normal authentication/authorization and consumes instance/tenant API QPS, but does not acquire Model Invocation or Provider concurrency Permits; a separate lightweight replay-read concurrency ceiling protects Gateway resources. A ceiling rejection is the existing `rate_limited` outcome and does not start Provider work. Exact Replay presenters emit `Cache-Control: no-store`; synchronous and SSE replay preserve the stored protocol, usage-event intent, and response identity, while replayed SSE uses normalized event order without original timing and the ordinary downstream backpressure/progress limits. Only client disconnect or cancellation of that replay HTTP request context ends the Replay Access transfer. The Gateway-native cancellation route targets only a still-running original invocation; if the original is terminal while replay is transferring, it returns `already_terminal` and leaves the transfer and Artifact unchanged. Status returns only authorized lifecycle/Attempt/Usage/cost and safe-evidence summaries; neither surface resolves or decrypts Replay Artifact content.

Before resolving a key or disclosing any lifecycle/content, Replay Access revalidates the current Authorization Context and the original tenant/scope binding. Failure is the normal non-disclosing `401`/`403` path. A publication that disables or restricts `encrypted_exact_replay` immediately revokes existing Replay Artifacts, including those referenced by already admitted invocations; revoked artifacts return `409 replay_unavailable`, physical deletion may be asynchronous, and the revocation never cancels Provider work or changes the original live result, Usage, Cost Ledger, or terminal outcome.

Replay Artifact Revocation, including SecretSource encryption-key rotation or revocation, uses one Replay Security Invalidation Fence. A read that began before the fence but has not emitted a replay is discarded with `409 replay_unavailable`; an already emitted replay is not withdrawn. Old-key artifacts are not dual-read or re-encrypted online, and new artifacts use only the current key.

Replay Artifact Eligibility is limited to a complete successful synchronous result or normally completed SSE event sequence whose content-retention policy permits it. Successful Provider fallback, Local Structured Repair, and an eligible complete Cached Degraded Result may be stored; partial/interrupted streams, failures, cancellations, uncertainty, Structured Validation Failure, and Safety Refusal retain no raw replay content. If an eligible artifact write fails, the live result and its metering remain unchanged, a safe write-failure signal is recorded, the durable Idempotency binding still blocks regeneration, and later same-key content access returns `409 replay_unavailable`.

When the optional `encrypted_exact_replay` policy is enabled, the PostgreSQL Replay Artifact Store is the durable authority for encrypted Replay Artifact content and non-content lifecycle metadata. It uses isolated tables or a logical schema rather than ordinary Evidence, Logs, Trace, or Cost Ledger storage; Redis and optional external object storage are not exact-replay authorities. A Replay Access that cannot read PostgreSQL because persistence is unavailable returns `persistence_unavailable` (HTTP 503 where applicable), without disclosing storage details or starting a new invocation, Attempt, route, or fallback. A confirmed absent, expired, revoked, or retention-ceiling-skipped artifact remains `replay_unavailable`. Before writing, Gateway enforces the published per-Artifact ceiling and deployment-owned retained-content ceiling; a ceiling rejection skips the artifact without truncation, semantic rewriting, or implicit deletion of other artifacts, leaves the completed response and metering unchanged, and records safe evidence. For an eligible SSE sequence, a Replay Capture Cutoff stops normalized capture when either ceiling would be exceeded but does not stop or rewrite the live stream.

The Replay Artifact Commit Boundary is after the terminal transaction: successful result, final Usage, Cost Ledger, terminal Evidence, and Idempotency binding are durable before Gateway returns the synchronous response or flushes the SSE `[DONE]`; a separate bounded Replay Artifact Async Persistence operation then enters a bounded process-local Replay Artifact Write Queue with independent task-count and estimated-byte limits. Tasks are FIFO by terminal-commit handoff time; a retry remains in its original task and does not reserve another slot. Queue saturation drops only the new Artifact write and does not block live execution. A dedicated bounded Replay Artifact Persistence Worker performs writes through a separate bounded PostgreSQL Persistence Pool, without Model/Provider concurrency permits or readiness dependencies. Every task has a bounded Replay Artifact Task Deadline covering queue wait, write, and its one permitted retry; expiry releases reservations and drops the task. The task carries a deterministic, uncompressed Replay Artifact Wire Form, and canonical envelope bytes plus fixed encryption/metadata overhead are the size-accounting basis. The Wire Form is stored in a versioned authenticated-encryption envelope with nonce, key identity, AAD bindings, and integrity metadata; its Content Hash is computed before encryption and verified after decryption. Before the first write, Replay Task Revalidation applies the effective Resource Ceiling, policy constraints, fixed expiry, revocation state, and security fence; a stricter or revoked state drops the task. A write failure, timeout, queue loss, or restart never rolls back the live result or permits a new Provider execution. A duplicate while the asynchronous write is pending returns `replay_unavailable` and does not join the write. A transient PostgreSQL or network failure permits one additional bounded persistence attempt with jitter; immediately before it, the Replay Persistence Retry Gate rechecks fixed expiry, policy constraints, revocation state, and the current security fence. Policy, authorization, serialization/integrity, size/retention-ceiling, capacity/quota, and SecretSource contract failures do not retry. Each write uses immutable `artifact_id`/`call_id` idempotency and can only confirm or complete the same content after an unknown outcome. If the immutable key exists with a different content hash, the first record remains unchanged and the new write returns `persistence_unavailable` without retry. Exact Replay preserves the original response/event protocol and semantic identity, including the stored OpenAI identifiers and model fields, while the Replay Access request retains fresh request/Trace identity and only adds the replay marker. PostgreSQL cleanup makes expired or revoked content physically removable asynchronously after persisted markers have already made it logically ineligible; cleanup delay, restart, or failure does not affect readiness or live behavior. Artifact writes are all-or-nothing and Replay Access reads only complete committed records. A partial, integrity-failed, or undecryptable record is a Replay Artifact Integrity Failure and returns `persistence_unavailable`; a confirmed absent or policy-ineligible record returns `replay_unavailable`.
After ciphertext becomes expired or revoked, cleanup may delete it asynchronously but retains a minimal non-content Replay Artifact Tombstone (immutable identity, status, fixed expiry, policy/revocation epoch, and safe reason) at least until the original Idempotency Binding expires; an explicit longer key-reuse quarantine may extend it. No plaintext, Wire Form, Prompt, Provider payload, or usable key material remains. Replay Access performs a final Replay Access Fence Check after decryption/integrity verification and before its first downstream byte; a pre-emission invalidation returns `replay_unavailable`, while an already emitted access finishes without rollback. Replay Key Failure Isolation keeps SecretSource lookup, key-format, and key-version failures out of readiness, Provider Health, Circuit state, permits, fallback, and live metering.

Replay Artifact expiry is an absolute deadline derived from the original successful terminal-commit time plus the effective TTL; Replay Access and delayed persistence never slide or reset it. A material exact-replay policy tightening (TTL, per-Artifact size, eligible result type, or access scope) immediately invalidates existing Artifacts that fail the new policy, while non-semantic metadata changes do not. A deployment retained-content limit change constrains later writes but is not retroactive policy invalidation. PostgreSQL capacity or quota pressure is an Artifact-write failure only: valid existing Artifacts remain readable, no implicit eviction/revocation occurs, and readiness, Provider work, live results, and metering remain unchanged.
The same Replay Security Invalidation Fence linearizes material policy tightening and encryption-key revocation. Reads begun before the fence but not emitted are discarded, writes after the fence are suppressed, and emitted replays are not withdrawn. A policy expansion applies only to future writes and still-valid compliant Artifacts; it cannot resurrect missing or invalidated content or reset an existing expiry. An exact-replay policy must explicitly provide TTL, encryption Secret Reference, a per-Artifact ceiling, eligible result types, and access scope before publication; missing values are validation failures rather than implicit defaults. Retained-content capacity remains a deployment hard ceiling and is not duplicated in the policy Snapshot.
At Model Invocation admission, Gateway captures an immutable Invocation Replay Policy Snapshot containing the published mode and all effective retention, encryption-key identity, eligibility, ceiling, and access-scope values. Same-key reuse resolves this snapshot rather than the current policy; the security fence may still override its replay eligibility. If SecretSource cannot provide the current key during Artifact write, the write is skipped as a persistence failure; if a referenced Artifact cannot obtain its key during read, Replay Access returns `persistence_unavailable` without key fallback or Provider execution. The policy object and its version/digest are part of the canonical PostgreSQL Active Snapshot and publication audit, while secret values remain only in SecretSource.
Candidate validation checks the Exact Replay Secret Reference and all policy constraints locally; it never resolves or decrypts the referenced key. The Exact Replay policy and Replay Artifact Revocation epoch are committed together in the PostgreSQL publication transaction, and only a successful commit advances the in-process policy snapshot and replay fence. `execution_dedup_only` still records a mode-bearing replay snapshot, so later policy enablement cannot add content retention to an already admitted invocation.

Replay Artifact uses a versioned AES-256-GCM envelope, with Content Hash format `sha256:<64 lowercase hex>` computed over canonical pre-encryption bytes and verified after decryption. AAD is a versioned canonical UTF-8 map of the fixed `artifact_id`, `call_id`, tenant/scope, Idempotency Index Digest plus its profile/key identity, Request Fingerprint, protocol version, and Replay Policy/Key identity fields; the raw Idempotency Key is absent and callers and Providers cannot add fields. Each Artifact read or write performs Replay Key Resolution just in time; key bytes live only in ephemeral operation memory and never in PostgreSQL, Redis, configuration, telemetry, or a process-wide cache. SecretSource returns an immutable key identity/version and exactly 32 raw AES-256 bytes; malformed, missing, or ambiguous material is non-retryable. Rotation/revocation advances the Replay Security Invalidation Fence, so the Worker drops queued old-key tasks before writing and never re-encrypts or performs dual-key reads; live results remain unchanged.

Idempotency and execution identity use separate digests. Request Fingerprint is produced after API normalization but before mutable Gateway resolution and covers caller intent, including the canonical already-rendered message hash, opaque Tool-field hash, and semantic timeout fields, while excluding credentials, correlation, transport ordering, and client-only wait settings. Same-key conflict uses this fingerprint, so later Gateway configuration publication does not change the original binding. Execution Fingerprint is produced after admission from the behavior-affecting projection of the locked snapshot, model/parameter/output-Schema decisions, canonical message hash, opaque Tool-field hash when present, and policy decisions; raw snapshot revision/digest and non-semantic labels remain Evidence but are excluded when behavior is unchanged. Cache and replay/audit evidence use the Execution Fingerprint plus independent authorization/policy isolation. Both fingerprints use versioned deterministic canonicalization and keyed HMAC-SHA-256. Key versions remain verifiable until dependent records expire or are revoked, and key material remains in SecretSource.

Lifecycle advancement uses required PostgreSQL Persistence Checkpoints. In the atomic Admission Checkpoint statement, Gateway performs the final credential-expiry comparison against PostgreSQL `statement_timestamp()`; admission is allowed only when `Authorization Context.expires_at > statement_timestamp()`, and equality is expired. Failure returns HTTP 401 `unauthorized` without creating a Model Invocation, Idempotency Binding, Attempt, Invocation Evidence, or Cost Ledger entry and without Provider work. A successful Admission Checkpoint atomically writes the invocation shell, identity/idempotency binding, locked references, locked Authorization Context, and `accepted` state before any Attempt. Its credential expiry is never rechecked for that invocation, so queueing, synchronous generation, and SSE may cross the Instant; a later status, cancel, or Replay HTTP access authenticates afresh. Each Attempt is durably started before upstream I/O, and its outcome plus recovery decision is durable before another Attempt. The External Commitment Point is written before the first downstream business event. A terminal transaction writes final state, Usage, Cost Accrual, validation, and evidence before synchronous success or `[DONE]`. Deltas and raw content are not persisted by default. Any checkpoint failure after possible Provider execution stops recovery and maps to `persistence_unavailable`; pre-barrier requests receive HTTP 503, committed streams receive one error event, and the invocation remains potentially billed/uncertain. PostgreSQL loss stops admission, and existing calls may advance only to their next checkpoint. Recovery classifies durable non-terminal records as uncertain rather than replaying them.

## 6. Reliability

Provider Circuit state, counters, and samples are process-local runtime state. Gateway restart initializes every configured circuit as `closed`; PostgreSQL stores historical transition evidence but never live circuit counters or samples.

Cache writes use one generic rule: a normally completed, non-exception result is a candidate only when the active cache policy accepts it. Direct success, successful permitted Provider/model fallback, successful Local Structured Repair, and successful bounded identical-request retry are equivalent for write eligibility; failure, cancellation, `uncertain`, expiry, partial completion, incomplete validation, or Safety Refusal never writes. A cached fallback result retains its actual `resolved_model` and degradation provenance. Existing Tool/side-effect, tenant/policy, retention, semantic-key, and version restrictions still apply. Structured Output has no separate cache-write policy. A cache hit creates no Provider Attempt, Provider Usage Measurement, or Cost Ledger Accrual. The Data Plane omits `usage` in synchronous and `include_usage` streaming responses; authorized Invocation Evidence records the cache hit and source invocation identity, while source metering remains on its original live invocation.

Cache is a degradation-stage lookup only. Gateway first exhausts the live routing, bounded retry, and permitted fallback path for the requested service. Only then may an active Degradation Policy select an eligible Cached Degraded Result. Cache availability never changes live candidate selection, and unavailable or ineligible cache state never blocks live routing.

Cache selection is limited to exhausted Provider availability/capacity recovery: retryable upstream connection, timeout, 429, retryable 5xx, or circuit/health unavailability. It is never a bypass for authentication/authorization, caller request or Schema validation, configuration/readiness, Safety Refusal, Structured Validation Failure, cancellation, `uncertain`, or any other non-availability outcome.

Cache stores only the complete terminal result. For an eligible streaming cache hit, Gateway translates that result into the ordinary ordered SSE completion subject to normal event-size and backpressure limits. It does not retain or simulate Provider chunk boundaries, Provider TTFT, or generation pacing.

The cache key is a versioned canonical representation of the effective result contract, not merely the raw request. It includes the logical model/service, canonical effective generation parameters, response format, Output Schema, canonical message hash, and existing authorization/policy/configuration isolation dimensions. Any result-affecting effective-parameter difference is a logical cache miss.

Cache population is non-blocking after a completed live result. A Redis write failure preserves the live response and all of its normal Usage, Cost Ledger, retry/fallback, and Provider-health outcomes; Gateway records only safe failure evidence and Metrics, and a later invocation sees an ordinary cache miss.

If Redis cannot be read in the degradation stage, Gateway does not retry the cache or create a new Provider Attempt. It records safe cache-read failure evidence and Metrics, leaves Provider Health State unchanged, and returns the already classified terminal result from the exhausted live path.

Cached response content is an explicit content-retention exception, not ordinary telemetry. Cache enablement requires the applicable retention-policy authorization; Redis uses authenticated encrypted transport and values use application-layer encryption with SecretSource-managed keys. Missing, revoked, or unusable encryption material makes the entry ineligible or skips non-blocking population, never changes a completed live result, and never exposes plaintext in ordinary Evidence, Logs, Metrics, or Trace.

Define deadline propagation, timeout, cancellation, retry ownership, fallback ownership, rate limiting, circuit breaking, backpressure, uncertain-effect behavior, and the complete Degraded Outcome taxonomy. Caller deadlines are clamped/defaulted into one monotonic-clock remaining limit shared by queue, retry/backoff, Provider, repair, and fallback work; fallback never resets it. These reliability limits and Gateway Resource Ceilings are not Business Budgets. Configurable Token, cost, spend, and tenant quota enforcement is deferred; Usage measurement, pricing, and append-only Cost Ledger recording remain active. The execution order is validation and admission, snapshot lock, capability filtering, security/health/circuit filtering, policy ranking, Provider Attempt, failure classification, bounded same-candidate retry, remaining-candidate fallback, explicitly allowed reduced-capability/cache degradation, then terminal outcome. A failover-only disposition may skip same-candidate retry. Each Attempt updates runtime health/circuit state before remaining candidates are reevaluated, while preserving the locked snapshot, shared reliability limits, and prior candidate evidence. The design must cover pre-commit Provider fallback, explicit terminal failure, policy-controlled Cached Degraded Results, and reduced-capability models, including their ordered Degradation Policy, opt-in contract, freshness/capability disclosure, evidence, cache/side-effect rules, and post-commit restrictions. Cache eligibility uses two configured windows: `fresh_ttl` and opt-in `stale_ttl`, with stale disabled by default. Versioned semantic keys provide normal logical invalidation, while audited revocation markers make emergency invalidation immediate even if Redis deletion is asynchronous. Static circuit and rate-limit policy comes from the published configuration snapshot; live counters and state are runtime-managed and emit transition evidence. Passive Provider health is based on real Attempts; optional active probes use independent operational limits and do not enter user-call usage/cost accounting. Concurrency limits at instance, tenant, and Provider scopes are primary; QPS is supplementary. First-phase admission rejects on a full limit; pool switching is deferred. Retry has finite attempt, delay, and deadline limits; exhaustion enters an explicitly configured Degraded Outcome or terminal failure and never silently presents a substitute as the requested full result. Crossing the External Commitment Point skips every remaining recovery/degradation stage. Client cancellation and shutdown drain terminate work as `cancelled`; deadline exhaustion terminates as `failed/deadline_exceeded`; all stop further retry and failover.

Router order is deterministic and staged. Hard filters first remove capability/Tool/Schema, override, authorization/safety/egress, health/circuit, and Provider capacity/rate failures with specific reasons. Remaining candidates form ascending integer priority tiers. Each tier receives one seeded weighted-without-replacement permutation: positive weights participate, zero disables, and invalid weights block publication. Same-candidate retry precedes the next ordered candidate; a tier is exhausted before the next. Projected cost is calculated from input plus effective maximum output and the locked pricing basis for evidence and operator policy authoring; unavailable inputs are reported as unavailable, never zero. First-phase routing performs no projected-cost ceiling, cost quota, or `cost_unknown` rejection. Operators may encode pricing preference in published priority and weight; dedicated dynamic cost-aware ranking is deferred. The versioned keyed seed derives from `call_id` plus the Routing Policy Resource ID and Configuration Revision. Dynamic state is reevaluated before each Attempt and may skip a candidate without changing the original order. Provider-binding saturation may fall through to another candidate while instance/tenant permits remain held; total capacity exhaustion returns rate limiting without queueing.

Streaming Downstream Backpressure uses a per-stream queue capped at 64 events and 4 MiB serialized bytes, with a ten-second monotonic no-progress timeout. Reading pauses upstream when possible; non-pausable transports receive no larger buffer. Queue/timeout breach becomes `client_too_slow`, separate from the 30-second Provider `upstream_timeout`. Before commitment an unwritable caller enters cancellation without recovery; after commitment the Gateway sends one error event only if writable, otherwise closes, then follows Provider cancellation with no `[DONE]` or replacement output. TTFT ends at successful downstream flush. Permits remain held through cleanup and terminal persistence, while evidence and low-cardinality metrics capture only queue sizes, timings, discarded counts, and cancellation outcome.

`X-Gateway-Timeout-Ms` supplies a relative timeout. The default Invocation Deadline Budget is 120 seconds and the deployment maximum is 600 seconds. Queueing is bounded by min(2 seconds, 10% remaining), Provider connect by 5 seconds, first business delta by 60 seconds, and stream business-idle time by 30 seconds; heartbeats do not refresh progress. Connection/first-delta/idle timeouts classify as `upstream_timeout`, while total-budget exhaustion is `deadline_exceeded`. All nested operations consume the same monotonic budget. Shutdown drains for 30 seconds and then cancels remaining work without replacement execution.

The first-phase Provider Attempt Budget has a hard ceiling of three total Attempts and one retry after the initial Attempt for any one candidate; Routing Policy may tighten those values. The default backoff uses a 200-ms base, multiplier 2, full jitter, and a 2-second calculated-delay cap, while the closed Routing Policy may tighten within FR-975. A trusted `Retry-After` is honored only within the configured 0–5-second ceiling and remaining deadline; otherwise the candidate is skipped rather than retried early. Retryable causes are 429, transient connection failure, explicitly retryable 5xx, and the separately constrained allowlisted pre-commit JSON Structure Failure after Local Structured Repair fails. The JSON exception uses the same backoff and allowance but never fallback. Other non-retryable causes and the External Commitment Point prohibit retry. Exhaustion proceeds only through stages allowed for the classified cause; Structured Validation Failure terminates without reduced-capability or cache substitution.

Retryability Decision is the only authorization for a same-candidate request retry and never carries a request mutation. After bounded Local Structured Repair fails, an allowlisted pre-commit `json_*` JSON Structure Failure may yield `retryable=true` once; it uses the same bounded exponential-backoff mechanism and shared candidate/Attempt/deadline allowance as other retries. `schema_mismatch`, `output_truncated`, `structured_resource_limit`, and post-commit failures yield `retryable=false`. Every Structured Validation Failure remains `failover_eligible=false` and cannot advance to another Provider/model. Messages, canonical Output Schema and identity, output mode, parameters, Requested Model contract, safety/policy state, snapshot, and Execution Fingerprint remain immutable. No hidden repair instruction, parameter tuning, Schema reduction, required/optional conversion, root/type change, mode downgrade, or higher-tier-model escalation exists. A request retry receives a new Attempt and Provider request identity; an authorized transport fallback translates the same internal contract exactly through the next Adapter. Provider idempotency is used only under a trusted documented generation contract and cannot remove the Gateway's duplicate-execution/billing uncertainty. Evidence retains classification, local-repair outcome, reason allowlist decision, calculated/capped delay and jitter when applicable, remaining deadline, Attempt relationship, and identical semantic-request hash. Advanced Structured Recovery is explicitly deferred and requires a future separately designed opt-in workflow.

Each `provider_binding_id` has a single-instance Provider Circuit. Rate evaluation uses up to the 20 most recent eligible Attempts from the previous 60 seconds and requires 10 samples; a 50% qualifying failure rate or five consecutive qualifying failures opens the Circuit. Connection, timeout, 429, and retryable 5xx count; caller, auth/config, Safety Refusal, and Schema/validation outcomes do not. Open duration starts at 30 seconds. Half-open allows one concurrent trial and requires two consecutive successes to close; any failure reopens with doubled duration capped at 5 minutes. Closure resets the duration. Optional active probes may serve as trials under their separate budget. All transitions and Router rejections retain explainable evidence.

Admission Permits default to 200 concurrent Model Invocations per instance, 50 per tenant, and 20 active Provider Attempts per `provider_binding_id`. Invocation permits remain held for the complete synchronous or streaming lifecycle; retry/fallback transfers only the Provider-binding permit. First-phase queueing is disabled by default, so a full limit returns 429 `rate_limited`. Supplementary token buckets default to 100 instance QPS and 50 tenant QPS, while Provider QPS is required published configuration. QPS cannot override concurrency. All exit and exception paths release permits exactly once, and `Retry-After` appears only when refill/release timing is meaningfully bounded.

## 7. Security

Bootstrap resolution selects exactly one authorization topology: `dev_bypass`, `local_jwt`, or `online_authority`; multiple Authorities, authentication chains, fallback, and degraded authorization are invalid. If source configuration omits `startup_profile`, it resolves to `dev`; if the effective profile is `dev` and omits `authorization.mode`, that mode resolves to `dev_bypass`. An effective `production` profile must explicitly select `local_jwt` or `online_authority` and cannot use `dev_bypass`; `online_authority` has no development transport form. Shipped Docker examples explicitly spell both the profile and authorization mode even where they equal defaults, and both resolved values enter the canonical Bootstrap digest.

The `local_jwt` Bootstrap variant is closed and contains only its mode, one read-only mounted local public-key file and selected PEM/JWKS form, the exact Issuer and target Audience, and a PEM-only explicit Key ID. Inline key material, environment-variable key material, URL/remote retrieval, and SecretSource resolution are forbidden. Gateway reads the file once during startup and retains the validated public representation for that process lifetime; file replacement has no effect until restart. The file is at most 256 KiB. PEM contains exactly one SPKI or PKCS#1 RSA public-key object and rejects a certificate or any additional PEM object. JWKS contains at most 32 keys and derives trust only from RSA `n` and `e`; bounded certificate metadata may be ignored but cannot establish trust. Every configured `kid` is unique and 1–128 visible ASCII bytes, and PEM obtains its mandatory `kid` from Bootstrap. Optional JWK `alg`, `use`, and `key_ops` must respectively be `RS256`, `sig`, and exactly `["verify"]`. The v0.1 algorithm allowlist is exactly `RS256`, with RSA modulus size from 2048 through 4096 bits. A missing or unknown Token `kid` or Token Header algorithm other than exact `RS256` is HTTP 401. Duplicate Key IDs, private key material, remote key locators, HS/EC/OKP/`none`, unusable public parameters, inconsistent `alg`/`use`/`key_ops`, and reliance on certificate metadata are startup defects that keep admission non-ready. Remote JWKS retrieval, online key rotation, and background JWKS refresh are deferred to v1.

Authorization is fail closed and preserves an internal reason while keeping the public taxonomy stable. In production, API parsing requires exactly one original `Authorization` Header and never joins duplicate field lines or comma-separated credentials. The scheme is case-insensitive `Bearer`, followed by exactly one ASCII SP and one 1–16,384-byte ASCII `token68` value. Missing Header, duplicate Header, comma joining, leading/trailing OWS, controls, non-ASCII, zero/multiple separator spaces, invalid token68 grammar, and length overflow are HTTP 401. `dev_bypass` ignores the Header without parsing it. Every authentication 401, including an online `unauthenticated` decision and expiry at the final Admission Checkpoint, carries exactly `WWW-Authenticate: Bearer`; the public error body retains stable `unauthorized` and discloses no normalized internal cause.

A normalized immutable Authorization Context has required `subject`, `tenant_id`, `scopes`, `issuer`, `audience`, `expires_at`, and `authentication_method` fields. `subject` and `tenant_id` are opaque UTF-8 strings of 1–255 bytes, `issuer` is an opaque UTF-8 string of 1–2048 bytes, and `audience` is the one logical Audience the selected Adapter actually matched, represented as an opaque UTF-8 string of 1–255 bytes rather than an unmatched input list. All Context strings reject control characters and leading or trailing whitespace; Gateway never trims, changes case, or performs Unicode normalization. `expires_at` is a UTC Instant. `authentication_method` is exactly `dev_bypass`, `local_jwt`, or `online_authority` and records the verification path, not the presented Token type. `tenant_id` is retained for correlation and Idempotency Namespace isolation; broader tenant modeling remains deferred. The required `scopes` field may validly contain an empty set. Any local-JWT Token, signature, Header, algorithm, `kid`, Claim mapping, issuer, audience, temporal, Context-string, or scope-format failure is caller authentication failure and returns 401. An online decision envelope with `status=unauthenticated` is likewise 401 and carries no identity. Authority transport/resource/protocol failure is `authority_dependency_unavailable` and HTTP 503 `authorization_unavailable`; it sets the Live Fault Latch. Only a closed, protocol-valid `authenticated` result that cannot form a valid normalized Context is request-local `authorization_context_contract_invalid` and HTTP 503; it does not close the Probe Gate or set a live fault, but the underlying valid HTTP 200 decision may clear an older Live Fault Latch. A valid Context lacking the exact route permission is HTTP 403 `forbidden`. Gateway does not retry authorization failures, emits no `Retry-After`, performs no cache lookup, lifecycle/configuration disclosure, admission, or Provider work, and never updates Provider Health/Circuit state. An Adapter registration, Bootstrap mapping, local Key Set, required-Claim mapping, or topology that can be proven incapable of satisfying the contract at startup is instead a static configuration defect and keeps Data Plane admission non-ready.

The local JWT Claim contract is fixed. Required Claims are string `sub`, string `tenant_id`, string `iss`, string-or-duplicate-free-string-array `aud`, and integer NumericDate `exp`; integer NumericDate `nbf` and `iat` are optional, and `scope` is optional. `iss` compares exactly with the Bootstrap Issuer. `aud` must exactly contain the one configured target Audience, which alone becomes Context `audience`; other array members do not enter the Context. `scope` accepts either the standard U+0020-delimited ASCII token form or a string array; an absent Claim yields an empty immutable set, while malformed members return 401. Unknown Claims are ignored. The common Context string and scope profiles apply after mapping, and failure remains part of local authentication rather than becoming a post-success Adapter contract failure.

JWT time evaluation uses one fixed 30-second leeway. It requires `now + 30s >= nbf` when `nbf` exists, requires `iat <= now + 30s` when `iat` exists, and defines effective expiry as `exp + 30s`; that effective Instant is written to Context `expires_at`, and equality is expired. v0.1 does not impose a separate maximum Token lifetime. The Parser accepts only three unpadded canonical-Base64url JWS Compact segments and at most 16 KiB of encoded Token, 4 KiB of decoded protected Header, and 12 KiB of decoded Payload. Header and Payload must be strict UTF-8 JSON objects. Duplicate members, non-finite numbers, `crit`, `zip`, embedded `jwk`, `jku`, and `x5u` are invalid. `typ` is optional and, if present, is exactly `JWT` or `at+jwt`. Every such Parser or Claim failure returns 401 with the common Bearer challenge, creates no Provider work, and does not affect Provider Health/Circuit state.

`online_authority` is a versioned, generic HTTP JSON introspection/context Adapter valid only under the production startup profile. It converts a presented credential into the normalized Context and classifies unauthentication, Context-contract failure, or dependency/protocol failure; it does not authorize Gateway routes. Its closed Bootstrap branch contains the mode discriminator plus exactly `live_endpoint`, `probe_endpoint`, `authority_id`, `live_service_token_secret_ref`, `probe_service_token_secret_ref`, and a non-empty list of canonical CIDR Authority allowlist entries. The endpoints have distinct fixed paths on the same exact origin, and a request can override neither. HTTPS with TLS 1.2 or newer, mandatory certificate-chain and hostname verification, and the dedicated Authority allowlist are unconditional. Userinfo, query, fragment, redirects, configured/environment-discovered proxies, HTTP, loopback or private destinations, and all development transport exceptions are rejected. Every new connection resolves DNS again and requires every returned address to pass the allowlist; one disallowed address rejects the mixed result before connection. Product-specific authorities integrate behind that Adapter contract directly or through a sidecar. Gateway stores no user, role, group, or policy lifecycle. Stable `subject` semantics across credential refreshes are an Adapter responsibility and are verified by a required pair of conformance fixtures representing the same principal before and after refresh. At runtime Gateway checks only the normalized subject's frozen field contract, persists no principal-correlation map, and does not attempt to detect identity drift. If an Adapter later emits a different valid subject, Gateway treats it as a different principal and therefore a different Idempotency Namespace.

Live introspection sends `POST` with `Content-Type: application/json`, `Accept: application/json`, no request compression, and a strict UTF-8 closed object containing exactly `protocol_version="gateway.authorization.introspection/v1"`, `credential_type="bearer"`, and `credential`. The API Layer removes only the already-validated Bearer scheme and its one ASCII SP; `credential` is the remaining raw token68 Token with no trimming or normalization. Duplicate or unknown request members are impossible at the outbound boundary. After the operation deadline begins, each live or Probe operation resolves its configured service Secret exactly once. SecretSource must return one distinct raw 1–16,384-byte ASCII `token68` with no scheme: one or more alphanumeric/`-._~+/` bytes followed only by optional trailing `=`. The Adapter rejects whitespace, controls, non-ASCII, comma, internal `=`, and every other byte rather than trimming, splitting, decoding, padding, or normalizing, then constructs exactly `Authorization: Bearer <service-token>`. Plaintext service Tokens are not cached or reused across operations, and the operation-scoped Credential Lease is erased on every exit. Authority 401/403 therefore invalidates that lease, receives no same-request retry, and causes a later operation to resolve its reference again.

Live and Probe own separate HTTP/1.1 pools. Live permits at most 64 simultaneous operations and Probe exactly one; neither pool has a hidden acquisition queue, and they share no connection, credential, or permit. Each operation has one total deadline—`min(2 seconds, request remaining deadline)` for live and two seconds for Probe—covering its Secret resolution, pool acquisition, DNS, connect, request write, and response read. All HTTP-library retries are disabled. Both pools use a fixed 30-second idle timeout and five-minute maximum connection lifetime. A connection at either bound accepts no new acquisition; every replacement connection re-resolves DNS and validates every address against the locked allowlist. Caller cancellation cancels an outstanding live operation. Caller cancellation, Gateway shutdown, timeout caused solely by a caller deadline shorter than two seconds, and local live-capacity refusal are request-local and do not create a Live Fault observation. Responses require UTF-8 `application/json`, identity content encoding, at most 64 headers, 16 KiB of aggregate header bytes, and 64 KiB of decoded JSON. Caller credentials, service/probe credentials, outbound request body and headers, raw Authority body, and raw exceptions are prohibited from Logs, Trace, Metrics, Evidence, and persistence.

Only exact HTTP 200 is a decision response. The closed unauthenticated form is `{"protocol_version":"gateway.authorization.introspection/v1","status":"unauthenticated"}` and contains no identity members. The closed authenticated form has the same protocol version, `status="authenticated"`, and exactly string `subject`, `tenant_id`, `issuer`, and `audience`, RFC 3339 UTC string `expires_at`, and a JSON array of string `scopes`; `authentication_method` is not accepted from the Authority and Gateway synthesizes `online_authority`. Gateway then applies the route scope matrix. A protocol-valid authenticated envelope that fails Context field or scope validation is request-local `authorization_context_contract_invalid` and HTTP 503, but remains a valid live decision for clearing an older Live Fault Latch. Live service-Secret resolution or token-profile failure, runtime DNS/allowlist/TLS/connect/write/read failure, exhaustion of the full two-second Authority budget, invalid content type/encoding, resource overflow, malformed JSON, duplicate/unknown member, unknown protocol version/status, an incomplete decision form, and every status other than exact 200—including 204, 3xx, 400/401/403/404/409/415, 429, and 5xx—are eligible `authority_dependency_unavailable`, HTTP 503, and set the Live Fault Latch at their monotonic observation generation. Caller cancellation/disconnect, Gateway shutdown, a shorter-caller-deadline timeout, and local live-capacity exhaustion retain their request-local outcome without setting or refreshing that Latch. Authority 401/403 specifically diagnoses rejection of the Gateway service credential and never authenticates or rejects the caller credential. Explicit `unauthenticated` is the sole online 401 path. A later protocol-valid live HTTP 200 authenticated or unauthenticated decision may clear a prior Live Fault Latch only under the generation rule below.

Production Authorization Context scopes are ASCII tokens matching `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`. Each token is at most 128 bytes; after exact-string de-duplication the immutable set has at most 64 members and at most 4096 aggregate token bytes. Matching is case-sensitive and exact, and Gateway does not otherwise transform accepted tokens. A malformed or over-limit `local_jwt` scope Claim is caller input and returns HTTP 401 `unauthorized`; an explicitly successful `online_authority` result that violates the same limits is `authorization_context_contract_invalid` and returns HTTP 503 `authorization_unavailable`. A syntactically valid unknown token is retained in the Context but authorizes nothing. There is no `*`, prefix, hierarchy, or `admin` implication. The synthetic `dev:*` value is exempt from the production scope-token grammar and is only a marker that the resolved `dev_bypass` topology skipped ordinary authorization; it is never evaluated as a wildcard. The closed v0.1 permission registry is `gateway.model.invoke`, `gateway.model.provider_override`, `gateway.invocation.read`, `gateway.invocation.cancel`, `gateway.config.providers.write`, `gateway.config.bindings.write`, `gateway.config.routing.write`, `gateway.config.pricing.write`, `gateway.config.safety.write`, `gateway.config.resources.write`, `gateway.config.replay.write`, `gateway.config.read`, `gateway.config.export`, `gateway.config.publish`, `gateway.config.rollback`, `gateway.audit.read`, and `gateway.cost.reconcile`.

`POST /v1/chat/completions` requires `gateway.model.invoke`; use of the Provider Selection Override additionally requires `gateway.model.provider_override`. Both lifecycle status routes require `gateway.invocation.read`, and both cancellation routes require `gateway.invocation.cancel`. Configuration metadata/revision reads require `gateway.config.read`, export requires `gateway.config.export`, publication requires `gateway.config.publish`, and rollback Candidate creation requires `gateway.config.rollback`; activating that Candidate still requires a later authorized publication. Validation, Candidate creation, and rebase of a Bundle or typed Change Set require the union of the applicable `gateway.config.{providers,bindings,routing,pricing,safety,resources,replay}.write` scopes for every touched domain. Missing any member rejects the whole operation as 403 with no partial validation result, Candidate, rebase, or mutation. `gateway.audit.read` and `gateway.cost.reconcile` remain reserved for their privileged application use even where the corresponding HTTP management surface is deferred.

`online_authority` retains the public process-local states `unknown | available | unavailable`, derived internally from a Probe Gate and a Live Fault Latch. Startup leaves the Gate unsatisfied and exposes `unknown`, then immediately starts one dedicated Probe. Later Probes are due every five seconds, are single-flight, and use the separate one-slot pool and shared two-second operation deadline without retry. Bootstrap supplies the distinct exact `probe_endpoint` and an opaque UTF-8 `authority_id` of 1–255 bytes with no control character or leading/trailing whitespace. Probe sends `GET`, no body, `Accept: application/json`, and its separately resolved Bearer service credential. It uses the live response's UTF-8 `application/json`, identity-encoding, 64-header, 16-KiB-header, and 64-KiB-body limits. Probe success is only exact HTTP 200 with the closed body `{"protocol_version":"gateway.authorization.probe/v1","status":"ready","authority_id":"<configured exact value>"}`; comparison is exact, case-sensitive, and without Unicode normalization. Any status, media type, version, shape, duplicate/unknown field, or identity mismatch leaves or makes the Gate unsatisfied. A TCP connection or arbitrary 2xx is insufficient, and Probe never creates a real-user Context.

Every Probe and live operation captures one monotonic observation generation. A result may affect a gate only if it is later than the generation of the state it would replace. A successful Probe opens only the Probe Gate and never clears the Live Fault Latch. Only an eligible Authority/service-credential dependency observation sets that Latch; caller cancellation, Gateway shutdown, exhaustion caused only by the caller's shorter deadline, and local live-capacity refusal do not. Only a later-started, protocol-valid live HTTP 200 decision—authenticated or unauthenticated, including authenticated followed by Context-normalization failure—clears it; an older completion can neither mask a newer fault nor undo a newer recovery. The public state is `unknown` only while the initial Probe Gate is unresolved and no eligible live fault is latched, `available` only while the Probe Gate is open and the Live Fault Latch is clear, and otherwise `unavailable`. Whenever the Probe Gate is open, any normally protected Data Plane or Control Plane request may perform its ordinary live authentication before general Data Plane readiness even when another readiness cause exists. A valid decision clears the Latch and the same request then continues through its route-specific Context, scope, PostgreSQL, configuration-recovery, and Data Plane readiness checks; unauthenticated remains 401 and Context-invalid remains 503. Direct listeners continue accepting requests while `/readyz` is 503, and the existing 64-slot live pool is the only recovery concurrency control. When the Probe Gate itself is unresolved or closed, requests cannot use live traffic to bypass it. `/readyz` reads only the derived local state and never calls the Authority synchronously. Entering a different public state emits one safe transition Log; repeated observations of the same state increment only bounded counters. Neither internal gate is persisted, and v0.1 has no debounce, circuit, half-open trial, backoff, recovery single-flight, shared authentication result, synthetic canary, or operator reset. An online Adapter without a contract-complete dedicated Probe remains non-ready and cannot be selected as a production authorization topology.

Authorization is evaluated before admission and the resulting immutable Authorization Context is eligible only while its `expires_at` is strictly later than PostgreSQL `statement_timestamp()` in the atomic Admission Checkpoint statement. Equality is expired. Once the atomic checkpoint commits, the Context is locked into the invocation and is not revalidated for expiry; a later expiry or Authority outage does not interrupt an already admitted queued, synchronous, or streaming invocation. Every later lifecycle or Replay access is a separate authentication. `local_jwt` and `dev_bypass` have no online-Authority readiness state.

An explicit authorization revocation affects subsequent admission and access checks only in the first phase. Gateway does not maintain a continuous revocation channel or actively cancel already admitted work; that workflow is deferred.

Provider egress is deny-by-default in production. Candidate validation requires an explicit Provider host/network allowlist and production HTTPS; absence prevents publication and runtime dispatch. Provider transports never follow 3xx redirects and never retry the same candidate after one; before external commitment the Router may continue with the next eligible fallback Candidate. Every new connection—including retry and fallback Attempts—performs fresh DNS resolution and requires every returned address to pass the locked allowlist. One disallowed address rejects the entire connection before network I/O; Gateway never chooses an allowed address from a mixed set, and a prior or cached resolution grants no later authority. DNS timeout, `SERVFAIL`, and equivalent transient resolver failures may consume the shared bounded same-candidate retry, then pre-commit fallback, then explicitly eligible cache degradation before a stable terminal failure, and they contribute to Provider health/circuit policy. A disallowed or mixed DNS result is instead an egress-policy violation: no same-candidate retry, health/circuit mutation, or cache degradation is permitted, although pre-commit fallback remains eligible. A Provider-scoped Provider Trust Bundle may be configured for private PKI; when present it replaces system roots for that Provider, and when absent system roots apply. Its content-derived identity is locked by the invocation's Active Snapshot; rotation publishes a new snapshot for later admissions, and first phase does not watch or hot-reload mutable CA files. Already-established TLS connections are not rewritten. Certificate-chain and hostname verification remain mandatory and Data Plane callers cannot select trust material. First-phase transports disable environment proxy discovery and reject configured HTTP/HTTPS/SOCKS proxy settings. Docker startup may independently pass, replace, or omit standard proxy variables for other container concerns, but Provider Transport ignores them. Development or test access to loopback, private, or other local destinations requires an explicit environment-scoped allowlist entry and cannot be enabled by a Data Plane request.

A rejected 3xx normalizes to `provider_protocol_error`; it creates no same-candidate retry, Provider Health/circuit sample, or cache-degradation eligibility, while the locked pre-commit fallback order may continue. Candidate Blacklist is computed from existing eligibility inputs rather than stored as another runtime state: Provider Circuit covers transient failure, the invocation's rejected/attempted Candidate set covers a current egress-policy rejection, and a published Provider/binding status covers administrative disablement. No resolved address becomes blacklist state. When egress-policy rejection exhausts the route, the presenter returns `provider_unavailable`; authorized Evidence records `egress_policy_violation` and rejected Candidate identities but ordinary Data Plane output omits destination addresses. Provider Trust Bundle canonical PEM, content-derived identity, and optional human-readable label are embedded directly in the Provider's PostgreSQL configuration record and locked Active Snapshot; first phase has no shared Trust Bundle registry. Import decodes and stores canonical UTF-8 without BOM, converts every line ending to LF, removes excess trailing blank lines, appends exactly one final LF, preserves certificate order/content otherwise, and assigns/verifies `sha256:<64 lowercase hex>` over the resulting bytes used for export. The optional label is excluded from identity, routing, transport, validation, and Execution Fingerprint decisions; a label-only update still creates an audited Configuration Revision. Before Candidate creation/publication, local validation enforces PEM parsing, at least one CA certificate, absence of private keys, identity equality, validity of every certificate, and effective byte/count ceilings without network I/O. Defaults are 1 MiB and 100 certificates per Provider. Provider Transport materializes the locked identity for a new TLS connection without consulting an external mutable CA file. A local network-free task refreshes minimum-lifetime Metrics and expiry transitions, and the transport rechecks certificate dates immediately before opening every new connection. Reusing an established connection does not repeat date validation. Expiry of any member invalidates the whole Bundle for new connections; dependent Candidates use ordinary pre-commit fallback or terminal `provider_unavailable`, with no Provider Circuit sample, readiness change, or established-connection termination. A published valid replacement restores immediate eligibility and creates its pool without Circuit half-open, sample reset, or cooldown. The bounded-Provider `trust_bundle_days_until_expiry` gauge reports the minimum member lifetime; from 30 days, one warning per Provider/identity is allowed in each 24-hour window, and one error is emitted on transition to expired. Neither telemetry surface carries PEM, label, identity, subject, issuer, serial, or destination as a Metric label or unsafe field; external systems own notification.

Provider Transport pool identity is the tuple `(provider_id, trust_bundle_identity, transport_config_digest)`. The transport digest covers only endpoint origin, TLS mode/settings, HTTP protocol selection, connection/pool limits, and other connection-affecting behavior; it excludes model/routing/generation inputs, labels, and resolved credential values. Publication builds only local immutable pool descriptors and performs no DNS/socket/TLS/Provider operation. The first eligible Attempt initializes a matching pool lazily; credential material is resolved per Attempt and applied to its request without changing pool identity. If a configuration-valid descriptor cannot initialize because of an unexpected local resource or program failure, execution returns `internal` and performs no retry, fallback, cache degradation, Provider Health State update, or circuit sample. First phase configures Provider clients for HTTP/1.1 only and defers HTTP/2. Each Provider defaults to a 30-second idle timeout and five-minute maximum connection lifetime; published Provider configuration may change those values, making them part of the transport digest. Once either bound is reached, that connection receives no later acquisition. Active synchronous or streaming work continues only until completion, cancellation, or its original Invocation Deadline. A published behavior-changing identity/digest creates a new lazy pool; a label-only or credential-only change does not. The old pool is atomically removed from acquisition, idle connections close immediately, active requests retain their connection until completion, cancellation, or original Invocation Deadline, and the pool closes after its final active lease returns. Pool drain creates no independent timeout, does not reset or shorten a request deadline, and never migrates a request between pools.

Use the external Authorization Authority adapter and normalized Authorization Context; resolve Provider credentials through SecretSource; enforce configured egress/SSRF policy; and apply an explicit telemetry field allowlist. Configuration locks only Secret References. Each Attempt resolves one Provider Credential Lease just in time and keeps that version immutable; a later Attempt resolves again. Protected in-memory cache is TTL-bounded and invalidated by supported rotation/revocation signals. SecretSource outage may use only a valid unrevoked lease; otherwise the candidate is `provider_credentials_unavailable` and may pre-commit fallback. Provider credential 401/403 invalidates the lease and never retries the same version; only a confirmed new version may consume existing same-candidate/Attempt/deadline budget. Credential faults do not enter availability circuits. Emergency revocation blocks new Attempts and triggers best-effort cancellation of sent work. Evidence retains reference/version/state only, never plaintext or credential-derived hashes. Each invocation locks a Safety Policy Reference with Gateway Safety Policy Resource ID, Configuration Revision, content digest, and enforcement identity, and records trusted Provider policy identity when available. Safety Refusal evidence normalizes category, code, stage, enforcer, Provider request/Attempt, and configuration revision; unavailable Provider policy identity remains explicitly unavailable. A refusal terminates retry, fallback, reduced-capability, and cache substitution, and later evidence must show that no recovery Attempt followed it. Ordinary telemetry excludes credentials, authorization headers, raw messages/output, opaque Tool payload content, and unredacted Provider errors. Raw content requires the approved encrypted, redacted, audited retention path and remains opaque if it contains Tool fields. Published configuration/Cost Ledger history is immutable; cleanup creates policy-authorized non-content tombstones and cannot rewrite historical execution or financial facts.

Provider Transport capacity is bounded by the Provider concurrency ceiling: maximum simultaneous connections and maximum idle connections cannot exceed that ceiling, and the transport adds no hidden request queue. First-phase upstream clients use HTTP/1.1 only. HTTPS requires TLS 1.2 or newer, permits TLS 1.3, retains certificate-chain and hostname verification, and uses secure runtime cipher defaults. Provider responses accept identity or gzip only; gzip is decompressed incrementally before response/event resource ceilings, while unknown, malformed, or truncated encoding maps to `provider_protocol_error`. Response headers are capped at 64 KiB and 100 fields; a Provider policy may tighten but never raise either limit. These protocol failures follow the existing pre/post-commit boundary and raw header content remains outside ordinary telemetry.

The v0.1 Docker path is API-driven: after a clean Docker startup, an operator submits configuration through the Control Plane API (or explicit YAML apply), validates and publishes a Candidate, waits for Data Plane admission readiness, then sends a real Query to `POST /v1/chat/completions`. No manual PostgreSQL mutation, container-private setup script, caller-supplied Provider URL, or plaintext credential is required. This path must reach a configured real model; MockTransport is limited to deterministic CI tests. Source Bootstrap without `startup_profile` resolves it to `dev`, and effective `dev` without an authorization mode resolves that mode to `dev_bypass`; the shipped Docker examples nevertheless state both values explicitly. Those resolved values are canonical Bootstrap inputs and participate in its digest. In Docker `dev`, the Gateway process listens on `0.0.0.0` inside its container while Compose publishes the ports only on host loopback by default, and wider host exposure requires an explicit deployment setting. `dev_bypass` ignores any Authorization Header without parsing it, skips bearer and Gateway route authorization checks for local/controlled Smoke, and injects the exact deterministic Context `subject=dev`, `tenant_id=dev`, `issuer=urn:llm-gateway:dev`, `audience=llm-gateway`, `expires_at=9999-12-31T23:59:59Z`, `authentication_method=dev_bypass`, and `scopes={dev:*}`. An effective `production` profile must explicitly choose `local_jwt` or `online_authority`; the mode is not request-selectable, and every mode resolves Provider credentials only through SecretSource.

The v0.1 real Smoke uses the Development SecretSource: a Docker Secret or mounted file is the default input selected by `secret_ref`; an explicitly enabled named environment-variable source is allowed only in `dev`. Environment variables are never auto-loaded from `.env`. Production accepts only approved mounted/Docker Secret or dedicated Secret Manager sources. Secret values remain in the SecretSource/Adapter boundary and are absent from PostgreSQL, configuration responses, caller payloads, and ordinary telemetry.

## 8. Configuration

Within Bootstrap Configuration, the Idempotency Index Key Ring is a process-lifetime descriptor snapshot with exactly one active member and zero to eight verification-only members. Every member contains exactly `key_id`, `key_version`, `role`, and `secret_ref`; `(key_id, key_version)` and the complete `secret_ref` are independently unique, while one `key_id` may intentionally have several versions. Each reference names one exact immutable SecretSource version, never a bundle or moving `current` reference. Key bytes never enter the PostgreSQL Active Snapshot, configuration API/YAML bundle, export, or telemetry. Bootstrap validation checks descriptor/reference syntax, uniqueness, role cardinality, and the nine-member bound without reading secret bytes. Before locking the snapshot, startup queries PostgreSQL using its database clock and rejects any proposed removal for which an Idempotency Index record of that version has `protected_until > CURRENT_TIMESTAMP`; it does not compare expiry with the host clock. A new active version and demotion of the prior active therefore take effect only through an explicit deployment restart. v0.1 exposes no Key Ring mutation/rotation API, performs no in-process descriptor reload, and never auto-evicts a retained version.

A Configuration Revision identifier is a positive PostgreSQL `BIGINT`. Every non-null reference in Gateway-native JSON or YAML is a string containing its canonical unsigned decimal digits with no sign or leading zero, including `revision`, `base_revision`, `expected_active_revision`, and `rollback_of`; a JSON number or YAML numeric scalar is invalid even when small. Path parameters use the same canonical digit text and reject `0`, overflow, non-decimal, signed, and noncanonical forms before repository lookup. The string `"0"` is reserved only inside documented `base_revision` and `expected_active_revision` request fields for the completely empty initial state; numeric zero is invalid, and the string is never stored as a Revision, returned as a revision reference, or accepted as a `{revision}` path.

Revision state is the closed set `candidate | active | superseded | stale`. Failed validation creates no revision. A Candidate can become Active through a successful compare-and-swap publication or become Stale after a competing publication invalidates its base; a new Active makes the previous Active Superseded. Neither Superseded nor Stale returns to an earlier state. `rollback_of` records provenance on a newly created Candidate and never changes this state machine. Every revision representation uses the `gateway.config/v1` common metadata contract with exactly the foundational fields `revision`, `state`, `base_revision`, `snapshot_digest`, `created_at`, and `rollback_of`; route-specific envelopes may add only separately specified fields. Revision references use the canonical JSON strings above; every Candidate created from the Initial Configuration Base has `base_revision=null`, and `rollback_of` is null when absent. `snapshot_digest` retains the `sha256:<64 lowercase hex>` profile, and `created_at` is UTC RFC 3339 with exactly six fractional digits. Ordinary configuration responses omit actor identity.

Candidate creation compares the submitted base inside its transaction with the current Active state and proceeds only on exact equality. Throughout the period in which no Active exists, the Control Plane API/YAML path accepts the Initial Configuration Base (`"base_revision":"0"` in JSON and `base_revision: "0"` in YAML), including after another unpublished initial Candidate exists. Each fully validated command creates a distinct immutable Candidate and records `base_revision=null`; no Candidate is edited or deleted for correction. Publication with `expected_active_revision="0"` atomically permits one null-base Candidate to become Active and marks every other null-base Candidate Stale. After that publication, the zero sentinel is invalid and those Stale Candidates may use ordinary rebase. This preserves clean Docker-to-API bootstrap and correction without manual database edits or container-private scripts.

The first publication uses `"expected_active_revision":"0"` as an Active Revision Precondition for the empty Active state. Every publication additionally requires a Candidate whose recorded base is that transaction-time Active state; a Candidate based on any earlier Active state cannot publish. Publication is an atomic compare-and-swap: only one Candidate can win while the Active state is empty; later or repeated requests receive `409 conflict`. Once Revision 1 is Active, publication requests must name the actual Active Revision as a canonical string.

Published configuration changes affect later admissions only. An already admitted invocation continues under its locked Active Snapshot even if a later revision removes one of its Provider bindings; emergency Provider credential revocation still blocks any subsequent Attempt.

The configuration database is the canonical state and the only runtime-read authority. Development deployments may choose a Control Plane API or pure configuration file as the revisioned ingress into PostgreSQL; Router and execution components never read or merge the file directly. File-based operation uses one explicit operator/CLI apply command whose publish option executes the ordinary Candidate creation, validation, precondition, audit, and publication steps; neither process startup nor file change auto-publishes. YAML import/export and Control Plane API mutation are synchronized, versioned paths that validate candidate revisions: syntax/Schema, references, capability/routing/degradation, replay-policy completeness/scope, security/endpoint, limits, and cost/Secret/dependency rules. Candidate validation and publication are Provider-I/O-free: they make no Provider network request, health probe, model-generation call, or SecretSource key read. Runtime availability is instead learned from real Provider Attempts or separately configured, non-billable active probes after publication. Global Structured Output extraction lives under `resource_policies.structured_output.local_extraction_enabled` and defaults true; Model Alias `structured_output.local_extraction` accepts only `inherit` or `disabled`. Provider, tenant, and request-level forms are rejected. A YAML import contains a complete snapshot plus string `base_revision`; it creates a Candidate Configuration Revision and never activates directly unless the same explicit apply operation also requests the ordinary publish step. A revision export is deterministic, secret-free except for Secret references, and generated from PostgreSQL. The Gateway neither watches nor rewrites configuration files; CLI, deployment Job, or operator actions invoke synchronization. Stale bases return 409 without last-write-wins. Successful candidates receive a deterministic non-secret Snapshot Digest under the fixed `gateway.snapshot-digest/v1` profile, rendered exactly as `sha256:<64 lowercase hex>`. Its canonical input is the complete default-resolved non-secret domain configuration, including Secret References, and excludes revision/base IDs, revision state, timestamps, actor, description, audit metadata, and `rollback_of`. Candidate identity, Active identity, deterministic export, prospective validation, publish precondition, API/YAML ingress, and rollback-derived content all use this same definition; identical resolved content therefore has the same digest regardless of history. Snapshot Digest has no uniqueness constraint and performs no content deduplication: two otherwise valid explicit commands may create distinct Revisions with the same digest, and Gateway never returns an older Revision in place of creating the new history event. Operation-specific semantic no-ops such as rebasing a current Candidate or rolling back the Active Revision remain invalid independent of digest equality. Failed candidates never affect the active snapshot. Import, export, mutation, conflict, validation, publication, rollback, synchronization, and cleanup produce immutable configuration audit events with actor/source/revision/hash/result/Trace fields and redacted sensitive diffs. Publication activates one complete, internally consistent snapshot; rollback only copies one historical complete snapshot into a new Candidate and requires a later ordinary publication. In-flight invocations retain the revision selected at admission, and runtime modules do not mix snapshot revisions. Gateway-wide hard ceilings bound repair, attempts, request/input/output size, queue time, total duration, and Replay Artifact Write Queue task/byte reservations. The closed Resource Policy may tighten only its six declared ceilings, Alias may cap output Tokens, and a request may lower applicable output/deadline values. Replay queue and detailed parser/evaluator limits remain deployment-owned and have no Snapshot override.

Every Candidate row owns two immutable semantic forms: the complete default-resolved canonical Snapshot used for validation, digest, publication, and export, and a deterministic canonical typed Configuration Change Set relative to its recorded base. A `change_set` Submission validates and canonicalizes its closed typed operations directly. The six registries admit only whole-entry add, replace, or remove; the Gateway-wide resource and replay singletons admit only whole-value replace. Embedded Provider transport/Trust Bundle state and each Model Alias candidate list are atomic parts of their parent resource, so field and subresource patches do not exist. A full Bundle Submission first resolves defaults, then a domain-semantic diff against the base produces the equivalent whole-resource Change Set; persistence-row or textual YAML differences never become operations. Rebase replays that stored Change Set against the transaction-time current Active Snapshot. It does not re-diff the Candidate, edit either source Revision, or apply JSON Patch.

Each registry operation is the closed object `{op, section, resource_id, value}` for `add`/`replace` or `{op, section, resource_id}` for `remove`; each singleton operation is exactly `{op:"replace", section, value}`. The eight legal section names are the Bundle root section names, and operation IDs, field paths, per-operation preconditions, unknown members, singleton add/remove, `value` on remove, and `resource_id` on a singleton are invalid. `operations` is an order-independent set and may be empty, but a target may occur at most once. Canonicalization uses Bundle section order and then Resource ID UTF-8 bytes. Dynamic write authorization is computed from every structurally submitted target before equal-content operations are normalized away, so a no-op cannot evade its domain scope. An equal-content replace disappears from the canonical Change Set; an identical Bundle or empty Change Set may still create a distinct same-digest Candidate. Against Base, add-existing and replace/remove-missing are 409 conflicts. Gateway applies the complete operation set atomically to a provisional Snapshot without cascading deletes and then validates references and domain rules, allowing coordinated edits while rejecting any remaining dangling reference as 422.

Bootstrap Configuration is limited to `startup_profile`/environment identity, the resolved Authorization Integration Mode and its deployment-owned references, process binding, PostgreSQL/SecretSource access, the Idempotency Index Key Ring and its Secret References, an optional Cache Backend Connection Profile, telemetry export, expected Schema version, and optional first initialization input. Resolved profile and authorization-mode defaults remain explicit canonical values in the Bootstrap digest. Bootstrap cannot override domain policy, production does not auto-load `.env`, Secrets use approved mounted/bootstrap delivery, invalid bootstrap remains non-ready, and initialization YAML creates only a Candidate Revision. Graceful shutdown drains live invocations under their existing bounds but gives no separate replay-worker drain window.

`resource_policies.idempotency` contains positive integer `binding_ttl_seconds` and `key_reuse_quarantine_seconds`. Schema defaults resolve into canonical Snapshot data as 86,400 and 604,800 seconds respectively; the Gateway hard maxima are 604,800 and 2,592,000 seconds and cannot be widened by lower-level policy. Candidate validation rejects non-integers, non-positive or over-ceiling values, Exact Replay TTL greater than the Binding Window, or Status retention shorter than that window. These resolved values participate in canonical export and Snapshot digest.

The YAML v1 Configuration Bundle is a single full `gateway.config/v1` document. Its transport envelope has canonical order `schema_version`, string `base_revision`, optional non-domain `metadata`, required registries `providers`, `provider_model_bindings`, `model_aliases`, `routing_policies`, `pricing_tables`, and `safety_policies`, required Gateway-wide singleton `resource_policies`, then optional Gateway-wide singleton `replay_policies`; YAML cannot carry a typed Change Set. Each registry is a mapping keyed by stable resource ID, its closed value does not repeat that ID, input order has no semantics, and canonical order compares decoded ID UTF-8 bytes. All cross-resource choices are explicit references; the parser never infers the unique, first, or latest entry. A resource version is located by Configuration Revision, resource kind, and Resource ID; values carry no operator-assigned resource version. Empty-state input spells the value as `base_revision: "0"`; numeric zero and every other numeric Revision scalar are rejected. Prompt, Tool, and `service_requirements` sections are rejected. Providers hold required `status=enabled|disabled`, Adapter/base-URL/Secret-Reference, egress/transport/health/rate configuration, and may directly embed one Provider-scoped Trust Bundle with content-derived `identity`, optional `label`, and canonical PEM; there is no separate first-phase Trust Bundle registry. Stable Binding values likewise hold required `status=enabled|disabled`, Provider reference, concrete upstream model, capabilities/limits, pricing-table reference, and optional tokenizer reference. Other registries have no common status field. References to disabled Providers or Bindings remain structurally and referentially valid, while Router excludes every affected Candidate with a stable administrative-disabled reason and Evidence; runtime health/circuit state never synthesizes that status. Alias values hold explicit Binding candidates with priority/weight, routing/safety references, generation defaults, and the disable-only Structured Output override. The selected Routing Policy owns the Degradation Policy projection; Alias has no second degradation reference. The external `model` names only an Alias; the Application derives Service Requirement internally.

The parser accepts only a resource-bounded YAML 1.2 Core subset and rejects interpolation, custom tags, aliases/anchors/merge keys, duplicate keys, multi-document input, unknown fields, and object construction. Missing required domain sections are rejected. Only versioned constant leaf defaults may be omitted; they are materialized before semantic diff, persistence, Snapshot Digest, and export. Omitted `replay_policies` materializes as `execution_dedup_only`; a present exact-replay singleton must satisfy Exact Replay Policy Completeness. Deployment hard ceilings are not copied into the domain Snapshot. When a domain policy does not tighten one, its resolved value is explicit inherit/no-additional-tightening, so one Bundle retains one content identity across deployments. The resolved Snapshot contains `schema_version` and all fully resolved non-secret domain content but excludes envelope base/metadata, Revision/state/lineage, description/actor/audit, deployment ceilings, runtime health/circuit, and secret values. Structural and reference/semantic validation supports a no-write dry run with complete safe errors and impact/digest. Successful import creates only a Candidate. Deterministic export orders sections, IDs, fields, and scalar forms; Bootstrap values never substitute domain content.

Control Plane configuration writes are immutable revision commands, never Active-row CRUD. The complete v0.1 HTTP surface is `GET /gateway/v1/config/active`, `GET /gateway/v1/config/revisions`, `GET /gateway/v1/config/revisions/{revision}`, `GET /gateway/v1/config/revisions/{revision}/export`, `POST /gateway/v1/config/validate`, `POST /gateway/v1/config/revisions`, `POST /gateway/v1/config/revisions/{revision}/publish`, `POST /gateway/v1/config/revisions/{revision}/rebase`, and `POST /gateway/v1/config/revisions/{revision}/rollback`. JSON requests and responses require strict UTF-8 `application/json`; YAML Submission and export use UTF-8 `application/yaml`. Unsupported request Content-Type or charset is HTTP 415, while an unsupported `Accept` representation is 406. Every success and error carries `Cache-Control: no-store`. v0.1 emits no ETag; any `If-*` Header returns `invalid_request`/400 and no request produces 304/412. A read or `/validate` request carrying `X-Gateway-Command-Id` also returns 400. Explicit Revision/digest fields provide concurrency. Candidate creation, successful rebase, and successful rollback return HTTP 201 with `Location` naming the new `/gateway/v1/config/revisions/{revision}` resource. Validate, publish, and every successful read return 200; no configuration route returns 204.

Validate and Candidate creation consume the same closed Configuration Submission. JSON is a discriminated union with exact `kind=bundle | change_set`; YAML is only a full Bundle. Each branch contains one string base Revision and exactly its selected semantic payload, and arbitrary JSON Patch, persistence fields, and branch mixing are invalid. Validate performs the complete no-write parse, domain validation, semantic-diff/Change-Set derivation, impact analysis, and prospective digest. Candidate creation independently repeats the required checks, compares the submitted base to the transaction-time Active state, and writes both canonical forms. While Active is empty, string `"0"` may create multiple independent null-base Candidates even when another Revision exists; after publication establishes Active, that Sentinel is invalid. All JSON and YAML Revision values are strings, and YAML numeric zero is a structural error.

Publication accepts only a Candidate based on the transaction-time Active state and retains the explicit expected-Active and Candidate-digest preconditions. Digest equality with another Revision does not block publication of an otherwise valid Candidate. For empty Active, exactly one null-base Candidate wins; success makes it Active and atomically marks every other null-base Candidate Stale. Otherwise success makes the selected Candidate Active, its prior Active Superseded, and competing unrebased Candidates Stale. Rebase accepts only a Stale Candidate and only the current Active Revision as target, then replays the stored typed Change Set through a whole-target three-way comparison: if current content equals original Base, apply the intended result; if it already equals the intended result, record a convergent no-op, including identical add or already-absent remove; otherwise return `resource_changed`/409 for the whole resource or singleton. Disjoint field edits to the same resource therefore conflict and Gateway performs no field merge. Surviving operations are canonicalized and applied to a provisional Snapshot, followed by full reference/domain validation; such later failures are 422, create no Revision, and are not reclassified as merge conflicts. Rollback accepts only a Superseded source Revision; attempting to roll back the current Active Revision is a semantic no-op and returns deterministic 409. Successful rollback copies the source Snapshot into a new Candidate based on the transaction-time current Active Revision, records `rollback_of=source`, and requires a later ordinary publish. Rebasing a Candidate already based on the current Active Revision is likewise a deterministic 409 state/precondition failure rather than a new same-digest Revision. Every other lifecycle or mutable-state precondition failure in these commands is also deterministic HTTP 409.

Read representations use the common `gateway.config/v1` Revision metadata contract. With no Active Revision, `GET /gateway/v1/config/active` returns HTTP 200 and the closed result `{"active":null}`. Revision listing orders by Revision descending, defaults to 50 items, has an absolute page maximum of 200, and uses an exclusive Revision keyset for continuation; it has no total-count or state-filter behavior. Detail and export perform authorization before lookup and return 404 for a missing Revision. Detail returns the base DTO plus one bounded, deterministic, redacted semantic diff relative to `base_revision`; it never returns the full Snapshot. Only export returns that complete Snapshot as deterministic UTF-8 YAML without BOM, with LF line endings and exactly one final LF. Export writes its Bundle `base_revision` as the exported Revision's own canonical string without changing stored state or Snapshot Digest. It is directly resubmittable only when that Revision remains current Active; a Candidate, Stale, or Superseded export is archival until the operator deliberately substitutes the current Active base, or `"0"` while Active is empty, and submits a new fully validated command. It sends `X-Gateway-Snapshot-Digest` only as metadata, never as an ETag or conditional validator.

All operations are audited, the exact scope matrix applies before semantic work begins, and API/YAML paths converge on the same Application validation, Change Set, and canonical digest. HTTP query surfaces for Audit, Invocation Evidence, and Cost, manual Uncertain Outcome resolution, Capability Revocation, and cleanup are deferred to v1 rather than exposed through undocumented routes.

Candidate creation, publication, rebase, and rollback each require exactly one `X-Gateway-Command-Id` HTTP header whose value is a canonical lowercase, hyphenated UUIDv4; callers use a distinct ID for each logical command, and successful original or idempotently replayed results echo it unchanged. The command ID never appears in the request body, YAML Configuration Bundle, or Snapshot Digest. `POST /gateway/v1/config/validate` and every configuration read route reject that header as `invalid_request`/400.

After management-listener and route-template selection, configuration processing short-circuits in this exact order: HTTP framing and size ceilings; authentication; any route-fixed scope; `Accept` and request `Content-Type`; conditional/Command/Header, path, and query syntax; strict UTF-8 decode plus JSON/YAML parse and closed structural Schema; touched-domain discovery and exact dynamic union-scope authorization; required PostgreSQL/dependency access; mutation Config Command Index lookup/reservation; mutable Revision/Active state plus semantic/reference validation; then read presentation or atomic effect. Structural request failures use `invalid_request`/400, an authorized missing Revision uses `not_found`/404, negotiation uses `not_acceptable`/406 or `unsupported_media_type`/415, lifecycle/precondition/rebase conflicts use `conflict`/409, and mutation domain validation uses `configuration_invalid`/422. Validate/create derive touched domains from all structurally submitted targets before semantic no-op normalization. Rebase may read only its source's immutable touched-domain metadata before dynamic authorization, without examining mutable state or returning content; a missing source returns the authenticated 404. Every early failure prevents later work. Configuration recovery skips Data Plane readiness only, never authentication, authorization, or PostgreSQL. Every `If-*` Header, and `X-Gateway-Command-Id` on read or validate, fails at Header syntax with 400; 304/412 are impossible. Once `/validate` has passed those ordinary request/dependency stages, it returns 200 with `valid=false` for collected semantic failures or `valid=true` for a valid Submission; it never translates malformed input or dependency failure into a validation result.

Configuration validation and conflict reporting expose only closed diagnostics shaped as `{reason, path}`. `path` is an RFC 6901 pointer into the logical parsed Submission for JSON and YAML, or null where no body location exists. v0.1 accepts only the reason catalog in FR-960, returns no raw value, Secret Reference content, endpoint, PEM, Provider payload, parser text, validator text, or exception, and emits at most 100 entries. Results always carry `diagnostics_truncated`; deterministic ordering is validation phase, then non-null path UTF-8 bytes with null last, then reason UTF-8 bytes. HTTP status and the top-level Gateway error code remain separate from these entry reasons.

The validation response has exactly `valid`, `base_revision`, `snapshot_digest`, `change_set`, `impact`, `diagnostics`, and `diagnostics_truncated`. A valid result returns the prospective Snapshot Digest, the canonical full Change Set, a deterministic impact array, an empty diagnostic array, and false truncation. Each impact item is exactly `{section, resource_id, change}`; registry IDs are non-null, singleton IDs are null, change is `add|replace|remove`, and ordering matches Configuration Operation canonical order. An invalid semantic result returns null for digest, Change Set, and impact and at least one safe diagnostic. Both outer and nested result bases normalize the Initial Configuration Base to null; response representations never emit the input sentinel `"0"`. Candidate create, rebase, and rollback use `201 {"revision":<base DTO>}`, while publish uses `200 {"active":<base DTO>}`. No result permits extension members.

Every unsuccessful configuration access retains the common Gateway `error` object with stable `code` and safe stable-English `message`. Only a response with Configuration Diagnostics adds `error.gateway={diagnostics,diagnostics_truncated}`; otherwise `gateway` is absent. Diagnostic content is never copied into the message or root, and the fresh request correlation remains only in `X-Request-Id`. Semantic invalidity from `/validate` is the ordinary HTTP 200 validation result rather than this error shape.

Each Provider value contains exactly the required roots `status`, `adapter`, `endpoint`, `credential`, `egress`, `transport`, `health`, and `rate_limit`. These respectively own administrative enablement; Adapter type/protocol version; the approved OpenAI-compatible base URL; a Secret Reference only; destination/DNS/IP/proxy rules; TLS, optional embedded Trust Bundle, connection pooling, and transport timeouts; probes/health sampling; and Provider concurrency/QPS ceilings. All child objects are closed. Upstream model identity, price, Alias membership, priority/weight, routing policy, and runtime health/circuit state are forbidden in this resource.

Each Provider Model Binding value contains required `status`, `provider`, `upstream_model`, `capabilities`, `limits`, and `pricing_table`, plus optional nullable `tokenizer`. Provider and pricing are Resource ID references, while upstream model and tokenizer are opaque case-sensitive names. Capabilities contains only Boolean `streaming`, Boolean `tool_calling`, and `structured_output=none|json_object|json_schema`; limits contains positive integer `context_tokens` and `max_output_tokens`, with context at least output. The effective capability set is the intersection with the Adapter contract, and a declaration outside that contract blocks publication. Omitted/null tokenizer disables local estimation; absent trustworthy Provider Usage, Usage is `unavailable` under FR-719. Routing order, retry/fallback/degradation, and generation defaults belong to Alias/Policy resources instead.

Provider `adapter`, `endpoint`, and `credential` are closed DTOs containing respectively `{type,version}`, `{base_url}`, and `{secret_ref}`. Adapter type uses the resource-ID lexical profile and must match a registered implementation; its version is a 1–64-byte case-sensitive ASCII contract version. The base URL is an absolute API root that may include a fixed path but has no userinfo, query, fragment, or trailing slash. Production requires HTTPS; dev HTTP still passes Egress rules. Credential configuration is only a Secret Reference and never chooses headers, formats, environment variables, or plaintext.

Provider `egress` is exactly `{allowed_hosts,allowed_networks,proxy}` with non-empty duplicate-free canonical lists. Hosts are lowercase DNS A-labels without wildcard, port, or IP literal, and include the endpoint host. Networks are canonical CIDRs or the token `public`, which authorizes only public addresses. Every newly resolved address must match; one disallowed address rejects the full result. Private or loopback development access therefore needs an explicit CIDR. v0.1 proxy is the sole literal `disabled`, and transport ignores proxy environment variables.

Provider `transport` is exactly `{http_version,connect_timeout_seconds,idle_timeout_seconds,max_connection_lifetime_seconds,tls}`. HTTP is fixed to `1.1`; integer seconds use ranges 1–30, 1–300, and 30–3600 and canonical defaults 5, 30, and 300. TLS is either system trust with null bundle or bundle trust with identity, canonical PEM, and optional label; chain and hostname verification are mandatory. Pool capacity is derived from `rate_limit.max_concurrency`, not duplicated. `health` is exactly `{active_probe}`: null means passive-only, otherwise the same-origin GET probe contains path, 10–3600-second interval, and smaller 1–10-second timeout under isolated concurrency one. `rate_limit` is exactly three positive integers `{max_concurrency,qps,burst}`; fixed Circuit policy is not repeated here.

Each Routing Policy is the closed object `{selection,retry,fallback,degradation}`. Selection is exactly `{strategy:"priority_weighted_without_replacement",seed_profile:"gateway.routing-seed/v1"}`. Router first filters capability, Safety, administrative status, Health, Circuit, Egress, and capacity, then separates full/reduced service, exhausts lower numeric priority tiers first, and creates one deterministic seeded weighted-without-replacement order per tier. The seed profile consumes `call_id`, Routing Policy Resource ID, and Configuration Revision. Before each later Attempt, Router reevaluates dynamic Health, Circuit, concurrency, QPS, and deadline eligibility but never reorders the locked Candidate order.

The seed is a domain-separated HMAC-SHA-256 output under the active Execution Fingerprint key over length-prefixed call ID, Routing Policy ID, and Revision, stored as 64 lowercase hexadecimal characters. Historical replay consumes the stored seed. Within each service-level/priority tier, positive Candidates begin in Binding Resource ID UTF-8 byte order. For each pick, a counter-stream HMAC incorporating service level, priority, and pick index uses rejection sampling to obtain an unbiased integer below the remaining integer-weight sum; cumulative weights select and remove the Candidate. Floating point, logarithmic weighted keys, modulo bias, runtime PRNG/shuffle, and submitted order are forbidden.

Retry is exactly `{max_attempts,max_attempts_per_candidate,base_delay_ms,multiplier,max_delay_ms,jitter,max_retry_after_seconds}`. Values are respectively integer 1–3, integer 1–2 not exceeding total Attempts, integer 1–2000 ms, integer 1–4, integer from base delay through 2000 ms, literal `full`, and integer 0–5 seconds; zero ignores Provider Retry-After. Same-candidate retry precedes candidate advance. Fallback is exactly `{mode:"pre_commit_only"}`. The existing fixed retry-reason allowlist and Circuit profile remain code/protocol constants rather than DTO members. The External Commitment Point ends retry, candidate switching, reduced-service execution, cache substitution, and output splicing.

Routing Policy owns its closed `degradation` projection and is its revision-scoped policy identity. Degradation is exactly `{reduced_service,cache,terminal}` and has one non-configurable stage order after the full-service live path: optional reduced Candidates, optional cache, then terminal preservation of the original classified live failure. `reduced_service` is exactly `{enabled:<boolean>}`; enabling it requires every referencing Alias to contain a positive-weight reduced Candidate, but never relaxes hard capabilities, Safety, or request constraints. Disabled cache is exactly `{enabled:false}` with no other member. Enabled cache is exactly `{enabled:true,fresh_ttl_seconds,stale_ttl_seconds,encryption_key_secret_ref,retention:"successful_results_only",key_profile:"execution_fingerprint_v1"}`. Fresh TTL is 1–86400 seconds; stale TTL is an additional 0–604800 seconds after the fresh window, where zero disables stale use. Only complete successes are stored, Tool-bearing requests are ineligible by default, and only the fixed availability/capacity degradation reasons may read cache. Safety, Structured Validation, authentication/authorization, request/configuration, cancellation, and Uncertain outcomes never do. The cache encryption key is a distinct Secret Reference; Redis authentication remains Bootstrap-owned. Missing Redis or key availability affects only this stage, not publication or readiness. Terminal is exactly `{mode:"preserve_live_failure"}` and cannot replace the live failure with a cache error. Alias selection of the Routing Policy also selects this projection; evidence uses Routing Policy ID and Revision plus the projection digest. There is no degradation registry, independent Alias reference, or anonymous copy.

Pricing Table values are exactly `{currency,unit,effective_from,rates,rounding}`. Currency is uppercase ISO 4217, unit is `per_million_tokens`, and effective time is UTC RFC 3339. Input/output rates are required non-negative ordinary decimal strings; cached-input/reasoning-output rates may be null rather than guessed. Values have at most 12 fractional digits, and cost uses decimal `half_even_12dp` arithmetic while preserving partial/unavailable certainty.

The first-phase Safety Policy value is only `{mode:"provider_refusal_terminal"}`. Provider refusal/content-filter outcomes are normalized and terminal for retry, fallback, model switching, and cache substitution. Gateway defines no content-rule DSL, keyword list, Prompt checker, caller override, or moderation-service configuration in this Bundle version.

Replay Policy is the closed default `{mode:"execution_dedup_only"}` or exact branch `{mode:"encrypted_exact_replay",ttl_seconds,max_artifact_bytes,encryption_key_secret_ref,eligible_results,access_scope:"same_subject"}`. Exact-mode fields are all required, numeric fields are positive and ceiling-bounded, eligible results is a canonical non-empty subset of `sync|stream`, and the Secret Reference never contributes key bytes to the Snapshot. v0.1 has no cross-subject/tenant-wide or lower-scope override.

Each Model Alias is exactly `{candidates,routing_policy,safety_policy,generation_defaults,structured_output}`. Its 1–64 unique Binding candidates are closed `{binding,service_level,priority,weight}` values: service level is `full|reduced`, lower integer priority wins, and zero weight preserves but disables selection. At least one full candidate has positive weight. Service level describes disclosure-bearing quality degradation, not a capability exemption; reduced candidates still pass every hard request capability and require the Routing Policy's explicit permission. Generation defaults contain temperature, top-p, and max output with materialized 1.0/1.0/4096 defaults; max output is also the Alias ceiling, may only be lowered by a caller, and must be supported by at least one full candidate. Structured local extraction materializes to `inherit` and may only be disabled.

The required Gateway-wide Resource Policy is exactly `{structured_output,idempotency,limits,routing_evidence_ttl_seconds}`. Structured output materializes global local extraction enabled and a 1–32 validation-error retention bound; idempotency carries the established Binding Window and Key-Reuse Quarantine. Limits contains only request bytes, message count, content-item bytes, output-Schema bytes, SSE-event bytes, and invocation seconds. Each is explicit `inherit` or a positive deployment-ceiling-bounded tightening and materializes to inherit. `routing_evidence_ttl_seconds` is a required default-materialized integer, defaults to 2,592,000 seconds, has a minimum of 86,400 seconds, and cannot exceed Bootstrap `routing_evidence_max_ttl_seconds`. Cache behavior remains in Routing Policy degradation, Redis connection remains Bootstrap, and generic parser/evaluator counters, retry/queue/replay-worker controls, Business Budget, Token/cost quota, and tenant subtrees are absent.

Transport, authentication, authorization, media-type, syntax, and structural-Schema failures occur before command digest construction and create no Configuration Command Index row or reservation. Once the command is structurally valid and dynamically authorized, `gateway.config-command-digest/v1` Schema-parses the complete semantic command object, excludes authentication/context material and `X-Gateway-Command-Id`, applies RFC 8785 JSON Canonicalization, and computes SHA-256 over the canonical bytes. Equivalent JSON member ordering or YAML layout therefore shares identity. Gateway then performs Index lookup or reservation before mutable Revision/state checks, validation against current state, or mutation. The PostgreSQL Index remains independent of Model Invocation idempotency, Idempotency-Key namespace, Idempotency Index Key Ring, and Lockout and keys records by `(Authorization Context.tenant_id, Authorization Context.subject, operation, command_id)`.

The Index atomically retains successful results and deterministic 409/422 outcomes with the command transaction. It never retains 429 capacity results, request/dependency timeout, or transient 5xx; those paths roll back or release an uncommitted reservation. Repeating an identity with another digest returns the deterministic 409 before state checks. Concurrent requests with the same identity and digest wait on the first transaction only until their own deadline. If the leader commits, waiters replay its stored result; if it rolls back, exactly one waiter obtains the reservation and executes while the others continue to coordinate on that execution; a waiter whose deadline expires returns `deadline_exceeded` and neither invents nor persists another result. The lookup-before-state-check order means a retried committed command returns its original stored outcome even after configuration state has changed. v0.1 performs no automatic Index deletion and retains each entry for at least as long as configuration history.

The validation route is an optional dry run: it creates no reusable validation token or Configuration Command Index entry and is not a prerequisite for Candidate creation. Every create, rebase, rollback, and publish command independently performs the validation required by its own state transition; an earlier validation result never waives that check.

Configuration Resource IDs are the keys of the six registries and the values of their explicit references. They contain 1–128 ASCII bytes and match `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`; comparison is exact, and invalid input is rejected without trimming, case folding, or Unicode normalization. This grammar does not constrain opaque upstream model names, Secret References, or Revision IDs. ID syntax is a structural check, while target existence is a semantic check. Resource rename requires removal plus addition and explicit reference updates.

The exact JSON Submission is `{"kind":"bundle","bundle":{...}}` or `{"kind":"change_set","change_set":{...}}`. The outer object has only those two members, and each payload owns its base and optional metadata. Bundle uses the complete `gateway.config/v1` envelope already specified. Change Set has exactly `schema_version="gateway.config-change-set/v1"`, canonical string `base_revision`, optional `metadata`, and required `operations`; the operation union is specified separately. YAML contains the Bundle directly without a Submission wrapper. Validate and create share the same DTOs, with no outer duplicate version/base/metadata and no branch mixing.

| Lifecycle operation | Exact required JSON body fields | Revision precondition |
|---|---|---|
| publish | `expected_active_revision`, `candidate_snapshot_digest`, `description` | Expected Active may be `"0"` only while Active is empty; digest must equal the path Candidate's Snapshot Digest. |
| rebase | `expected_active_revision`, `description` | Positive expected Active is the explicit target base and must still equal transaction-time Active. |
| rollback | `expected_active_revision`, `description` | Positive expected Active is the new Candidate's base and must still equal transaction-time Active. |

These lifecycle bodies are closed and reject extra source/target Revision fields or source digests; the path selects the source. Structurally valid precondition mismatches return the existing deterministic 409 before mutation. The Command ID remains solely in its Header. Command identity includes the semantic path selector and complete body, so two different source Revisions cannot replay as the same command merely because their bodies match.

Every Configuration Change Description is 1–1024 strict UTF-8 bytes of single-line text without control characters or leading/trailing whitespace, and validation performs no trimming or Unicode normalization. Optional Bundle/Change Set `metadata`, when supplied, contains exactly one required `description` member. Create stores that supplied creation metadata; rebase and rollback use their own mandatory description for the new Revision's creation metadata. Publish stores a separate mandatory publication description without changing creation metadata. Descriptions enter Command Digest and applicable immutable metadata/Audit but not the resolved domain Snapshot or Snapshot Digest. Export reconstructs the Bundle envelope with the selected Revision's original creation metadata; absent creation metadata remains omitted, and later publication text never replaces it.

## 9. Observability and Evidence

Separate structured JSON Logs, Prometheus-compatible Metrics, OpenTelemetry Trace, PostgreSQL-backed Invocation Evidence, and the append-only Cost Ledger. Versioned cost tables define Provider/model/token-type rates, effective time, currency, and rounding; each Attempt records an immutable Cost Accrual using its locked pricing basis and Usage Measurement. Approved locally estimated observable input/output counts use published standard rates and produce `estimated/partial` accruals without assuming cache discounts or hidden reasoning charges; unavailable parent estimates yield unavailable cost rather than zero. Trusted later billing creates idempotent positive or negative Reconciliation Adjustments referencing the original accrual, never mutation. Aggregates expose estimated/accrued/reconciled/disputed states; unmappable Provider-period discrepancies remain unallocated rather than guessed. Original settlement currency is preserved, and optional reporting conversion is separately versioned. Reconciliation is a separately authorized Control Plane import with source, actor, evidence hash, and audit record. Routing always uses prospective published prices and is never retroactively rewritten by billing adjustments. Routing Decisions and candidate rejection reasons are append-only Invocation Evidence with configurable retention bounded by a Gateway-wide maximum, independent retention, and authorized Control Plane/audit access; expiry never mutates Cost Ledger records. Each invocation persists one `gateway.routing-decision/v1` record with immutable invocation/policy identity and Candidate snapshot plus monotonically sequenced `preselection`, `attempt_gate`, `attempt_started`, `attempt_finished`, `candidate_skipped`, `degradation_entered`, and `routing_terminal` events. The snapshot retains Binding, Service Level, priority, weight, and initial order; events reference only applicable Candidate/Attempt IDs, one decision, and ordered stable reasons, permitting multiple specific reasons without rewriting prior facts. Raw request/output, Schema, Tool, Provider payload/error, credentials, and secrets are forbidden. v0.1 Status returns a safe summary plus closed Evidence availability and an opaque reference only when available; full query is deferred while internal Eval/audit may consume the record. The Agent Loop supplies the root Trace; each `call_id` is a Gateway Model Invocation span with Provider Attempt, Adapter, routing, retry, and fallback child spans. Agent correlation follows `task_id → turn_id → step_id → call_id`; non-Agent evidence preserves absent business levels as null while always retaining `call_id` and `trace_id`. Business IDs are not forwarded to Providers by default, and Trace Context propagation requires explicit Adapter/egress policy. Evidence must link Model Invocation, Provider Attempt, configuration revision, Routing Decision, and cost records without persisting prohibited raw content by default. Gateway Added Latency is measured independently of Provider queue/generation time, while end-to-end TTFT and availability remain segmented by Provider and Resolved Model.

Effective Routing Evidence retention is the admission-locked `resource_policies.routing_evidence_ttl_seconds`, default 2,592,000 seconds, validated between 86,400 seconds and the deployment Bootstrap hard ceiling. `routing_evidence_max_ttl_seconds` defaults to 7,776,000 seconds and may be configured only from 86,400 through 31,536,000 seconds. The hard ceiling is excluded from Snapshot identity; a Candidate exceeding it fails configuration validation. v0.1 has no tenant, request, Alias, Provider, or model override. Expiry deletes the complete normalized Routing Decision aggregate for one call and leaves its Invocation shell and Cost Ledger unchanged.

The routing-terminal checkpoint uses PostgreSQL database time to persist immutable `terminal_at` and `expires_at = terminal_at + admission_locked_routing_evidence_ttl`. A non-terminal aggregate has null expiry and cannot be selected by ordinary retention cleanup. Startup reconciliation appends the established uncertain terminal, assigns both timestamps, and never treats incomplete execution as expired. The single-instance cleanup worker runs every 60 seconds; one pass uses the expiry index to process at most ten batches of 1000 call IDs and stops after five seconds. Each selected call loses its whole Routing Decision aggregate atomically while retaining Invocation and Cost records. A cleanup error, backlog, restart, or shutdown changes no readiness or live invocation; shutdown waits for no new cleanup pass and a later process continues from PostgreSQL. Metrics remain low-cardinality backlog, delete-count, failure, and latency observations.

One logical Routing Decision read uses a read-only `REPEATABLE READ` transaction. It computes effective expiry from PostgreSQL time before loading, reconstructs and validates every normalized relation from the same snapshot, then repeats the database-time expiry check immediately before emission; expiry at either boundary returns no Evidence content. Cleanup uses `READ COMMITTED`, expiry-index selection, and `FOR UPDATE SKIP LOCKED`, deleting the selected header and all child rows atomically. A locked aggregate is not awaited or retried inside the pass. PostgreSQL MVCC therefore permits a reader to finish against a complete pre-delete snapshot only while the final expiry gate still permits disclosure.

A found Status response keeps lifecycle and summary facts independently and carries exactly one closed Evidence projection: `{state:"available",reference:<opaque-reference>}`, `{state:"expired"}`, or `{state:"unavailable"}`. Only available carries a reference. Expired means the effective expiry derived from stored expiry and applicable ceiling history was reached; unavailable means a complete aggregate was never durably established or cannot be proven. Neither exposes timestamps, TTL, deletion cause, persistence detail, or optional fields. Routing Evidence expiry does not produce lifecycle `unknown_or_expired`, which continues to mean the Invocation Status target itself is unavailable.

At runtime, the effective expiry of any existing record is `min(stored_expires_at, terminal_at + strictest_applicable_historical_ceiling)`. Lowering the deployment ceiling therefore hides and makes over-age evidence cleanup-eligible immediately. If the Active TTL now exceeds that ceiling, Data Plane readiness is false while the authorized configuration-recovery surface remains usable, and Gateway does not rewrite Active state. Raising either ceiling or policy, restarting, or accessing evidence cannot extend the immutable stored expiry.

The routing record is a closed top-level DTO containing protocol version, call and configuration identities, Alias and Routing Policy reference/digests, Service Requirement digest/capability/override summary, safe seed, Candidate list, event list, and terminal projection. Candidate entries contain only Binding, Service Level, priority, weight, and nullable zero-based initial order; hard-rejected and zero-weight entries have no order. Each event is a discriminated closed variant with positive gap-free sequence starting at one and only the fields applicable to its kind. The final event must be `routing_terminal`; its canonical object equals the top-level terminal projection. No event may follow it.

The logical `gateway.routing-decision/v1` record maps to four normalized PostgreSQL relations: `routing_decision` is inserted once as the aggregate header; `routing_candidate` receives the immutable preselection batch; `routing_event` only appends and has unique `(call_id,sequence)`; and `routing_terminal` is inserted once and references the final Event. Foreign keys require Candidate and Attempt references to share the same `call_id`. Database constraints enforce unique sequence and terminal identity, while Application validation enforces a gap-free sequence beginning at one. Candidate/Event rows are never updated. Recovery appends the established uncertain outcome and terminal instead of replaying Provider execution. Logical reads assemble by sequence and verify terminal equivalence. Retention deletes all four relations atomically for one `call_id`, never a partial history, and leaves the Invocation shell and Cost Ledger untouched.

Existing Persistence Checkpoints govern routing evidence durability. Admission persists the invocation shell; Candidate/preselection state must be durable before the first Attempt; Attempt start is durable before Provider I/O; Attempt outcome plus the recovery decision is durable before any later Attempt; External Commitment is durable before the first business event; and terminal Routing Decision, Invocation state, Usage, Cost, and validation evidence commit before synchronous success or `[DONE]`. A checkpoint failure follows the established `persistence_unavailable` and uncertain-execution rules, while startup recovery appends an uncertain terminal interpretation for durable non-terminal work rather than replaying Provider execution.

Routing Reason is exactly `{code,subject}`. The closed codes are `weight_zero`, `service_level_disabled`, `provider_override_mismatch`, `provider_disabled`, `binding_disabled`, `capability_mismatch`, `limit_exceeded`, `parameter_unsupported`, `safety_ineligible`, `egress_policy_violation`, `trust_bundle_expired`, `health_unavailable`, `circuit_open`, `circuit_half_open_busy`, `provider_credentials_unavailable`, `concurrency_exhausted`, `qps_exhausted`, `deadline_insufficient`, `attempt_budget_exhausted`, `commitment_reached`, `degradation_not_enabled`, `cache_ineligible`, `cache_backend_unavailable`, `cache_miss`, and `security_invalidated`. Only capability, limit, parameter, and Provider-override codes carry a required canonical registry subject; every other subject is null. Rejected/skipped events require reasons, eligible/allowed events forbid them, and arrays sort by evaluation stage then code/subject bytes. Attempt Outcome is succeeded/failed/cancelled/uncertain and Routing terminal is completed/failed/cancelled/uncertain. Success/completion has no failure reason; other outcomes reuse existing stable errors. Completion requires full/reduced Service Level; a no-result terminal has null. Terminal degradation stage is none/reduced-service/cache/terminal.

Routing Reason subject registry `gateway.routing-subject/v1` is closed. `capability_mismatch` allows `streaming`, `tool_calling`, `structured_output.json_object`, `structured_output.json_schema`, and `structured_output.feature.<feature-id>` where the suffix exists in the locked Output Schema Feature Registry. `limit_exceeded` allows `context_tokens` and `max_output_tokens`. `parameter_unsupported` allows `temperature`, `top_p`, `max_output_tokens`, `stop`, `presence_penalty`, `frequency_penalty`, `reasoning_effort`, and `verbosity`. `provider_override_mismatch` carries exactly the requested Provider Resource ID. Other registry subjects are 1–128-byte lowercase ASCII identifiers following the Configuration Resource ID lexical form; Provider subjects follow the exact Resource ID. Deprecated `max_tokens` normalizes to `max_output_tokens`. Subjects contain no raw value, Schema/error text, or Provider response. Registry/profile identity and Service Requirement digest are stored once at the Routing Decision top level.

An authorization-path failure occurs before Model Invocation admission and therefore creates no `call_id`, Model Invocation, Invocation Evidence, Cost Ledger entry, or PostgreSQL authorization-health row. It emits only a security-structured Log, the HTTP server span plus an Authorization child span, and low-cardinality Metrics. Logs and spans may retain `request_id`, `trace_id`, authorization mode, Adapter type/version, normalized reason, outcome, and authorization latency. They exclude caller Token, Claims, `subject`, `tenant_id`, the Authorization Authority endpoint, Authority raw response, and raw exception; Metrics use only bounded mode, Adapter version, outcome, and normalized-reason labels and never include request- or Trace-level IDs or identity values. The online-Authority readiness state remains process-local and is observed through bounded status Metrics rather than persisted history.

Idempotency Index Key Lockout is also operational state rather than invocation state. It exposes one process-global lockout gauge and bounded counters partitioned only by normalized lockout reason and keyed-operation class. Entering lockout and recovering from it each emit exactly one safe transition Log and one alert signal; repeated failures while the state is unchanged increment counters only. Metrics, Logs, and alerts carry no key ID, key version, Secret Reference, Index digest, tenant, or subject as labels or unsafe fields. An affected HTTP access may still have its ordinary safe access Log and Span, but lockout creates no `call_id`, Model Invocation, Invocation Evidence, Cost Ledger record, or PostgreSQL health/state row.

## 10. Lifecycle and deployment

Idempotency Index readiness distinguishes static deployability from SecretSource material availability. An absent/malformed required Key Ring reference, invalid role/count/identity topology, or startup retirement-precheck failure is a Bootstrap/deployment defect and makes `/readyz` return 503. Once that structure is valid, failure to resolve or validate Index key bytes—during cold start or later—is not a global readiness dependency: only requests requiring key derivation fail closed with `persistence_unavailable`, while headerless admission and `call_id` lifecycle routes remain usable. A still-protected emergency revocation imposes the same closed Key-path lockout until exact-version restoration advances the Fence and a current-generation all-member Ring validation succeeds, or until database-clock expiry plus a restart activates a valid descriptor ring without that version.

The Docker Compose deployment includes a one-shot `gateway-migrate` Migration Job that applies ordered, auditable PostgreSQL Schema artifacts before the Gateway is admitted. Gateway startup only verifies Schema compatibility and never applies destructive or irreversible migrations. Compose must not consider the Gateway path usable until the migration job succeeds; a failure or partial/incompatible Schema blocks Data Plane admission and leaves configuration recovery subject to the existing non-ready boundary.

Inside the Gateway container, the default process listeners are `0.0.0.0:8000` for Data Plane traffic and `0.0.0.0:8001` for Control Plane resources and `/healthz`/`/readyz`. Docker Compose publishes only host `127.0.0.1:8000` to container port `8000` and host `127.0.0.1:8001` to container port `8001` by default. Bootstrap/deployment settings may explicitly change host publication or ports without changing route paths; production keeps the management/health listener on the internal/编排 network and does not route it through public Data Plane ingress.

The Migration Job runs on every Compose start with a bounded PostgreSQL readiness wait. It exits successfully without changes when the recorded Schema is current, applies only pending ordered artifacts otherwise, and exits non-zero on failure or partial application; it never performs automatic rollback of destructive or irreversible changes.

The documented first Smoke uses a complete `gateway.config/v1` Minimal Configuration Bundle: exactly one Provider, one Provider Model Binding, one Model Alias, and explicit routing, pricing, safety, and resource-policy sections. Gateway does not synthesize omitted domain-policy sections or create an implicit Active Snapshot; any schema-level optional defaults are resolved as part of the submitted canonical snapshot and its digest.

The Gateway exposes `GET /healthz` as a process-only liveness probe and `GET /readyz` as the Data Plane admission readiness probe. Liveness does not wait for PostgreSQL, Active Snapshot, Authorization Authority, or Provider reachability. Readiness checks PostgreSQL, a valid active snapshot, required local execution dependencies, and an online Authorization Authority only when configured as a required dependency; Provider runtime health/circuit/capacity is excluded. Both probes are status-only at the application boundary, return 503 when the relevant condition is not met, disclose no configuration detail, bypass caller JWT/permission evaluation, and are exposed only on an internal/编排 listener in production, never on public Data Plane ingress.

The current Fingerprint HMAC key is a required local execution dependency. After authentication/protocol preflight and Idempotency Index resolution, but before Request Fingerprint comparison or new admission, Gateway obtains one immutable active-member lease. It uses that lease for Request Fingerprint, admission/snapshot resolution, Execution Fingerprint, and domain-separated Routing seed, then releases it before Provider I/O. An existing Idempotency Binding instead names the exact historical member used only to recompute and compare its Request Fingerprint; no Ring fan-out or new execution identity occurs. Unkeyed hashing, randomness, another member, and fallback keys are forbidden. Invalid startup descriptor or active validation failure keeps `/readyz` false. Runtime missing, revoked, unavailable, malformed, or mismatched active material returns `persistence_unavailable`/503 before admission, creates no `call_id`, Invocation, Evidence, Cost, or Provider work, sets process-global Fingerprint Key Fault, and makes `/readyz` false. A verification-only failure is request-local. The isolated five-second recovery check keeps its one-second deadline and no retry. Rotation affects new executions only; already derived identities and admitted work remain locked, and historical Eval consumes the stored seed.

Bootstrap contains one closed `gateway.fingerprint-key-ring/v1` descriptor, separate from the Idempotency Index Key Ring and cache/Replay encryption keys. It contains exactly one active member and zero through eight verification-only members; each closed member is `{key_id,key_version,role,secret_ref}` with unique identity and resolves to exactly 32 raw HMAC-SHA-256 bytes. The descriptor is immutable for one process lifetime and changes only at restart; v0.1 has no live rotation or partial reload. Startup validates all descriptor structure and resolves the active member before readiness. Verification-only members resolve just in time for dependent historical operations; their failure returns `persistence_unavailable` for that operation without changing new-routing readiness. A version cannot be removed while an unexpired or non-revoked fingerprint, cache, or Replay dependency remains; persisted Routing seeds do not count.

PostgreSQL table `fingerprint_key_protection` contains one non-content row per `(key_id,key_version)` and monotonically advances `protected_until` using database time. Idempotency admission extends it in the Binding transaction. Cache and Replay retention authorization extend it before their optional enqueue/persistence handoff; failure drops that optional retention work without changing the live completion, whereas an Idempotency protection failure fails admission. Startup keeps readiness false when the descriptor omits a version whose horizon is still in the future. SecretSource absence, Redis loss/miss, or storage uncertainty never shortens protection and no Redis scan is allowed. Only an audited PostgreSQL security-invalidation fact may release an explicitly revoked dependency; ordinary paths never decrease the horizon.

The closed protection row is `{key_id,key_version,protected_until,invalidated_at,invalidation_generation,updated_at}`. `protected_until` advances only by maximum; `invalidation_generation` is a non-negative monotonic integer and begins at zero, while `invalidated_at` is null until one authorized audited whole-version invalidation atomically sets PostgreSQL time and increments the generation once. No individual dependency is decremented or counted. Invalidation permanently makes every Fingerprint comparison, cache entry, and Replay dependency under that version unusable and allows startup retirement despite the horizon. The same `(key_id,key_version)` cannot be restored or reused. Invalidating the active version sets Fingerprint Key Fault; recovery requires restart with a distinct active version, not restoration of identical bytes.

Startup's active validation is a bounded probe and releases the bytes. Each request resolution has one deadline of `min(1 second, request remaining deadline)`, no retry, and one operation-scoped lease released on every exit. The process admits at most 32 concurrent Fingerprint-key leases. Lease-capacity exhaustion is request-local `persistence_unavailable` and does not set the global Fault. Active material contract/availability failures set it; verification-only failures affect only the exact historical access. No lease or key material enters persistence, cache, telemetry, Evidence, errors, or a process-wide key-material cache.

Fingerprint leases and Idempotency Index Key Material Leases use independent 32-permit semaphores with immediate try-acquire and no acquisition queue. For a keyed request, the Index lease derives all candidate digests and is fully released before the PostgreSQL lookup begins. Only after lookup returns either no protected Binding/new-binding eligibility or the exact stored Fingerprint key identity may the request acquire the Fingerprint lease. No task holds both lease classes simultaneously; neither pool borrows, reserves, or reduces the other's capacity. Either local-capacity failure returns `persistence_unavailable` before admission without setting Index Lockout, Fingerprint Key Fault, any Fence, Circuit, or readiness state.

The first phase runs one Gateway service with logical Control Plane and Data Plane API surfaces. Gateway liveness is process-oriented. Data Plane admission readiness validates the active snapshot and enabled local execution dependencies, not transient Provider reachability, health, circuit, or capacity state; requests encountering those conditions use ordinary routing/resilience and return the applicable uniform failure. The Control Plane configuration-recovery path remains available when PostgreSQL and authorization are healthy. Standalone Data Plane service decomposition, independent release lifecycle, and separate service readiness are deferred.

If PostgreSQL and authorization remain available but the active snapshot is invalid or absent, Data Plane admission stays non-ready while the Gateway Control Plane may perform only authorized configuration recovery: configuration read/export, import, validation, and publication of a complete replacement snapshot. This path cannot access invocation status, cancel/replay invocations, or perform Provider-affecting work. Publication atomically updates PostgreSQL and the in-process snapshot; the Gateway re-runs admission readiness validation before resuming normal admissions, without a restart.

Data Plane requests rejected solely because no valid Active Snapshot is ready map to `gateway_not_ready`/HTTP 503 without configuration detail. PostgreSQL unavailability maps separately to `persistence_unavailable`/HTTP 503.
`gateway_not_ready` omits `Retry-After` because configuration recovery duration cannot be reliably calculated.

Define versioned PostgreSQL migrations executed by an independent job, encrypted external backup/recovery with RPO/RTO and disposable Redis recovery, startup Schema-version verification, Gateway startup validation that loads/verifies the latest active PostgreSQL snapshot, process-oriented liveness, Data Plane admission readiness, bounded in-flight drain, Docker runtime, resources, and health endpoints. The default Compose path starts Gateway, PostgreSQL, and `gateway-migrate`; Redis is started only by the explicit `cache` profile and remains optional to live admission. The cache profile uses temporary Redis storage by default and does not require a named volume or authoritative backup; an operator-provided volume is best-effort only. Missing/incompatible Schema, missing/invalid snapshot, failed restore validation, or required PostgreSQL keeps Data Plane admission non-ready and unable to accept calls; optional Redis unavailability does not. Redis and Gateway restart/restore may begin with an empty cache and carry no continuity or replay guarantee; cache loss never blocks readiness or live execution. The Control Plane can remain available for configuration recovery when PostgreSQL and authorization are healthy. The first-phase topology runs one Gateway container alongside PostgreSQL. Performance acceptance uses one 4-vCPU/8-GiB Gateway instance, a deterministic local transport, 50 QPS, up to 200 streams, and a 30-minute soak; it checks 50-ms P99 Gateway processing, 20-ms P99 delta forwarding, under 0.1% unexpected Gateway 5xx, terminal-event correctness, and bounded memory.

Fingerprint identity comparisons, admission, and cache/Replay protection handoffs check the Lease's key/version/generation against a non-invalidated PostgreSQL row in the corresponding transaction, together with the process-local observed-revocation fence. Losing the ordering returns `persistence_unavailable` without Binding, replay, conflict decision, or retention write. Optional retention failure preserves live completion; admission that wins allows execution to continue. SecretSource changes advance the local fence only when observed.

FR-998's irreversible version mutation is v1 work with dedicated authorization, idempotent commands, and atomic audit. v0.1 keeps reserved fields, defensive checks, planned rotation, protection horizons, and observed SecretSource fail-closed behavior. No API/CLI, manual-SQL workflow, startup/configuration side effect, or hidden command writes the invalidation fields.

An available Evidence reference is `rd_` plus the original canonical UUIDv4 call ID without hyphens. It is an opaque identifier with no authority and no v0.1 dereference API. Future complete reads require authentication, `gateway.audit.read`, and tenant/subject checks.

Cleanup uses partial indexes `(expires_at,call_id) WHERE expires_at IS NOT NULL` and `(terminal_at,call_id) WHERE terminal_at IS NOT NULL`. Each predicate supplies bounded ordered expired candidates; merge/deduplicate them, sort by effective expiry then call ID, take at most 1000, then perform existing skip-locked atomic deletion. Metrics report `expired_backlog_present`, indexed `oldest_expired_age_seconds`, selected/deleted counts, failures, and duration without an exact full-table backlog count.

Retention ceiling history is durable PostgreSQL state ordered by effective time. Replace every current-ceiling-only eligibility calculation with the strictest historical ceiling applicable during the record's lifetime. Subsequent increases apply only to new admissions and never undo an earlier tightening for old calls, including when cleanup has not run. The original terminal timestamp, Events, and stored expiry are immutable. Read eligibility, cleanup candidates, Status availability, and backlog metrics must all derive the same effective expiry from this history.

Independent Invocation Status persistence keeps minimal internal Evidence lifecycle metadata: successful-establishment fact, terminal timestamp, and original expiry. Routing aggregate deletion does not delete these Status-owned facts. Together with applicable ceiling history they classify expired Evidence after physical deletion; Evidence never successfully established remains unavailable. They expire with Status, do not copy Candidate/Event content, and never add public time/TTL fields to the closed availability DTO.

Startup commits the configured ceiling, database effective time, and ordered activation sequence in one PostgreSQL transaction before enabling Evidence reads or Data Plane admission. An unchanged latest value reuses the existing activation; failed commit leaves both paths closed and readiness false. Admission persists the active sequence, also retained by independent Status metadata. For a call admitted at sequence S, the applicable historical ceiling is the minimum ceiling across S and all later committed activations visible to the eligibility check. This includes tightening before terminalization or during recovery; a later increase cannot relax the minimum for old calls. The admission-locked TTL and original terminal/expiry facts remain unchanged. Cleanup and backlog calculations must use this same sequence-aware minimum, not merely the latest ceiling predicate.

All committed ceiling activations remain in PostgreSQL throughout v0.1: no history pruning or compaction runs at startup, during Evidence cleanup, or when Status expires. Same-value restart continues to reuse the latest activation. v1 may design history lifecycle optimization only while preserving surviving Evidence/Status dependencies and identical historical-expiry outcomes.
