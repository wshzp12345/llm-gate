# LLM Gateway Test and Acceptance Design

- Status: Approved
- Created: 2026-08-24
- Last updated: 2026-09-07

## 1. Test strategy

2026-09-13 scope amendment: basic Prompt management is now Gateway-owned under [ADR-0148](adr/0148-gateway-owned-basic-prompt-management.md). Older tests requiring rejection of all Prompt management/rendering are superseded only for the newly documented basic surface. Replacement tests must cover version immutability, concurrent publication versus fixed-version invocation, authorized access, missing/invalid variables, rendering limits, no executable template effects and sensitive-content exclusion. The [six-capability checklist](basic-capabilities.md) defines current completion gates; neither a scope amendment nor existing synchronous smoke proves them complete.

Test behavior through confirmed public seams. Do not couple tests to private helpers, FastAPI internals, Provider SDK internals, internal dictionaries, or exact implementation call order. An HTTP 200 response alone never proves acceptance.

The first-pass completion gate follows the proposed [Initial Scope v0.1](scope-v0.1.md); v1 candidates are tracked but do not block v0.1 acceptance.

## 2. Candidate test layers

- Unit: pure policy, validation, state transition, and failure classification.
- Contract: HTTP/JSON/SSE protocol and shared Provider Adapter behavior.
- Integration: FastAPI Host, persistence, Secret delivery, cancellation, and Docker dependencies.
- Acceptance: Agent Runtime client to Gateway to deterministic or approved Provider path.
- Architecture: dependency direction and framework/Provider isolation.
- Package/deployment: clean install, image build, non-root startup, health checks, and configuration failure.

## 3. Test seams

The test design must expose or inject these seams without requiring real Provider access:

- Model Adapter protocol with a `MockTransport` that captures translated requests and returns deterministic responses, streams, timeouts, and errors.
- Capability Registry and Router policy inputs for capability matching, priority, weights, health, cost, and candidate rejection evidence.
- Clock, deadline, retry-allowance, and backoff scheduler abstractions so retry behavior can be tested without real `sleep`.
- Internal Stream Event source and SSE serializer for ordered content, opaque compatible payload fragments, usage, terminal, and interruption behavior.
- Structured-output extractor, incremental parser, Schema validator, and bounded repair policy.
- Trace, Metrics, Invocation Evidence, and Cost Ledger sinks that can be inspected after each invocation and Provider Attempt.

## 4. Requirement traceability

Each accepted requirement will map to one or more stable Case IDs. Every Case must state:

- fixed input;
- expected observable result;
- negative evidence;
- what the Case proves;
- what the Case cannot prove.

## 5. Failure and recovery coverage

Include invalid protocol, authentication/authorization, deadline, cancellation, duplicate request, Provider rejection, rate limit, timeout, connection loss, malformed output, uncertain effect, restart, and partial failure. MockTransport must drive timeout and error cases; tests must assert retry count and backoff decisions without real waiting.

## 6. Security coverage

To include credential leakage scans, message/output logging restrictions, request limits, unsafe configuration, Provider egress restrictions, and dependency isolation.

## 7. Acceptance gates

Acceptance gates must include supported Python versions, lint/typecheck, the Adapter translation suite, routing suite, retry/backoff suite, SSE event-order suite, structured-output suite, telemetry/evidence suite, cache policy/TTL/eviction suite, clean wheel, one Gateway instance plus separate PostgreSQL and Redis Docker containers when cache mode is enabled, liveness/Data Plane admission readiness behavior, startup failure, graceful drain, restart/recovery, contract compatibility, independent Review, documentation consistency, and explicit live-test boundaries. Standalone Data Plane service and multi-instance consistency are outside this gate.

## 8. Evidence limits

Offline tests will not automatically prove real Provider behavior, real network/TLS behavior, production isolation, multi-instance correctness, or production SLOs. Those claims require separate live evidence.
