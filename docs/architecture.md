# LLM Gateway Architecture

- Status: Approved
- Created: 2026-08-24
- Last updated: 2026-09-07

## 1. Architecture drivers

2026-09-13 accepted amendment: [ADR-0148](adr/0148-gateway-owned-basic-prompt-management.md) supersedes older exclusions of basic Prompt assets, versions, publication and rendering. These responsibilities belong in Gateway-owned domain/application modules with outer management/storage adapters, not in a Provider Adapter. Existing rendered-message invocation remains supported. Old Prompt-specific exclusions below are historical where conflicting; Tool/Agent ownership and content privacy remain unchanged. See [implementation gates](basic-capabilities.md).

Derived from approved requirements after `requirements.md` review.

The proposed delivery boundary is [Initial Scope v0.1](scope-v0.1.md). This architecture retains the full target model while marking transport, recovery, and distributed-operation extensions as v1 candidates until explicitly re-scoped.

## 2. System context

The first-phase Gateway has two externally addressable logical surfaces within one deployable service:

- **Data Plane:** First-phase OpenAI-compatible Chat Completions model invocation, including synchronous JSON, SSE streaming, Tool Calling, and Structured Output, for the Agent Loop and other approved consumers. It executes Provider Attempts.
- **Control Plane:** Versioned, Gateway-native configuration and operational management for Providers, Model Aliases, routing, resilience, pricing, resource, safety, and health policy; Prompt, Tool, and first-phase Business Budget management are absent.

The surrounding system context still includes:

- Agent Runtime and other approved consumers;
- LLM Gateway deployment boundary;
- external Providers;
- credential, configuration, persistence, and observability systems.

## 3. Module responsibilities

Define separate Data Plane and Control Plane API modules, a generic OpenAI Chat Completions HTTP Model Adapter, and Gateway-owned application/domain protocols without coupling application rules to a vendor-specific Provider SDK. The Application-owned Provider Port exposes explicit `complete`, `stream`, and optional `resolve_uncertain` operations rather than one stream-flag union. Provider Events are internal and terminally complete; API presenters alone create external SSE. Ordinary Data Plane calls select a configured Model Alias; the Application derives a provider-independent Service Requirement from that Alias and the validated request. A permission-controlled Provider Selection Override is limited to configured candidates and cannot bypass Router or security policy. Adapter contract behavior is exercised through `MockTransport`; live evidence uses a configured OpenAI-compatible endpoint.

## 4. Dependency direction

Dependencies point inward through four layers:

1. **Domain:** pure Gateway entities, value objects, policies, failure semantics, reliability/resource limits, and event/state invariants.
2. **Application:** delivery-independent use cases for invocation, streaming, cancellation, status, and configuration publication; this layer owns the output Ports it consumes.
3. **Interface Adapters:** thin OpenAI-compatible and Gateway-native controllers/presenters plus Provider anti-corruption Adapters and persistence mappers.
4. **Infrastructure:** FastAPI host, HTTP transports, PostgreSQL/Redis implementations, Authorization Authority integration, SecretSource implementations, telemetry exporters, clock, and random source.

`ProviderPort`, structured-output parser/validator/repair Ports, configuration/evidence/cost/cache repositories, authorization, Secret, clock, and randomness abstractions belong to the consuming Application layer. Outer implementations depend on these abstractions. Boundary data is limited to Gateway-owned Commands, Results, Stream Events, Failures, identifiers, and value objects; HTTP/Pydantic DTOs, Provider payloads, ORM rows, sessions, and Redis representations do not cross inward. Pydantic remains in API validation and the Structured Output validation Adapter. The Composition Root is the outermost plugin: it reads Bootstrap Configuration, creates implementations, and injects use cases without making domain decisions.

## 5. State ownership

The Gateway configuration database is the canonical owner of Provider, Model Alias, routing, resilience, pricing, resource, safety, and static health/circuit policy configuration. Prompt and Tool state remain in the Agent Loop or dedicated services. YAML and Control Plane API are synchronized ingress/egress surfaces over Gateway-owned state. A Configuration Revision is a canonical positive PostgreSQL `BIGINT`; every non-null Gateway-native JSON or YAML revision reference is its unsigned decimal string without leading zeroes, avoiding loss beyond JavaScript's safe-integer range. The string `"0"` exists only as the explicitly documented empty-Active sentinel in request bodies and is never a stored Revision or revision resource identifier; numeric JSON or YAML Revision values are invalid. Revisions use the closed `candidate | active | superseded | stale` lifecycle: invalid input creates no revision, a Candidate becomes Active or Stale, and publishing a new Active makes the former Active Superseded. `rollback_of` is provenance metadata rather than another lifecycle state. Revision representations share the `gateway.config/v1` metadata fields `revision`, `state`, `base_revision`, `snapshot_digest`, `created_at`, and `rollback_of`; revision references are canonical decimal strings, every Candidate created while Active is empty has `base_revision=null`, `created_at` is UTC RFC 3339 with exactly six fractional digits, and ordinary configuration responses omit actor identity. A resource version is the resource kind and ID as captured by one Configuration Revision; configuration values do not carry independent operator-maintained versions. Only an explicit publish atomically activates one complete snapshot, and each Model Invocation retains its admitted revision. Live health counters and circuit state are runtime state; their transitions emit evidence but do not write the database per request.

Every resolved configuration snapshot has one content identity, `sha256:<64 lowercase hex>`, computed under the versioned `gateway.snapshot-digest/v1` profile. The digest covers the complete constant-default-materialized, non-secret domain configuration, including Secret References, and excludes Bundle base/metadata, revision identity/state/lineage, timestamps, actor, description, audit data, deployment hard ceilings, runtime observations, and secret values. API, YAML, rollback, Candidate, Active, export, and prospective validation all use that same definition, so semantically identical content has the same digest regardless of ingress, deployment hard-ceiling values, or history. Snapshot Digest is content identity, not Revision identity: distinct valid configuration commands may create distinct immutable Revisions with the same digest, and PostgreSQL applies no digest uniqueness constraint, content deduplication, or old-Revision substitution. A valid same-content Candidate may be published as its own history event. Operation-specific state/precondition failures, including rebasing against the already-current base or rolling back the current Active Revision, remain deterministic HTTP 409 even though digest equality itself is permitted.

The Gateway Control Plane owns configuration mutation/publication. It atomically publishes Active Snapshots to PostgreSQL and atomically replaces the in-process snapshot used by later Data Plane admissions. Gateway liveness is process-oriented; Data Plane admission readiness verifies the active snapshot and required local execution dependencies, not transient Provider reachability, health, circuit, or capacity state. Standalone Data Plane service decomposition, service-to-service snapshot propagation, and independent release/readiness are deferred.

PostgreSQL remains the only canonical runtime configuration authority in every environment. A development deployment may use either a Control Plane API or a pure configuration file as the ingress path into PostgreSQL, but execution never reads that file directly or merges two authorities. File-based operation uses an explicit one-shot apply/publish command over the ordinary Candidate validation and publication workflow; startup and file changes do not auto-publish.

The same first-phase PostgreSQL deployment also persists Invocation Evidence, the append-only Cost Ledger, durable idempotency records, terminal invocation summaries, and—when optional exact replay is enabled—the PostgreSQL-owned Replay Artifact Store in separate schemas/tables with independent retention and access policies. PostgreSQL is the sole durable authority for configuration, evidence, cost entries, idempotency, and Replay Artifacts; runtime retry, rate-limit, health, and circuit counters remain process-local in the single-instance phase. Provider credentials are owned by the configured SecretSource and are never copied into Gateway state. A separate cache component may serve policy-controlled Cached Degraded Results; cache contents are not the configuration, evidence, or Replay Artifact authority. Redis endpoint, transport protection, and cache Secret Reference are deployment-owned Bootstrap Configuration, while cache behavior is part of the PostgreSQL-backed Active Snapshot. Neither callers nor domain YAML bundles can override the Redis connection profile. Trace is emitted through OpenTelemetry, Metrics through a Prometheus-compatible surface, and Logs as structured JSON; their storage remains external to the Gateway.

Compiled Schema Cache is a distinct process-local optimization, not the Redis-backed Cached Degraded Result component or a Schema authority. It may retain sensitive Schema literals only inside bounded application memory, disappears on restart, and cannot bypass request preflight or the locked capability/resource identities.

Cache-policy disablement and reactivation are evaluated at Model Invocation admission and captured in an Invocation Cache Policy Snapshot; later publications affect only later admissions. Explicit Cache Revocation and cache-encryption key rotation/revocation are security exceptions that override that snapshot for cache eligibility, including already admitted invocations, without cancelling Provider work or changing a live result, Usage, Cost Ledger, or terminal outcome. The snapshot is Gateway request state, not an Agent Session or caller-provided session identifier.

Those security exceptions use one Cache Security Invalidation Fence: a cache read that started before the fence but has not yet emitted a hit is discarded, later writes are suppressed, and an already emitted cache result is not withdrawn.

If that discarded read was the final degradation option after Provider recovery is exhausted, the Gateway returns the previously classified live terminal result without another Attempt, retry, fallback, or revocation detail. A live success remains unchanged when only its optional cache population is skipped.

After authorization and Request Fingerprint checks, a same-key/same-fingerprint duplicate or replay resolves the original Model Invocation and reuses its admission-locked snapshots, including the Invocation Cache Policy Snapshot and Invocation Replay Policy Snapshot. It creates no fresh route or Provider Attempt and does not consult the current cache or replay policy, even after the original reaches a terminal `no_route` or `provider_unavailable` outcome; a new execution requires a new Idempotency Key. Cache Revocation, Replay Artifact Revocation, and encryption-key invalidation remain authoritative exceptions that may block cache- or replay-artifact reuse.

The `Idempotency-Key` header is optional; without it every accepted request is a new logical invocation with no key-based deduplication, replay, or status lookup. The only caller-visible exact-replay content entry point is the original `POST /v1/chat/completions` route repeated with the same key and Request Fingerprint; no `/replay`, Artifact download, Control Plane content-fetch route, or caller-addressable `artifact_id` exists. Because `stream` and `stream_options.include_usage` are part of the Request Fingerprint, changing either under an existing key is a 409 `conflict`, not a protocol conversion. A valid replay retains the original synchronous/SSE mode and usage-event intent. Replay Artifact expiry while the Binding Window remains active uses `replay_unavailable`; afterward, a non-content Idempotency Tombstone prevents reuse until the configured Key-Reuse Quarantine expires.

Idempotency identity is namespaced by `(Authorization Context.tenant_id, Authorization Context.subject, api_operation, idempotency_key)`; `subject` is required and the selected Authorization Adapter owns the guarantee that it is the same Stable Authorization Subject across credential refreshes. Adapter conformance fixtures verify that guarantee, while Gateway runtime checks only the frozen Context contract and never tries to infer semantic stability from request history. Two otherwise valid requests carrying different subjects are different principals and Idempotency Key Namespaces, not a Gateway-detected contract failure. Scopes are revalidated separately, and bearer-token bytes never define identity. A caller-controlled credential or local-JWT Claim/Context value that cannot authenticate is `unauthorized`; only a protocol-valid online-Authority `authenticated` decision whose source fields cannot form the promised normalized Context fails as `authorization_unavailable`. `dev` uses `subject=dev`. The single header value is opaque, case-sensitive, 1–255 visible ASCII bytes (`0x21`–`0x7E`), with no trimming, normalization, or duplicate-value joining. The `gateway.idempotency-index/v1` HMAC input is exactly `ASCII("gateway.idempotency-index/v1")` followed by four tagged fields in order: `0x01 || uint32be(len(tenant_utf8)) || tenant_utf8`, `0x02 || uint32be(len(subject_utf8)) || subject_utf8`, `0x03 || uint32be(len(operation_ascii)) || operation_ascii`, and `0x04 || uint32be(len(key_ascii)) || key_ascii`. Lengths are byte counts, and the bytes are the exact already-validated values without normalization. Gateway persists the resulting 32-byte `HMAC-SHA-256` Idempotency Index Digest as PostgreSQL `BYTEA` together with profile, `key_id`, and `key_version`; it never exposes that digest through APIs or telemetry. Raw keys never enter durable state or telemetry, and this HMAC key is distinct from Fingerprint and content-encryption keys. The Binding Window defaults to 24 hours and is capped at seven days; Replay Artifact TTL cannot exceed it and status retention cannot be shorter. An additional non-content Key-Reuse Quarantine defaults to seven days and is capped at 30 days. At `protected_until`, PostgreSQL atomically compares and creates the next monotonic protection-record generation under the namespace uniqueness constraint: exactly one contender binds the new invocation, and every loser observes that Binding and applies the ordinary same-Fingerprint replay or different-Fingerprint conflict rule. The prior invocation remains reachable only through `call_id`, and no unprotected interval exists.

The deployment-owned Idempotency Index Key Ring is referenced only from Bootstrap Configuration and contains exactly one active key version and at most eight verification-only versions. Its membership, roles, and versions form an immutable process-lifetime snapshot: new bindings use only active, lookup covers every retained version, and a different active version or membership becomes effective only after Gateway/Docker restart. v0.1 has no live reload, rotation API, or concurrent key-switch lock. Before admission readiness, startup uses PostgreSQL database time to reject removal of any version whose persisted Idempotency Binding or Idempotency Tombstone has not passed its `protected_until`; no raw-key persistence, online reindexing, or automatic old-version eviction is permitted.

A malformed Bootstrap reference, duplicate/invalid role or version, count overflow, or removal that violates `protected_until` is structural configuration failure and keeps Data Plane admission non-ready. Every keyed HTTP operation obtains the complete Ring through one all-or-nothing, just-in-time `resolve_many` lease: at most nine members, a deadline of `min(1 second, request remaining deadline)`, Adapter-internal parallelism at most four, and at most 32 concurrent process leases. A failed operation cancels remaining resolutions, erases acquired bytes, and does not retry. Local lease-capacity exhaustion rejects that access without entering Key Lockout; a retained member's missing, revoked, mismatched, malformed, or unavailable material is a material failure and does. Such failures are isolated even on first startup: readiness remains unchanged, calls without `Idempotency-Key` and lifecycle operations by `call_id` remain available, while every operation requiring the key ring returns `503 persistence_unavailable` without model execution or Provider work. An unresolved lookup is never treated as a miss.

The monotonic process-local Idempotency Index Security Fence defines the revocation observation boundary. Gateway observes revocation through a just-in-time resolution, metadata check, or supported SecretSource notification; it makes no instantaneous-detection promise for an externally changed file source. Observing either revocation or exact restoration advances the Fence generation. A result begun under an older generation cannot authorize a commit, disclosure, Replay read, cancellation mutation, or recovery from Lockout. Recovery requires a successful all-member Ring validation begun after the current Fence; stale success cannot clear a newer failure, and the generation never decreases. A still-protected revocation clears controlled in-memory bytes and locks all keyed operations, while an already admitted Model Invocation continues. The alternative recovery after PostgreSQL time passes the member's maximum `protected_until` still requires restart with a valid descriptor ring that omits it; Gateway never reconstructs the index or treats an ambiguous lookup as a miss.

In the default `execution_dedup_only` mode, a completed success with no retained content returns `409 replay_unavailable` from the Data Plane with `call_id` and an authorized status-query reference; the Gateway never fabricates an OpenAI success or returns a non-compatible status body on that route.

Replay Access receives fresh request/Trace identity and links to the original `call_id` only in restricted evidence. It passes normal authorization and consumes ordinary instance/tenant API QPS, but does not acquire Model Invocation or Provider concurrency Permits, Usage, or Cost Ledger entries; a separate lightweight replay-read concurrency ceiling protects Gateway resources. Exact Replay responses use `Cache-Control: no-store`; replayed SSE preserves normalized event order and terminal semantics without original timing and uses ordinary downstream backpressure limits. A client disconnect cancels only that Replay Access transfer and leaves the original invocation and Artifact unchanged.

Replay resolution revalidates the current Authorization Context and the original tenant/scope binding before key or content disclosure; failures use non-disclosing `401`/`403`. Disabling or restricting `encrypted_exact_replay` publishes a Replay Artifact Revocation that immediately blocks existing artifacts, including for already admitted invocations, while physical deletion and cleanup may be asynchronous and the original live execution remains unchanged.

Replay Artifact Revocation, including Replay encryption-key rotation/revocation, has one Replay Security Invalidation Fence: an uncommitted read is discarded with `replay_unavailable`, an emitted replay is not withdrawn, old-key artifacts are not dual-read or re-encrypted online, and new artifacts use only the current key.

Replay Artifacts are limited to complete successful sync results or normally completed SSE sequences allowed by content-retention policy, including successful fallback, Local Structured Repair, and eligible complete Cached Degraded Results. Partial/interrupted, failed, cancelled, uncertain, validation-invalid, and Safety Refusal outcomes retain no raw replay content. An artifact-write failure leaves the live result and metering unchanged, records safe evidence, and causes later same-key content access to return `replay_unavailable` without Provider work.

When exact replay is enabled, Replay Artifact content and lifecycle metadata are stored in the PostgreSQL Replay Artifact Store, isolated from ordinary Evidence and telemetry. A confirmed absent, expired, revoked, or retention-ceiling-skipped artifact returns `replay_unavailable`; an unavailable PostgreSQL read returns `persistence_unavailable` without re-execution, routing, fallback, or Provider work. The published per-Artifact and deployment-owned retained-content ceilings are checked before a write; exceeding either skips the artifact without truncation or semantic rewriting and leaves the completed live response and metering unchanged. For SSE, a Replay Capture Cutoff stops normalized capture at the ceiling while the live event stream continues unchanged through `[DONE]`.

The Replay Artifact Commit Boundary follows the terminal transaction: the successful result, final Usage, Cost Ledger, terminal Evidence, and Idempotency binding are durable before the Gateway returns the synchronous response or flushes the SSE `[DONE]`; bounded Replay Artifact Async Persistence then proceeds independently through a bounded process-local Replay Artifact Write Queue with separate task-count and estimated-byte limits. Tasks are FIFO by terminal-commit handoff time; a retry stays with its original task and cannot consume another slot. Queue saturation drops only the new Artifact write and does not block live execution. A dedicated bounded Replay Artifact Persistence Worker performs writes through a separate bounded PostgreSQL Persistence Pool, outside Model/Provider concurrency and readiness dependencies. Each task has a bounded task deadline covering queue wait, write, and its one permitted retry; expiry releases reservations and drops the task. The task carries a deterministic, uncompressed Gateway Replay Artifact Wire Form, and its canonical bytes plus fixed encryption/metadata overhead are the size-accounting basis. The Wire Form is stored in a versioned authenticated-encryption envelope with nonce, key identity, AAD bindings, and integrity metadata; its Content Hash is computed before encryption and verified after decryption. Before the first write, Replay Task Revalidation applies the current Resource Ceiling, policy, expiry, revocation, and security Fence; stricter state drops the task. A failed, interrupted, queued, or restarted Artifact write cannot roll back or regenerate the live result. A duplicate arriving while that write is pending still receives `replay_unavailable` and never joins it or starts Provider work. A transient PostgreSQL/network write failure gets at most one bounded retry with jitter; immediately before retry, the Replay Persistence Retry Gate rechecks expiry, policy, and the security fence. Policy, integrity, ceiling, capacity, and SecretSource contract failures do not retry. Each write is keyed by immutable `artifact_id`/`call_id` and is idempotent: an unknown outcome can only confirm or complete the same record, never duplicate or overwrite content. A key collision with a different content hash preserves the first record and ends the new write as `persistence_unavailable`. Exact Replay preserves the original response/event identity and protocol while the access request uses fresh request/Trace identity and only the replay marker header. PostgreSQL cleanup removes expired or revoked content asynchronously after logical ineligibility is already enforced; cleanup delay or restart does not affect readiness or live execution. Replay reads see only complete committed records. A partial, integrity-failed, or undecryptable record is treated as `persistence_unavailable`; only a confirmed absent or policy-ineligible record uses `replay_unavailable`.
PostgreSQL cleanup retains a minimal non-content Replay Artifact Tombstone (identity, status, expiry, policy/revocation epoch, safe reason) at least until the original Idempotency Binding expires; an explicit longer key-reuse quarantine may extend it. Replay reads perform a final Replay Access Fence Check after decryption and integrity verification and before the first downstream byte; a pre-emission Fence change discards the access, while an emitted replay is not withdrawn. Replay Key Failure Isolation keeps SecretSource and key-format failures within Artifact persistence/access and outside readiness, Provider Health, Circuit state, permits, fallback, and live metering.

Replay Artifact expiry is a fixed deadline from the original successful terminal commit and is never extended by reads, delayed writes, cleanup retries, or restarts. A material policy tightening immediately invalidates existing Artifacts that no longer fit the effective TTL, ceiling, eligibility, or access scope; non-semantic relabeling does not. PostgreSQL capacity pressure rejects only new Artifact writes, preserves valid existing Artifacts, and does not affect readiness, Provider routing, live responses, or metering.
The same Replay Security Invalidation Fence orders material policy tightening and encryption-key revocation: uncommitted reads are discarded, post-fence writes are suppressed, and emitted replays remain visible. A policy expansion never resurrects invalidated or missing content or extends an existing expiry. Exact-replay publication requires explicit TTL, encryption Secret Reference, retention ceilings, eligible result types, and access scope; no field is silently defaulted or widened.
Each Model Invocation locks an Invocation Replay Policy Snapshot from the published Active Snapshot, including mode, TTL, key identity, ceilings, eligibility, and access scope. Same-key reuse follows that snapshot, subject to the security fence. A missing SecretSource key skips a new Artifact write without changing live execution; inability to obtain a key for an existing Artifact is a `persistence_unavailable` read failure. Replay policy version/digest is canonical PostgreSQL configuration and audit metadata; key material never enters Gateway state.
Exact Replay policy validation is local to the Candidate workflow: a Secret Reference is checked without live SecretSource access, and key availability is deferred to Artifact I/O. The canonical policy and its revocation epoch are committed as one Active Snapshot publication; the in-process snapshot and Replay Security Invalidation Fence advance only after that transaction succeeds.

The Replay Artifact Wire Form uses a versioned AES-256-GCM authenticated-encryption envelope, and its Content Hash is fixed as `sha256:<64 lowercase hex>` over canonical pre-encryption bytes and verified after decryption. Each Artifact operation resolves the key just in time from SecretSource; key bytes exist only ephemerally for that operation and are never persisted or process-cached. SecretSource must return an immutable key identity/version plus exactly 32 raw AES-256 bytes; malformed or ambiguous material is a non-retryable persistence failure. Key rotation/revocation advances the Replay Security Invalidation Fence, drops queued tasks bound to older key identities, and never performs dual-key reads or re-encryption.

## 6. Communication model

The Data Plane uses OpenAI-compatible synchronous JSON and SSE streaming semantics under `/v1`. The Control Plane, cancellation, and status recovery use a separate versioned Gateway-native JSON protocol under `/gateway/v1`. Lifecycle lookup is available either by `call_id` through `GET /gateway/v1/invocations/{call_id}` and `POST /gateway/v1/invocations/{call_id}/cancel`, or by the original key through `GET /gateway/v1/invocations/by-idempotency-key` and `POST /gateway/v1/invocations/by-idempotency-key/cancel`. The key-based routes require the single validated `Idempotency-Key` header and derive the namespace with the current Authorization Context plus the fixed original operation identifier `chat.completions.v1`; they never use the status/cancel route name as `api_operation`. A `call_id` route carrying `Idempotency-Key` is rejected as `400 invalid_request` rather than choosing an implicit locator. All four routes use one observable evaluation order: authentication (`401`), exact route authorization (`403`), locator/header syntax (`400`), required Gateway/PostgreSQL/Index-key dependencies (`503`), then target lookup or cancellation and its found/non-disclosing `200` result. Every response carries `Cache-Control: no-store`, including success, validation, authentication/authorization, unknown-target, conflict, and dependency-failure responses. For either locator, an absent target, a target outside retention, or a target under another tenant/subject is non-disclosing. Status returns exactly HTTP 200 with a fresh `X-Request-Id` and body `{"state":"unknown_or_expired"}`; cancellation returns the same status and headers with body `{"state":"unknown_or_expired","cancellation_accepted":false}`. Both strictly omit `X-Gateway-Call-Id`, `call_id`, and every other response field; explicit authentication or authorization failure remains `401` or `403`. Gateway allocates a canonical lowercase UUIDv4 `call_id` under a PostgreSQL uniqueness constraint before creating a Model Invocation or doing Provider work. A collision permits at most three UUID generation/insert attempts; all remain pre-admission and create no Invocation, Attempt, Evidence, or cost. Exhaustion returns HTTP 500 `internal` and increments only a low-cardinality, ID-free counter. A reverse proxy exposes a separate internal listener or hostname for Control Plane configuration, audit, and privileged operational resources and enforces their route allowlist before Gateway; public Data Plane ingress does not route them. Gateway does not accept caller-supplied forwarded/internal-marker headers as management-ingress proof. Invocation status and cancellation remain caller-authorized Data Plane lifecycle extensions despite their Gateway-native route family. Status exposes only lifecycle/Attempt/Usage/cost and safe evidence summaries, and cancellation affects only a still-running original invocation; neither surface decrypts, returns, downloads, revokes, or transforms Replay Artifact content, even when generic encrypted content retention is enabled. If the original invocation is terminal while Replay Access is transferring, the cancellation route returns `already_terminal`; only disconnection or cancellation of the replay HTTP request context stops that transfer. Structured JSON recovery is application-owned and ordered: bounded repair of the existing JSON result first, followed only when still invalid and before external commitment by at most one identical-request same-candidate retry for an allowlisted `json_*` reason. This path never switches Provider/model and never contributes to Provider health or circuit state. Streaming disconnects cancel the active invocation; synchronous calls use the Gateway-native cancellation extension. Status responses are always tenant-scoped content-free summaries.

The closed v0.1 configuration HTTP surface on the management listener is exactly `GET /gateway/v1/config/active`, `GET /gateway/v1/config/revisions`, `GET /gateway/v1/config/revisions/{revision}`, `GET /gateway/v1/config/revisions/{revision}/export`, `POST /gateway/v1/config/validate`, `POST /gateway/v1/config/revisions`, `POST /gateway/v1/config/revisions/{revision}/publish`, `POST /gateway/v1/config/revisions/{revision}/rebase`, and `POST /gateway/v1/config/revisions/{revision}/rollback`; none is exposed on public Data Plane ingress. JSON representations require strict UTF-8 `application/json`; YAML submissions and exports use UTF-8 `application/yaml`. Unsupported request media types return 415, unsupported `Accept` values return 406, and every configuration response is `Cache-Control: no-store`. v0.1 emits no ETag; every `If-*` Header is rejected as `invalid_request`/400 and can never produce 304/412. A read or validation request carrying `X-Gateway-Command-Id` is likewise 400. Candidate creation, successful rebase, and successful rollback return 201 plus the new Revision resource in `Location`; every other success is 200 and no route returns 204. Static route registration and canonical positive-`BIGINT` revision validation prevent resource-name collisions.

Validate and Candidate creation accept the same closed Configuration Submission union. JSON selects exactly `bundle` or `change_set` through `kind`; YAML represents only a full Bundle. JSON Patch and persistence-row mutation are forbidden. Revision references are canonical strings in both JSON and YAML, including the empty-state string `"0"`; YAML numeric zero is invalid. The Bundle transport envelope carries `schema_version`, `base_revision`, optional non-domain metadata, six required stable-ID-keyed registries (`providers`, `provider_model_bindings`, `model_aliases`, `routing_policies`, `pricing_tables`, and `safety_policies`), required Gateway-wide `resource_policies`, and optional Gateway-wide `replay_policies`; it contains no `service_requirements` section. Registry values do not repeat their key identity, and every relationship uses an explicit stable-ID reference. Versioned constant leaf defaults and the omitted replay mode are materialized before diff, persistence, digest, and export; deployment hard ceilings remain outside the Snapshot, with no stricter policy represented by explicit inherit/no-additional-tightening semantics. Every Candidate persists both this complete canonical resolved Snapshot and one deterministic canonical typed Change Set relative to its base. A full Bundle is converted through a domain-semantic diff into that Change Set, and rebase replays the stored Change Set rather than diffing arbitrary persistence rows.

The Change Set wire is a closed union of whole-resource registry `add|replace|remove` and whole-singleton `replace` operations. Operations form an order-independent, duplicate-target-free set; canonical order is Bundle section order then Resource ID UTF-8 bytes, while authorization is derived from submitted targets before no-op normalization. Gateway atomically applies the set to a provisional Snapshot, never cascades deletion, and validates the completed graph. Rebase is a whole-target three-way comparison of original Base, intended result, and current Active: unchanged current targets accept intent, already-intended targets converge to no-op, and every other same-target change conflicts without field merge. Safe configuration diagnostics are closed `{reason,path}` values, deterministically ordered and capped at 100 with an explicit truncation flag; they never disclose raw or sensitive configuration material.

Validation success is a closed result containing validity, normalized base, prospective digest and Change Set, bounded impact, and diagnostics. An invalid semantic result exposes no partial digest, Change Set, or impact. Candidate-producing mutations return one Revision DTO and publication returns one Active Revision DTO. Configuration failures retain the common Gateway `error.code`/safe English `message` envelope; optional bounded diagnostics live only under `error.gateway`, while access correlation remains in `X-Request-Id`.

Provider configuration is separated into closed administrative status, Adapter, endpoint, credential reference, egress, transport, health, and rate-limit blocks; it owns no concrete model or routing choice. A Provider Model Binding then names one Provider and opaque upstream model, intersects its streaming/Tool/Structured Output declaration with the Adapter contract, declares context/output Token limits, and references pricing. Candidate priority, weight, generation, retry, fallback, and degradation remain outside the Binding.

Provider leaf contracts are deliberately narrow: registered Adapter identity/version, one approved API-root URL, one Secret Reference, deny-by-default host/network Egress with no proxy, HTTP/1.1 plus mandatory TLS verification and bounded connection lifetime, optional same-origin isolated active probe, and positive concurrency/QPS/burst limits. The transport pool derives its connection capacity from the Provider rate limit. Pricing uses ISO currency and decimal per-million-Token rates with fixed rounding. Safety Policy v0.1 only makes Provider refusal terminal and defines no content-rule DSL. Exact replay is either content-free execution deduplication or a same-subject encrypted branch with TTL, per-Artifact size, key reference, and result-type constraints; retained-content capacity is deployment-owned.

Degradation Policy is not another registry. It is a closed projection owned and atomically published by a Routing Policy; the Routing Policy Resource ID and Revision plus projection digest form its evidence identity. A Model Alias selects degradation by selecting that Routing Policy. The closed Routing Policy also owns one fixed seeded priority/weight selection profile, bounded retry values, and pre-commit-only fallback. Router filters hard capability, safety, administrative, health/circuit, egress, and capacity conditions before separating full and reduced service; it exhausts each priority tier using the invocation's deterministic weighted-without-replacement order, retries the same candidate before advancing when authorized, and reevaluates dynamic eligibility without reordering. The External Commitment Point ends every recovery/substitution path.

Degradation execution order is fixed rather than operator-arranged: full-service live Attempts, optional reduced-service Candidates, optional cache, then the original classified live failure. Reduced service never relaxes hard capability or Safety constraints. Cache is disabled by default and, when enabled, retains only complete successes under the Execution Fingerprint key profile with a required SecretSource encryption-key reference; its stale duration is additional to its fresh duration. Only the established availability/capacity reasons can reach cache, while Safety, structured-validation, authentication/authorization, request/configuration, cancellation, and uncertain outcomes cannot. Missing Redis or key material disables only that cache stage and never substitutes a cache error for the live failure or changes readiness. Full and reduced Cache Result Variants have separate identities and never overwrite one another; lookup order is fresh full, fresh reduced, stale full, stale reduced, with reduced variants eligible only under an enabled reduced-service policy. Result provenance is composable at the HTTP boundary: cache source uses the existing result-mode and age headers, while reduced service uses an independent service-level header. A cached reduced result carries both dimensions, preventing either deviation from being hidden.

A Model Alias contains only unique Binding candidates, routing/safety references, generation defaults, and local-extraction inheritance. Candidate Service Level distinguishes full from disclosure-bearing reduced service without weakening capability filters; priority and seeded weight order candidates within the appropriate stage. The Alias max-output default also caps caller override. The Gateway-wide Resource Policy is limited to Structured Output extraction/error collection, Idempotency lifetimes, Routing Evidence retention, and six high-value inheritable request/stream/duration ceilings. Cache behavior remains routing degradation, while cache connection and detailed parser/worker hard limits stay in their owning deployment boundaries.

Candidate creation requires its submitted base to equal the transaction-time current Active Revision; whenever Active is empty, `"0"` may create another immutable null-base Candidate even when earlier Candidates exist. Publish accepts only a Candidate based on the transaction-time Active state. Exactly one null-base Candidate may win the empty Active compare-and-swap, and the same transaction marks every other null-base Candidate Stale. Rebase accepts only a Stale Candidate and targets the current Active Revision; a replay conflict returns 409 with one bounded, redacted conflict list, creates no Revision, and performs no inline resolution. Rollback accepts only a Superseded source, rejects the current Active source as a semantic no-op, and creates a Candidate based on the current Active Revision with `rollback_of` naming the source; a later ordinary publish remains mandatory. Every lifecycle or mutable-state precondition failure in these commands is a deterministic HTTP 409.

Configuration requests use one short-circuit evaluation pipeline after management-listener and route-template selection: HTTP framing/size; authentication; any route-fixed scope; `Accept` and request media type; conditional/Command/Header, path, and query syntax; strict UTF-8 JSON/YAML parsing and closed structural Schema; touched-domain discovery and dynamic union-scope authorization; required PostgreSQL/dependencies; mutation Command Index lookup/reservation; mutable Revision/Active state plus semantic/reference validation; then presentation or atomic effect. Validate/create derive touched domains from the submission. Rebase may read only the immutable touched-domain metadata of its source before dynamic authorization, without examining mutable state or exposing content; a missing source produces the authenticated 404 result. Any failure stops later stages. Control Plane recovery bypasses Data Plane readiness, not authorization or PostgreSQL.

Candidate creation, publish, rebase, and rollback each require exactly one distinct canonical lowercase UUIDv4 in `X-Gateway-Command-Id`; a successful original or idempotently replayed command response echoes the same header. The Configuration Command Index is separate from Model Invocation idempotency and the Idempotency Index Key Ring and is keyed by `(tenant_id, subject, operation, command_id)`. Transport, authentication, authorization, media-type, syntax, and structural-Schema failures never enter it. After the command is structurally valid and its `gateway.config-command-digest/v1` digest exists, Gateway looks up or reserves the Index before inspecting mutable configuration state. It stores successful outcomes and deterministic 409/422 outcomes, but never stores 429, timeout, or transient 5xx outcomes. Concurrent uses of the same identity wait only within their request deadline for the first transaction: commit replays its stored outcome, rollback lets exactly one waiter become the executor, and a waiter's expired deadline returns `deadline_exceeded` without persisting a result. Under the digest profile, Gateway Schema-parses the complete semantic command object, excludes authentication/Authorization Context material and the command header, applies RFC 8785 JSON Canonicalization, and hashes the exact canonical bytes with SHA-256; JSON field order and YAML formatting therefore do not change identity. Reusing the same Index identity with another digest returns 409 without executing state checks or mutation. v0.1 performs no automatic Configuration Command Index deletion and retains entries for at least the lifetime of configuration history. Validation is a no-write dry run and accepts no command header. General Audit/Invocation Evidence/Cost queries, reconciliation beyond the specified import contract, manual uncertain resolution, Capability Revocation, and cleanup have no v0.1 HTTP route and are deferred to v1; no generic `/admin`, wildcard scope, or undocumented private route substitutes for them.

Configuration reads are deliberately bounded. When no Active Revision exists, the Active route returns HTTP 200 with exactly `{"active":null}`. The Revision list is newest-first by Revision, defaults to 50 entries, caps the requested page at 200, and uses an exclusive Revision keyset; it exposes neither a total count nor state filtering. After authorization, a missing detail or export Revision is 404. Revision detail is the common metadata DTO plus a bounded, deterministic, redacted semantic diff relative to its base and never includes the complete Snapshot. Export alone returns the complete deterministic UTF-8, no-BOM YAML with LF line endings and exactly one final LF; its exported `base_revision` is the exported Revision itself. That file is directly apply-ready only when the Revision remains current Active. Candidate, Stale, and Superseded exports are archival views until an operator explicitly selects the current Active base, or `"0"` while Active remains empty, and submits a new command through ordinary validation. `X-Gateway-Snapshot-Digest` carries the digest as metadata and is explicitly not an ETag.

Configuration resource identity uses one exact lowercase ASCII ID profile across the six registries and their references (FR-949); changing an ID is a remove/add operation. Change Sets operate on complete registry values through add/replace/remove and replace each Gateway-wide singleton as a whole; Provider embedded state and Alias candidate lists share their parent's atomic boundary. Provider and Binding status is explicitly enabled or disabled and remains distinct from runtime health/circuit state. API Layer Submission DTOs carry exactly one self-contained `bundle` or `change_set` payload, and YAML carries the Bundle directly. Application lifecycle commands receive the path source plus an explicit expected Active; publish additionally requires the Candidate Snapshot Digest. Rebase and rollback use that expected Active as their target base. Creation and publication descriptions are immutable history metadata: they enter command identity and Audit, while executable Snapshot content and its digest exclude them. Export reconstructs creation metadata from the selected Revision without substituting a later publication description. Exact fields and text rules are defined by FR-949–FR-956 and the configuration section of Detailed Design.

## 7. Security and data boundaries

The v0.1 acceptance path includes a real end-to-end Query: a caller reaches the OpenAI-compatible API, the Gateway routes through its internal domain protocol and selected HTTP/1.1 Adapter, a configured Provider executes the request against a real model, and the translated result returns to the caller. The minimum live Smoke topology is one Provider, one Model Binding, and one Model Alias; multiple Providers, fallback, and complex routing remain supported and are verified separately with MockTransport/strategy tests. MockTransport remains the deterministic seam for contract and failure tests; it is not evidence that the live Provider path is wired.

Startup mode and authorization topology are deployment/bootstrap concerns. When a Bootstrap source omits `startup_profile`, v0.1 resolves it to `dev`; when that effective profile is `dev` and `authorization.mode` is omitted, it resolves to `dev_bypass`. `production` never has an authorization default and must explicitly select exactly one of `local_jwt` or `online_authority`. Shipped Docker examples spell out both fields even when they equal the development defaults, and the resolved values—not merely the source omissions—enter the canonical Bootstrap digest and startup evidence. The Gateway process listens on `0.0.0.0` inside its container, while Docker Compose publishes the `dev` ports only on host loopback by default and requires an explicit deployment setting for any wider host exposure. `dev` with a production mode and `production` with bypass are invalid; requests cannot select, combine, weaken, fall back between, or degrade authorization modes. `dev_bypass` ignores any Authorization Header rather than parsing it, skips bearer/permission validation on every Gateway API for local or controlled Smoke calls, and supplies the deterministic Development Authorization Context `subject=dev`, `tenant_id=dev`, `issuer=urn:llm-gateway:dev`, `audience=llm-gateway`, `expires_at=9999-12-31T23:59:59Z`, `authentication_method=dev_bypass`, and `scopes={dev:*}`. `local_jwt` is a closed Bootstrap branch that selects one read-only mounted PEM or JWKS public-key file, its file form, an Issuer, one target Audience, and—for PEM only—the explicit Key ID. The process reads that file once during startup; a file change requires restart, and inline key material, environment-variable keys, URLs, remote retrieval, and SecretSource are forbidden. Its v0.1 cryptographic profile is RS256 with 2048–4096-bit RSA public keys; every usable local key and every Token has a unique explicit `kid`, including single-key deployments. The file is at most 256 KiB and a JWKS contains at most 32 keys. Remote JWKS retrieval and online signing-key rotation, multi-Authority chains, and authorization fallback are deferred. Invalid or contradictory profile/mode configuration fails closed and cannot silently activate development bypass. Every topology retains SecretSource-only Provider credentials.

Authorization failures are normalized without conflating caller input, Adapter output, dependency failure, or a request-local event. Outside `dev_bypass`, the API accepts exactly one original `Authorization` Header and never comma-combines duplicates. Its scheme is case-insensitive `Bearer`, followed by exactly one ASCII SP and a 1–16,384-byte ASCII `token68` value; leading or trailing OWS, controls, non-ASCII, a second space, duplicate Headers, and comma-joined credentials are invalid. The immutable Authorization Context requires opaque UTF-8 `subject` and `tenant_id` strings of 1–255 bytes, an `issuer` of 1–2048 bytes, one Adapter-matched logical `audience` of 1–255 bytes, a UTC Instant `expires_at`, `authentication_method` equal to exactly `dev_bypass | local_jwt | online_authority`, and a present immutable `scopes` set that may be empty. The method records the verification path, not a Token type. Context strings reject control characters and leading or trailing whitespace; Gateway does not trim, fold case, or perform Unicode normalization. `tenant_id` is retained for correlation and Idempotency Namespace isolation without introducing a first-phase tenant-management or broader isolation model.

A missing, duplicate, malformed, unsupported, unverifiable, expired, or not-yet-valid Bearer credential—or a local-JWT failure of Token algorithm, `kid`, signature, issuer, audience, temporal or required Claim mapping—is caller authentication failure and returns HTTP 401 `unauthorized`; an online Authority's protocol-valid `status=unauthenticated` decision does likewise. Every authentication 401 carries `WWW-Authenticate: Bearer` and its public body omits the detailed internal reason. An eligible online Authority/service-credential dependency failure maps to HTTP 503 `authorization_unavailable` and sets the Live Fault Latch; caller cancellation, Gateway shutdown, a timeout caused solely by a shorter caller deadline, and local live-capacity exhaustion remain request-local and do not set or refresh it. Authority HTTP 401/403 specifically means the Gateway service credential was rejected and never represents the caller's credential result. A closed `authenticated` decision whose identity or scopes cannot form the Context is request-local `authorization_context_contract_invalid` and HTTP 503; it never closes the Probe Gate or sets a new live fault, while its protocol-valid 200 decision may clear an older Live Fault Latch under the generation rule. The Adapter owns semantic stability of `subject`; paired-credential conformance fixtures compare refreshes, while the request path checks the frozen Context contract only. An Adapter registration, field mapping, local key set, or topology defect detectable before serving requests is invalid configuration and keeps Data Plane admission non-ready as `gateway_not_ready`, rather than producing a request-local 503. These failures perform no cache lookup, configuration/status disclosure, admission, or Provider activity, receive no Gateway retry, emit no `Retry-After`, never substitute stale or inferred authorization, and do not affect Provider Health State. `dev_bypass` synthesizes its Context and cannot produce a runtime Adapter-result contract failure. After either production Adapter returns a valid Context, Gateway—not the Authority—returns HTTP 403 `forbidden` when the scope set is empty or lacks the exact permission required by the selected operation.

Local JWT Claim mapping is fixed rather than deployment-scripted: `sub`, `tenant_id`, `iss`, `aud`, and integer NumericDate `exp` are required; integer NumericDate `nbf` and `iat` are optional, and `scope` is optional. `iss` exactly matches the configured Issuer. `aud` is either one string or a duplicate-free string array and must contain the one configured target Audience; only that matched value enters the Context. `scope` is either a standard U+0020-delimited ASCII scope string or an array of strings; absence maps to an empty set, and accepted values then pass the common scope profile. Unknown Claims are ignored. The fixed temporal leeway is 30 seconds: `now + 30s >= nbf`, `iat <= now + 30s`, and effective expiry is `exp + 30s`, which becomes Context `expires_at`; equality at that Instant is expired. v0.1 imposes no additional maximum Token lifetime.

The local JWT parser accepts only an unpadded, canonical-Base64url, three-segment JWS Compact Token of at most 16 KiB, with a decoded protected Header of at most 4 KiB and Payload of at most 12 KiB; both JSON values are strict UTF-8 objects. Duplicate JSON members, non-finite numbers, `crit`, `zip`, embedded `jwk`, `jku`, and `x5u` are rejected. `typ` may be absent and, when present, is exactly `JWT` or `at+jwt`. Token `alg` must be exactly `RS256`; a missing or unknown Token `kid` is 401. Every configured `kid` is 1–128 visible ASCII bytes. A PEM file contains exactly one SPKI or PKCS#1 RSA public-key object, no certificate or additional PEM object, and obtains its mandatory `kid` from Bootstrap. A JWKS contains at most 32 keys, derives trust only from each JWK's RSA `n` and `e`, and requires unique explicit `kid` values; optional `alg`, `use`, and `key_ops` must respectively be `RS256`, `sig`, and exactly `["verify"]`. Bounded certificate metadata may be ignored but never establishes trust. Private material, remote key locators, HS/EC/OKP/`none`, duplicate Key IDs, JWK algorithm/use/operation mismatch, and reliance on certificate metadata are startup defects that keep admission non-ready. Parser or Claim failure never begins Provider work or changes Provider Health/Circuit state.

Authorization remains valid for one access only if the atomic Admission statement satisfies `expires_at > statement_timestamp()` against PostgreSQL database time. Equality is expired; failure creates no Model Invocation and performs no Provider work. Once that checkpoint commits, expiry is not rechecked for the same invocation: queueing, synchronous generation, and SSE may cross the Instant, while every later status, cancellation, or Replay access authenticates again.

`online_authority` exposes the same process-local, non-persistent `unknown | available | unavailable` readiness state, derived internally from a Probe Gate and a Live Fault Latch under one monotonic observation generation. Startup leaves the Probe Gate unresolved and exposes `unknown` only while no eligible live fault has been observed; an eligible Authority/service-credential dependency fault immediately exposes `unavailable`, as does a resolved-closed Probe Gate. Caller cancellation, Gateway shutdown, a timeout caused only by a shorter caller deadline, and process-local live-capacity exhaustion do not set or refresh the Latch. A later-generation successful Probe opens only the Probe Gate and can never clear a latched live failure. A protocol-valid live HTTP 200 decision—either `authenticated` or `unauthenticated`, including one whose authenticated Context later fails normalization—clears the Live Fault Latch only when that operation began after the fault generation. `available` therefore requires an open Probe Gate and a clear Live Fault Latch. Whenever the Probe Gate is open, any normally protected Data Plane or Control Plane request may run its ordinary live authentication before general Data Plane readiness, even when another readiness cause such as absent Active configuration also exists. A valid decision clears the Latch and the same request then follows route-specific permission, persistence, configuration-recovery, and readiness checks; unauthenticated still returns 401 and Context-invalid still returns 503. Listeners continue accepting direct traffic while `/readyz` is 503, bounded only by the existing live pool; there is no recovery single-flight, shared result, synthetic canary, or reset endpoint. A request cannot use live success to open an unresolved or failed Probe Gate. Older Probe or live completions cannot overwrite a later failure or recovery.

The scheduler starts the first `AuthorizationPort.check_readiness()` Probe immediately rather than waiting one interval. Later Probes are due every five seconds, have one shared two-second operation deadline and no retry, and never overlap; a tick while one is in flight is coalesced or skipped. Bootstrap fixes a distinct `probe_endpoint` on the exact same origin as live introspection. The Probe sends `GET` with no body and the separately resolved least-privilege Bearer service credential. Success is exactly HTTP 200 plus the closed UTF-8 JSON object `{"protocol_version":"gateway.authorization.probe/v1","status":"ready","authority_id":"..."}`. The configured `authority_id` is a 1–255-byte opaque UTF-8 value with no control character or leading/trailing whitespace and is compared exactly without case folding or Unicode normalization. The Probe uses the live response's identity encoding and header/body ceilings; any other status, media type, version, shape, duplicate/unknown member, or identity mismatch fails the Probe Gate. `/readyz` reads only the derived local state. v0.1 adds no debounce, circuit breaker, half-open state, backoff, or durable authorization-health record. The Probe never reuses caller Tokens, and an online Adapter without this safe contract cannot become ready. Each externally visible state transition emits one warning or recovery Log while repeated same-state observations update bounded counters without repeating the transition Log. `dev_bypass` and `local_jwt` have no online-Authority readiness dependency, and liveness never depends on this state.

Pre-admission authorization failure creates no `call_id`, Model Invocation, Invocation Evidence, Cost Ledger entry, or PostgreSQL authorization-health row. It emits only a security-oriented structured Log, OTel HTTP/Auth spans, and low-cardinality Metrics. Logs and spans may carry request/Trace identity, selected topology, Adapter version, normalized reason, and latency; Metrics carry only bounded topology/Adapter/reason dimensions and latency, never request- or Trace-level identifiers. Tokens, Claims, `subject`, `tenant_id`, the Authorization Authority endpoint, raw Authority responses, and raw exceptions are forbidden from every signal.

Idempotency Key Lockout is also an explicit operational security signal without becoming a readiness dependency. Gateway exposes one process-global 0/1 Lockout Gauge, bounded transition and keyed-rejection counters by normalized reason and keyed operation family, one safe structured Log on entry, and one on recovery; repeated observations do not repeat transition Logs. Deployments may alert on the Gauge even though `/readyz` is unchanged. A keyed access rejected before admission by material failure or the Index Security Fence may emit only its safe HTTP Span/access Log and these signals; it creates no `call_id`, Model Invocation, Invocation Evidence, Cost Ledger entry, Replay Artifact access, or PostgreSQL key-health row and omits `X-Gateway-Call-Id`. Request-specific correlation remains confined to that Log/Span. No signal contains key bytes, raw Idempotency Keys, Index Digests, member key identity/version, Secret References, tenant, subject, credentials, or another unbounded identity.

In `online_authority` mode, the Authorization Port is implemented by a replaceable, explicitly versioned HTTP JSON introspection/context Adapter and is valid only with the production startup profile. Its closed Bootstrap branch contains exactly `live_endpoint`, `probe_endpoint`, `authority_id`, `live_service_token_secret_ref`, `probe_service_token_secret_ref`, and a non-empty canonical CIDR Authority allowlist in addition to the mode discriminator; the two endpoints have distinct fixed paths on one exact origin, and requests override none of them. HTTPS with TLS 1.2 or newer, certificate-chain and hostname verification, and the independent Authority allowlist are mandatory. Userinfo, query, fragment, redirect following, configured/environment-discovered proxies, HTTP, loopback, private destinations, and development transport exceptions are all forbidden. Every new connection resolves DNS again and proceeds only when every returned address is allowed; a mixed result is rejected as a whole. Live introspection is `POST` with `Content-Type: application/json`, `Accept: application/json`, UTF-8 body, and no compression. Its closed request object is exactly `protocol_version="gateway.authorization.introspection/v1"`, `credential_type="bearer"`, and `credential`, where `credential` is the caller Token bytes after the API Layer removes the validated Bearer syntax; no trimming or normalization occurs. Duplicate or unknown members are invalid. Each live or Probe operation resolves its own service Secret exactly once after its deadline begins, and Secret resolution plus all HTTP work share that operation's two-second deadline. SecretSource returns a separate raw 1–16,384-byte ASCII `token68` with no scheme for each reference; the Adapter rejects whitespace, controls, non-ASCII, comma, internal `=`, or any other invalid byte rather than trimming, splitting, decoding, padding, or normalizing, then creates exactly `Authorization: Bearer <token>`. It never caches plaintext across operations and erases the operation-scoped Credential Lease on every exit. Authority 401/403 therefore discards that lease without a same-request retry; a later operation resolves its reference again. Caller and service credentials, request body/headers, raw response, and raw exceptions are excluded from Logs, Trace, Evidence, and metrics.

Live introspection has a total deadline of `min(2 seconds, request remaining deadline)`, performs no retry or hidden queue, and uses a dedicated HTTP/1.1 pool capped at 64 simultaneous operations. Probe uses another HTTP/1.1 pool capped at one operation and with no hidden acquisition queue. The pools share no connection, credential, or permit. DNS, connection, request write, response read, pool acquisition, and the preceding Secret resolution all consume the one operation deadline; HTTP-library retries are zero. Both pools use a fixed 30-second idle timeout and five-minute maximum connection lifetime; a connection at either bound accepts no new acquisition, and each replacement connection re-resolves and revalidates every address. Caller cancellation cancels the in-flight live operation. Responses must be UTF-8 `application/json`, accept only identity content encoding, and contain at most 64 headers, 16 KiB aggregate header bytes, and 64 KiB decoded JSON. Exactly HTTP 200 carries one closed decision envelope. `unauthenticated` is exactly `{protocol_version,status}` with the accepted protocol version and no identity fields. `authenticated` additionally carries exactly string `subject`, `tenant_id`, `issuer`, and `audience`, RFC 3339 UTC string `expires_at`, and a string-array `scopes`; Gateway, not the Authority, adds `authentication_method=online_authority` and decides route permissions. A valid authenticated envelope that violates the Context contract is request-local `authorization_context_contract_invalid`. Secret resolution/credential-profile failure, runtime DNS/allowlist/TLS/connect/write/read failure, exhaustion of the full two-second Authority budget, 204 or any non-200 status, response resource/encoding/media/UTF-8/JSON/protocol failure, or non-decision envelope is eligible `authority_dependency_unavailable`; Authority 401/403 service-auth rejection, 429, and 5xx are included and never become caller unauthentication. Caller cancellation, shutdown, a shorter-caller-deadline exhaustion, and local live-pool saturation retain their own request outcome without setting the Latch. A later protocol-valid live 200 decision may clear an older Latch under the generation rule above. No Provider request begins on any failure. `local_jwt` is a separate local-verification Adapter, not an online-Authority fallback. An independently deployed compatible open-source Authority may implement the contract, but the Gateway side remains production-only HTTPS with no private or development transport exception.

Gateway owns a closed, case-sensitive, exact-match route-to-scope matrix. Each production scope token is ASCII and matches `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`, is at most 128 bytes, and a Context contains at most 64 unique tokens and 4096 aggregate token bytes. Exact-string de-duplication produces the immutable set without changing case or spelling. A malformed local-JWT scope Claim is caller input and returns 401; a successful online-Authority response whose scopes violate this Context contract returns 503. A syntactically valid but unknown name remains in the Context but grants nothing. Scope names have no wildcard, prefix, hierarchy, or implicit-admin semantics; synthetic `dev:*` is exempt from the production token grammar and is only a bypass marker because `dev_bypass` performs no scope evaluation. Each HTTP access freezes its normalized scope set for that access, while a later lifecycle or replay access authenticates and freezes a fresh Context. `POST /v1/chat/completions` requires `gateway.model.invoke`, plus `gateway.model.provider_override` when an override is requested. Both Status routes require `gateway.invocation.read`; both Cancel routes require `gateway.invocation.cancel`. Configuration Active/list/detail reads require `gateway.config.read`, and deterministic export requires `gateway.config.export`. Validate, Candidate creation, and rebase require the union of every affected domain write scope: `gateway.config.providers.write`, `gateway.config.bindings.write`, `gateway.config.routing.write`, `gateway.config.pricing.write`, `gateway.config.safety.write`, `gateway.config.resources.write`, and `gateway.config.replay.write`; a full Bundle requires all seven, and a missing member rejects the whole request as 403 without partial validation or mutation. Publish requires `gateway.config.publish`. Rollback requires `gateway.config.rollback`, creates only a Candidate, and a later publication separately requires `gateway.config.publish`. Health probes use the management-network boundary and no Gateway scope.

The same-key Replay Access through Chat Completions also requires `gateway.model.invoke`. `gateway.invocation.read` grants only the existing content-free lifecycle, Attempt, Usage, cost, and safe-Evidence summary for the authorized subject/tenant; it grants neither cross-subject nor raw-content access. The closed catalog additionally reserves `gateway.audit.read` and `gateway.cost.reconcile` for their specified privileged application operations even though general Audit/Cost query routes are deferred.

The Gateway integrates with an external Authorization Authority through that Adapter only in the selected `online_authority` topology. Adapters normalize successful authentication into the same immutable Authorization Context; `tenant_id` is retained as a correlation and evidence field. Detailed tenant-isolation topology and cross-tenant data-access rules remain deferred. The Gateway enforces its Data Plane and Control Plane matrix but does not own users, roles, tenants, or authorization policy lifecycle. Provider configuration stores Secret references only; runtime credentials are resolved through a replaceable SecretSource and remain inside the Adapter boundary. Provider egress uses only active published configuration, enforces production HTTPS and explicit host/network allowlists, and blocks SSRF-prone destinations. Missing production allowlists fail configuration validation and deny egress; local or test targets, including loopback, require explicit environment-scoped entries. Provider transports reject redirects without same-candidate retry but permit pre-commit fallback, re-resolve/revalidate destinations for every new connection, and disable configured/environment-discovered outbound proxies in the first phase. Transient DNS failure follows bounded retry, pre-commit fallback, and eligible cache degradation and contributes to health/circuit policy; any disallowed or mixed DNS result fails as an egress-policy violation with no same-candidate retry, health/circuit mutation, or cache use, while pre-commit fallback remains available. Private PKI uses an immutable, versioned Provider-scoped Trust Bundle that replaces system roots for that Provider while certificate and hostname verification remain mandatory; absent a bundle, system roots apply. Trust Bundle rotation occurs only through a newly published Active Snapshot for later admissions, with no mutable-file hot reload. Output Schema resolution is strictly in-document and performs no network, file, or registry I/O. Raw messages, model output, Output Schema bodies, opaque Tool payload, Provider error, credential, and authorization header content are not emitted through ordinary telemetry; safe Schema hashes may be emitted under policy, while opt-in encrypted content retention requires tenant/deployment policy, redaction, access audit, and TTL. Redis cache keys and authorization are tenant/policy scoped subject to the deferred isolation design. Deployment-owned Gateway Resource Ceilings bound HTTP bodies, headers, messages/content, output Schemas, stream events, Token/Context use, and Replay Artifact Write Queue task/byte reservations; opaque Tool fields consume these generic safety limits, and lower-level published policies may only tighten them. Configurable Token/cost/spend/tenant Business Budgets are not part of the first-phase architecture, while Usage and cost measurement remain evidence and accounting concerns.

Redirect rejection normalizes to `provider_protocol_error`; it may use only pre-commit Candidate fallback and does not affect health/circuit state or authorize cached degradation. Candidate Blacklist is a derived eligibility view rather than another state machine: transient failures use Provider Circuit, current-invocation policy rejection excludes that Candidate locally, and administrative disablement uses published configuration; no IP blacklist is learned. Exhausting Candidates through egress-policy rejection returns the existing `provider_unavailable`, while authorized Evidence retains the safe internal `egress_policy_violation` reason. Trust Bundle content identity, optional non-semantic label, and PEM are embedded directly in the Provider's immutable canonical PostgreSQL configuration and Active Snapshot, not a shared registry or externally mutable file. Import canonicalizes PEM to UTF-8 without BOM, LF line endings, and exactly one final LF, then assigns `sha256:<64 lowercase hex>` over the canonical persisted/exported bytes as the immutable identity. Snapshot Candidate validation parses the bundle locally, requires CA certificates only, rejects private keys, identity mismatch, invalid certificate dates, and the active size/count ceilings, and performs no Provider I/O; defaults are 1 MiB and 100 certificates per Provider. Expiry of any member invalidates the whole Bundle for new connections, drives ordinary fallback/`provider_unavailable`, and emits bounded-Provider `trust_bundle_days_until_expiry`, at most one warning per Provider/identity per 24 hours from 30 days, and one transition error without changing Gateway readiness, Provider Circuit, or an established TLS connection. A network-free local task refreshes this expiry state, while every new connection rechecks certificate dates; established connections are not revalidated. Publishing a valid replacement restores immediate eligibility without half-open/cooldown. Provider Transport pools are isolated by Provider ID, Trust Bundle identity, and a digest of endpoint origin, TLS/HTTP protocol, and connection/pool limits; model/routing/generation settings, labels, and resolved credentials are excluded. Publication performs no Provider I/O, and the first eligible Attempt initializes its pool lazily. Unexpected local pool initialization failure is an `internal` Gateway fault and cannot trigger retry, fallback, cache degradation, health mutation, or circuit sampling. First-phase upstream transport is HTTP/1.1 only. Pools default to a 30-second idle timeout and five-minute connection lifetime, configurable per Provider; an expired connection takes no new acquisition while active work retains its original completion, cancellation, and deadline bounds. A changed behavior digest creates a new lazy pool while the old pool stops acquisition, closes idle connections, and drains active requests only to their existing cancellation/deadline bounds before closing. Credential rotation remains per-Attempt request material and does not recreate a pool. Label-only publication remains auditable configuration history but changes neither pool nor execution behavior; Execution Fingerprint hashes a behavior projection rather than raw revision identity.

## 8. Deployment topology

Inside the Gateway container, the process listens on `0.0.0.0:8000` for the Data Plane and `0.0.0.0:8001` for Control Plane and health probes. The default Docker Compose publication maps host `127.0.0.1:8000` to container port `8000` and host `127.0.0.1:8001` to container port `8001`; deployment/bootstrap configuration may explicitly override host publication or ports while preserving route and protocol semantics. Production keeps the management/health listener internal and never routes it through public Data Plane ingress.

The Gateway exposes `/healthz` for process liveness and `/readyz` for Data Plane admission readiness. These probes are status-only, bypass caller JWT/permission checks, and in production are reachable only through an internal/编排 listener rather than public Data Plane ingress. `/healthz` does not depend on PostgreSQL, Active Snapshot, Authorization Authority, or Provider reachability; `/readyz` checks PostgreSQL, a valid Active Snapshot, required local execution dependencies, and any online Authorization Authority dependency configured as mandatory, while Provider runtime health/circuit/capacity remains outside readiness. Key Ring descriptor validity and protected-version retirement are readiness concerns, but Idempotency Index key-material availability and Idempotency Key Lockout are explicitly not.

Provider Transport uses HTTP/1.1 only in the first phase. HTTPS requires TLS 1.2 or newer, permits TLS 1.3, preserves certificate-chain and hostname verification, and uses secure runtime cipher defaults without weak-version overrides. A pool's maximum simultaneous connections equals the published Provider concurrency ceiling, its idle count cannot exceed that ceiling, and it has no hidden transport queue. Pools default to a 30-second idle timeout and five-minute connection lifetime, configurable per Provider; an expired connection takes no new acquisition while active work retains its original completion, cancellation, and deadline bounds. Provider responses accept identity or gzip only; gzip is decompressed incrementally before response/event ceilings, and unknown or malformed encoding is `provider_protocol_error`. Response headers are limited to 64 KiB and 100 fields, with Provider policies allowed only to tighten.

The first phase runs one Gateway service with PostgreSQL; Redis is an optional cache component. The default Compose profile does not start Redis. An explicit `cache` profile starts Redis, but cache use still requires an explicitly enabled policy in the published Active Snapshot. Its Data Plane admission readiness requires a valid Active Snapshot and enabled local execution dependencies; temporary Provider or optional-cache unavailability does not change readiness and is handled by normal routing/resilience policy. The Control Plane configuration-recovery path remains available when PostgreSQL and authorization are healthy. A reverse proxy exposes a distinct internal listener or hostname for Control Plane configuration/audit/privileged operations and a public listener for Data Plane traffic; it enforces the separation before Gateway and no client header asserts an internal origin. Management ingress does not require mTLS in this phase: internal network isolation, proxy enforcement, and external authorization are the accepted controls. Standalone Data Plane service deployment, independent service readiness, and independent release lifecycle are deferred.

When PostgreSQL and authorization are available but no valid Active Snapshot exists, Data Plane admission remains non-ready while the Gateway Control Plane keeps the authorized configuration-recovery path available to read/export, import, validate, and publish a replacement snapshot. That path cannot access Invocation status/cancellation/replay or perform Provider-affecting work. After publication, the Gateway validates the replacement snapshot before admitting work.

The first-phase deployment target is Docker with one Gateway instance and PostgreSQL; Redis is a separate disposable container started only by the explicit `cache` Compose profile. The default cache profile uses temporary Redis storage and does not require a named volume or authoritative backup; an operator-provided volume is best-effort only. The Redis endpoint, transport settings, and Secret Reference are supplied by deployment-owned Bootstrap Configuration; the published Active Snapshot supplies only cache behavior and policy. Changes to that connection profile take effect only at Gateway restart or an explicit Bootstrap reload; mutable connection files are not watched automatically. At admission Gateway locks the applicable connection profile for the invocation, so a reload affects only later admissions; an already admitted invocation retains its old profile for any cache stage or records `cache_backend_unavailable` if that profile is no longer usable. A changed profile creates a new logical cache namespace for later admissions; entries are not migrated or read across profiles. Docker startup may independently pass, replace, or omit standard proxy environment variables, but the first-phase Provider Transport ignores them and remains direct-only.

PostgreSQL authority data is covered by external encrypted backup/recovery with defined RPO/RTO. Redis supplies the policy-controlled cache only when both the profile and published cache policy are enabled; cache is disabled by default. A published cache policy remains valid when its connection profile is absent or unusable: Gateway marks the cache stage `cache_backend_unavailable`, records safe Evidence/Metrics, performs no cache I/O, and preserves live routing and recovery semantics. This disposition is internal-only and does not enter OpenAI-compatible bodies, SSE events, cache headers, or caller-visible error codes; operational records exclude Redis endpoint, credential, and raw error details. When Redis becomes usable again, a later eligible invocation automatically re-enters the cache stage; the failed cache operation is not retried in place and no restart or configuration publication is required. Redis or Gateway restart/restore may begin with an empty cache and has no continuity or replay guarantee; cache loss never blocks readiness or live execution.

At Model Invocation admission, Gateway locks the effective cache-policy Resource ID, Configuration Revision, content identity, administrative status, logical freshness-clock state, and Cache Backend Connection Profile in an Invocation Cache Policy Snapshot. A later cache-policy publication, including disablement or reactivation, affects only later admissions; an already admitted invocation follows its locked cache rules for reads and writes. The closed disabled projection contains only `enabled=false`; retained timing identity instead lives in PostgreSQL Cache Policy Clock State keyed by Routing Policy ID and the canonical enabled-cache material digest excluding `enabled`. A row holds running/paused state, accumulated enabled milliseconds, nullable running start, last transition Revision, and update time. Only successful Active publication changes that state, atomically with publication under the Active and affected-row locks and one publication timestamp. Disabling pauses the previously active material identity; re-enabling identical material resumes its logical time, while different material starts at zero and leaves the old identity inactive. Candidate/validation/export and failed publication have no clock effect. At most one material digest runs per Routing Policy, and clock regression never reduces accumulated time. Physical Redis TTL/eviction remains best-effort and a missing entry is an ordinary miss. Explicit revocation or a material policy-content identity change is required for forced invalidation. This request-scoped Gateway value is not an Agent Session or caller-provided session identifier.

Paused clock rows are not automatically deleted in v0.1, including after Routing Policy removal, Redis expiry/loss, or Cache Revocation, because cleanup would silently change later rollback/reactivation semantics. Removal pauses the active material; re-adding the same Resource ID and material resumes it, while rename creates a new identity. Startup inconsistency disables only the affected optional cache stage as internal `cache_clock_state_invalid`; Gateway does not guess elapsed time, expose the condition to Data Plane callers, or make live admission non-ready. Recovery uses a consistent PostgreSQL restore or a newly published material identity, not runtime database editing.

Cache population is immutable first-complete-write-wins per complete Cache Result Variant key. Atomic create-if-absent fixes content, provenance, creation time, and expiry; contention neither overwrites nor refreshes TTL. Each non-blocking write checks the current encryption key and Cache Security Invalidation Fence immediately before creation, never retries, and cannot affect the completed live result. Corrupt, undecryptable, or revoked existing values are rejected and may be asynchronously compare-deleted, never replaced in place by the current operation.

Population and physical cleanup run through separate bounded, process-local, non-durable queues. Their capacity, byte, concurrency, operation-deadline, and shutdown-drain limits are fixed deployment behavior in v0.1 rather than Resource Policy. Capacity loss, restart loss, and cache-operation failure remain cache-local observations: they do not alter the live result, readiness, metering, Provider Health, or Circuit. Cleanup receives scheduling priority but never establishes logical cache eligibility or invalidation.

A queued population item carries only the retention-authorized canonical Gateway result and the identities, absolute expiry, byte reservation, and security-fence observation required to perform the later immutable write. It excludes raw request and Provider material. Encryption intentionally begins after worker pickup so live completion is not coupled to SecretSource or cryptographic latency; queue wait consumes the original fixed lifetime, and the worker drops expired or newly ineligible work before resolving the current cache key. The first phase guarantees reference release and telemetry exclusion, not physical zeroization of language-runtime memory.

Routing explanation is persisted as one append-only, versioned Routing Decision Evidence record per invocation. It separates immutable policy/Candidate input from a monotonic event sequence covering preselection, per-Attempt gating and outcome, candidate skipping, degradation entry, and routing terminal. The top level, Candidate, and each event kind are closed DTOs; sequences start at one without gaps, the final event is terminal, and its canonical value equals the top-level terminal query projection. Stable stage-specific reasons may accumulate without mutating earlier facts; raw model/request/provider content is excluded. The first phase returns only a safe Status summary plus closed Evidence availability and a reference while available, while complete inspection remains an internal Eval/audit capability pending a dedicated authorized Control Plane surface.

PostgreSQL stores that logical aggregate in normalized append form: an insert-once decision header, an immutable Candidate batch, append-only Events, and one insert-once terminal projection linked to the final Event. Candidate and Attempt references are constrained to the same invocation. Recovery appends uncertainty rather than overwriting history, logical reads validate sequence and terminal equivalence, and retention removes one complete routing aggregate atomically without deleting the Invocation shell or Cost Ledger.

The Active Snapshot's Gateway-wide Resource Policy owns the effective Routing Evidence TTL, while Bootstrap owns only a deployment hard ceiling. The v0.1 defaults are 30 days effective and 90 days maximum; the maximum may be deployed between one and 365 days. Publication cannot exceed that ceiling, and there is no tenant, caller, Alias, Provider, model, or per-request override in the first phase.

Retention begins at the PostgreSQL routing-terminal checkpoint, not admission. The terminal transaction fixes the stored expiry; incomplete aggregates have none, and recovery first appends an uncertain terminal before they become retention-eligible. A bounded process-local worker periodically deletes complete expired aggregates from PostgreSQL without blocking readiness or live work. A stricter deployment ceiling applies immediately to existing evidence as an access and cleanup bound, while a later relaxation never extends a stored expiry. An Active policy above a newly lowered ceiling keeps Data Plane admission non-ready until the authorized recovery path publishes a valid replacement.

Evidence readers use one consistent PostgreSQL snapshot and enforce effective expiry both before assembly and immediately before returning content. Cleanup locks and atomically removes only unlocked terminal aggregates, skipping contention until a later pass. Status remains independently available: its closed Evidence projection distinguishes `available` with an opaque reference, `expired`, and `unavailable`, without exposing TTL, deletion, or persistence details and without changing the Invocation lifecycle state.

The established PostgreSQL Persistence Checkpoints apply directly: preselection precedes first Provider I/O, Attempt start precedes dispatch, outcome/recovery precedes another Attempt, commitment precedes downstream business output, and terminal routing evidence commits with Invocation terminal state before synchronous success or `[DONE]`. A failed checkpoint stops recovery and retains the existing persistence-unavailable/uncertain semantics; restart reconciliation never replays model execution.

Routing Reason is a closed code plus a tightly governed subject used only for capability, limit, parameter, or Provider-override specificity; Attempt and terminal failures reuse the existing normalized ModelFailure/Gateway error taxonomy rather than inventing a competing one. The reason catalog covers static eligibility, administrative and policy rejection, runtime health/circuit/credential/capacity/deadline gates, recovery-budget/commitment boundaries, and cache-stage dispositions. Successful Attempt/completed routing has no failure reason, while cancellation and uncertainty retain their established terminal meanings.

Routing Reason subjects follow the versioned `gateway.routing-subject/v1` registry. Capability, limit, parameter, and Provider-override subjects come only from their closed canonical families; deprecated external aliases normalize before evidence is written. Subjects identify the incompatible dimension only and never carry request values, Schema material, or Provider error text.

Weighted routing is cross-language deterministic and integer-only. A domain-separated HMAC derived from the active Execution Fingerprint key produces a persisted 32-byte seed from call, Routing Policy, and Revision identity. Each service-level/priority tier starts from canonical Binding-ID byte order and uses an HMAC counter stream plus rejection sampling against the remaining integer-weight sum. This forbids modulo bias, floating-point logarithms, runtime shuffles, and configuration input-order dependence; historical Eval uses the stored seed without old key material.

After authentication/protocol preflight and Idempotency Index resolution, a new execution leases one current Fingerprint key before Request Fingerprint comparison and admission. The same operation lease later derives Execution Fingerprint and the domain-separated Routing seed, then ends before Provider I/O. A duplicate bound to an old version resolves only that exact historical member and creates no new execution identity. The Gateway never substitutes randomness, an unkeyed digest, another Ring member, or a retired fallback. Active material failure returns persistence unavailable before admission, creates no invocation facts or Provider work, sets a process-global Fingerprint Key Fault, and makes Data Plane admission non-ready; a bounded isolated probe alone clears it.

Request and Execution Fingerprints share one bounded Bootstrap Fingerprint Key Ring that is separate from the Idempotency Index Key Ring and content-encryption keys. It contains one active key and up to eight verification-only versions, each referenced through SecretSource and fixed for the process lifetime. Only the active 32-byte HMAC-SHA-256 key gates new routing readiness; unavailable historical members fail only the dependent historical operation. Rotation is restart-only in v0.1, and old versions may be removed only after their fingerprint, cache, and Replay dependencies end.

PostgreSQL proves planned retirement through a non-content, monotonically extended protection horizon for each Fingerprint key version. Idempotency, cache, and Replay retention establish their dependency before their respective persistence handoff; Redis state and SecretSource availability are never evidence that a dependency ended. Startup rejects a Ring that omits a still-protected version. An audited security invalidation may explicitly release revoked dependencies, while ordinary lifecycle code cannot shorten the horizon.

Invalidation is version-wide and irreversible rather than dependency-counted. Its PostgreSQL record fixes an invalidation timestamp and monotonic generation once, permanently disables every Idempotency Fingerprint comparison, cache, and Replay dependency under that version, and permits later Ring removal regardless of the old horizon. The same key/version can never be restored; invalidating the active version makes routing non-ready until restart with a distinct active version.

Startup key validation and request operations use bounded SecretSource leases rather than a process-wide material cache. One new execution resolves active material once for at most the shorter of one second and its remaining deadline; an old Binding resolves only its recorded version. At most 32 leases coexist. Capacity exhaustion is request-local, while an active-material contract or availability fault changes global readiness; verification-only failure stays isolated to the historical access.

Idempotency Index and Fingerprint keys have separate 32-permit, no-queue lease pools. A keyed request derives its Index Digests and releases every Index key byte before PostgreSQL lookup; only after lookup identifies the new-execution path or exact historical Fingerprint version may it acquire a Fingerprint lease. The two lease classes are never held together, cannot borrow capacity, and cannot starve one another through a shared semaphore.

Gateway startup loads and verifies the latest active PostgreSQL snapshot before Data Plane admission readiness; missing or invalid state fails closed, including after restore. Liveness is process-oriented; Data Plane admission readiness checks the active configuration and enabled execution dependencies, not optional Redis availability. Startup validation blocks Data Plane admission on invalid required configuration or dependencies, and shutdown uses bounded graceful drain. Rate-limit policy is published through configuration and applies at Gateway instance, tenant, and Provider scopes, with QPS as a supplement. First-phase admission rejects when the applicable limit is full; concurrency-pool switching is deferred. Standalone Data Plane service deployment, multi-instance coordination, networking, and rollout strategy remain outside the first-phase acceptance scope.

The v0.1 Docker delivery gate is API-driven end to end: a clean Docker startup exposes an authorized Control Plane path to validate and publish Provider configuration, then `POST /v1/chat/completions` routes a real Query through the Gateway to a configured model and translates the result back. Manual PostgreSQL edits, container-private setup scripts, and caller-supplied Provider credentials or URLs are not part of the supported path.

Fingerprint comparisons, admission, and retention handoffs check database key-version generation plus observed local revocation. Already admitted work continues. Irreversible database Version Invalidation is v1 scope; v0.1 supports planned rotation, protection checks, and observed SecretSource fail-closed behavior without an invalidation mutation surface.

Evidence references are `rd_` plus the call ID without hyphens and convey identity only. Future complete reads require audit permission and tenant/subject authorization. Cleanup merges bounded results from stored-expiry and terminal-time indexes before skip-locked deletion; backlog telemetry reports presence and oldest age rather than a full-table count.

PostgreSQL retains effective-time ceiling history so every Routing Decision remains bound by the strictest ceiling applicable during its lifetime. A later increase benefits new calls only; evidence cannot become visible again while delayed cleanup is pending. Original terminal, event, and expiry facts are unchanged. Reads, cleanup, Status, and backlog telemetry share this rule.

Invocation Status independently retains only whether Evidence was established, its terminal time, and original expiry. It can therefore distinguish expired Evidence after aggregate deletion from Evidence never established, without duplicating routing history or exposing retention metadata to callers.

Startup activates retention ceiling history in PostgreSQL before exposing Evidence reads or Data Plane admission. A failed activation keeps those paths closed and readiness false; same-value restart reuses the latest activation. Admissions lock its sequence, and all subsequent tightening applies even to already admitted non-terminal work. Status preserves this association independently of Routing Decision retention.

v0.1 keeps committed ceiling activation history without pruning or compaction. Routing Evidence cleanup and Status expiry never own or delete this history. History lifecycle optimization is v1 work, not part of first-phase retention workers.

## 10. Consequences and risks

Cover latency, network uncertainty, contract drift, failure isolation, operational cost, and migration from the current in-process Provider path. Migration preserves the Agent Loop model-call Port, uses incremental explicit cutover, permits only no-side-effect comparison, and ends with one real execution authority.
